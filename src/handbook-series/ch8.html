AI Gateway 的边界

原书 9.1 节

单个应用接一个模型，SDK 直连就够了。模型、团队、工具一多，接入问题就变成共同的治理问题：调用者是谁、凭证谁保管、模型故障能切到哪里、哪些工具和参数能用、费用归哪个项目、拒绝和重试怎么追溯。这些适合在调用入口集中处理，但任务成功标准、业务状态、检查点和恢复流程由业务模型和执行系统定义，不属于网关。

AI 流量的新约束有四类：长连接与流式输出（HTTP 200 之后仍可能流内出错，首字节不一定是首个有效 token）、大请求体与上下文（全量缓冲的内存随并发放大）、按 token 计费（准入时的估算与结束时的实际不同，并发调用会同时消耗余额）、多轮与长程任务（路由亲和有助于缓存复用，但替代不了状态持久化）。原书点了两个容易混的地方：SSE 只是传输形式，字节切片可能含半个或多个事件，首个事件可能只是心跳，所以 TTFT 不等于 HTTP 首字节时延；KV cache 复用是推理性能优化，不是业务状态恢复，缓存未命中应表现为变慢而不是任务丢失。

三种治理语义是分析框架，不是成熟度阶梯，也不要求建三个产品：LLM Gateway 治理模型调用及每次实际尝试，MCP Gateway 治理工具协议与调用，Agent Gateway 治理 Agent 接入与跨调用关联。统一的关键是身份映射一致、策略边界清晰、记录可关联，以及同一次上游调用不会因穿过多个组件而被重复计费。网关本身也是关键基础设施：多副本解决实例故障，但共享存储、外部策略服务、内容检测服务的故障行为要逐项定义。

    LLM Gateway：路由、重试、超时

    原书 9.2.1–9.2.5 节

    LLM Gateway 在一次调用里要同时协调三件事：选满足要求的模型或端点、控制失败与重试的影响、对所有实际消耗负责。便宜模型如果导致大量返工，总成本可能更高；自动容灾如果忽略协议兼容和计费语义，会把可用性故障变成质量或成本事故。统一接口（OpenAI 风格 /v1/chat/completions、Anthropic 风格 /v1/messages）要先声明支持的能力子集，不支持的参数明确报错，而不是静默忽略；客户端看到同一个模型名，不意味着平台可以不经验证地替换实际能力。

    原书把模型选择和端点选择分开：静态映射与权重、成本感知路由（要有可验证的质量下限，还要算重试和返工）、语义路由（分类器要评估过、有回退）是在选模型；推理端点选择是在同一模型的实例间挑（队列、在途请求、前缀缓存信号）。网关记录的前缀关联只是“缓存可能还在”的信号，缓存驱逐、实例重启后都要允许失配。

    可靠性的原则是先判断能否重试，再选择重试目标：限流看重置时间和配额，服务端错误只在调用语义允许时重试，认证错误应终止，上下文超限不应靠网关截断历史（那会改变任务输入）。流式响应一旦提交给客户端，网关通常不能透明重放；“没收到响应体”也不等于“上游没执行”。最容易失控的是多层重试叠加：每层都以为上限是 3，端到端却没有 3 这个约束。解法是尝试预算跨层传递：绝对截止时间，剩余尝试额度由调用方给出、网关按 call_id 原子扣减，耗尽就返回明确的预算耗尽错误；每次尝试有独立 attempt_id。超时也要分清：建连、首字节、TTFT、流式空闲、总截止各管一段，一个一直发心跳的流永远不会触发空闲超时，却可能始终没有有效内容。

    预算：速率、配额与严格上限不是一回事

    原书 9.2.6–9.2.8 节

    原书区分四种机制：请求速率限制（QPS / 令牌桶，控制准入速度，不直接控制 token 成本）、token 时间窗限制（请求前查、结束后累计，存在在途消耗与并发超限窗口）、余额型配额（准入查余额、结束后扣减，近实时但不是严格并发预算）、严格预算（可证明的最大消耗 + 原子预留 + 结算与退款）。“请求前检查、响应后扣减”无法单独保证硬上限：余额 100，两个最大消耗各 80 的请求同时通过检查，最后可能花到 160；响应后的原子扣减能避免丢账，但撤销不了已发生的消耗。

    严格预算的不变量：可用额度 = 已授权额度 − 已结算消耗 − 在途预留，准入条件是 本次最大可计费消耗 ≤ 可用额度，检查和预留在同一原子操作里完成；结束后按实际消耗幂等结算，释放多余预留。预留要覆盖输入、受约束的最大输出和其他计费项，重试也要单独占额度；流式中断或结果未知的请求，不能因租约到期就无条件退款。如果实际消耗可能超过预留，说明“最大值”并不可靠，只能声明有界超额或软预算。多层预算（组织、团队、项目、任务）要一起验证，token 配额与金额预算也要分开，因为同样的 token 数在不同模型、缓存类型、价格版本下费用不同。

    流式 usage 还有细节：要显式请求（如 stream_options.include_usage，只对支持它的适配器注入）；缺少 usage 不能记成零消耗，客户端取消也不能证明上游停止了生成，这些记录要保留“估算 / 未结算”状态等待对账。语义缓存可以减少重复生成，但缓存键必须区分租户、权限、模型版本、系统提示和知识版本，含副作用的工具调用不能重放缓存结果。

    MCP Gateway：发现、授权与执行分离

    原书 9.3 节

    MCP 降低了接入成本，却不会自动解决企业授权、凭证托管、工具健康或业务副作用。一个工具出现在清单里，只说明它被服务端通告了；调用者有没有权执行、依赖系统是否可用、这次调用是否成功，都要独立判断。协议本身也在演进：2025-03-26 引入 Streamable HTTP，2025-11-25 引入实验性 Tasks，2026-07-28 改为逐请求元数据与 server/discover，Tasks 成为可选扩展。网关要声明支持的版本集合、桥接方向和能力子集；支持核心工具调用不等于支持所有扩展，协议无状态也不等于后端业务无状态。

    MCP 请求的准入按四步理解：认证（谁在调用，由独立于协议的凭据映射主体）→ 协议校验（按版本检查头部镜像、方法与报文）→ 授权（按主体、工具、参数决定是否放行）→ 转发（按策略重新构造上游请求）。逐请求元数据（protocolVersion、clientCapabilities、clientInfo）只服务第二、四步，协议说明不是调用者身份证明。头部可以辅助分类和路由，但执行前要验证与正文一致，避免头部鉴权和正文执行面对不同对象。Registry 管目录（端点、版本、声明能力、所有者），不授予当前任务执行权限；健康检查也分层：连接可达、能通告兼容能力、受控业务探测，写入与支付类工具不能为了探活执行真实副作用。

    授权方面：过滤 tools/list 能减少模型误选，但 tools/call 必须再次鉴权；权限取调用者原有授权、工作负载授权、任务委托范围和资源侧限制的交集，不能被模型声明的身份、工具描述或 clientInfo 扩大。Schema 校验只保证结构合规，业务策略还要约束范围（数据查询的行级权限、支付的金额阈值与收款方范围、集群管理的环境与操作动词）。把 REST 包成 MCP 工具时，请求模板要限制可变主机和路径，防止变成 SSRF 入口；用字符串前缀判断“只读 SQL”不可靠。最后，网关只有在一组条件同时成立时，才可能成为不可绕过的策略执行点。

    易混辨析：可发现 · 已授权 · 健康 · 执行成功

    可发现：服务端通告了这个工具（initialize 或 server/discover）。已授权：当前主体、任务委托、资源侧限制的交集允许这次带这些参数的调用。健康：连接、协议、依赖系统可用。执行成功：这次调用实际产生了预期结果。四者分别检查、分别记录，任何一个都不能推出另一个。

    Agent Gateway：入口路由、任务关联与账本

    原书 9.4 节

    一个 Agent Task 可能包含多个 Session、多轮模型和工具调用，还会因审批、补充信息或故障进入等待与恢复，成本分散在各阶段，失控循环还会挤占同租户的预算和并发。Agent Gateway 把可信身份和任务关联信息带入入口策略：可以拒绝新调用、报告预算压力、把请求路由到声明具备相应能力的 Runtime，但Task 怎样暂停、保存状态和恢复，由业务任务模型与执行系统决定。网关可以保存亲和键、任务标识映射、在途计数、配额预留和观测关联，不应解释业务 State、定义 Checkpoint 或决定从哪一步恢复。比如 Coding Agent 的会话需要回到能访问工作区的运行时，目标不可用时可以返回暂不可路由，不能转到一个空运行时后声称“已经续跑”。

    原书的归因链路是 task_id → session_id → turn_id → model/tool call → attempt_id。task_id 来自业务应用，session_id、turn_id 来自权威执行上下文，网关可以生成请求或尝试标识；客户端传来的关联头要绑定已认证主体并校验租户，防止伪造 Task 或项目标识转移费用；缺可靠关联时记为待归因，不自行编造业务 Task。账本分四层：Attempt（哪次重试花了钱、是否结果未知）、Call / Turn（本轮慢在哪）、Session（是否重复调用或上下文膨胀）、Task（长程任务总成本、恢复成本、Outcome 引用）。网关记录只是任务账本的数据来源之一，Runtime 资源费用、审批等待、业务恢复事件要由各责任系统补充；Trace 有采样和缺失，不能自动成为财务或 Task 的权威账本。

    租户隔离里，身份（人、工作负载、Agent 实例、Task）和财务归属（组织、团队、项目）是正交维度：一个 Agent 可以服务多个项目，一个项目也可以用多个 Agent。入口在途请求与 Runtime 中的活动任务也不同，HTTP 结束后异步任务可能还在跑。协议上，ACP 服务编辑器、IDE 与编码 Agent 的交互（v2 截至核验仍为 Draft），A2A 面向 Agent 间协作（v1.0.0 已正式发布），协议中的完成通知不等于业务 Task 的 Outcome。原书还介绍了开源项目 HiRoute：把“想”和“做”分开，由主 Agent 按用途把有界任务委派给 Codex、DeepSeek Harness 等工作 Agent，计划有稳定调用名、受理时的计划版本固定，路由不依赖模型自动分类。

    网关能做，还是不该做？

    统一治理：审批后重新准入，审计不等于证据

    原书 9.5 节

    模型、工具、Agent 入口如果各自定义身份和成本维度，同一调用者在不同路径上会受到不一致的约束。转发侧的硬要求是：主体映射（把 OAuth、mTLS、API Key 映射成稳定的策略主体与财务归属，清除客户端伪造的内部身份头，例如不能直接信任外部传入的 x-mse-consumer）、委托核验（任务委托可验证、可撤销、范围清晰，并与委托者原有权限取交集）、凭证处理（上游凭证按显式策略生成或委托，默认不透传下游凭证）、记录（每次判定的规则、版本、拒绝原因）。审计既记准入依据，也记实际执行结果，“放行日志”代替不了“执行成功日志”。

    审批落到转发路径上只有一条约束：审批未决的请求不得转为实际执行。挂起期间网关不长时间持有 HTTP 连接，等待与通知由业务侧承接。批准也不意味着必定放行：等待期间身份可能过期、参数可能改变、预算可能被其他调用占用，所以执行前要重新准入；审批记录绑定工具、版本、参数摘要和任务上下文，回调要认证防重放。超时不应自动解释为“改成只读执行”，那会改变请求含义；结果未知的外部操作不能盲目重试，交给业务查询、对账或补偿。

    结构化审计能说明谁在何时申请了什么、命中哪条策略、审批怎么决定、执行结果是什么，但它不天然构成业务判定所需的 Evidence。原书给的审计事件示例里，execution_status: succeeded 只描述工具调用，不是 Task 的 Outcome；usage_status: pending_reconciliation 也不能因执行成功而省略。DLP 与内容检测放在入口便于覆盖多个调用方，但会让入口接触明文；检测失效时放行、拒绝还是转人工，要按风险预先定义。

    审批进入不同状态时，转发侧该怎么做？

    控制面联动：从观测到受控发布

    原书 9.6 节

    数据面执行已发布策略，可观测系统记录运行事实，评估系统生成评分与诊断。原书强调：Evaluation 不天然拥有发布授权，不应直接改生产路由或预算。完整路径是观测形成候选建议 → 构建与验证 → 治理授权与发布门禁 → 灰度与控制面发布 → 运行反馈。模型映射、语义路由、工具 Schema、预算策略这些会改变调用行为的配置都走这条链；低风险调参可以在预先批准的范围、幅度和资源集合内自动进行，超出范围要重新授权。长程任务跨会话执行时，避免一次任务里混用不兼容的策略。

    可观测性要补充生成式负载的事实：用量与成本（输入、输出、缓存 token，估算还是实际，价格版本，结算状态）、时延（建连、首字节、TTFT、流式空闲、总耗时）、可靠性（流内错误、取消、重试、结果未知）、治理（命中策略、拒绝、审批、预留与结算）、关联（Task、Session、Turn、Call、Attempt、Trace 引用）。指标要控制基数：模型、路由适合当指标维度，Task、Session、调用 ID 更适合日志、事件或 Trace。OpenTelemetry 的 gen_ai.* 语义约定整体仍处于 Development 状态，要固定版本并保留迁移映射。

    还有一组容易混的概念：网关内部的运行时自适应（如 Higress ai-load-balancer 用 EWMA 时延、在途请求、失败信号在候选端点间选）只能在已授权的候选集合和约束内工作，不能自行扩大模型范围、数据地域、工具权限或预算，它和治理策略变更是两回事。回滚也不只是恢复配置文本，还要考虑已执行的副作用、未结算额度和仍在运行的任务。

    1. 三种 Gateway 各管什么？退款请求经过哪些检查？

    LLM Gateway 管模型调用与尝试（选模型 / 端点、限流、容灾、计量），不判断输出是否满足业务；MCP Gateway 管协议代理与工具调用授权，不把可发现等同于已授权、健康或可执行；Agent Gateway 管 Agent 接入、路由、亲和、并发与跨调用关联，不定义 Task、State、Checkpoint、恢复。退款：Agent 入口校验委托身份并按能力路由 → 模型调用经 LLM Gateway 路由与降级 → 查订单是只读工具，鉴权后放行 → 申请退款是资金操作，挂起进入审批 → 批准后重新校验委托范围、参数摘要、预算预留再执行 → 结果与用量回写任务账本，由业务系统判定结果。

    2. 为什么先查后扣不能保证上限？重试会放大到几次？

    并发请求可能同时通过余额检查，最终合计超过余额；后扣减撤销不了已发生的消耗。严格预算要在准入时原子预留最大可计费消耗（可用 = 授权 − 已结算 − 在途预留），结束后幂等结算。SDK 3 次 × 网关 3 次 = 上游最多 9 次，供应商侧是否重投还不受控；要跨层传递绝对截止时间和剩余尝试额度，由网关按 call_id 原子扣减。

    3. 为什么元数据不是身份证明？审批通过后为什么还要重新准入？

    逐请求元数据只说明协议版本和能力，由客户端自述；身份要由独立凭据认证，授权要按主体、工具、参数判断，权限取各方授权的交集，不能被 clientInfo 或工具描述扩大。审批等待期间身份可能过期、参数可能变化、预算可能被占用，所以执行前要重新校验身份、委托、参数摘要和预算；超时也不能偷偷降级成只读执行。
