上线以后，还要持续回答什么

原书第 18 章

传统应用用代码规定行为，输入、状态、依赖相同时执行可以预测和复现。Agent 把一部分决策交给了模型，同一任务可能因为上下文、工具反馈或生成结果不同走出不同路径。以退款为例，Agent 还要从对话里确认用户指的是哪笔订单、识别适用规则、选择操作、核实退款是否完成：对话顺利结束、接口没有报错，都不足以说明这件事办对了。所以 Agent 不只要验证接口契约，还要验证目标达成、业务约束和交付结果，区分理解、上下文、工具使用、恢复策略的问题，并观察重复执行是否稳定、质量成本延迟怎样变化。

原书引了几组带日期的公开结果，提醒“会做、做完、稳定交付”是不同层次：OSWorld 2.0（2026-07 论文）长流程任务上严格完成率 20.6%、部分得分 54.8%，完成许多中间步骤不等于交付完整结果；τ-bench（2024-06 原论文）GPT-4o 原生工具调用在零售任务上 pass¹ 为 61.2%，pass⁸ 低于 25%。pass⁸ 是同一任务八次全部成功，区别于“八次中至少成功一次”的 pass@8。这些是各自测试条件下的结果，不能换算成企业业务成功率。

上线后的团队要持续回答两组问题：任务有没有做好，以及做好花了多少代价。一条回答正确的轨迹可能反复查了同一份资料，一次 Token 大幅减少的执行也可能省掉了必要验证。评估把“好不好”落成可检查的标准，调优根据结果改变系统，两者要通过真实任务连起来：否则要么只有分数没有修改方向，要么不停改 Prompt 却说不清哪些修改有效。

数据飞轮：两条反馈路径

原书 18.2–18.4 节

一次排障往往能修好眼前的问题，却帮不了下一次：原因在工程师脑子里，Trace 散在日志里，修复记录在另一个系统，几周后同类问题换个说法又出现，团队还得从头查。数据飞轮要接上这种断裂：把执行留下的事实整理成可复用样本，用评估找问题，用实验检验修改，再把有效变更带回运行环境；轨迹、样本、评分规则、失败模式、版本记录都留给下一轮用。

两条反馈路径同时推进：一条改进数据和判断方法（原书的客服演示里，“有哪些功能”和“如何配置评估”最初共用一个评估器，实验后发现标准不合适，于是给 Dataset 加了逐题 Rubric）；另一条改进 Agent 的行为（缺配置步骤补 Skill，工具用错改工具描述，超时后反复提交检查重试和结果核实逻辑）。所以数据有两个作用：帮助判断该改哪里，也帮助拒绝没有效果或带来退化的修改。样本变多、经验入库、候选生成都只是过程产物；有效变更进入运行后，新任务的结果才是下一轮反馈。

模块之间不是一条只能向前的流水线：评估结果可以写回 Dataset 供人工复核，复核可能修正样本也可能修正评估器，优化候选要回到实验，已采用的 Skill 或经验又会改变后续轨迹。原书也强调各模块的边界：轨迹组织不能凭空补出业务事实，Pipeline 不能替代人工确认，评估不能代替候选执行，保存了一个版本也不等于运行中的 Agent 已经在用它。第一次建设时，原书建议从一个团队确实想解决的问题开始，把第一轮完整做完。

    轨迹：先看懂一条真实执行

    原书第 19 章

    用户说“没解决问题”时，团队要知道：Agent 没理解需求，没找到材料，还是没正确使用材料？轨迹把输入、行动、工具反馈和输出放在一起。原书建议第一次先找一条自己知道发生了什么的任务，记下时间、问题、回答和 TraceID，核对记录是否正确；列表为空时，先区分“数据没采集到”和“Agent 没正确执行”，不要反复发业务请求来代替定位。检索方式按问题选：已知执行用 TraceID，连续交互用 SessionID，“意思相近、措辞不同”的同类问题用语义搜索（相似度只负责选候选，不是质量分）。

    读一条轨迹的顺序：先看输入输出了解任务，再看步骤数、工具调用、Token、耗时概览确定重点，然后沿“用户补充 → Agent 行动 → 工具返回 → 后续回答”展开关键步骤。结论要落到一组相邻事实，例如“用户要求操作步骤 → 检索返回了步骤 → 最终回答遗漏步骤”，这样便于别人复核，也能直接用于评分；单写一句“回答质量不好”，下游不知道该查什么。多 Agent 任务要沿委派关系看主 Agent 交给子 Agent 的目标和实际收到的返回，不能只看子 Agent 是否结束。

    三个对象要分清：Trace 是追踪上下文关联的一组调用（适合定位某次执行），Session 是一段连续交互、可能含多条 Trace（同一会话里可能有多个任务），Trajectory 是整理后的用户与 Agent 步骤、工具交换、结果和指标（适合阅读行为过程和加工样本），原书的平台用 ATIF 格式组织。SessionID 能帮你找相关交互，但不会自动证明它们属于同一个任务，不能凭时间接近或文字相似认定。轨迹记录发生了什么；要重新实验，还需要题目、运行入口、环境和评分标准。

    Pipeline：把轨迹加工成业务能用的样本

    原书第 20 章

    原书的场景很具体：客服负责人要每天看一批退款对话，找出“工具没办成，Agent 却告诉用户已经办好”的问题，改完提示词后还要用这些案例检查问题有没有减少。质检人员需要的是一张直接能用的表：用户问了什么、Agent 怎么答、执行了哪些操作、记录来自哪里；每次都靠开发者导日志、改脚本，质检就成不了日常工作。Pipeline 把这套整理方法保存为数据处理任务，按约定持续生成 Dataset：开发者把业务字段接对，业务负责人围绕预览确认样本是否合用。

    动手前先定一行代表什么：退款质检可以从“一次任务一行”开始；分析用户为何反复补充信息需要连续多轮；比较并行 Agent 要分别保留各条路径。这决定了后面怎样分组、采样、评分，也决定业务人员打开表格能否直接看懂。处理模块按需选：字段投影 / 扩展 / 过滤（日志变成表）、实例构建（分散事件组装成完整样本）、精确 / 近似 / 语义去重（整理题库）、随机 / 分组采样与语义聚类（人看不过来时缩到能处理的量）、LLM 或智能体调用（补分类、摘要、候选标签）、文本统计（找异常长的内容）、周期执行（日常收集）。

    用预览确认这张表好不好用：展开一条普通任务和一条工具报错或没有答复的任务，看是否都保留下来；只保留最后一句话，之后很难判断为什么不对；过滤条件删掉了工具失败记录，正好丢了最需要的样本。处理顺序按成本安排：能用已有字段筛的先筛，明确只要 100 条的先采样，再做模型处理。模型生成的标注先用于筛选和人工复核，正式质量评分交给可校准、可比较的评估器；合成的数据增强样本要保留合成来源，与真实用户任务区分。原书的判断标准很朴素：管线简单而输出被持续使用，通常比配置了很多处理却无人消费更有价值。

    黄金数据集：题目与判断依据

    原书第 21 章

    研发补了 Prompt 后再问一次，回答完整了。接下来还要知道：换一种问法还行不行，其他问题有没有答差，以后换模型会不会再漏。黄金数据集是一组经过业务确认的任务：既有题目，也有判断任务是否完成的依据。知识问答的依据是参考答案和必须覆盖的要点；退款、订票等操作任务还要写明业务应达到的状态；代码任务可以是测试与验收条件。“黄金”指题目与标准可信，Agent 曾经答错的任务，只要补齐了正确要求，同样是黄金样本，往往比只收集漂亮的成功回答更有用。它的价值来自反复使用：从没进入评估、实验或发布检查的数据集，整理得再精细也还没参与改进。

    起步字段可以很少：题目、原回答、参考答案、评分要求（rubric）、场景、来源。参考答案给一个合格示例，评分要求说明必须做到什么、允许不同措辞，开放任务通常不宜要求逐字一致。原书给了“如何做评估”这道题的 rubric 示例：按四项检查，每项 0.25 分（准备并选择数据、选择或创建评估器、字段映射、运行与处理低分样本），编造产品能力或操作入口另标记为不通过。先手工确认几条，提前暴露标准分歧，再交给更多人或 AI 预标注；AI 预标注减少整理工作，黄金题的标准仍要由业务人员确认。

    选题时只收低分题会看不到正常能力的退化，只收高频题会漏掉代价高的少数情况。三种用法：校准评估器（拿人工确认过的好、坏、边界回答检查机器评分）、比较版本（同一批题、同一套标准）、长期回归（升级前重复运行）。正式比较前创建版本留档，比较期间不再修改。最后一条很重要：参与改写 Prompt、生成 Skill 或提炼经验的题，要和最后独立检查效果的题分开，一旦反复看这些题并据此修改 Agent，它们就已经参与了调优，要另留新的验证题。

    评估发现问题，实验比较改动

    原书第 22 章

    评估检查已经发生的执行；实验让修改后的 Agent 重新回答，产生新的输出和轨迹。第一次建评估器不必覆盖所有业务，先选一类投诉，拿几条专家认可和几条明显有缺陷的回答讨论差别。方式按问题选：确定条件（JSON 格式、必填字段）用 Code 规则；切题、遗漏必要信息用 LLM 评估，把参考材料和评分细则给齐；多步骤任务是否完成、工具结果与最终回复是否一致用 Agent 评估，结合轨迹检查。一个任务可以挂多个评估器分别看“回答质量”和“业务操作是否完成”，但不能把多个结果简单平均就当成业务质量。

    试评时至少覆盖一条已知好回答、一条已知坏回答、一条信息不完整的样本，问自己：扣分依据真的出现在这条回答里吗？评估器引用的是正确的工具结果吗？缺少证据时它会说无法判断吗？坏回答得了高分，先看它收到的输入，再看条款，例如只检查是否提到“评估器”这个词，就会把泛泛介绍当成操作指导。读结果时不要看到低分就立刻改 Prompt：回答确实遗漏 → 纳入调优样本；回答有步骤而解释说没有 → 修评估器或映射；声称完成但轨迹显示工具失败 → 交给负责该行为的团队；执行异常或材料缺失 → 先补条件再判断质量。评估器误判的样本也留下，作为校准材料；高分样本也要抽检。

    实验与历史评估的关键区别：被评分的必须是本次生成的新回答和新轨迹，参考答案和 rubric 来自 Dataset。第一轮只改最有依据的一项，否则分数变化难以解释。接入企业自己的 Agent 时，有会话状态的服务要适配成“创建 Session → 发送问题 → 获取最终响应”，API 先返回“已受理”不能当题目完成，独立样本用独立会话。对比时从退化题开始看，再看改善题和关键正常场景；输出变长本身不代表改善。采用候选除了平均分，还要看严重错误是否消失、原本正常的场景是否退化、耗时消耗是否可接受（补一次状态查询多花一次调用，换来不再“失败仍告知成功”，是值得的；靠省略必要步骤换来的低耗时不是升级理由）。小批通过后，扩大到历史回归集，再验证一批没参与本轮修改的独立样本。

    受控自进化：把有效方法沉淀下来

    原书第 23 章

    一个排障 Agent 解决过某类问题，下次遇到相似故障仍可能重新查资料、试错误参数、漏掉上次确认过的关键步骤。原书先按现象选方向：方法只在特定条件下适用、相似故障总要重新探索 → 经验库（遇到什么情况、可以怎样处理，带来源和适用条件）；经常漏掉前置检查、测试或结果确认 → 修改 Skill；反复编写相近的统计查询或清洗脚本 → SQL 模板、Script 或工具；固定流程总要人盯着 → Workflow；重复提交、恢复后状态不明、长任务忘记约束 → 改 Harness。“先找首次异常，再分析连续重试”这样的方法，比某次故障的最终答案更有复用价值。

    经验要能检查：它解决什么问题、建议什么动作、什么条件下适用，再回到来源 Trace 确认动作真的出现、结果支持这项建议。例如“查询不到日志时扩大时间窗口”，要分清当时是窗口太短还是数据根本没采集。接入后要亲自验证一次召回：Agent 口头说“参考了历史经验”，还需要对应真实的调用和执行动作。召回多少、什么时候用要靠实验：保留不用经验的 Baseline，用新会话、重置任务状态，逐项比较召回阈值、返回数量、触发时机、放置位置、使用要求；召回开销也算进完整任务成本。某条经验让 Agent 反复扩大范围或照搬历史参数，就缩小它的使用范围，把出问题的任务留作反例。

    失败样本可以推动 Skill 甚至 Harness 改进：先写清“应该在哪一步采取什么行动”，再把原 Skill、失败轨迹、相邻成功任务和预期行为交给优化助手生成局部修改建议。原书的表格 Agent 案例提出了三个具体修改：写入前确认目标工作表、提交前检查公式、完成后回读目标单元格，每一项都能对应执行证据，而不是把整份 Skill 重写成更长的通用注意事项。Harness 改进的例子是“提交已发生，但会话恢复后再次提交”：区分尚未开始、已开始但结果未知、已完成，结果未知时先核对业务状态；验收时要构造真正触发原问题的任务。自动化可以分三档：手动调优、半自动（系统整理失败模式、挖经验、生成候选，人决定）、受控自动（已规定范围内自动检查和实验，满足条件才采用，异常交给负责人）。

    边缘运行时：调优的最后一公里

    原书第 24 章

    第 24 章把调优体系从 Region 延伸到全球边缘，针对四个问题：延迟不对称（端到端延迟里排队、环境准备、推理、工具、沙箱、人工等待六项在 Region 内产生，只有网络传输由物理距离决定，跨洋用户的网络传输在 TTFT 中可能占很大比例）、成本不透明（Token、回源带宽、边缘请求分散在不同计费体系）、安全前置（DDoS、Bot、直接注入在到达 Region 前初筛，间接注入等深层攻击仍需 Region 结合上下文检测）、内容适配（外部网页在边缘转成 Markdown 等 Agent 可消费的形态）。

    分工原则：边缘能处理的（缓存命中、安全拦截、就近路由）不回源，处理不了的（复杂推理、状态变更、长任务）才进 Region。判断“能处理”不能只看算力，还要看事实权威、身份与权限、写副作用、数据驻留和故障恢复语义：只有无需权威状态判定、无需写副作用、且符合数据驻留要求的请求，才适合在边缘就地完成。语义缓存要限定在公开、幂等、低风险请求，把租户、权限域、地区、模型、Prompt 和知识版本纳入缓存键。原书也列了不适用的场景：单区域业务、严格数据驻留、个性化或权限敏感或时效性高的回答、小流量或缓存命中率低导致成本反转，这时“不优化”才是正确选择。

    这个请求适合在边缘就地完成吗？

    厂商方案说明原书第 18–23 章以阿里云“Agent 观测与优化”平台（数据中心、Pipeline 与 Loopie、Dataset、评估器、实验计划、经验库、SkillForge、Trace2Optimizers）的操作为例；第 24 章以阿里云 ESA 边缘安全加速平台为基础设施，并说明章中性能数字均为示例假设，需企业基线和压测校准。笔记只保留与平台无关的方法。

    回扣开头的三个问题

    先自己答，再点开
    1. pass¹ 61%、pass⁸ 不到 25% 说明什么？要回答哪两组问题？

    说明一次做对不代表能稳定重复做对：pass⁸ 要求同一任务八次全部成功，与“八次中至少一次成功”的 pass@8 完全不同，企业业务需要的是稳定交付。上线后持续回答：任务有没有做好（业务结果、执行过程），以及做好花了多少代价（时间、Token、工具调用、人工介入），模型、工具、规则或需求变化后还要复查。

    2. “黄金”指什么？为何分开优化题和验证题？

    指题目与判断标准经过业务确认、可信，答错过的任务补齐正确要求后同样是黄金样本。参与改写 Prompt、生成 Skill、提炼经验的题已经影响了 Agent 的设计，用它们验证会高估效果；必须留出未参与本轮优化的独立题做最后检查，反复看过的验证题也要换新。
