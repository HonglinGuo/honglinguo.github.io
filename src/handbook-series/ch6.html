Action Plane：从意图到环境事实

原书 6.1 节

一条完整的行动链不从“调用 Tool”开始，也不在“返回文本”处结束：模型意图 → Schema 校验 → 身份绑定 → 策略判定（ALLOW / DENY / ASK）→ 审批 → 执行 → Observation → 状态与 Trace，再回到模型。原书强调三个必须区分的事实：模型看见某个工具（描述进了当前 Context）、Harness 注册了它（系统知道怎么调用和解析）、当前用户和任务获得授权（这次具体行动才可以发生）。如果“出现在 Tool Schema 里”就等于“可以调用”，最小权限、用户委派、阶段性只读都无从谈起。

Function Calling、Shell、浏览器、远程 Agent 表达方式各不相同，Harness 先把它们转换成统一的 Action Request：action / task ID、能力与版本、参数和期望输出、行动者身份、目的与当前阶段、环境与资源范围、副作用 / 可逆性 / 风险分级、幂等键与超时、审批与审计要求。模型的自由文本只能作为 purpose 的候选，能力名、参数类型、影响范围和身份必须由确定性代码解析。Action 有自己的生命周期（REQUESTED → VALIDATED → AUTHORIZED / WAITING_APPROVAL → RUNNING → SUCCEEDED / FAILED / CANCELLED），和任务状态相关但不相同：一个工具失败不一定让任务失败。Action Result 也不只是给模型看的文本，要有状态（含“未知”和“部分完成”）、结构化数据、原始结果引用、错误类别与是否已产生副作用、实际执行身份与环境、对任务状态的候选 Patch（由 Harness 统一提交）、给 Verifier 的证据。

原书的案例：“创建变更单”和“发布生产”即使最终调用同一个变更平台，也必须是两个 Action，因为身份、风险、可逆性、审批要求都不同。企业 Tool 应优先暴露这种业务语义，而不是让模型用通用 HTTP 或 Shell 自己拼生产操作。

Tool、MCP 与远程 Agent
原书 6.2 节

  

    
三种协议处在不同层次：Function Calling 是模型与 Harness 之间的意图接口（想调哪个能力、给什么参数）；MCP 是 Harness 与能力提供方之间的连接协议（以标准方式发现和连接工具、资源）；A2A 面向拥有独立任务循环、状态和自主性的远程 Agent，传递任务、消息、状态和 Artifact。协议不替 Harness 做授权、租户隔离、业务语义验证和效果评估：MCP Server 能描述工具，不代表调用方有权访问底层数据；A2A Agent 声明完成，委派方仍要按契约验收。选择看能力本身：短时、参数明确、立即返回 → Tool；跨 Host 复用工具或数据 → MCP；有自己的任务循环、需要异步状态和 Artifact → A2A 或等价 Agent API。不看协议新旧或流行程度。

    
面向 Agent 的 Tool 设计，原书给了六条：名称和描述说明业务目的、适用条件与非目标；输入用明确类型、枚举、边界、示例；输出区分结构化结果、给模型的摘要、原始证据引用；声明是否只读、有无副作用、可否逆、是否支持预览和幂等；错误用稳定分类（能否重试、要改参数还是转人工）；认证和 Secret 留在执行侧。粒度太粗，一次调用影响太大，审批和验证都不精确；太细，模型要编排大量低级步骤。合理粒度对应一个可描述、可授权、可观察、可验证的业务动作。

    
远程 Agent 不应获得父 Agent 的全部 Context：发送最小必要信息，把数据使用限制作为机器可执行策略一并传递；对方返回的消息和 Artifact 都是外部输入，要过 Schema、权限和内容安全检查，不因为来源是另一个 Agent 就当成可信指令。能力数量多、多个团队共享时，用 Registry（元数据、所有者、版本、健康、作用域）+ Gateway（入口、身份、凭证、路由、限流、审计）避免治理逻辑在每套 Harness 里重复。

执行环境与 Sandbox 契约
原书 6.3 节

  

    
File、Shell、Code Interpreter、Browser、Computer Use 给模型提供了通用操作空间，也显著扩大了副作用和攻击面。原书的建议是：能用窄 Tool 完成的高风险动作，不要优先开放通用 Shell 或 Computer Use；处理长尾应用和非结构化工作区时，再用 Sandbox 把通用能力限制在可接受边界内。

    
Harness 不应假定“本机一定有某目录、某版本依赖、能访问公网”，而是提交一份 Environment Contract：镜像 / 系统 / 架构、挂载与读写范围、网络出入站策略、Secret 引用与委派身份、所需工具与版本、CPU / 内存 / 存储 / GPU 配额、超时与并发、持久化与快照要求、审计与清理策略。环境满足不了，Action 应在执行前失败或请求降级，而不是让模型进入不确定状态自己猜。隔离可以按 Agent、Session、Task 或 Action 划分：越细，污染和横向移动风险越低，创建和状态传递成本越高；在线多租户任务通常至少按 Task 或 Session 隔离。

    
Secret 不应出现在 System Prompt、Tool Schema、Task State 或模型可见的环境变量里，执行侧按 Action、身份和目的获取短时凭证，只注入目标进程，记录使用而不记录密文。网页、下载文件、工具返回一律标记为不可信内容。原书的案例：Sandbox 允许修改 payment-service 副本并构建，却不提供生产集群凭证，发布只能通过受控的 production.deploy；这样即使工作区里的恶意文件诱导模型执行部署命令，网络与 Secret 边界仍挡得住。Sandbox 防止进程越界，Policy 决定业务上是否允许，二者缺一不可。

Permission、HITL 与 Prompt Injection
原书 6.4 节

  

    
Harness 同时记录三种身份：发起任务的用户或服务、发起行动的 Agent 版本、实际执行工具或 Sandbox 动作的 Runtime 身份，并明确数据访问和副作用最终归属于谁。权限决策至少看主体、租户、目的、能力、参数、目标资源、环境、阶段、数据敏感度、影响范围、可逆性、预算和历史审批。只按 Tool 名称做静态白名单，分不清“读一条测试记录”和“导出整个生产库”。

    
策略结果统一为三类：ALLOW（直接执行并记录依据）、DENY（无论模型怎么解释都不执行，返回结构化原因和允许的替代项）、ASK（可以执行，但需指定的人或系统确认）。ASK 不是默认兜底：审批太多，用户会机械确认，Agent 也失去连续性。应优先用更窄的 Tool、参数约束、预览、资源范围和 Sandbox 降低风险，只在目的或后果无法由策略充分判断时请人参与。HITL 有三个层次：Plan 审批、Action 审批、结果验收。审批请求要写清做什么、为什么、以谁的身份、作用于什么、预计影响、参数与差异、是否可逆、失败怎么办、批准范围（仅本次、本任务、还是一类受限动作）；批准后 Harness 还要重新校验对象版本和策略，防止等待期间环境已经变了。不可逆或高影响动作统一用 Preview—Approve—Commit—Verify。

    
Guardrail 可以部署在输入、Context 构建、Action 请求、Tool 结果和输出各处，但不应是唯一安全边界：能编码的权限和资源限制交给 Policy 与 Sandbox，模型或分类器识别复杂语义风险，作为额外信号。Prompt Injection 的关键防线是区分指令与数据：网页、邮件、文档、MCP Server、工具结果、远程 Agent 的返回都不能改变平台政策、授权范围或当前 Tool Set。用户中途纠偏（Steering）应作为高优先级任务事件，在安全点处理，而不是追加到长历史末尾。

    事件流、Channel 与交互协议
    原书 6.5 节
    
  
    
    
    长任务如果只在结束时返回一段文本，用户不知道 Agent 在做什么、是否在等审批、是否卡住，也无法纠偏。Harness 应产生一组与内部事件对应、经过脱敏的外部语义事件：Text、Progress、Tool、State、Approval、Artifact、Error、Usage。模型的隐藏推理不需要流式暴露，用户要的是状态、可见说明、行动、证据和可操作选项。Channel 是 Agent 与 Web、App、IDE、IM 之间的适配层：映射身份、把线程映射到 Session 并选择或创建 Task、转换输入与输出、跨入口保持任务连续、做渠道级限制与审计。它不应成为唯一状态存储。
    
    
    事件流必须假定网络会断、客户端会重复连接、消费者速度不同：每个事件有单调序号或可恢复游标，重连从最后确认位置续传，服务端去重；慢消费者先读状态快照再补关键事件。高频文本 token 和细粒度工具日志可以合并或采样，但状态、审批、Artifact、终态事件不能因背压丢弃。用户发出取消后，要区分“已收到取消”和“底层 Action 已安全停止”。同一个 Task 在不同 Channel、对不同身份显示的内容也不同，不能把内部 Trace 原样广播。
    
    
    两个协议的分工：AG-UI 表达 Agent 与应用之间双向、流式的交互事件（生命周期、文本、工具、状态、中断）；A2UI 让 Agent 输出声明式界面（表单、卡片、列表、动作），客户端用本地受信组件渲染，而不执行模型生成的任意代码。原书提醒先稳定 Task、Event、Approval、Artifact 的语义模型，再选 AG-UI、A2UI、WebSocket、SSE 或消息平台承载。托管路径还有一个细节：Qoder Cloud Agents 等待工具确认时返回 session.status_idle 且 stop_reason.type = requires_action，不能仅凭 idle 判定完成，要用 user.tool_confirmation 回应。

    易混辨析：AG-UI vs A2UI
    
    
    AG-UI 处理“Agent 与应用如何交换事件”，是交互事件协议；A2UI 描述“界面是什么”，是声明式界面格式，由客户端用受信组件渲染。A2UI 的载荷可以通过 AG-UI 或别的传输发送，两者不互相替代。同站 Agent UI 协议一文有更详细的对照。
    
  
    
  
    

    


    
  
    Trace、Evaluation 与效果闭环
    原书 6.6 节
    
  
    
    
    问题可能出在 Context、计划、工具、权限、环境、状态或验证任一环节，所以 Task Trace 不能只记模型输入输出，要关联：Agent / 模型 / Harness 版本、Session / Task 拓扑、Context Manifest 与压缩决定、状态转换、模型调用与成本、Action 请求与审批、工具与远程结果、工作区变更与 Artifact、重试与降级、Verifier 结果、业务 Outcome 与反馈。关键是因果关系而不只是时间顺序：哪次决策用了哪份 Context、产生哪个 Action、更新了哪些状态、触发了哪次验证。原书说得很重：如果构建时没有稳定事件、版本和关联 ID，后续平台补不出可信的 Agent Trace。
    
    
    再次区分两套系统：Agent Harness 在真实或测试环境中完成一次任务；Evaluation Harness 以一致方式运行、回放、比较多个 Agent 版本，必须固定或披露模型、推理设置、Harness、工具版本、预算、重试、环境和评分规则，否则分数差异可能来自运行条件。评测分三层：单步（工具选对没、参数对不对）、轨迹（绕路、重复、越权、过度消耗）、最终结果（目标是否真正达成）。只评结果会掩盖高成本或高风险轨迹，只评单步又会惩罚有效探索。人工反馈也不是天然真值，要和环境证据结合解释。
    
    
    效果闭环不应从单条失败直接改 Prompt：Trace + Outcome → 失败聚类 → 诊断 → 最小针对性 Patch → 回归 → 发布门禁 → 新版本。Patch 与根因一一对应：缺事实调 Context / Knowledge；错误经验反复出现修 Memory；不会执行稳定方法加 Skill；工具误用改 Tool Schema 或权限；无进展调 Loop、Plan 或模型；环境不一致修 Environment Contract；完成误判强化 Verifier；只有确定是模型能力不足，才优先换模型。回归集要同时包含原失败用例、相邻正常用例、安全对抗用例；模型升级后，还要回头检查旧 Harness 里的补偿逻辑是否已经失效。

      先自己答，再点开
      
  
      
    
      1. 看见、注册、授权有何区别？为什么拆成两个 Action？
      看见是工具描述进入了本轮 Context；注册是系统知道怎么调用和解析；授权是当前用户和任务被允许执行这次具体行动。三者分开，最小权限、委派和只读阶段才成立。创建变更单（中风险、可逆、ALLOW）与生产发布（高风险、ASK、需审批类型 / 对象版本 / 目标环境 / 短时授权）的身份、风险、可逆性和审批不同，拆开才能分别授权、审计、重试和验证。
      
    
      2. 三种协议各在哪层？何时用 Tool，何时用 Remote Agent？
      Function Calling 是模型与 Harness 之间的意图接口；MCP 是 Harness 与能力提供方的连接协议；A2A 用于有独立任务循环的远程 Agent。短时、参数明确、立即返回的动作用 Tool；跨 Host 复用工具和数据用 MCP；有自己的循环、需要异步状态、进度、Artifact 的用 A2A 或 Agent API。把固定 API 包装成 Agent 不会自动获得规划恢复能力，把远程 Agent 当同步 Tool 会丢失任务语义。
      
    
      3. ASK 为什么不是兜底？两种 Harness 有何区别？
      审批过多导致机械确认、破坏连续性；应先用窄 Tool、参数约束、预览、资源范围和 Sandbox 降风险，只在策略无法充分判断时请人。Agent Harness 完成一次任务（产出轨迹、Artifact、证据、Outcome），其中的 Verifier 是单次完成门禁；Evaluation Harness 在固定条件下运行、回放、比较多个版本，产出指标、失败聚类和发布建议。
