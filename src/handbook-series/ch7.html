Sandbox：可编程、受控的工作空间

原书 7.1–7.2 节

原书对 Sandbox 的定义是：按任务需要配置、具有隔离边界和明确生命周期的执行环境，包含操作系统用户空间、计算资源、文件系统、语言与依赖，以及终端、浏览器或桌面等入口，还可以配网络、数据挂载、身份凭证、观测和状态保留方式。它适合操作路径要在执行中逐步确定的任务（检查样本、写转换脚本、装解析库、按运行结果修正）；参数明确、行为固定的业务动作直接调 API，不必为每次查询开沙箱。沙箱给判断提供可检查的运行依据，但业务结果是否正确，仍由测试、规则、评测器或用户验收确认。

Agent 与沙箱有两种部署关系：Agent use sandbox（编排逻辑在外，通过接口调用里面的代码、浏览器等工具，便于给已有应用加执行能力）和 Agent in sandbox（Agent 进程和工具链一起跑在沙箱里，模型推理仍可在远端，适合需要完整项目环境和持续进程的任务）。训练评测（Agent RL / Eval）是另一个维度，可以采用任一部署关系。三类典型负载的关注点各不相同：工具执行看首次可用时延和隔离，长时任务看会话连续性和等待成本，训练评测看环境吞吐、重置分叉和可复现。

环境类型上，Code（脚本、构建测试）、Browser（真实页面状态）、Computer（没有 API 的桌面软件）、AIO（浏览器、代码、终端共享一个工作区，省掉步骤间的上传下载和路径转换）、MCP / Skill 环境（把只在某台开发机上能跑的、带本地依赖的工具变成可按需分配的环境）。共享范围要与任务匹配：同一任务的工具可以共享文件，不同租户和项目仍要分开。

长时任务：亲和、挂载、休眠、围栏

原书 7.3、7.5.2 节

长时任务围绕一个项目展开：下一次用户提修改意见时，前一次的代码、依赖和项目结构应当还在。连续性依赖两类映射：会话亲和把带稳定会话标识的请求路由到已有环境（或触发恢复），动态挂载按已验证的租户、用户、项目关系把工作区挂到环境上。两者不必一一对应，原实例释放后可以新建实例、重新挂载项目文件。仅把用户编号拼进目录名，代替不了服务端对归属和权限的检查；调用方也不应把某个容器的临时地址当成长期入口。恢复时要核对状态可读性、归属和必要文件的完整性，检查不通过就保持失败或等待，不能把空工作区当恢复结果交付。工作区和任务状态的保留期也要独立于计算实例设置。

长会话的计算需求并不连续：等模型、等用户、等网页、等事件。一直占着完整资源，成本随会话时长增长；每次等待都销毁，又要反复装依赖、恢复上下文。原书列了四档状态策略：持续运行、浅层暂停（保留内存与文件，减少活跃计算）、深度休眠（状态持久化后释放执行资源，外部连接需重建）、保留文件后重建。唤醒入口在休眠沙箱之外（定时器、消息入口、路由），休眠中的 Agent 不再跑循环；判断能否休眠不能只看“没有新请求”，还要看在跑的工作和未完成操作。恢复后要重新检查文件、进程、端口、外部连接和临时凭证：接口返回成功只是一个环节，以任务能否继续为准。

实例故障时还有一个陷阱：失去心跳只表示平台暂时观察不到它，旧进程可能还在运行。需要串行修改同一任务或工作区时，先确认旧实例已停或使其写权限失效，再让新实例写入。做法是给每次接管一个执行代次，由受保护的存储或写入入口拒绝旧代次，这叫围栏（Fencing）。只更新控制面上的编号挡不住旧进程。已提交给外部系统的操作（比如构建），新实例要凭原标识查状态，再决定等待、读结果或重试。

训练与评测：Template、Snapshot、Fork、Reset

原书 7.4 节

Agent 的强化学习和评测需要真实执行：每次尝试都要取仓库、装依赖、跑 Agent、执行测试、收结果，一次从初始状态经过多步动作得到结果的过程是一条 rollout 轨迹。并行时，即使模型推理还有余量，任务也可能卡在环境没就绪或操作没返回。训练追求足够多的有效探索，评测强调不同版本面对可比较的条件；二者都要记录模板、数据和依赖版本，并清楚区分“Agent 没完成任务”和“环境本身没提供好服务”，否则环境故障会被误记成模型能力变化。

四个能力各解决一个问题：Template 定义初始配置，让重复任务有一致起点；Snapshot 保存某时刻的运行状态（文件系统或内存），把已做完的准备工作存下来；Fork 从同一快照创建独立分支，让多次尝试从同一阶段并行展开；Reset 把环境恢复到约定初始条件，防止上一轮的改动污染下一轮。注意：沙箱快照回退不了外部数据库、已发出的消息、已完成的业务操作，评测要用独立数据副本或测试租户；沙箱快照也不同于模型训练检查点（权重、优化器状态）。环境返回观察和证据，成功和奖励怎么算属于评测逻辑；会改代码的 Agent 要与评分规则隔离，避免它通过修改评分环境拿到失真结果。

架构与接入：隔离后端、首次可用、上线验证

原书 7.5.3–7.7 节

职责边界再说一遍：Harness 编排层持有任务目标、上下文和下一步决策；Runtime 把任务组织成可启动、可等待、可取消、可恢复的过程；Sandbox 提供具体环境并执行分配给它的操作。三者不要求是三个独立服务，但平台不应根据一个进程是否存活来猜任务是否完成。

隔离后端有三类：容器（生态成熟，常见实现共享宿主机内核）、用户态内核（如 gVisor，减少工作负载直接接触宿主内核，要验证系统调用兼容性）、MicroVM（如 Firecracker，硬件虚拟化提供独立内核边界）。选择取决于代码可信度、租户边界、系统能力、设备需求和运维成本；对外提供 SDK 或 K8s 接口，说明不了底层隔离强度。预热环境在分配前不能携带用户数据或凭证，实例重新分配前要清理进程、文件、挂载和网络规则。接入方式上，SDK / API 面向应用开发者（创建、连接、命令、文件、生命周期），Kubernetes 自定义资源面向平台团队（模板、实例、预热池、控制器），二者可以指向同一底座；接口兼容不代表模板、超时、暂停恢复、网络、持久化语义一致，要用代表性任务验证完整生命周期。

首次可用时延要从申请环境算到命令通道、依赖、工作区、所需服务全部就绪；冷启动、镜像缓存与预热、实例预热池是不同策略，分别记录。用户身份、工作区挂载和恢复检查不能靠预热提前做，也要计入。容量耗尽时有界排队或明确拒绝；缩容先停止接新活、等在途任务到可恢复点，CPU 低不能单独作为回收依据。成本口径用单位成功任务成本：窗口内归属该负载的计算、状态存储、网络、预热费用（含失败和重试）÷ 成功任务数。

状态外置之后，状态由什么承载

原书 8.1 节

传统应用的数据分工比较清楚：订单账户进事务库，附件日志进对象存储，分析走数仓。Agent 则持续地生成和消费状态：以“分析客户流失原因并生成挽留方案”为例，每一步都产生新状态，也依赖已有状态继续。状态没被可靠承载，实例故障或人工介入后无法准确恢复，多个 Agent 无法共享一致上下文，结果出偏差时也说不清 Agent 基于什么做了判断。

原书把 Agent 状态分四类：运行时状态（事件日志、检查点、任务进度、执行租约、状态指针）要明确的写入顺序、原子更新、幂等和可恢复历史；工作区与产物（文件、代码、图表、快照、分支）要版本、快照、引用关系和可回滚；记忆与知识（会话摘要、偏好、经验、文档、向量索引、知识图谱）要可检索、时效、来源可信度和权限过滤；业务语义与治理状态（本体对象、关系、规则、租户、权限、审计）要对象身份、关系完整、规则边界和审计证据。

一个向量库或一张会话表能存一部分，却无法天然满足所有语义：把任务事实当可检索文本，会丢失顺序与原子性；把成果当无版本附件，难以回滚复用；把记忆、知识、权限混成一份上下文，过期或越权内容会持续影响决策。正确的起点是先定义各类对象的正确性边界，再匹配存储能力，最后用统一契约组织，而不是先挑一个引擎。

把这些对象归到四类状态里。

Event Log、Checkpoint 与跨副本恢复

原书 8.2 节

Event Log 记录任务事实的变化：生成计划、申请租约、发起工具调用、收到返回、等待确认、提交结果，每次追加一条不可改写的事件。顺序在边界上至关重要：“发送审批请求”已成功但结果事件没记下来，重启后就可能再发一次。强一致的范围应当是任务、会话或业务对象，而不是让所有 Agent 争用一条全局日志。事件与当前状态同时维护时，要在一个事务里提交，或用 Outbox 等机制保证最终同步并按事件 ID 去重；诊断日志和模型输出不能代替这份记录。

Checkpoint 记录某个可信时刻的状态：阶段、已完成和未完成步骤、工具结果引用、工作区版本、子任务、等待条件、状态版本，而不是上下文的简单拷贝。频率与任务成本匹配：秒级、可廉价重试的查询型任务不必频繁快照；要在外部调用前后、长计算完成后、人工确认前后、工作区重要变更后、交接给其他 Agent 时主动形成。增量快照只存变化集，恢复时组合最近完整快照与后续增量。

恢复 = 读最新 Checkpoint + 回放其后的事件，这就是 Durable Execution：执行不依赖特定进程，而依赖外部持久状态。还要解决“谁有权继续”：执行租约像接力棒，只有持最新接力棒的实例能提交下一次状态变化；状态指针把任务、事件序列、Checkpoint、工作区快照、产物引用关联起来，恢复实例不必四处找上下文。原书特别提醒：Durable Execution 不等于所有外部动作天然恰好执行一次，平台能保证的是状态变化有明确事实边界，外部副作用还要靠幂等标识、结果确认和补偿，所以运行时状态必须同时保存调用意图、调用标识和调用结果，而不能只记一句“正在执行”。

易混辨析：Durable Execution vs 恰好一次

Durable Execution 保证任务状态不依赖进程存活，能从最近可信点续上；它不保证模型调用、消息发送、审批提交、数据写入这些跨系统的外部动作恰好执行一次。恢复时对外部动作要先用调用标识查结果，再决定继续、重试、补偿或转人工。

工作区、快照与 Artifact Store

原书 8.3 节

运行时状态让 Agent 知道“做到哪了”，工作区与产物保证“已经做出了什么”。工作区不应是执行实例上的临时目录：实例只是工作区的一个临时挂载点，工作区本身有独立身份、权限、版本历史和生命周期。底层可以是共享文件（目录结构、频繁小文件）、对象存储（大文件、不可变成果、归档）和近端加速层（热点数据），但对 Agent 呈现为统一的任务空间。

分层工作区的思想是“共享不变部分，隔离变化部分”：底部是只读的基础层（运行环境、依赖、模板、公共数据，由平台维护），中间是任务或租户可共享的数据层，顶部是当前任务独占的可写层。Copy-on-Write 让快照不必复制整份工作区，只有新写入或修改的部分形成新数据块，于是可以像代码分支一样低成本地试验和回退。快照要和运行时 Checkpoint 关联，避免“任务状态恢复了、文件状态却变了”。注意环境回滚不撤销已提交到外部系统的操作，快照是否具备容灾能力也取决于它存在哪个故障域。

可写层的并发也要围栏：仅更新任务表里的租约，挡不住仍持有文件句柄的旧实例。可以用校验执行代次的写接口、独占挂载、撤销旧端访问，或让实例写私有分支、只允许当前持有者发布新版本。多 Agent 协作不要让大家同时改一个目录，而是各写各的分支、通过快照或 Artifact 引用读取对方结果、按版本合并。Artifact 进入 Artifact Store 后不可原地修改，后续变更生成新版本；它带来源任务、版本、生成 Agent、输入依据、审批状态、权限和保留策略，后续任务可以引用“经审批的第三版客户流失报告”，而不是某个易变的临时路径。

语义层：记忆、知识与本体

原书 8.4–8.6 节

三者差别首先在来源、用途和维护责任：记忆来自筛选过的交互与执行经验，知识来自可追溯的外部资料，本体维护业务概念、关系与规则。并非所有应用都需要三者齐备。原书的长期记忆参考架构用两个正交维度：按来源分用户显式表达、Agent 行为归纳、外部业务事实；按稳定性分人设与身份层、画像层（周、月更新）、事件偏好层（最细最易变）。Persona 不算经验性记忆，由构建方显式维护、受版本与权限控制。写入要抽取、合并、去重，冲突时结合时效、来源可靠度保留待确认；检索用向量 + BM25 + 实体关系多路召回再 Rerank，叠加时间衰减，但长期有效的约束不应因少被调用而淡出，引用频率也不等于正确性。归档、降权和删除是三种不同操作。

知识库这一侧：深度文档解析保留标题层级、表格、实体、时间、数值等锚点（避免把“海外业务”的退货政策用到国内）；切片过大引入噪声、过小丢上下文；增量更新要记录源版本、解析版本、索引水位，新索引验证后再切换。检索有三条受控路径：RAG 做语义相似、GraphRAG 面向跨实体关系推理（股权穿透、供应链关联）、DataProbe 用只读账号在授权 Schema 内查结构化业务事实，多路候选统一 Rerank、保留溯源。

本体解决“找到一段文本不等于理解它”：检索到“该客户订单已逾期”，还要知道订单、客户、产品的关系、逾期对应的规则、可能触发的动作。原书的本体四要素是对象、关系、动作、规则，并强调三种责任分离：本体负责语义建模，动作的执行由 Runtime 完成，授权决策由治理方作出。引入时机：只需检索少量文档就从常规检索开始；实体身份、关系约束和多跳查询成为持续需求时，再承担本体的建模和维护成本。记忆、知识、本体之间的反馈要走受控更新，不得把模型推测直接写成组织规则。

多租户隔离、一致性与选型

原书 8.7 节

多租户的边界不只在业务数据库里，还要贯穿记忆召回、知识检索、文件访问、向量搜索、工具执行和运维观测，否则 Agent 会通过共享索引、缓存命中、产物链接或日志检索接触不该看的信息。身份层次从组织、工作空间、Agent、用户到 Task 和 execution。隔离策略分三层并可组合：物理隔离（强监管、高敏感、重要客户专属）、逻辑隔离（独立库、Schema、索引命名空间、对象目录）、行级隔离（共享服务里按租户、角色、标签控制）。向量和图谱要特别注意检索前过滤：先跨租户召回再过滤，候选生成阶段就已经暴露了数据。

一次执行会同时改动日志、检查点、工作区、记忆、索引、本体，不能用“所有组件同时成功”定义一致性。原书的思路是区分权威事实与派生视图：执行租约、工具调用结果、关键检查点要强一致或可验证提交；向量索引、全文检索、统计聚合、读副本可以短暂最终一致，但要标明新鲜度和对应的源版本。写入先可靠提交权威事实，再异步推动索引与副本；读取按任务重要性选择最新权威状态或略有延迟的派生视图。知识文档更新先生成新版本，再解析、切分、向量化、建索引，达到可用水位后才切换查询流量，失败可重放或回退。回答还要能标出引用的对象版本、索引时间和来源，这样答案过期时能分清是推理问题、源数据问题还是索引未同步，而不是一律归咎于“幻觉”。

元数据层给每个对象记录类型与 ID、租户、创建者、来源、摘要、敏感级别、版本、位置、访问策略、生命周期、关联关系，血缘让源文档更新时能找到受影响的索引、图谱、记忆摘要和下游任务（法律保留和不可变审计记录要留显式例外）。容灾按对象定恢复目标：关键事件与检查点要更低的恢复点目标，派生索引保留源数据和构建记录以便重建；恢复后先定位最后确认事件、加载检查点、校验租约与幂等标识、确认外部调用状态，再决定继续、重试、补偿或转人工。选型上，组件组合可复用既有设施，但要自己维护跨组件的身份、版本、更新、恢复契约；一体化 Agent 数据库收敛这些契约，代价是依赖产品能力与迁移路径。无论哪种，验收要落到实际任务和故障场景。

1. use 与 in 的区别？等待期间怎么处理环境？

use：编排在沙箱外，通过接口调用里面的工具，便于给已有应用加执行能力；in：Agent 进程与工具链一起在沙箱内，适合完整项目环境和持续进程。等待处理按完整任务周期权衡：连续计算或即时服务保持运行；短等待且恢复敏感用浅层暂停；长等待用深度休眠（外部连接需重建）；进程易重启、文件是主要状态时只留文件后重建。判断能否休眠要看在途工作，恢复后以任务能否继续为准。

2. 怎样防旧实例覆盖？Durable Execution 能保证恰好一次吗？

给每次接管分配执行代次，由受保护的存储或写入入口拒绝旧代次（围栏）；工作区可用独占挂载、撤销旧端访问或私有分支 + 只允许当前持有者发布。只在控制面改编号不够。Durable Execution 只保证状态续行，外部动作要靠幂等标识、结果确认和补偿，恢复前先按调用标识查结果。

3. 为什么一致性要分层？为什么召回前就要过滤租户？

影响任务正确性的权威事实（租约、调用结果、关键检查点）要强一致或可验证提交；索引、统计、副本等派生视图可以短暂滞后，但要标明新鲜度与源版本，这样避免把分布式事务扩展到所有操作。语义检索若先跨租户召回再过滤，候选生成阶段已经暴露了数据，所以要在索引空间、检索条件和重排序中前置租户与权限约束。
