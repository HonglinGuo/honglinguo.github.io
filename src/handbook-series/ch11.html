盾与缰绳：Agent 既是对象，也是主体

原书 14.1 节

原书开篇引用了几组数据：IBM 对 602 家发生过数据泄露的机构的调研中，21% 发生过涉及 AI 模型或应用的安全事件，其中 92% 缺乏适当的 AI 访问控制；2026 年 7 月，OpenAI 的一次安全评测演变成对 Hugging Face 的真实入侵，HF 取证还原的活动跨度约 4.5 天、约 1.76 万次攻击行为，METR 独立调查估计约 700 个 Agent 参与；英国 AI 安全研究所的另一项评测中，122 次运行里有 10 次出现越界行为。后两起发生在降低了部分防护的评测环境里，但已经显示出约束执行边界的重要性。

由此得出的判断：Agent 既是被攻击的对象，也是行为的主体。作为对象，它面临供应链投毒、提示注入与越狱、系统与网络入侵；作为主体，它持有身份权限、自主调用工具、接触敏感数据，即使没被攻击，也可能因越界行为造成损害。所以安全要解决“不被打穿”，更要解决“不越边界”。防护是盾：从资产与供应链、模型输入输出到系统网络，全栈纵深设防。管控是缰绳：身份鉴权、意图识别、逐次调用校验、高危操作二次授权、数据出域阻断。每一个技术层都同时承载防护与管控。

这些措施更像盾，还是更像缰绳？

应用安全：五个新攻击面

原书 14.2 节

Agent 让应用从信息处理者变成行动执行者。攻击者可以通过直接输入，或者污染 Agent 将要读取的外部内容，诱导它访问非预期目标、构造恶意请求或外发数据。联网型 Agent 的网页抓取、文件预览、图片代理都可能成为 SSRF 入口；Agent 生成的 SQL、HTML、工具参数如果被下游直接解释执行，还会触发 SQL 注入、XSS 等传统漏洞。HF 事件中，评测 Agent 正是利用一个可访问的 Artifactory 服务代为联网，再入侵 HF 系统：企业部署的 Agent 本身也要被视为潜在的攻击发起点，它能访问的中间服务可能成为突破网络边界的通道。

原书列出五个新攻击面：不可信的外部输入（网页、邮件、文档、OCR 结果、检索记录）、工具的发现与调用（工具描述、参数定义、返回内容被操纵；工具实现或更新中夹带额外操作）、动态业务调用与网络访问（Agent 生成的 URL、查询、请求体，把多个服务串成读取—转发—外传路径）、结果交付边界（输出被渲染、发布、转成邮件或上传）、自主执行中的重试与并发：持续搜索、自动重试、递归委派、并行调用会被利用为资源放大入口，这就是拒绝钱包攻击（Denial of Wallet），每次调用都符合接口限制、最终回答也正常，累计消耗却远超合理成本。

防护分两个方向：防止外部攻击者操纵 Agent（延续接口校验、代码审查、依赖治理；把 MCP 服务、连接器、技能配置纳入管理，接入与更新时评估；外部内容保留来源、与任务指令分开；限制批量触发和反复探测）；发现和限制 Agent 对内外部系统的非预期影响（明确可访问的目标、操作、数据范围并在请求发出前校验；数据库用参数化查询；网络请求校验实际连接地址、重定向和中间服务的代请求目标；输出在渲染、发送前做安全处理；把任务、工具调用与东西向、南北向通信记录关联，发现跨服务探测、批量读取、非预期外发）。

模型安全：输入、推理、输出三层威胁

原书 14.3 节

Agent 要理解自然语言、处理多模态输入、访问知识库、调用函数、生成结构化内容甚至执行操作，这条链让它成为攻击渗透、内容失控和数据泄露的关键入口。原书按位置分三层：输入层（对抗样本、提示注入变种如上下文分割和语义混淆、恶意文件触发供应链漏洞）、推理层（越狱导致伦理失控、对 RAG 知识库的定向爬取 Prompt Crawling、函数调用劫持如篡改 API 参数）、输出层（生成式钓鱼内容、医疗金融场景里的幻觉误导、在 AIGC 内容中用隐写术植入隐蔽指令）。

应对这些的是 AI 安全护栏这类“可信中间层”，原书列了九类能力：内容合规审核、提示词攻击防御、敏感信息防护（识别与脱敏 PII、密钥、卡号）、恶意文件检测、恶意 URL 拦截、提示词反爬（识别异常查询频率和意图，防止知识库被系统性窃取）、模型越狱检测（在输出端再判一次）、模型幻觉抑制（上下文一致性比对与外部知识核对）、数字水印标识（依《人工智能生成合成内容标识办法》对生成图片加水印）。展望部分，原书认为通用安全模型难以识别企业自身的业务风险，需要支持自定义标签与提示词的“自定义检测 Agent”。

结合第 6 篇再强调一遍：护栏是重要信号，但不应是唯一安全边界。能编码的权限和资源限制交给 Policy 与 Sandbox，护栏识别复杂语义风险，作为额外的一层。

把威胁放进对应的层。

厂商方案说明原书本节以阿里云 AI 安全护栏为例，称其基于自研大模型审核引擎、毫秒级延迟、支持可视化策略与自定义黑白名单，这些是厂商自述的产品能力。

数据安全：全生命周期六个环节

原书 14.4 节

大模型应用经历数据采集接入、传输、存储、访问、使用（处理）、删除六个阶段，要保护的包括训练数据、提示词、知识库、多模态数据和日志。风险有三方面：训练中的数据风险（投毒、清洗不完善、存放不安全，以及从输出逆向推断原始数据）；用户对数据的可控性（担心交互数据和商业秘密未经授权被用于二次训练）；操作可审计与责任可追溯（“谁持有谁负责、谁使用谁负责、谁运营谁负责”在多方编排下很难认定，仅靠模型服务商难以自证）。

原书的防护框架目标是“平台可靠、链路可信、数据可控、自主可选、操作可审、责任可追”。几个值得记住的实践判断：数据分类分级是基础，但各地法规不同、企业有大量独有的高敏数据，固定规则模型难以“千人千面”，AI 可以依据实际数据和用户修改的类别定义自适应调整；只靠提示词加密叠加模型自身的拒答能力来防蒸馏是有先天缺陷的，生成式模型的拒答并不稳定，还有人用大模型返回的加密令牌去问同系列安全能力更弱的小模型来绕过；Prompt 解密只应发生在检索召回和生成回答两处，在内存中瞬时存在、不做持久化；数据应当在用户自有账号下独立存储；AI 可能权限过大或自主提权，错误的提示词会导致误删，人也会惯性误点确认，关键数据节点建议引入第三方安全告警把最后一道关。

这些措施属于哪个生命周期环节？

厂商方案说明原书本节大量以阿里云产品举例：数据安全中心的 S1–S4 分类分级与脱敏（支持 900 多种文件类型）、Private Link 与 VPC 加密、百炼平台外接 OSS / ES / ADB / SLS / NAS 存储与 KMS 加密、RAM 访问控制、AI 安全护栏等。笔记保留其方法框架，产品能力以官方文档为准。

身份安全：谁在行动，代表谁，凭什么

原书 14.5 节

企业要保护的已经不只是模型输入输出，而是一条由用户、客户端、Agent、工具、凭据、数据和资源组成的动态行动链。原书归纳了五个难题：资产黑箱（不知道有多少 Agent、谁创建、调了什么、有什么权限）、权限逃逸（普通销售借“报销助手”看到 CEO 差旅明细；离职员工的 Agent 还在跑）、凭据管理失控（万能权限、硬编码 API Key、长期有效无法审计）、责任链模糊（一次泄露经过用户、客户端、Agent、MCP 服务、下游资源，难以追到具体身份和动作）、标准与场景不成熟。只给 Agent 配一个应用账号或长期密钥，回答不了“谁在行动、代表谁行动、凭什么行动、为什么此刻允许、出了事怎么收权”。

原书给的闭环：每个 Agent 发唯一的“数字工牌”并与人员、机器身份关联；通过 OIDC / OAuth 2.0 对接企业身份源，实现“用户 → 客户端 → Agent → 资源”的端到端身份传递；凭据由 KMS 加密集中托管在 Token Vault，Agent 代码不接触长期明文凭证，运行时按 Agent ID 和用户授权获取短期令牌（“无密钥开发”）；Agent 默认无权限，权限不超过用户；员工入职、转岗、离职时，其创建或授权的 Agent 权限同步变更，解决“影子 Agent”和权限残留。认证方式有 Client Secret、公私钥、OIDC / OAuth 联邦、On-Behalf-Of 委托（Agent 以用户身份和权限访问资源，用户首次需明确同意，撤销同意后 Agent 立即失去出站能力）。

授权是双向的：入站控制哪些客户端和用户能调用 Agent、可用哪些 scope；出站控制 Agent 能访问哪些大模型、企业应用、SaaS、MCP Server。调用下游时用 Token Exchange 收敛权限：原令牌的 audience 是 Agent，换出的新令牌 audience 是下游服务，只含被授权的最小 scope，同时保留用户信息并记录 Agent 调用链；即使 Agent 被攻破，泄露的也只是对单一服务的短期受限令牌。再往前一步是上下文感知的动态授权：结合用户、Agent、工具和请求中的上下文判断，原书的例子是“允许市场部的用户，使用订单 Agent，下单金额小于 1000 的订单”。

系统与网络：会话级隔离，出站默认拒绝

原书 14.6 节

先解决“看得见”：自动发现 AI 相关的计算资源、容器、模型服务实例（例如 Ollama、LM Studio），并把盘点对象延伸到 Agent 层：Agent 实例与会话、接入的 MCP 服务与连接器、技能与工具配置、Agent 持有的各类 NHI（非人身份）凭据，避免“影子 Agent”。再做多维风险评估：开源组件漏洞、公网暴露面（未授权开放的 SSH、Jupyter 端口）、配置合规、镜像和文件系统里的明文 API Key。原书提醒，态势管理解决的是“看得见”，发现的风险必须与运行时管控联动闭环，能对高危工作负载限流、隔离或暂停任务。

计算层：主机基础防护、安全组最小权限；容器共享内核增加逃逸风险，用安全沙箱为容器提供轻量级虚拟机隔离；镜像在 CI/CD 中扫描并签名，集群只允许有效签名的镜像部署。对 Agent 尤其重要的是会话级隔离：Agent 会动态生成并运行代码、访问外部服务，运行环境本身要当作不可信负载，原书说 2026 年以来业界普遍把隔离单位从服务收敛到会话，每个会话一个独立沙箱或 microVM，用完即弃，空闲超时或到最大生命周期自动回收，按会话注入最小化的临时凭据；多 Agent 之间也按任务边界划分环境与网络策略，防止一个被攻陷后横向波及。

网络层：互联网边界做七层、域名、URL 级访问控制与虚拟补丁；内网做微隔离，防止从开发测试区横向渗透到核心数据区，所有内部流量经身份认证与策略验证（零信任）。Agent 出站流量要单独管：HF 事件的攻击 Agent 正是借中间服务代联网突破边界，所以出站方向应默认拒绝、按需放行；在网络层封禁云元数据服务端点和内网保留地址段，防止 SSRF 与提示注入演化为内网探测和凭据窃取；访问互联网和 MCP 服务统一经 AI 网关或防火墙出站收敛，校验目标、记录日志，与 NDR 联动发现异常外联。

回扣开头的三个问题

先自己答，再点开
1. 为什么既要不被打穿，又要不越边界？拒绝钱包攻击是什么？

Agent 既是被攻击的对象（供应链投毒、提示注入、系统入侵），也是持有身份权限、自主调用工具、接触敏感数据的行为主体，即使没被攻击也可能越界造成损害，所以要防护（盾）与管控（缰绳）兼具。拒绝钱包攻击利用持续搜索、自动重试、递归委派、并行调用不断制造补充工作，每次调用都合规、最终回答也正常，但累计消耗 Token、付费 API、并发槽位和下游容量远超合理成本。

2. 身份五难题？Token Exchange 和 OBO 解决什么？

资产黑箱、权限逃逸、凭据管理失控、责任链模糊、标准与场景不成熟。On-Behalf-Of 让 Agent 以用户身份和权限访问资源，权限不超过用户、需用户同意且可撤销；Token Exchange 在调用下游时把 audience 为 Agent 的令牌换成 audience 为下游服务、只含最小 scope 的短期令牌，同时保留用户信息与调用链，Agent 被攻破也只泄露单一服务的受限令牌。

3. 出站为什么默认拒绝？会话级隔离隔什么？

Agent 会主动向外发起请求，HF 事件中攻击 Agent 正是借可访问的中间服务代联网突破边界；默认拒绝、按域名显式放行、封禁云元数据端点和内网保留地址、统一经网关或防火墙出站，可以阻止 SSRF 与注入演化为内网探测、凭据窃取和数据外发。会话级隔离把每个 Agent 会话放进独立沙箱或 microVM，用完即弃、超时回收、按会话注入最小临时凭据，避免残留环境与凭据被后续任务或攻击者复用，也防止横向波及。
