为什么用平台

原书 5.1.1 节

原书把这一步类比为建网站从手写 HTML 走到 WordPress：手写是为了理解，实战中往往要站在巨人的肩膀上。第四篇的 ReActAgent 等类虽然可以复用，但业务逻辑一复杂，纯代码的维护成本和开发周期就急剧上升。

低代码平台的四个价值：降低门槛（API 调用、状态管理、并发控制都封装成节点，产品经理和业务专家也能参与设计）；提升效率（原型几小时甚至几分钟就能搭出来，精力放在业务逻辑和提示词上）；可视化与可观测（数据在节点之间怎么流、哪一步最慢、哪个工具调用失败，画布上一目了然，比翻终端日志直观）；沉淀最佳实践（预置 ReAct 模板、优化过的检索引擎、标准化的工具接入）。

原书的定位很清楚：平台不是要取代代码，而是更高一层的抽象，让你把注意力放在智能体“思考”与“行动”的逻辑上。

平台组件 ↔ 手写代码

原书 5.2.1、5.5.1 节

学平台最快的办法，是把每个组件翻译回第四篇的代码。原书给 Coze 打了个游戏比方：工作流是关卡路线图，插件是技能卡，知识库是游戏百科，数据库是云存档，效果评测是闯关评分。换成工程语言就是：工作流是你写的编排逻辑（主循环、Plan-and-Solve 的步骤序列）；插件 / 工具节点是注册进 ToolExecutor 的函数；知识库是第 8 篇要讲的 RAG；提示词还是那个模板；记忆是 history 或 Memory 类；AI Agent 节点则是把模型、记忆、工具打包好的 ReActAgent。

n8n 的两个基本概念尤其值得记：节点是最小执行单元，分触发节点（工作流的起点，比如收到邮件、定时、Webhook，一个工作流有且只有一个）和常规节点（处理数据和逻辑）；工作流是节点连成的图，节点之间传 JSON。

四个平台，四种定位

原书 5.1.2、5.2.3、5.3.3、5.4.3、5.5.5 节

Coze（字节跳动）主打零代码：可视化界面友好，插件商店极其丰富，一键发布到抖音、飞书、微信公众号等渠道；原书实操的是从 36 氪、虎嗅、GitHub、arXiv 等源抓取内容的“每日 AI 简报”。原书认为它最致命的局限是不支持 MCP（截至成书时仍在其路线图上），另外复杂插件配置仍需技术背景，导出的是只能导回 Coze 的 zip 而非通用 JSON。

Dify 是开源的全栈 LLM 应用平台，融合后端即服务（BaaS）与 LLMOps：模型中立，Docker Compose 一键私有部署，Marketplace 插件数千个（原书写时 8000+），有 RAG 管道、工作流、RBAC 和审计日志。局限：对零基础用户仍有学习曲线；服务端是 Python，高并发有性能瓶颈；多模态支持有限；企业版贵；API 格式不兼容 OpenAI。

FastGPT 把知识库问答当一等公民：导入、智能分块、索引增强（标题入索引、自动补充索引、图片自动索引）、检索，每一步都可配、可看；原生支持 MCP，模型中立。局限是模板和预置工具较少、免费额度紧、社区和文档仍在完善。

n8n 本质是通用工作流自动化工具，LLM 只是流程里的一个节点；强项是“连接”，几百种预置节点能串起 SaaS、数据库和 API，支持私有部署。局限：复杂流程调试要逐节点查输入输出；内置 Simple Memory 和 Simple Vector Store 是内存级的，重启即丢，生产必须换 Redis、Pinecone 之类；导出 JSON 做版本管理远不如 git diff 清楚，多人协作易冲突；超高并发下调度有开销。

先翻牌复习四个平台，再做一轮归类。

Dify：用分类器做路由

原书 5.3.2 节，习题 3

原书用 Dify 做了一个“超级个人助手”，覆盖日常问答、文案优化、多模态生成、数据查询、MCP 工具（高德地图等）几类请求。核心结构是一个问题分类器节点：先让 LLM 判断用户意图属于哪一类，再把请求分发给对应的子智能体，每个子智能体有自己专门的提示词（原书用“角色、背景、任务、限制、输出格式”五段式）和工具。

为什么不让一个智能体包办一切？原书习题 3 的答案方向：单一智能体的提示词会塞满所有任务的规则，彼此干扰；工具一多就容易选错；出了问题也难定位是哪类任务的规则没写好。分类器路由把问题拆小，每个分支可以单独调优、单独换模型，这正是路由模式，也是多智能体架构最简单的一种。

数据查询分支还有个典型问题：50 张表、每张 20 个字段，把全部 DDL 塞进提示词会撑爆上下文。思路是先检索、后生成：给每张表写摘要并向量化，按问题先召回相关的几张表，只把这几张的 DDL 交给模型写 SQL。

输入一句话，看分类器会把它送到哪个分支（分类规则为示意，真实平台由 LLM 判断）。

n8n：一个 AI Agent 节点装下 ReAct

原书 5.5.2–5.5.4 节

n8n 的“智能邮件助手”分两段。准备知识：用 Code 节点放原始知识（JSON），经 Embeddings 模型向量化后写进 Simple Vector Store，只需在知识更新时跑一次。主工作流：Gmail 触发器（收到新邮件）→ AI Agent 节点 → Gmail 发送节点。

AI Agent 节点里挂三样东西：Chat Model（思考核心）、Memory（Simple Memory，用邮件的 threadId 作 key，同一线程的往来邮件共享上下文）、Tools（SerpAPI 搜公开信息，Simple Vector Store 以“作为 Agent 工具的检索模式”查私有知识）。System Message 里写角色、可用工具、执行步骤，并要求严格的 JSON 输出（含 shouldReply 等字段），后面的 Gmail 节点用表达式取 JSON 字段填收件人、主题和正文。

原书反复强调一个坑：向量库作为工具读取时，Memory Key 和 Embeddings 模型都必须和写入时完全一致，否则相当于拿错钥匙、说错语言，什么也查不到。另一个坑是工具的 Description：它就是第四篇说的“工具描述”，写清楚何时必须用这个工具，Agent 才会去用。

怎么选：平台、代码，还是混合

原书 5.6 节，习题 1、7

原书的选型建议浓缩成四句：快速原型、非技术用户选 Coze；企业级应用、复杂业务逻辑、多模态选 Dify；私有知识库问答、智能客服选 FastGPT；深度业务集成、通用自动化选 n8n。

更重要的是最后一句：混合开发才是工程化的最佳实践。用平台快速验证想法，用代码做精细控制；用平台处理标准化流程，用代码处理特殊逻辑。平台没有你要的工具（比如公司内部系统 API）时，三条路：写平台插件、包成 MCP 服务接入、或者在平台里用 HTTP / Code 节点直接调。

面试演练

题目取自原书第 5 章习题与 Extra01

低代码平台、纯代码、混合开发三种模式各适合什么场景？原书第 5 章习题 1

  • 低代码：快速验证想法、标准化流程、非技术人员参与、内部工具；代价是定制深度、性能、版本管理受限。
  • 纯代码：核心产品、高并发、需要精细控制循环和状态、要求严格测试和版本管理。
  • 混合：平台做编排和可视化，复杂逻辑写成插件、MCP 服务或 Code 节点；或者原型用平台，跑通后把核心链路迁到代码。

你用过哪些 Agent 平台或框架？选型是怎么选的？Extra01 · Agent 第 12 题

  • 先说需求维度：数据能否出域、是否需要私有部署、团队技术栈、需要哪些集成、预期并发、迭代速度。
  • 再说候选与取舍：如 Dify 私有部署 + 插件生态、n8n 做系统集成、FastGPT 做知识库问答；或代码框架（第 6 篇）做核心链路。
  • 最后说评价指标：任务成功率、响应延迟、单次成本、人工介入率、可维护性；并说明上线后怎么监控（第 12 篇）。

问题分类器路由相比单一智能体有什么好处？会引入什么问题？原书第 5 章习题 3

  • 好处：每个分支提示词更短更专注、工具更少更不易选错、可以按分支选不同模型控制成本、出问题容易定位。
  • 问题：分类错误会把请求送错分支，需要兜底分支或置信度阈值；跨类请求（“查天气并写一段朋友圈文案”）需要拆分或多分支串联；分类本身多一次调用。

回扣开头的三个问题

先自己答，再点开
1. 平台解决了什么痛点？组件对应什么？

降低门槛、提升效率、可视化与可观测、沉淀最佳实践，让人把精力放在业务逻辑和提示词上。工作流对应编排逻辑和主循环；插件 / 工具节点对应 ToolExecutor 里注册的函数；知识库对应 RAG；记忆对应 history 或 Memory；AI Agent 节点对应封装好的 ReActAgent；触发节点对应调用 run 的入口。

2. 四个平台的定位与最大局限？

Coze：零代码、插件丰富、多渠道发布；局限是不支持 MCP、配置只能导回 Coze。Dify：开源全栈、私有部署、插件市场大、企业级安全；局限是学习曲线、Python 服务端高并发性能、API 不兼容 OpenAI。FastGPT：知识库问答极致、原生 MCP；局限是生态和免费额度。n8n：通用自动化、连接能力强、私有部署；局限是内置存储非持久、调试和版本协作不如代码。

3. 怎么选？什么是混合开发？

快速原型选 Coze，企业复杂业务选 Dify，私有知识库问答选 FastGPT，深度业务集成选 n8n，核心链路或高并发用代码。混合开发是按阶段和模块组合：平台验证想法、代码精细控制；平台跑标准流程、代码处理特殊逻辑；缺的工具写成插件或 MCP 服务接入平台。
