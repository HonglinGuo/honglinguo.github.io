从脚本到框架

原书 6.1 节，表 6.1

框架的本质是一套经过验证的“规范”：把所有智能体共有的重复工作（主循环、状态管理、工具调用、日志）抽象封装，让你只写独特的业务逻辑。原书列了四个价值：复用与效率（通用 Agent 基类封装了 Agent Loop）；解耦与扩展（模型层、工具层、记忆层分开，换模型、加工具、改记忆策略互不影响）；标准化的状态管理（上下文窗口限制、历史持久化、多轮状态跟踪，第四篇的 Memory 类只是起点）；可观测与调试（在 on_llm_start、on_tool_end、on_agent_finish 这类生命周期节点挂回调，比到处 print 系统得多）。

如果说 LangChain、LlamaIndex 定义了第一代通用 LLM 应用框架，原书选的四个新框架则各自专攻一个难题：多智能体协作和复杂流程控制。一句话记住它们：AutoGen 以对话驱动协作；AgentScope 工程化优先、消息驱动；CAMEL 角色扮演加引导性提示；LangGraph 把流程建模为带循环的图。

AutoGen：一场自动进行的圆桌会议

原书 6.2 节

原书以 0.7.4 版为例，这一版做了架构重构：拆成底层的 autogen-core（模型交互、消息传递）和上层的 autogen-agentchat（对话式应用接口），并且全面异步（async/await），等一个智能体回复时可以处理别的事。

两个核心组件：AssistantAgent 封装一个 LLM，是任务的主要解决者，用 System Message 赋予专家角色；UserProxyAgent 身兼二职，既是人类用户的代言人（发起任务、验收），又可以配置为执行代码或调用工具的执行器，把“思考”和“行动”分开，也是天然的人类在环接口。多智能体用 Team 组织，原书用的是 RoundRobinGroupChat：参与者按列表顺序轮流发言，每条回复加入共享历史再激活下一位，直到满足终止条件（TextMentionTermination("TERMINATE")，有人说出 TERMINATE 就停）或到达 max_turns 安全阀。

案例是一个四人软件团队开发“实时显示比特币价格”的 Streamlit 应用：产品经理拆需求、工程师写代码、审查员查质量、用户代理执行验证并在最后说 TERMINATE。接非 OpenAI 模型时，要在 OpenAIChatCompletionClient 里多传一个 model_info 字典，告诉框架模型是否支持函数调用、JSON 输出、上下文长度等能力边界。优点：把流程映射成角色对话，开发者只需定义“谁”和“做什么”；角色可复用；轮询提供可预测的流程。局限：对话本质上不确定，可能跑偏甚至循环；出了问题没有错误堆栈，只有一长串聊天记录，原书称之为对话式调试难题。

AgentScope：一切交互都是消息

原书 6.3 节

AgentScope 由阿里巴巴达摩院开发，原书称它像一个“智能体操作系统”，主打工程化优先：分层架构（底层 Message、Memory、Model API、Tool；中层预置智能体和 ReAct 实现；协作层 MsgHub 与 Pipeline；顶层 Runtime 和可视化 Studio），组合式而非继承式设计。

它的核心是消息驱动：智能体之间不互相调用函数，而是收发 Msg（name、content、role、metadata）。好处有四：异步解耦（收发双方不必互等）、位置透明（对方在本机还是远程服务器无所谓，MsgHub 用 RPC 自动路由）、可观测（每条消息都能记录追踪）、可靠（消息可持久化、重试）。每个智能体继承 AgentBase，只需实现 reply(x) → Msg（思考与回应），可选 observe(x)（把听到的存进记忆）。

“三国狼人杀”把这些用得很充分：狼人夜聊时用 async with MsgHub(狼人列表, enable_auto_broadcast=True) 临时开一个只有狼人的频道，发言自动广播给频道内成员；投票时用 fanout_pipeline 并行向所有人发同一条消息并收集结果，模拟“同时投票”；每种行为用 Pydantic 模型做结构化输出（讨论要给出 1–10 的信心值，女巫要说明用不用解药、毒药、毒谁），把游戏规则变成代码层面的约束；单个智能体出错时 try/except 给一个默认响应，游戏继续。原书由此得出：游戏流程被表达为“在什么上下文里、以什么模式交换消息”，而不是一台僵硬的状态机。代价是要懂异步和分布式，简单场景有过度工程化之嫌。

切换游戏阶段，看消息发给了谁（玩家与身份取自原书日志）。

读日志时顺手挑个错

原书展示的夜晚日志里，狼人孙权的第一句话是“今晚我们应该除掉周瑜”，而周瑜正是他的狼人队友；周瑜还顺着接了一句“周瑜虽智，却未必是今晚的最大威胁”。这是“游戏身份”和“三国人格”双重角色设定下模型混淆了身份。原书没有点出这一点，但它恰好说明了两件事：结构化输出能约束格式，约束不了推理正确性；复杂角色设定需要在提示里显式列出“你的队友是谁”。这是我的读后观察，不是原书观点。

CAMEL：两个专家，一段开场白

原书 6.4 节

CAMEL 最初想探索的是：最少的人类干预下，两个智能体能不能自主协作完成复杂任务。它的两个基石：角色扮演，一个扮演“AI 用户”（懂领域、提需求、拆步骤，比如资深股票交易员），一个扮演“AI 助理”（懂实现、执行并给方案，比如 Python 程序员），任务变成两位跨领域专家的对话；引导性提示（Inception Prompting），对话开始前分别注入的结构化初始指令，包含四部分：明确自身角色、告知协作者角色、定义共同目标、设定行为约束与沟通协议（AI 用户一次只提一个具体步骤，AI 助理完成前不追问更多，用特定标记表示完成）。

原书案例是心理学家和作家合写一本拖延症心理学科普电子书：作家作为 user 提结构和要求，心理学家作为 assistant 提供专业内容，用 RolePlaying 会话驱动，检测到 <CAMEL_TASK_DONE> 就结束。优势是轻架构、重提示，协作行为自然涌现；CAMEL 现在也已扩展到多模态、工具和多智能体（Workforce 模块）。局限是高度依赖提示设计、效果不好时难定位是哪部分提示的问题、不同模型对同一提示理解不一；规模化时缺复杂对话路由、分布式状态和冲突仲裁。

LangGraph：把流程画成带循环的图

原书 6.5 节

LangGraph 是 LangChain 生态的扩展，和前三个基于对话的框架不同，它把智能体的执行建模为状态机，表示成有向图。三个要素：State，一个 TypedDict，所有节点共享读写（对话历史、中间结果、迭代次数）；Node，接收状态、返回更新后状态的普通 Python 函数；Edge，常规边固定地从 A 到 B，条件边则由一个函数看当前状态返回一个键，再按映射表决定跳到哪个节点或 END。条件边让循环变得自然，Reflection 那种“改到满意为止”只需一条指回去的边。

原书的实战是“三步问答助手”：理解问题 → 用 Tavily 搜索 → 生成回答，并在搜索失败时走备用路径。优势：高度可控、可预测、可审计，原生支持循环，节点高度模块化，插入一个人工审核节点很直接。局限：样板代码多，要思考“怎么控制”而不只是“做什么”；流程预先定义，缺少对话式那种涌现；出错可能在节点内部、状态传递或条件判断，需要对整张图有全局理解。

两条轴与选型

原书 6.6 节，习题 1、6

原书小结里最值得记的是两条轴。第一条：涌现式协作 ↔ 显式控制。AutoGen 和 CAMEL 定义角色和目标，让协作从对话中“涌现”，贴近人类交互但难预测、难调试；LangGraph 要求你写明每一步和每个跳转，牺牲涌现的惊喜，换来可靠、可控、可观测。第二条：工程化。无论选哪种协作范式，从原型走向生产都要面对并发、容错、分布式，AgentScope 代表了从“能运行”到“能稳定服务”的跨越。

面试演练

题目取自原书 Extra01 与第 6 章习题

什么是多智能体系统？相比单个 Agent 有什么优势？会引入哪些新的复杂性？Extra01 · Agent 第 8 题

  • 定义：多个具有不同角色、能力或视角的智能体，通过通信与协作共同完成任务。
  • 优势：分工专精（每个角色提示词更聚焦）、并行加速、互相审查纠错（审查员、反方）、模块化可复用、易于扩展新角色。
  • 复杂性：对话跑偏与循环、终止条件难定、成本与延迟成倍、上下文在成员间如何共享与隔离、冲突仲裁、调试只剩聊天记录、分布式下的消息顺序与一致性。
  • 框架对应：AutoGen 用群聊和终止条件，AgentScope 用 MsgHub 和结构化输出，LangGraph 用显式图控制，CAMEL 用角色约束。

如何理解“涌现式协作”与“显式控制”这两种设计哲学？原书第 6 章习题 1

  • 涌现式：只定义角色、目标和交流规则，具体流程由对话自然形成；灵活、贴近人类协作，适合开放、创造性任务；代价是不可预测、难调试。
  • 显式控制：把每个步骤和跳转条件写成代码（状态机 / 图）；可控、可审计、易测试，适合流程明确的业务；代价是样板代码多、缺少灵活性。
  • 实践：常常混用，例如 LangGraph 的某个节点内部放一个 AutoGen 群聊，外层用图保证流程和审批。

消息驱动架构相比传统函数调用有什么优势？分布式部署会带来什么挑战？原书第 6 章习题 3

  • 优势：异步解耦、位置透明、每条消息可观测、可持久化与重试；适合高并发、长时运行、跨机器部署的多智能体系统。
  • 挑战：消息顺序（夜聊发言要按序）、一致性（投票结果全员看到一致）、网络延迟与超时、部分节点故障时的游戏状态恢复。
  • 手段：按会话分区保证顺序、主持人作为单一状态权威、消息带序号与幂等处理、超时给默认响应（原书的 try/except 兜底）。

动手练（原书习题 2、5）

  1. RoundRobinGroupChat 顺序固定，审查不通过要回到工程师，怎么改？
    思路

    换成由模型或规则选择下一位发言者的群聊（如 AutoGen 的 SelectorGroupChat），或在审查员的输出里约定“APPROVED / REJECTED”标记，用自定义发言者选择函数据此跳转；也可以把外层流程改用 LangGraph，用条件边实现回退。

  2. 给三步问答助手加一个“反思”节点。
    思路

    在 answer 之后加 reflect 节点给答案打分写入 state；条件边：分数达标到 END，不达标且重试次数小于上限回到 search（并在 state 里记录换一个搜索词），否则带着说明结束。重试计数一定要放在 state 里。

回扣开头的三个问题

先自己答，再点开
1. 四个框架各用什么抽象？

AutoGen：可对话的智能体组成群聊（Team），按轮询等规则发言，靠终止条件结束，以对话驱动协作。AgentScope：一切交互是消息（Msg），由 MsgHub 路由，Pipeline 编排顺序与并行，工程化与分布式优先。CAMEL：AI 用户与 AI 助理两个角色加引导性提示，自主多轮对话推进任务。LangGraph：共享 State、函数节点、常规边与条件边构成的状态图，原生支持循环。

2. 两条轴分别是什么？

第一条是涌现式协作与显式控制：前者只定义角色和目标，让流程从对话中涌现（AutoGen、CAMEL），灵活但难预测；后者显式写出每步和跳转（LangGraph），可控可审计但样板多。第二条是工程化：并发、容错、分布式、持久化，决定能否从原型走到稳定服务，AgentScope 是代表。

3. 三个场景怎么选？

每秒上千请求、7×24 小时、水平扩展的客服：工程化优先，选 AgentScope 或自研服务。研究员与写作者多轮深度讨论、自主推进：选 CAMEL 角色扮演（或 AutoGen 群聊）。资料审核到最终决策的严格审批流程、要求可追溯可审计：选 LangGraph，每个环节一个节点，人工复核作为中断节点。
