为什么智能体评估难

原书 12.1 节

评估要回答三个问题：智能体有没有预期的能力？在不同任务上表现如何？和别人比处在什么水平？它的价值是把“感觉变好了”变成数字：量化表现、客观比较方案、发现弱点、向用户证明可靠。和传统软件测试相比，原书列了三个独特难点：输出不确定（同一问题可能有多个正确答案，很难简单判对错）、标准多样（工具调用要查函数签名，问答要看语义相似）、成本高（每次评估都要大量 API 调用，可能花掉数百元）。

应对办法是标准化的基准（Benchmark）：统一的数据集、指标和评分方法。原书按评估对象分三类：工具调用（BFCL：伯克利，1120+ 样本，四个类别，AST 匹配；ToolBench：清华，16000+ 真实 API 场景；API-Bank：微软，53 个常用 API）；通用能力（GAIA：Meta 与 Hugging Face，466 个真实问题，三级难度，准精确匹配；AgentBench：清华，8 个领域；WebArena：CMU，真实网页环境）；多智能体协作（ChatEval、SOTOPIA，或者自定义协作场景）。常用指标也分四类：准确性（Accuracy、Exact Match、F1）、效率（响应时间、Token 用量）、鲁棒性（错误率、故障恢复）、协作（通信效率、任务完成度）。HelloAgents 的评估模块按 Dataset、Evaluator、Metrics 三层组织，并照例封装成 Tool。

每个基准评的是哪类能力？

BFCL：函数调用调得对不对

原书 12.2 节，表 12.1–12.2

工具调用要做四件事：理解需求、选对工具、填对函数名和参数、处理复杂场景。BFCL 用四个难度递增的类别覆盖它们：simple（一个函数调一次）、multiple（给多个候选函数，要选对那一个）、parallel（一次请求要并行发出多个调用）、irrelevance（给的函数都不相关，正确做法是不调用）。每个样本有 question、可用的 function 列表（签名与描述）和 ground_truth。数据推荐从官方 gorilla 仓库克隆（含 possible_answer 标准答案），用 BFCLDataset 加载，也可以用官方 bfcl evaluate 命令行评估，结果与排行榜一致。

判分用 AST 匹配而不是字符串比较：把调用解析成抽象语法树再比较结构。三个条件：函数名精确一致（get_weather 和 get_temperature 是两个函数）；参数键值对集合相等（f(a=1, b=2) 等价于 f(b=2, a=1)）；参数值语义等价（单双引号不同的字符串视为相同）。多个调用时数量要相同、每个都要匹配，但顺序可以不同。指标是准确率、分类准确率、加权准确率（按类别权重求和）和错误率。原书的例子：simple 0.95、multiple 0.82、parallel 0.68，三类等权平均 0.817。

这条样本属于哪个类别？

读原文时值得多想一步：2 + 3 真的等于 5 吗

原书说 AST 匹配“允许等价表达式（f(x=2+3) 等价于 f(x=5)）”。但据我了解，BFCL 官方检查器的做法是把每个参数值和标准答案里给出的一组可接受取值逐一比对（比如 unit 可以是 "celsius" 或省略），并不会去计算表达式。所以“等价”主要来自标注时列出的多个可接受答案，而不是自动推导。这是我的补充，具体以官方实现为准。

GAIA：真实任务做不做得成

原书 12.3 节，表 12.3–12.4

GAIA 的理念是真实世界的问题往往需要多种能力综合运用：多步推理、知识运用、多模态理解、网页浏览、文件操作。466 道题分三级难度，Level 1 几乎不用或只用一两步，Level 3 需要长链条的复杂推理。样本带 Question、Level、Final answer、可能的附件文件，以及标注者给出的步骤和所需工具。它是受限数据集，要先在 Hugging Face 申请权限并设置 HF_TOKEN；结果可以提交到官方排行榜。

判分用准精确匹配（Quasi Exact Match）：先归一化再精确比较。数字去掉千分位逗号和 $、% 等单位；字符串转小写、去冠词、合并空格、去末尾标点；列表按逗号切开、每项归一化、排序后再拼起来。为了让答案能被这样比较，GAIA 规定了官方系统提示词：思考之后必须以 FINAL ANSWER: [答案] 结尾，答案要么是一个数、要么尽量少的词、要么逗号分隔的列表；数字不写逗号和单位，字符串不用冠词和缩写。指标除了精确匹配率和分级准确率，还有难度递进下降率 (Accℓ − Accℓ+1) / Accℓ，衡量难度升高时能力衰减得多快。

输入模型答案和标准答案，看归一化后是否一致；再算一道下降率。

易混辨析：AST 匹配 vs 准精确匹配

两者都是“先规范化再比较”，规范化的对象不同。AST 匹配规范的是调用结构：函数名、参数集合、参数值，因为工具调用的答案是一段结构化的代码。准精确匹配规范的是答案文本的写法：大小写、冠词、标点、单位，因为 GAIA 的答案是一个短事实。两者都无法处理真正的语义等价（“四十二”和“42”），这正是原书习题 3 追问的：需要更智能的匹配时，可以引入数值解析、同义词表，或者 LLM 判断。

评估生成数据：LLM Judge、Win Rate、人工

原书 12.4 节

第三个场景是评估“让智能体造数据”的质量。原书用 HelloAgents 生成 AIME 风格的数学题（美国数学邀请赛，答案都是 0 到 999 的整数，覆盖代数、几何、数论、组合、概率，难度相当于 AIME 第 6 到 9 题），从 900 多道历年真题里随机挑参考样例做风格示范，用英文生成以便与真题公平对比。一个工程细节：题目里的 LaTeX 反斜杠（\frac、\sqrt）在 JSON 里是非法转义，解析前要用正则把未转义的反斜杠加倍。

三种方法分工：LLM Judge 从正确性、清晰度、难度匹配、完整性四个维度给每道题打 1 到 5 分，汇总成平均分、及格率（平均 ≥ 3.5 的比例）和优秀率（≥ 4.5），并给出理由和改进建议；Win Rate 把生成题和 AIME 2025 真题成对比较，统计胜、负、平，理想值约 50%（生成质量接近真题），明显低于说明要改生成策略，明显高于则可能是评委有偏；人工验证用 Gradio 界面逐题看题目、答案和解答，四维打分并标注通过、拒绝或需修改，主要用来核实答案的正确性，也能发现创新性、趣味性这类自动评估看不到的东西。最后汇总成一份综合报告。

分层评估与持续监控

原书 12.5 节，习题 5

原书小结给了四个扩展方向：按 Dataset、Evaluator、Metrics 三件套添加新基准；按场景自定义指标；接入 CI/CD（每次提交自动跑评估、设阈值防止退化、报告归档）；把生成数据评估扩展到代码、对话等更多数据类型。习题 5 再追问了两个工程问题：评估成本和质量怎么权衡（分层评估：日常迭代跑快速的小样本，版本发布前跑标准集，重大更新或对外发布才跑全量加人工），以及外部 API 和用户需求变化导致性能漂移怎么办（持续评估：定时跑固定评估集，记录趋势，跌破阈值告警，线上抽样做人工复核）。

什么是 LLM-as-a-Judge？它有哪些优点和潜在偏见？Extra01 · 评估第 3 题

  • 定义：用一个 LLM 按给定标准给另一个模型的输出打分或做成对比较。
  • 优点：便宜、快、可规模化，标准一致，能给出理由，适合开放式输出。
  • 偏见：位置偏见（偏向先出现的答案）、长度偏见（偏向更长的）、自我偏好（偏向同家族模型的风格）、对自信语气和格式的偏好、在专业正确性上可能判错。
  • 缓解：交换顺序各评一次、细化评分量表和示例、多评委投票、用人工标注集校准一致性、关键任务保留人工复核。

评估 Agent 为什么比评估一个基础 LLM 更难？维度有哪些不同？Extra01 · 评估第 5 题

  • 更难的原因：多步交互、路径不唯一；依赖外部环境和工具（会变、会失败）；结果可能是对环境的改变而不是一段文本；随机性导致同一任务多次结果不同；评估成本高。
  • 维度：除了最终任务成功率，还有过程质量（工具调用正确率、步数、是否走弯路）、效率与成本（时间、Token）、鲁棒性（工具失败后能否恢复）、安全性（是否越权、是否被注入）。
  • 方法：可复现的沙箱环境、按状态而非文本判定成功、每题多次运行看平均与方差。

除了最终结果正确，评估 Agent 时还应关注哪些过程指标？上线后怎么持续监控？Extra01 · 评估第 7、10 题

  • 过程指标：步数与冗余调用、工具调用成功率与参数正确率、重试次数、Token 与延迟、人工介入率、失败后的恢复率。
  • 上线监控：固定回归集定时跑；线上指标（成功率、用户反馈、投诉、转人工率）看趋势；抽样轨迹做人工或 LLM 复核；依赖的模型或 API 变更时触发全量评估；设阈值告警。

回扣开头的三个问题

先自己答，再点开
1. 为什么难？基准怎么分？

三大难点：输出不确定（多个正确答案）、标准多样（工具调用与问答需不同方法）、成本高（大量 API 调用）。基准按对象分：工具调用（BFCL、ToolBench、API-Bank）、通用能力（GAIA、AgentBench、WebArena）、多智能体协作（ChatEval、SOTOPIA、自定义场景）。

2. AST 匹配与准精确匹配怎么判？为何各用各的？

AST 匹配把函数调用解析成语法树：函数名精确一致、参数键值对集合相等（忽略顺序）、参数值语义等价（如引号不同）；多调用时数量相同、顺序可不同。准精确匹配先归一化再比较：数字去逗号和单位，字符串小写、去冠词、合并空格、去末尾标点，列表切分归一化后排序。工具调用的答案是结构化代码，所以比结构；GAIA 的答案是短事实，所以规范写法。

3. 三种方法分工？Judge 有何偏见？

LLM Judge 按正确性、清晰度、难度匹配、完整性打 1–5 分，算平均分、及格率（≥ 3.5）、优秀率（≥ 4.5）；Win Rate 与真题成对比较，理想约 50%；人工验证核实答案正确性并标注通过、拒绝、需修改，补充创新性等主观维度。LLM Judge 可能有位置偏见、长度偏见、自我偏好、对自信语气的偏好，以及专业正确性误判。
