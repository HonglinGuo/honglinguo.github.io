从提示工程到上下文工程

原书 9.1–9.2 节

上下文就是一次采样时模型看到的那组 token。提示工程关心怎么写、怎么组织指令（尤其是系统提示）；上下文工程是它的自然演进，关心的是推理时怎样策划与维护最优的信息集合：除了提示，还有工具定义、MCP、外部数据、消息历史，一切会进入窗口的东西。一个循环运行的智能体每一轮都在制造可能有用的新信息，必须周期性地提炼，决定谁进窗口。

为什么窗口大了还要管？原书引用“大海捞针”类评测揭示的上下文腐蚀（context rot）：token 越多，模型从上下文中准确回忆的能力越差。这是一个性能梯度而非悬崖：长上下文下模型依旧强，但检索和长程推理的精度会下降。原因有二：Transformer 里每个 token 和所有 token 两两关联，关系数随长度平方增长，注意力被“拉薄”；训练数据里短序列远多于长序列，模型对长距离依赖的经验更少。位置编码插值能让模型适配更长序列，代价是位置理解变模糊。结论是：上下文是有限资源，有边际收益递减，每个 token 都在消耗注意力预算。

先估一下注意力“拉薄”的程度。

有效上下文的三个组件

原书 9.2.1 节

目标一句话：用尽可能少、但信号密度高的 token，最大化得到期望结果的概率。原书拆成三个组件。

系统提示要把握“刚刚好”的高度，避开两个极端：过度硬编码（在提示里写复杂、脆弱的 if-else，难维护）和过于空泛（只给宏观目标，缺少对期望输出的具体信号，或者假定了不存在的共享背景）。建议用 XML 或 Markdown 分区（背景、指令、工具指引、输出描述），追求“能完整勾勒期望行为的最小必要信息集”，最小不等于最短。做法是先用最好的模型跑最小提示，再按失败模式补指令和示例。

工具是智能体与信息、行动空间的契约：职责单一、彼此少重叠、对错误鲁棒、参数描述无歧义，返回 token 友好的结果。常见失败是臃肿工具集：边界模糊，“该选哪个”本身就说不清。原书的话很直接：如果人类工程师都说不准用哪个工具，别指望智能体做得更好，所以要精选一个最小可行工具集（MVTS）。示例：始终推荐给，但不要把所有边界情况堆进去，挑一组多样、典型的就够，好示例胜过千言万语。

即时上下文与渐进式披露

原书 9.2.2 节

原书对智能体的简洁定义是：在循环中自主调用工具的 LLM。模型越强，就越能自己去找需要的信息。于是工程实践正从“推理前一次性检索”转向即时（Just-in-time, JIT）上下文：不预先加载所有数据，只维护轻量引用（文件路径、查询、URL），运行时用工具按需加载，大文件用 head、tail 看一部分。这和人一样：我们不背下所有东西，而是靠文件系统、收件箱、书签按需提取。

引用的元数据本身就是信号：目录层级、命名、时间戳都在暗示用途和时效（tests/test_utils.py 和 src/core/test_utils.py 的含义不同）。自主导航带来渐进式披露：每一步产生的新上下文指导下一步，文件大小暗示复杂度、命名暗示用途，智能体逐层建立理解，工作记忆里只留当前必要的子集，再靠记笔记做持久化。代价是运行时探索比预计算检索慢，没有好的工具和启发式时可能误用工具、钻死胡同。所以常用混合策略：先放少量高价值上下文（比如项目约定的 README），再给 glob、grep 这类原语让它自己找。这正是 Claude Code 一类编码智能体的做法（原书在 1.4 节也提到了它）。

长时程任务的三种手段

原书 9.2.3 节

大型代码库迁移、持续数小时的研究，行动序列远超窗口。无限加大窗口治不了上下文污染和相关性退化，原书给了三种直接针对约束的手段。

压缩整合（Compaction）：接近上限时对对话做高保真总结，用摘要开一个新窗口。保留架构决策、未解决的缺陷、实现细节，丢弃重复的工具输出；新窗口带上摘要和最近访问的少量文件。调参先保召回（不漏关键信息），再提精度（剔冗余）；最安全的“轻触式”压缩是清理深层历史里的工具调用结果。结构化笔记：智能体定期把关键信息写到窗口之外的持久存储（TODO 列表、NOTES.md、结论与阻塞项索引），需要时拉回，用极低的上下文开销跨越几十次工具调用和多次上下文重置。子代理架构：主代理负责规划与综合，子代理在各自“干净”的窗口里深挖，只回传 1000 到 2000 token 的凝练摘要，庞杂的搜索过程留在子代理内部。

原书的经验法则：需要长对话连续性用压缩整合；有里程碑、阶段性成果的迭代式开发与研究用结构化笔记；能从并行探索中获益的复杂研究与分析用子代理。

ContextBuilder：GSSC 流水线

原书 9.3 节

ContextBuilder 把每次调用前的上下文拼装抽象成四步：Gather（汇集候选：系统指令、记忆检索 limit 10 且 min_importance 0.3、RAG 检索 limit 5 且 min_score 0.3、最近 5 条对话历史；每个来源都包 try/except，一个源挂了不影响整体）→ Select（打分与预算内选择）→ Structure（按固定骨架分区）→ Compress（超限兜底压缩）。每条候选是一个 ContextPacket（内容、时间戳、token 数、相关性、元数据）。

Select 是核心：系统指令单独拿出来，直接保留、不参与评分；其他候选的分数 = relevance_weight × 相关性 + recency_weight × 新近性（默认 0.7 和 0.3）。相关性用关键词重叠（生产中应换成向量相似度），新近性用 exp(−0.1 × 小时数 / 24) 并限制在 [0.1, 1]；相关性低于 min_relevance 的直接过滤；然后按分数降序贪心填充，加不下就停。Structure 输出固定骨架：[Role & Policies]、[Task]、[Evidence]（RAG 结果）、[Context]（历史与记忆）、[Output]。固定形态便于调试、A/B 测试和评估。Compress 按分区依次保留，超出部分截断并标注“内容已压缩”，剩余预算不足 50 token 就不再保留。Token 数用“中文字数 + 英文词数 × 1.3”估算。

原书强调了“最小规则”：不引入来源、优先级等更多分类维度，只用相关性加新近性，大多数场景已经够用。

候选信息为示意。调预算和权重，看 Select 选了谁、Structure 拼出什么。

Structure 之后的上下文

NoteTool：写在窗口之外的笔记

原书 9.4 节

MemoryTool 偏对话式记忆，NoteTool 则面向项目式任务的长期追踪，更轻、更人类友好：每条笔记是一个独立的 .md 文件，开头是 YAML 元数据（id、title、type、tags、created_at、updated_at），正文是 Markdown。好处是机器可解析、人可读可改、纯文本天然适合 Git 版本管理、不需要数据库。笔记按 type 分类，原书用到了 task_state（任务状态）、conclusion（阶段结论）、blocker（阻塞点）、action（下一步计划）、reference（参考资料）等，再用 tags 做多维检索。

和 ContextBuilder 配合的方式：每轮对话前先 list 出最多 2 条 blocker（阻塞点总是值得提醒），再 search 与问题相关的笔记，合并去重后转成 ContextPacket（相关性 0.7）作为 custom_packets 交给 build。也可以把一次重要的回答存成新笔记。这就是 9.2.3 节“结构化笔记”手段的落地。

易混辨析：NoteTool vs MemoryTool

MemoryTool 是给模型用的：向量与图存储、自动打分排序、整合与遗忘，人很难直接读改。NoteTool 是人机共用的：一个笔记一个 Markdown 文件，人可以打开改计划、加约束，智能体下一轮就能读到，Git 能看出每次改了什么。原书的代码库助手把两者都用上：发现的知识进记忆，任务进度和阻塞进笔记。

TerminalTool：按需看一眼，但要守住边界

原书 9.5–9.6 节

TerminalTool 是 JIT 上下文的落地：不预先把整个代码库灌进向量库，而是需要时 find、grep、head 一下；看日志用 tail | grep ERROR，看数据先 head -n 5。原书给了四层安全：命令白名单（只允许 ls、cat、head、tail、find、grep、wc、sort、uniq、cut、awk、sed、pwd、cd、file、stat、du、df、echo、which 等）、工作目录沙箱（只能访问指定 workspace 及子目录，绝对路径和 .. 逃逸都会被拒）、超时控制（默认 30 秒）、输出大小限制。

9.6 节把三样工具组装成一个代码库维护助手（约 50 个文件的 Flask 项目，重构要持续好几天）：TerminalTool 负责即时探索（信息量超出窗口），NoteTool 负责跨会话的进度、待办和阻塞（任务持续数天），ContextBuilder 负责每次对话的高信号密度上下文（回顾历史又不被淹没）。原书概括为分层：即时访问 + 会话记忆 + 持久笔记。

输入一条命令，看它在哪一层被拦下（按原书描述的规则模拟）。

读码时值得多想一步：白名单里的 sed、awk、find

原书说白名单“只允许安全的只读命令，完全禁止任何可能修改系统的操作”，但列表里的 sed 带 -i 就能原地改文件，awk 可以用 system() 执行任意命令或重定向写文件，find 带 -delete 或 -exec 也能删改。只按命令名做白名单不够，还需要检查参数（或者干脆在只读挂载的容器里执行）。这是我的读码观察，不是原书观点；原书习题 3 也在追问这套机制是否足够。

面试演练

题目取自原书第 9 章习题与 Extra01

什么是上下文腐蚀？模型支持 100K、200K 窗口了，为什么还要管理上下文？原书第 9 章习题 1

  • 现象：上下文 token 越多，模型从中准确回忆和推理的能力越差，是渐进的性能梯度。
  • 原因：注意力两两关系随长度平方增长被拉薄；训练中长序列少，长距离依赖经验不足；位置插值牺牲位置精度。
  • 还有成本：输入 token 计费、首 token 延迟、缓存失效。
  • 所以：把上下文当作有边际收益递减的预算，追求最少而高信号的 token：精简系统提示与工具集、JIT 按需加载、压缩、笔记、子代理隔离。

GSSC 某个阶段失效会怎样？什么时候截断比 LLM 摘要更合适？原书第 9 章习题 2

  • Gather 漏源：关键事实根本不在候选里，后面再好也没用。Select 选错：不相关信息占预算，相关的被挤掉，模型被带偏。Structure 混乱：证据和历史混在一起，模型分不清哪些是依据。Compress 过度：截掉关键数字或约束，产生看似合理的错误。
  • 截断 / 滑窗更合适：信息按时间线性衰减（闲聊历史）、需要逐字保真（代码、日志、法律条文）、对延迟和成本敏感、摘要模型可能引入幻觉时。
  • 混合：最近 N 轮原文保留 + 更早的摘要；结构化字段（决策、数字、待办）单独抽取不压缩。

长任务中断后如何“断点续传”？笔记里要记哪些状态？原书第 9 章习题 4

  • 记什么：任务目标与完成定义、计划与每步状态（未开始 / 进行中 / 完成 / 阻塞）、已产生的工件位置、关键决策与理由、未解决问题、最后一次成功的检查点。
  • 怎么恢复：读笔记重建计划 → 用工具核对真实状态（文件是否存在、测试是否通过、git 状态）→ 只有核对一致才从检查点继续，不一致先修正笔记。
  • 原则：笔记是事实的索引而不是事实本身，恢复前一定要验证，不能盲目重放最后一步。

回扣开头的三个问题

先自己答，再点开
1. 上下文工程 vs 提示工程？为何仍要管理？

提示工程关心怎么写指令；上下文工程关心每次推理时进入窗口的全部 token（提示、工具、外部数据、历史）如何策划与维护。即使窗口很大，上下文腐蚀让准确回忆随长度下降，注意力关系随长度平方增长被拉薄，长序列训练经验也少；再加上成本和延迟，上下文必须当作有边际收益递减的预算来管理。

2. 三种长时程手段各适合什么？

压缩整合：接近上限时高保真总结并开新窗口，适合需要长对话连续性的任务。结构化笔记：把进度、结论、阻塞写到窗口外的持久存储按需拉回，适合有里程碑的迭代开发和研究。子代理：主代理规划综合，子代理在干净窗口里深挖并只回传 1000–2000 token 摘要，适合可并行探索的复杂研究与分析。

3. GSSC 四阶段？Select 怎么做？

Gather 从系统指令、记忆、RAG、最近对话等多源汇集候选（各自容错）；Select 打分并在预算内选择；Structure 组织成 [Role & Policies] [Task] [Evidence] [Context] [Output] 固定骨架；Compress 超限时按分区保留、截断并标注。Select：系统指令直接保留；其余按 0.7 × 相关性 + 0.3 × 新近性打分，过滤低于 min_relevance 的，按分数降序贪心填充至预算用尽。
