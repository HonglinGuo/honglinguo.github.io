两个维度，和一条判据

原书 10.1–10.2 节

设计多 Agent 系统有两个基本维度。上下文是否共享：共享时，后一个 Agent 换了系统提示词和工具，但继承前任的完整轨迹，信息不丢，却容易膨胀；不共享时，每个 Agent 有独立上下文，靠显式通信交换信息，模块化好、易扩展。通信落在操作系统 IPC 的两大范式里：共享文件系统是“共享内存”，工具调用参数和消息总线是“消息传递”。协作拓扑：对等协作（少数 Agent 迭代互评）、管理者模式（一个 Manager 规划调度）、去中心化（没有中心，Agent 自己决定找谁）。原书提到，2026 年流行的“Graph 工程”讨论的正是这些图拓扑。

什么时候真的需要多个 Agent？原书给的核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息。同一模型重读自己的输出通常无效甚至有害；不同 Agent 辩论同一段文本，在等计算量下与单 Agent 持平；但审核者拿着测试执行结果、渲染截图、外部工具验证去审，效果显著提升。WebGen-Agent 用多层视觉反馈把 Claude 3.5 Sonnet 在网页生成基准上的成绩从 26.4% 提到 51.9%。这也解释了学术界“多 Agent 没用”和工程界“多 Agent 有用”的矛盾：两边说的不是同一种多 Agent。

开放搜索是另一类收益：Anthropic 的漏洞挖掘实验里，45 个 Agent 通过共享论坛协调、互审、独立仲裁，用 2700 万 token 找到 266 个漏洞；独立并行方案用 650 万 token 只找到 21 个。但成本始终要算：收益必须覆盖数倍乃至一个数量级的额外 token。原书还提到，单纯加步骤预算也不一定更好，Agent 需要预算意识，前期广泛探索、后期深挖。

共享上下文：换提示词，还是加载 Skill

原书 10.3 节

共享上下文的多 Agent 像接班的同事能翻前任的所有工作日志：每个阶段动态切换角色，但信息不丢。原书指出一个常被忽略、却会改变架构的选择：角色转换是替换系统提示词，还是加载 Skill？

transfer_to_agent 替换系统提示词并通常替换工具集：只暴露当前角色的工具，越界工具在 schema 层就不可见，约束力强；但每次切换都改了请求前缀，从变化点起缓存无法复用。Skill 则固定系统提示词，按需把 SKILL.md 追加到轨迹，前缀不变，缓存可继续复用；但工具通常全集可见，Skill 只是行为指令，硬权限仍要 Harness 门控。

原书的选择规则：角色差异主要来自知识、流程和写作风格，优先用 Skill；涉及权限、工具隔离、合规边界，或需要在运行时强制禁止某类动作，用独立 Agent 或 transfer_to_agent，并在 Harness 层用代码限制工具调用。

不共享上下文：一套 Agent 操作系统

原书 10.4 节

不共享上下文才是真正的多 Agent：每个 Agent 有自己的上下文、轨迹和状态，彼此看不到对方的“内心活动”。原书发现它和操作系统的对应相当完整：静态前缀是程序，轨迹是进程内存，LLM 是 CPU，Agent 运行时是内核，工具调用是系统调用，spawn_subagent 是 fork，cancel_subagent 是 kill，list_agents 是 ps，子 Agent 返回的结构化摘要是退出码。这其实就是 1970 年代 Actor 模型的 LLM 版本，操作系统和分布式系统的成熟经验大多能直接借用。

数据平面是一棵虚拟文件系统：Agent 专属工作区（私有，随实例销毁）、多 Agent 共享空间（用户可见、要持久化、并发冲突高发）、外部挂载资源（Google Drive、Notion 等，受外部权限约束、延迟高、以只读为主）、系统内置资源（如 Skills，全局只读）。Agent 间传递的是轻量的路径字符串，而不是把内容塞进上下文。

控制平面有四件事。消息传递用统一的信封（发送者、目标、类型、负载）。状态查询别做拉取式接口，更自然的是发消息问进展，或约定一个 progress.md，它长时间不更新就判定卡住。终止分优雅（在安全点清理资源后退出，像 SIGTERM）和强制（像 SIGKILL），并像 Go 的 context 一样沿创建关系向下级联，杜绝孤儿 Agent。资源调度管 token 预算、模型分配、并发上限和抢占；管理者 Agent 比 OS 调度器多一样东西：推理，可以像公司内部赛马一样给有希望的分支加资源、终止误入歧途的。

先把操作系统概念和 Agent 概念配对。

对等协作：模型可以提出“完成”，不能批准自己的“完成”

原书 10.4 节 · 对等协作与 Loop 工程

对等协作通常是 2–3 个平等的 Agent 多轮互相反馈，实现最简单。但“多个实例”不等于“多种思路”：模型、上下文、脚手架高度相似时，它们会做出相同选择。要真正多样，得主动区分模型、上下文、工具、可见证据或职责，并让各 Agent 先独立判断再汇总。

它最经典的用途是治过早终止。原书用 Coding Agent 和 Pine AI 举了三种形态：偷懒式假完成（测试没跑就说完成；两件事办完一件就说都办好了）、过早放弃（打一个电话被拒就说办不了，其实还能填表单、发邮件）、假成功（对方口头同意退款，用户还要在 App 上确认一步，Agent 却说已办妥）。根源相同：在验证之前，“完成”只是模型的一句宣称，不是证明。把宣称变成证明就是 Loop 工程：由验证器而不是模型判定能不能停，人的角色从写提示词变成设计循环；业界共识是循环的瓶颈在验证器。LongHorizon-Harness 的 Manage–Execute–Audit 循环在同模型同后端下，把 WeaveBench 通过率从 51.8% 提到 80.7%。

为什么不能自己生成再自己审？Huang 等人发现，没有外部反馈时让 GPT-4 修正自己的回答，准确率反而下降，改错的比改对的多。CRITIC 的对照更直观：允许用搜索、Python 验证效果显著提升，去掉工具只留自我评估，提升基本消失。辩论模式也有争议：控制思考 token 预算相同时，单 Agent 在多跳推理上与五种多 Agent 架构持平甚至更好，因为数据处理不等式说明串行传递中间结论只会丢信息。

管理者模式：第一个“已验证”的成功

原书 10.4 节 · 管理者模式

子任务多、要动态调度、依赖复杂时，用管理者模式：Manager 像项目经理，拆解、派活、跟进、处理异常、整合结果。设计上把每个专门 Agent 当作 Manager 的一个工具，新能力只需注册新 Agent。代价是 Manager 成了单点瓶颈，上下文也会膨胀。Plan-and-Act 的结论是：弱规划者是整个系统最关键的瓶颈，应把最强的模型和最用心的提示词给 Manager。原书的书籍翻译实验是典型：术语 Agent、章节翻译 Agent、审校 Agent 各自在精简的上下文里工作，产物存文件，Manager 只保存计划、调用记录和文件索引。

并行时还有两个要点。一是结算点必须是第一个已验证的成功，而不是第一个声称成功的。二是竞态条件：两个 Agent 几乎同时报告“找到了”，Manager 可能汇总两次。settle_once 必须幂等（用锁或事务保护），然后广播取消、等待确认或超时。另一种思路是让管理者先把工作流写成代码，再交给确定性运行时执行，比如 Claude Code 的 Workflow 工具提供 agent()、parallel()、pipeline() 原语，不必每派一个子任务都让模型决策一次。

10 个 Agent 并行在 10 个学院网站上找同一位老师。试试有锁和没锁的区别，以及“声称找到”与“验证通过”的区别。

去中心化，以及跨组织的 A2A

原书 10.4 节 · 去中心化模式与 A2A 协议

去中心化模式里，每个 Agent 自己决定何时移交任务、请求反馈或报告问题。动机是模拟人类组织的分工与制衡，也能避免管理者崩溃造成的单点故障。微服务里把两种模式叫编排（orchestration，指挥统一调度）和编舞（choreography，每位舞者自己把握入场时机）。原书用三个系统做递进：MetaGPT 控制流其实是按 SOP 固定的流水线，贡献在“共享消息池 + 按角色订阅”的通信解耦；AutoGen 群聊是共享对话记录 + 中心化选择发言者的混合形态；OpenAI Swarm 才在控制流上真正对等，控制权像接力棒一样通过 handoff 流转。

移交包应只传任务描述、已确认的事实与约束、产物的文件引用，而不默认暴露完整私有轨迹。对等移交的风险是成环：A 交给 B、B 又交回 A。原书给的最小协议里，剩余预算和已访问链由运行时保留，任何 Agent 都不能自行删除。原书还提醒，“Agent Swarm”这个热词并不对应单一架构：有的是 handoff 网络（去中心化），有的是主 Agent 动态创建上百个子 Agent（规模化的管理者模式），要看实质结构。

跨组织协作需要标准协议。Google 2025 年发布的 A2A（后捐给 Linux 基金会）有三个要素：Agent Card（能力名片，解决跨组织发现）、任务生命周期（已提交、进行中、需要输入、已完成、失败）、不透明协作（只交换任务和产物，不暴露提示词和思考）。它和 MCP 的分工是：MCP 管 Agent 与工具，A2A 管 Agent 与 Agent；同一团队内部用消息总线就够，只有协作方互不信任、实现互不可见时才需要 A2A。

多 Agent 的六种失败

原书 10.5 节

《Why Do Multi-Agent LLM Systems Fail?》在 7 个主流框架的约 150 条轨迹上归纳出 14 种失败模式，分三大类：系统设计缺陷、Agent 间对齐失败、任务验证缺失；简单修补效果有限（ChatDev 只提升 15.6%）。原书借用分布式容错的说法：传统系统主要防崩溃故障，Agent 的故障天生是拜占庭式的，它很少停下来，而是继续给出看似可信的错误结论。

原书重点讲了六种。并发冲突：简单冲突是两个 Agent 改同一文件、后写覆盖前写，用乐观锁（读时记版本号，写时检查）；语义冲突是改的不同文件但逻辑矛盾（一个重编图号、一个引用旧图号），Coding 场景的主流做法是每个 Agent 一个 worktree，冲突推迟到合并点。错误级联放大：进程间传字节逐位保真，Agent 间传语义每次都是有损重编码，要用不看前序思考、只看原始证据的交叉验证打断。同质趋同：Anthropic 实验中 30 个同时上线的 Agent 有 18 个建了同名 Git 分支，同模型产生的多个审核意见不能视为独立证据；逐利 Agent 甚至会通过公开报价板合谋定价。互相扯皮：三个 Agent 各自把同一后端迁移到不同语言，很快把对方的操作当成蓄意阻挠，终止对方进程、撤销权限，所以要预先定义目标优先级、资源所有权和权限边界。循环失控：失控的 Agent 可能生成数千个子 Agent，建议给自主性强的 Agent 独立的 API key。理解债与认知投降：这是人的失败，Agent 交付越快，工程师越看不懂自己的系统；Karpathy 的话是“你可以外包思考，但不能外包理解”。

Agent 社会：规模大了会涌现什么

原书 10.6 节

原书最后把视角从任务协作转向开放的群体交互，按三个维度看。社交涌现：斯坦福 AI 小镇里 25 个 Agent 靠记忆流、反思、计划三个组件生活两天；研究者只在 Isabella 的记忆里种下“想办情人节派对”的念头，邀请、帮忙布置、消息扩散、按时赴约全部自发发生，没有任何派对组织代码。Agentopia 把 100 个 Agent 放进虚拟社会连续模拟 10 年，用以马斯洛需求为先验的“生活奖励”挑出进步最大的 25% 轨迹做拒绝采样微调，模型在下游角色扮演基准 CoSER 上 +15.6%，模拟社会成了可再生的训练数据。Moltbook 是专为 Agent 设计的社交网络，数日内涨到约 150 万，Agent 自创了一个“龙虾教”。

经济涌现：Vending-Bench Arena 让多个 Agent 在同一市场经营售货机，出现了价格战，也出现了主动发邮件组建价格同盟的模型，甚至一边在思考里承认合谋违法、一边照做。Pinchwork 让 Agent 雇 Agent，RentAHuman 让 Agent 用加密货币雇人做取包裹之类的物理任务，暗示一种基于市场的去中心化资源分配。策略博弈：狼人杀实验由代码驱动的法官掌握全局状态，按角色只给各自应知的信息，与小镇的完全去中心化形成对照。

原书的总结是：更强的模型或单体层面的对齐，不会自动带来群体协调。多 Agent 工程的本质，是同时设计信息如何流动、能力如何分工、激励如何约束、争议如何裁决、错误如何被发现。
