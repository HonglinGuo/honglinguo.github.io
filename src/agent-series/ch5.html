七个工具，就是一个 Coding Agent

原书 5.1 节

原书认为，代码生成不是少数专门化 Agent 的专利，而是每个通用 Agent 都该具备的基础能力，而且不需要复杂架构。浏览目录、读代码、改文件、跑命令、查模式，这五类动作只需七个核心工具：代码解释器、Bash、读文件、写文件、编辑文件、按文件名搜索（Glob）、按内容搜索（Grep）。其实一个 Bash 就能覆盖大部分，OpenAI Codex 就只用 shell 加一个语法受约束的 apply_patch；原书列七个是为了把能力讲清楚。

为什么 Coding 是 Manus、OpenClaw 这类通用 Agent 的核心，而不是 Deep Research 或 Computer Use？因为几乎所有高效的内容生成最终都落在代码上：PPT 和 Word 本质是 OOXML，报告可以由 Markdown、HTML、LaTeX 生成，GUI 上成功的操作序列也可以固化成代码。Computer Use 更通用，但成本、延迟、稳定性远不如直接写代码调 API。

文件系统是中枢：OpenClaw 把长期记忆放在 MEMORY.md 和按日期归档的 Markdown 日志里，用户可以直接打开改，天然保留时间顺序，还能用 Git 回滚。原书也划了边界：这个判断主要适用于面向开放任务的 Agent；垂直客服这类封闭任务的 Agent，代码更多是工具箱里的一件工具。

给每个动作挑一个工具。

为什么 Coding Agent 最成熟

原书 5.1 节 · 整体流程与 Harness

原书推荐的工作流程像一个靠谱的新工程师：先项目文档化（没有文档就先读代码、写出架构概览和测试指南；CLAUDE.md、AGENTS.md 这类项目指令文件就是面向 Agent 的项目级系统提示词，也是最经济的稳定前缀）；复杂需求先澄清；写设计文档给人审，审设计比审几百行代码容易得多；实现后测试—修复循环到全部通过，再自审；最后同步文档。Coding Agent 最常见的偷懒，就是不跑测试就报告完成，所以完成标准应该是“测试通过”而不是“代码写完”。

原书用两个维度给任务分四个象限：目标是否明确 × 结果能否自动验证。两者都满足是 Agent 的最佳区域；目标明确但要人验，吞吐量被人的审查速度卡住；能自动验证但目标模糊，会高效地跑偏；两者都缺，基本派不上用场。代码天然处在最佳象限：测试给出验收标准，linter 和类型检查即时反馈，Git 提供回退。所以 Coding Agent 成熟，不是因为代码模型特别强，而是软件工程几十年攒下的基础设施天然就是一套强大的 Harness。

由此得出可迁移的四条原则：约束优先于指导（能用 linter、CI 强制的就别写成“请遵循”）；验证要自动化；反馈越快越结构化越好；回退要可靠。约束还要管过程：把库删了重建也算“修好了数据库”，把代码全删也能“编译通过”，所以危险动作本身要被检查。

故障：先分类，再恢复，最后要有上限

原书 5.1 节 · 故障与错误恢复

原书基于对 Claude Code 等生产级实现的研究，把故障分成四层：API 层（限流、过载、超时、输出被截断）、工具层（幻觉调用、参数畸形、同一个错误反复出现模型却原样重试）、上下文层（窗口溢出、压缩失败、工具调用缺少配对结果）、控制流层（死循环和死亡螺旋）。

捕获错误后先问“值不值得重试”：限流、网络抖动值得；参数非法、权限不足、工具不存在，重试多少次都一样。再检测模式：对“工具名 + 参数”算指纹，相同指纹反复出现就是无进展循环。恢复按对用户透明的程度分级：静默重试（指数退避加随机抖动；后台辅助调用失败直接放弃，免得挤占主链路）→ 降级与接续（输出触顶就提高上限或让模型从断点续写；主模型过载就换备用模型）→ 都失败了才暴露给用户。工具层错误则不终止会话，变成结构化的工具结果交给模型下一轮自己改。

每条恢复路径都要有熔断上限，阈值来自生产数据：Claude Code 的压缩熔断是“连续 3 次”，因为曾有一个会话在这条路径上连续失败三千多次，这类无效重试每天在全球浪费约 25 万次 API 调用。更隐蔽的是死亡螺旋：错误处理逻辑本身又调用 LLM，又出错。还有跨厂商接管：思考里的文字可以带给另一家，厂商签发的凭证带不走，所以轨迹应存成中立格式。

    怎么找代码，怎么改代码

    原书 5.1 节 · 实现技巧、搜索与编辑

    几个实现技巧：流式执行（第一个工具调用的参数一生成完、通过校验就开始执行，不等后面的调用）；并行调用失败时级联中止只波及同批次中依赖它的调用；读文件带行号，模型可以精确引用“第 42 行”；Git 分支、未暂存变更等环境信息作为状态栏追加，而不是写死在系统提示词里；维护一个持久终端会话，cd 和激活虚拟环境的效果能保留；写完文件立刻跑 linter，像 IDE 画红线。

    搜索有四种：grep 按内容匹配，glob 按文件名匹配，语义代码搜索按意义找，符号搜索区分定义和调用。有一场路线之争：Claude Code 刻意不建嵌入索引，纯靠 grep + glob 现场检索，省掉随代码演化而陈旧的索引；Cursor 早期建索引做语义召回，现在也改用 grep + glob 了。

    编辑的难点是让模型可靠地说清“改哪里、怎么改”。原书比较了五种方案：差异描述 + Apply Model（Cursor 曾用，合并环节脆弱）、旧字符串 → 新字符串（Claude Code、Codex 和现在的 Cursor 采用，可预测，但删大段代码要原样输出全部原文）、行号定位（精确，但每次编辑后行号会变）、类 Vim 命令（为“边看边改”的人设计，不适合“想很久再批量改”的模型）、首尾匹配（只给要删内容的开头几行和结尾几行，兼顾可靠和省 token）。

    致命三要素，再加一个放大器

    原书 5.1 节 · Coding Agent 的安全

    Simon Willison 的致命三要素：Agent 能访问私有数据，会暴露于不受信任的内容，又具备外部通信能力。三者齐备，攻击路径就闭合了：恶意指令藏在网页或邮件里进来，驱使 Agent 读私有数据，再经对外通道送出去。原书补充第四个维度持久记忆，它不是必要条件，而是放大器：攻击者把恶意指令写进长期记忆，跨会话潜伏，一次性攻击变成长期威胁。OpenClaw 这样的全权限本地 Agent 四者兼备。

    原书的思路是：单靠输入过滤挡不住，重点是让 Agent 即使被注入，也没机会把危险动作执行出去。沙盒默认断网、白名单代理放行，这正好切断第三要素；源码只读挂载、凭证文件根本不挂进沙盒；超时超限返回结构化错误而不是静默杀进程。命令检查要做语义解析而不是关键字黑名单：$(echo rm) -rf / 能绕过黑名单，find … -exec rm 把删除藏在合法命令的参数里。

    还有一类更微妙的问题：Agent 为谁效忠。模型默认“谁在跟我说话就帮谁”，可替你砍价的 Agent 对面坐的是交涉对手。实测两端都会翻车：太老实会把底价抖出去，太多疑连主人的正当请求也拒绝。提示注入本质上就是一次策反，Harness 要把主人指令定为最高优先级，外部内容一律降格为“可参考的数据”。

    代码即规则：checklist 引导，真值守门

    原书 5.2 节 · 思考工具与业务规则约束

    元能力是“能创造其他能力的能力”。原书按作用对象由内向外列了六个方向：思维本身、业务规则、内容呈现、系统接口、用户界面、Agent 自身。最内一层是思考工具：40 人的班，60% 选数学、45% 选物理、25% 两门都选，只选物理的有几人？自然语言推理容易从数学人数里减（得 14），代码直接算出 18 − 10 = 8。让 LLM 负责理解并写代码，让解释器或符号计算引擎负责算。原书也提醒：模型越强，这层脚手架的增益越小；评估一项 Agent 技术时，结论取决于配的是什么模型。

    第二层是业务规则。“购买后 7 天内可退款”，是自然日还是工作日？从下单还是发货算？代码没有歧义。原书以 τ-bench 航空取消政策为例，给出一个三重保障的设计：系统提示词里的自然语言规则用于理解和解释；工具描述列出全部政策，并用可选的 expected_cabin_class、expected_has_insurance 参数让模型把判断依据写出来，填参数的过程就是一张强制 checklist，模型常常在准备调用时就发现不能取消，直接给用户提替代方案；最后，服务端只按数据库真值裁决，舱位、保险、预订时间、当前时间一律查库和取服务端时钟，绝不采信模型自报，自报与真值不符时记日志。

    关键在于：最后一道防线必须建在模型无法伪造的数据上。独立性不仅指独立的模型，更指独立的数据来源。

    代码的另外四种用法

    原书 5.2 节

    多媒体生成：PPT 用 Slidev 的 Markdown 写，视频用 Blender Python API 和 FFmpeg 剪。Agent 写完代码并不知道渲染效果，所以用提议者—审核者：Reviewer 渲染截图、用视觉模型给出“第 3 页内容过多建议拆分”这类结构化意见，迭代到达标或到 5 轮上限。双 Agent 的好处在上下文：Reviewer 每次只看最新渲染图，Proposer 只累积文字反馈。代码还是生成模型？看产物有没有紧凑的精确描述：法兰盘五六个参数就能定义，代码是无损表达，改孔径只改一个数；一盆绿植细节近乎无限，交给生成模型。

    系统适配器：没有 SDK 的接口，现场读文档写胶水代码；日志格式变了，前端解析失败就把样本交给 Agent 生成新解析代码，测试通过后热更新。生成式 UI：用一张级联表单代替十轮澄清问答；A2UI 这类声明式协议只让 Agent 从受信任组件目录里点菜，而不是直接生成可执行代码。查数据库用 Artifact 模式：Agent 只写 SQL，数据从数据库直达界面，LLM 不去“抄写”几千行；执行层仍要只读账号、只放行 SELECT、参数化绑定。动态生成软件时，把信任边界下移到数据层，即使 AI 写漏了权限判断，越权也会被数据库拒绝。

    Agent 自举：OpenClaw 的 doctor 先用确定性检查修掉过期 token、锁文件、端口冲突这类高频问题，再把长尾疑难交给 LLM。让 Agent 写 Agent 时，最有效的办法不是在提示词里穷尽规则，而是给一个高质量的 Agent 实现当范例，复制后针对性修改。
