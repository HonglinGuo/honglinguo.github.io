规划模式：先出方案，再动手

原文「Planning Mode」

规划模式分两段：规划阶段 Claude 分析任务、写出详细的实施计划；你审阅、修改、批准之后，进入实施阶段按计划执行。原文给的适用场景：多文件的复杂重构、新功能、架构调整、数据库迁移、大的 API 改版；不适合：简单 bug、格式调整、单文件修改、快速提问。

进入方式有四种：/plan 描述；启动时 claude --permission-mode plan；会话里 Shift+Tab 在权限模式间切换；设成默认 "permissions": {"defaultMode": "plan"}。计划可以按 Ctrl+G 在外部编辑器里改；计划文件按产生它的提示词命名（v2.1.112）。模型别名 opusplan 表示用 Opus 规划、Sonnet 执行。两条行为规则要记住：v2.1.136 起 plan 模式无条件禁止写文件，即使 allow 里有匹配的 Edit 规则；v2.1.218 起如果 auto 模式可用（useAutoModeDuringPlan 默认开），规划期间的 shell 命令交给分类器审查，不再逐条问你。

一张功能卡，再判断几个任务要不要规划。

思考与强度

原文「Extended Thinking」，10-cli「Effort Levels」

扩展思考让 Claude 在回答前花更多时间推理：拆解问题、比较多种方案、权衡取舍、推敲边界情况。原文的示例是一个架构选择题（微服务还是单体），推理过程列出团队规模、运维资源、时间线等约束，最后推荐模块化单体。在当前的模型上，思考深度主要由 effort（强度）控制，从轻到重是 low → medium → high → xhigh → max；不同模型的默认档和支持的档位不同（原文对此有详细列表，版本变化很快，以原文和 /model 里的显示为准）。

设置方法有五种：会话里 /effort high（交互式滑块），/model 里左右键也能调；启动时 claude --effort high；环境变量 CLAUDE_CODE_EFFORT_LEVEL=high；提示词里写 ultrathink 触发深度推理；Skill 和子代理的 frontmatter 里写 effort: 只对它生效。Option+T（macOS）/ Alt+T 开关扩展思考，Ctrl+O 看推理过程；原文注明在 Opus 5.5 等部分新模型上思考不能关闭，这个开关无效。另外 /effort 滑块里有个 Ultracode 开关，它不是强度档位，而是让 Claude 默认用动态工作流（编排一批后台子代理）来做事，见第 11 篇。

判断这几种说法。

六种权限模式

原文「Permission Modes」

权限模式决定 Claude 不经你确认能做哪些事。原文列了六种：manual（v2.1.200 前叫 default，两个名字都能用）只读文件，其余都问；acceptEdits 读写文件不问，命令要问；plan 只读，不能改；auto 全部操作交给后台安全分类器审查；dontAsk 只执行事先放行的工具，其余一律拒绝；bypassPermissions 不做任何权限检查（危险）。

Shift+Tab 循环切换：manual → acceptEdits → plan，可用时再到 bypassPermissions 或 auto；dontAsk 不在循环里。设默认用 --permission-mode 或 permissions.defaultMode（注意键名是 defaultMode，没有 permissions.mode）。原文提到 v2.1.284 起交互会话在没配置模式时默认从 auto 开始，claude -p 在某些条件下从 default 开始，细节以原文为准。还有一个容易忽略的细节：即使在 acceptEdits 下，写 shell 启动文件（.zshenv 等）和会执行代码的构建配置（.npmrc、.pre-commit-config.yaml、.devcontainer/ 等）仍然要问（v2.1.160）。

选一个模式，看同一组操作各会怎样（auto 列取自原文的默认放行与拦截清单；dontAsk 假设事先放行了 Read 和 Bash(npm install:*)）。

权限模式

auto 模式：分类器替你点“允许”

原文「Auto Mode」

auto 模式用一个后台安全分类器，在每个操作执行前审查。原文给的判断顺序是：先看显式的 allow/deny 规则；只读和编辑自动通过；其余交给分类器；分类器连续拦 3 次或一个会话累计拦 20 次后，回退到弹窗问你。默认拦截：管道到 shell 的安装（curl | bash）、把密钥等敏感数据发出去、生产部署、大范围删除、IAM 权限变更、向 main 强推。默认放行：本地文件操作、按清单安装依赖、只读的 HTTP 请求、推到当前分支。此外还有基于意图的内置保护：git reset --hard、git clean -fd、terraform destroy 这类，除非你本次会话明确要求，否则拦下。

配置都在 autoMode 下：allow、soft_deny、environment（可信的基础设施，企业用）。v2.1.118 起数组里写 "$defaults" 表示在内置规则后面追加，不写就会整体替换内置规则；hard_deny（v2.1.136）是无论意图如何都拦的硬规则；classifyAllShell: true 让所有 shell 命令都过分类器。claude auto-mode defaults 打印默认规则，claude auto-mode reset 恢复默认。原文还提供了一个不用分类器的替代方案：脚本 setup-auto-mode-permissions.py 往 settings 里写一组保守的 allow 规则，危险操作一律不加。

读配置猜行为。

权限规则

原文 10-cli「Tool & Permission Management」，02-memory「Settings File Hierarchy」，09「Configuration and Settings」

权限规则写在 settings.json 的 permissions 下，分 allow、ask、deny 三组，跨层合并（不像其他设置那样高层覆盖低层，见第 3 篇）。规则格式是 工具（这个工具的所有调用）或 工具(说明符)：Bash(git log:*) 或 Bash(npm run test *) 按命令前缀；Read(./.env.*) 按路径；mcp__github__* 按 MCP 服务器；Skill(deploy *) 按 Skill；Agent(fork) 按子代理类型。v2.1.178 起还能按工具的参数匹配 工具(参数:值)，具体参数名各工具不同，写之前查官方文档。

几条原文点到的规则：超过 10,000 字符的 Bash 命令无论 allow 规则如何都要确认；Docker/Podman 用到改变守护进程的参数时要确认（v2.1.214）；FOO=bar 命令 这种带内联变量的写法不能靠只放行 FOO=bar 混过去（v2.1.145）。管理入口：/permissions（v2.1.234 起 Claude 工作时也能打开，改动对本轮剩余部分生效）；/fewer-permission-prompts 根据你最近的调用推荐 allow 规则。命令行上对应的是 --allowedTools、--disallowedTools、--tools（第 12 篇）。

沙箱：OS 级的文件与网络隔离

原文「Sandboxing」「Trust and Permission Scoping」

沙箱给 Claude 执行的 Bash 命令加上操作系统级的文件系统和网络隔离，是权限规则之外的另一层防护。开启方式：/sandbox（选择写进本项目的 .claude/settings.local.json）；所有项目都开就在 ~/.claude/settings.json 写 "sandbox": {"enabled": true}；临时用 claude --settings '{"sandbox": {"enabled": true}}'。原文特意说明没有 claude --sandbox 这个参数。

主要设置：sandbox.filesystem.allowWrite / allowRead / denyRead（比如拒读 ~/.ssh、~/.aws）；sandbox.network.allowedDomains（支持 *. 通配）与 deniedDomains（在通配之上再排除）；strictAllowlist（非白名单主机直接拒绝、不再询问）；failIfUnavailable；credentials（阻止读凭据文件，Linux/WSL 上还能用 mask 模式让进程读到假值、由代理在出口替换真值）。原文总结的一条趋势也值得记：凡是能让仓库里提交的文件扩大 Claude 权限的设置，现在多半只认用户级，比如嵌套仓库要单独确认信任、sandbox.ripgrep、Remote Control 自动启动。

先把三层防护的分工理清楚，再做题。

易混辨析：权限模式、权限规则、沙箱

权限模式决定“没有规则覆盖到的操作，默认问不问你”（manual 都问、acceptEdits 编辑不问、auto 交分类器……）。权限规则是按工具和参数写死的 allow / ask / deny，跨层合并，deny 和 ask 规则连 hook 的 allow 都推翻不了。

沙箱不管“问不问”，而是在操作系统层面限制 Bash 子进程能读写哪些路径、能连哪些域名；命令即使被批准执行，越界访问也会被挡。三者叠加使用：规则挡已知的危险，模式管默认行为，沙箱兜底未知的。

回扣开头的三个问题

先自己答，再点开
1. 何时用 Plan Mode？怎么进？能改文件吗？

多文件重构、新功能、架构调整、数据库迁移、大 API 改版用；简单 bug、格式、单文件、快速提问不用。进入：/plan 描述、claude --permission-mode plan、Shift+Tab、permissions.defaultMode: plan。v2.1.136 起 plan 模式无条件禁止写文件，即使有 Edit 的 allow 规则；auto 可用时规划期间的 shell 命令交给分类器。Ctrl+G 外部编辑计划；opusplan 用 Opus 规划、Sonnet 执行。

2. 六种模式的范围？auto 靠什么、默认拦放什么？

manual 只读其余都问；acceptEdits 读写不问、命令问；plan 只读不改；auto 交后台分类器；dontAsk 只执行预先放行的、其余拒绝；bypassPermissions 不检查（危险）。auto 判断顺序：显式规则 → 只读和编辑自动通过 → 分类器 → 连续 3 次或累计 20 次拦截后回退到询问。默认拦 curl|bash、外发敏感数据、生产部署、大范围删除、IAM 变更、强推 main；默认放本地文件操作、按清单装依赖、只读 HTTP、推当前分支。

3. 权限模式、规则、沙箱各管什么？谁能拦 Bash 访问网络？

模式管默认问不问；规则按工具和参数写死 allow/ask/deny，跨层合并，hook 的 allow 推翻不了 deny/ask；沙箱在 OS 层限制 Bash 子进程的文件和网络访问，sandbox.network.allowedDomains/deniedDomains 能拦住 Bash 子进程访问未授权的域名，即使命令本身被批准了。
