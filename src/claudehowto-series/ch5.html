它解决什么

原文 04-subagents「Overview」「Key Benefits」「Context Management」

原文列了 Subagent 的五个作用：隔离上下文（每个子代理从干净的窗口开始，不带主对话历史，只拿到任务所需的那部分）、定制系统提示词（专注某一领域）、控制工具权限（安全审查员只给 Read 和 Grep）、防止上下文污染、并行执行。干完以后结果被“提炼”交回主代理，主对话因此能撑得更久。

代价也写得很清楚：子代理从零开始，要自己重新收集上下文，会增加延迟。所以原文的判断表是：多步骤的复杂功能、并行任务、需要专门提示词、长时间分析——用；快速代码审查、单一任务——不用，“徒增开销”。

先看一张功能卡，再一步步看一次委派是怎么走的（过程为示意）。

Explore 子代理的窗口

定义文件

原文「Configuration」「Configuration Fields」「Tool Configuration Options」

子代理是一个 Markdown 文件：YAML frontmatter 写配置，正文就是它的系统提示词。必填只有两项：name（小写字母和连字符；含 : 的名字从 v2.1.218 起会被拒绝，冒号留给插件命名空间）和 description（什么时候该用它，写上 “use PROACTIVELY” 会让 Claude 更积极地委派）。

常用的可选字段：tools（不写就继承全部工具；可以写成 Bash(npm:*) 这种带条件的形式）、disallowedTools、model（sonnet / opus / haiku / 完整 ID / inherit）、permissionMode、maxTurns、skills（预加载 Skill 正文）、mcpServers（只给这个子代理用的 MCP）、memory、background、effort、isolation: worktree、hooks、color，以及 omitClaudeMd: true（启动时不带用户、项目、本地 CLAUDE.md）。创建方式原文推荐“让 Claude 帮你写”：说一句“创建一个审查安全问题的子代理”，它会生成文件；/agents 的交互向导在 v2.1.198 已移除。

读配置猜行为。

内置子代理

原文「Built-in Subagents」

Claude Code 自带六个子代理。general-purpose：继承模型、全部工具，做既要探索又要修改的复杂多步任务。Plan：plan mode 下用来调研代码库，工具是 Read、Glob、Grep、Bash。Explore：严格只读的快速代码搜索，可以指定 quick、medium、very thorough 三档深度，模型继承会话但封顶到 Opus（想快想省可设 haiku）。claude：兜底的通用代理，有子代理能用的全部工具，也是派发后台会话时的默认代理。statusline-setup：配置状态栏时用。claude-code-guide：用 Haiku 回答关于 Claude Code 本身的问题。

原文还提到两个开关：CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1 去掉内置的 Explore 和 Plan；非交互模式下 --append-subagent-system-prompt 给每个子代理的系统提示词追加同一段文字。

每个任务交给哪个内置子代理最合适？

位置与调用

原文「File Locations」「Using Subagents」「claude agents CLI Command」

定义有五个来源，同名时按优先级取第一个：托管设置（全组织）> 命令行 --agents（JSON，只在本次会话）> 项目 .claude/agents/ > 用户 ~/.claude/agents/ > 插件的 agents/。monorepo 里多个嵌套 .claude/agents/ 有同名定义时，离当前工作目录最近的赢（v2.1.178）。注意这里和 Skills 相反：Skills 是个人盖过项目，Subagents 是项目盖过用户。

调用有四种方式：自动委派（Claude 看任务描述和子代理的 description 决定）；点名（“用 test-runner 子代理修失败的测试”，名字大小写和分隔符都不敏感）；@ 提及（@"code-reviewer (agent)"，绕过自动判断，保证调用）；整个会话都用它（claude --agent code-reviewer 或 settings 里 "agent": "code-reviewer"）。另外一个常见误会：claude agents 打开的是后台会话的 Agent View，不是列出子代理定义；要看定义就问 Claude 或看两个 agents 目录。

同名冲突时谁生效？

易混辨析：同名优先级，Skills 与 Subagents 方向相反

Skills：企业 > 个人 > 项目，你 ~/.claude/skills/ 里的同名 Skill 会盖过团队仓库的。

Subagents：托管 > 命令行 --agents > 项目 > 用户 > 插件，团队仓库 .claude/agents/ 里的同名定义会盖过你个人的。

后台、隔离与分叉

原文「Background Subagents」「Worktree Isolation」「Forked Subagents」「Key Behaviors」

后台：从 v2.1.198 起子代理默认在后台跑，Claude 继续处理主对话，子代理完成时收到通知；background: true 的意思变成“强制后台、禁止内联”。Ctrl+B 把正在跑的任务放到后台，Ctrl+X Ctrl+K 停掉所有后台子代理（3 秒内按两次确认）。后台子代理需要未预先放行的权限时，确认框会出现在主会话里，并写明是哪个子代理在要。

worktree 隔离：isolation: worktree 让子代理在自己的 git worktree、单独分支上改代码；没改动会自动清理，有改动则把 worktree 路径和分支名交回主代理，供你审阅或合并。分叉子代理：不从干净窗口开始，而是继承分叉那一刻的整个对话（系统提示词、工具、模型、历史、prompt cache），用 /subtask 或 Claude 以 subagent_type: "fork" 发起；分叉不能再分叉，用 deny 规则 Agent(fork) 可以禁止。适合“带着现有上下文试另一条路”，不适合“独立的专项任务”。

还有几条上限：嵌套深度默认 3 层（CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH，设 1 关闭嵌套），同时运行默认最多 20 个（CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS），会话内总数不再设上限（v2.1.224 取消）；子代理上下文约 95% 时自动压缩；会话的扩展思考配置会被继承。

分叉还是干净上下文？

Agent Teams：会互相发消息的一组实例

原文「Agent Teams (Experimental)」

Agent Teams 是实验功能，默认关闭，用 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 打开（需要 v2.1.32 以上）。它和 Subagents 是两种协作模型：Subagent 是“父代理委派子任务、等结果”，结果只交回父代理，子代理之间不通信；Team 是一个队长拆任务，多个队员各自是独立的 Claude Code 实例，有自己持续的上下文，通过共享任务列表（自动管理依赖）协调，并能经由邮箱直接互发消息。

原文的经验：团队 3 到 5 人最合适；任务切成 5 到 15 分钟的粒度；给不同队员分配不同的文件或目录，避免冲突；第一次先用默认的 in-process 显示模式，熟悉后再用 --teammate-mode tmux 分屏。限制也不少：进程内的队员不能恢复会话、一个会话只能有一个团队、队长不能转让。团队还带来两个 Hook 事件：TeammateIdle 和 TaskCompleted。

持久记忆与安全

原文「Persistent Memory for Subagents」「Plugin Subagent Security」「Observability」

子代理默认每次从零开始，memory 字段给它一个跨会话保留的目录：user 在 ~/.claude/agent-memory/<名字>/（所有项目）、project 在 .claude/agent-memory/<名字>/（可随 git 共享）、local 在 .claude/agent-memory-local/<名字>/（不提交）。启动时自动加载其中 MEMORY.md 的前 200 行，并自动获得 Read、Write、Edit 来维护它；auto memory 被关掉时这个字段不起作用。适合长期跑的调研助手，在笔记里积累发现。

安全方面有两条值得记：插件带来的子代理里，hooks、mcpServers、permissionMode、initialPrompt 这几个字段会被忽略，防止插件借子代理提权；项目子代理 frontmatter 里的 hooks 需要先接受该目录的工作区信任（v2.1.218）。另外 v2.1.210 起，Claude Code 会扫描子代理的最终报告，把伪装成系统消息、伪造对话轮次、提到绕过权限的那类文本标出来，防止子代理读到的恶意网页借报告注入主会话。可观测性上，子代理发出的 API 请求带 x-claude-code-agent-id 和 x-claude-code-parent-agent-id 头，可以把花费归到具体子代理。

回扣开头的三个问题

先自己答，再点开
1. Subagent 多了什么、少了什么？什么时候不值得用？

多了：独立上下文窗口（不带主对话历史）、专属系统提示词、可限定的工具、可并行，结果提炼后交回，主对话不被污染。少了：主对话的历史，要自己重新收集上下文，因而增加延迟。快速审查、单一简单任务、需要来回讨论的工作不值得用。

2. 只读审查员最少写什么？tools 不写会怎样？放哪、同名谁生效？

.claude/agents/secure-reviewer.md 里写 name、description、tools: Read, Grep，正文写角色和输出格式。tools 不写就继承全部工具。来源优先级：托管 > 命令行 --agents > 项目 .claude/agents/ > 用户 ~/.claude/agents/ > 插件；嵌套目录同名时离工作目录最近的赢。和 Skills（个人盖过项目）方向相反。

3. 后台、worktree 隔离、分叉、Agent Teams 各解决什么？

后台（v2.1.198 起默认）：子代理跑的时候主对话不用等。worktree 隔离：子代理在独立的 worktree 和分支上改代码，不碰你的工作区，有改动才交回路径和分支。分叉子代理（/subtask）：继承完整对话去试另一条路，适合需要现有上下文的探索。Agent Teams（实验）：多个独立实例通过共享任务列表和邮箱互相协调、互发消息，适合需要彼此沟通的并行大任务。
