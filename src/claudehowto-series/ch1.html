为什么先看全景

原文 README「问题在哪里」

原教程把自己定位成“教程”而不是“参考手册”。它在 README 里列了三个痛点：官方文档讲功能，不讲组合（知道有 slash command，却不知道怎么和 hooks、memory、subagents 串成真正省时间的工作流）；没有学习路径（先学 MCP 还是 hooks？结果每样都碰一点）；示例太基础（hello world 级的命令帮不了你搭一条能用的审查流水线）。

这对天天用 Claude Code 写代码的人尤其成立：你大概已经会用 /clear、/compact、写过 CLAUDE.md，但未必说得清“一条团队规范应该写进 CLAUDE.md、做成 Skill，还是配成 Hook”。这三者的差别不在写法，而在谁来执行、是否一定执行、占不占上下文。

所以这一篇先建立一个判断框架：每种机制回答三个问题——谁触发它（你、Claude 还是事件）、它住在哪（哪个文件、什么作用域）、它花的是谁的上下文（主对话、按需、还是另开窗口）。后面每一篇都会回到这三个问题。

先看原文给每个功能的一句话定位，点开每一项。

一张分工图：按“谁触发”来分

原文 claude_concepts_guide「Feature Comparison Matrix」

原文在概念总览里用一张矩阵比较各功能的调用方式和持久性。按我的理解，最好用的切法是触发者：有些东西只在你敲 / 时才动（内置命令、手动调用的 Skill）；有些由 Claude 自己判断要不要用（自动触发的 Skill、委派给 Subagent、调用 MCP 工具）；有些每次会话都在（CLAUDE.md、Skill 的描述）；还有一类完全不经过模型判断，由事件确定性地触发（Hooks）。Plugin 则不在这条轴上，它是把以上几种打包分发的“容器”。

这张图最重要的一个结论：只有 Hooks 是确定性的。写进 CLAUDE.md 或 Skill 的规则是给模型看的“指令”，模型大多数时候会照做，但没有保证；Hook 则是 Claude Code 程序本身在某个事件点执行的脚本，可以直接拦下一次工具调用。原文在 Skills 一篇里有一句话很到位：“不要把 Claude 当 linter 用，用确定性的工具。”

点每一块，看它的定位和对应的那一篇。

易混辨析：写进 CLAUDE.md、做成 Skill、配成 Hook

CLAUDE.md：每次会话完整加载，是“永远在场的提醒”，模型通常照做但不保证；内容越长，遵循度越低（原文建议控制在 200 行内）。

Skill：平时只占一行描述，相关时才加载正文，适合多步骤流程和参考资料；同样是给模型的指令，不保证执行。

Hook：Claude Code 在事件点（如工具调用前后）执行的脚本，不经过模型判断，退出码 2 就能拦下操作。凡是“必须发生”或“绝不能发生”的事，用 Hook。

对照总表

原文 README「功能对比」、04-subagents「Comparison with Other Features」

原文分散在几处的对比表，我合成了一张，按“谁触发 / 放在哪 / 占用的上下文 / 最适合”四列排列。路径一列是最常用的那个位置，完整的作用域层级（企业、个人、项目、插件）放到各自的篇里讲。

两点值得先记住。第一，自定义斜杠命令已经并入 Skills：.claude/commands/ 下的文件还能用，但新写的推荐放 .claude/skills/<名字>/SKILL.md，同名时 Skill 优先。第二，MCP 服务器不是 settings.json 里的键，项目级的要写在根目录的 .mcp.json；Hooks 和权限才写在 settings.json 里。

先盖住右边两列，自己想一想再翻开。

易混辨析：Skill 与 Subagent

Skill 加载进当前对话的上下文，是“给我自己加一份说明书”；Subagent 是另开一个独立上下文窗口的助手，只把结果摘要交回来，是“派一个人去干活”。

两者可以叠加：Skill 的 frontmatter 写 context: fork，就会让这个 Skill 在一个分叉出来的子代理里运行；Subagent 的 skills: 字段可以预加载若干 Skill。注意 context: fork 是 Skill 的字段，写在 Subagent 定义里会被静默忽略。

易混辨析：MCP 与 Memory

原文的说法很简洁：Memory 存的是不怎么变的东西（偏好、规范、项目背景），MCP 取的是实时在变的东西（当前的 issue、数据库查询结果、线上服务状态）。把今天的 PR 列表抄进 CLAUDE.md，明天就过期了。

上下文账本：启动时到底装了什么

原文 02-memory、03-skills「Progressive Disclosure」、05-mcp「Tool Search」

分工的另一面是成本。每一种机制都会花上下文，但花法不同。原文给出的几条事实可以拼成一本账：CLAUDE.md 每次会话完整加载（用 @ 导入也一样，导入只是整理，不省上下文）；每个 Skill 启动时只占约 100 tokens 的描述，被触发后才加载正文（原文给的量级是 5k 以内），附带的脚本和参考文件要用时才读；MCP 工具默认走 Tool Search，定义被延后，用到才发现；Subagent 另开窗口，主对话只收到结果；Hook 在模型之外运行，除非它主动往对话里回写内容。

这本账解释了原文反复强调的几条建议：CLAUDE.md 要短（每一行都在和当前任务争注意力）；多步骤流程搬进 Skill；Skill 多了以后描述也会被截断（总预算约为上下文窗口的 1%）；长篇的调研交给 Subagent，避免把主对话塞满。

场景判定：这件事该交给谁

原文 claude_concepts_guide「Selection Decision Tree」及各模块“何时用”

原文概念总览里有一棵选型树：重复性的小任务，手动触发就做成斜杠命令、希望自动触发就做成 Skill；要外部数据，实时的用 MCP、跨会话不变的用 Memory；复杂项目有多个角色，就用 Subagents；要完整自动化，组合 Skills、Subagents、MCP。再加上原文其他模块的判断：要确定性执行用 Hooks，要分发给团队用 Plugins。

判断时最容易混的是三对：Skill 与 CLAUDE.md（流程放 Skill，事实和约定放 CLAUDE.md）、Skill 与 Hook（建议放 Skill，强制放 Hook）、Skill 与 Subagent（要不要另开上下文）。

十个场景，选你认为最合适的那一个机制。

学习顺序与自测定级

原文 LEARNING-ROADMAP.md

原教程的目录编号（01 到 10）不是推荐的学习顺序。它在学习路线里按三条原则重排：依赖（基础概念先学）、复杂度（简单的先学）、使用频率（常用的先学）。于是顺序变成：Slash Commands → Memory → Checkpoints → CLI 基础 → Skills → Hooks → MCP → Subagents → 高级功能 → Plugins，全程约 11 到 13 小时。Checkpoints 和 CLI 基础排得靠前，是因为它们让你“敢试”：有回退，才放心让 Claude 大改。

原文还给了一份 8 题自测：勾得越多，起点越靠后。0 到 2 项从 Level 1 开始，3 到 5 项从 Level 2（Skills + Hooks）开始，6 到 8 项直接从 Level 3（高级功能）开始；拿不准就往低一级走。本系列的篇目顺序按功能分组排，和原文路线不完全一致，下面的结果会同时告诉你该先读哪几篇。

回扣开头的三个问题

先自己答，再点开
1. 七种机制分别由谁触发？哪些每次加载、哪些按需、哪些不进主上下文？

你触发：内置斜杠命令、手动调用的 Skill（/名字）。Claude 自己判断：自动触发的 Skill、委派 Subagent、调用 MCP 工具。每次会话都加载：CLAUDE.md（完整）、Skill 描述（每个约 100 tokens）。事件触发：Hooks，由 Claude Code 程序执行，不经过模型。打包分发：Plugins。按需加载的是 Skill 正文和资源、MCP 工具定义（默认 Tool Search）；Subagent 另开上下文窗口，Hook 在模型之外运行，都不占主对话（除非回写内容）。

2. “提交前必须跑 lint”写进 CLAUDE.md、做成 Skill、配成 Hook 有何区别？

CLAUDE.md 和 Skill 都是给模型的指令：前者每次都在，后者相关时才加载，模型通常会照做但没有保证。Hook 是 Claude Code 在事件点执行的脚本，不经模型判断，可以用退出码 2 拦下操作，是唯一确定性的机制。“必须发生”的事用 Hook，原文的说法是不要把 Claude 当 linter 用。

3. 原文推荐的学习顺序？为什么 Checkpoints、CLI 靠前？

Slash Commands → Memory → Checkpoints → CLI 基础 → Skills → Hooks → MCP → Subagents → 高级功能 → Plugins，按依赖、复杂度、使用频率排序，全程约 11–13 小时。Checkpoints 让你敢于试错（随时回退），CLI 基础（交互模式与 -p、管道）是后面自动化的地基，所以放在 Level 1。
