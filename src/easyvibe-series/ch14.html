上下文这么长了，为什么还要 RAG

原教程 RAG 入门 第 1–2 节

RAG（检索增强生成）的思路是：生成回答前，先从外部知识库检索出与问题相关的信息，连同问题一起交给模型，让它基于真实资料作答。一个自然的疑问是：模型上下文窗口越来越大，把资料全塞进去不就行了？原教程的回答是：“能给出一个回答”和“在真实业务里持续、稳定、可控地给出正确答案”是两件事，只靠参数记忆或长上下文，至少有三类问题。

成本与效率：推理成本和上下文长度强相关，8K 和 200K token 的价格与延迟不在一个量级；绝大多数问题只需要极少量相关信息，全量塞入是浪费，还拖慢吞吐。注意力与聚焦：模型能“覆盖”超长上下文，却不能同等质量地利用每一段，早期信息容易被忽略，无关、重复甚至冲突的内容会把回答带偏。知识更新与可控性：知识写在参数里，一变就要重训或微调；写在提示词里要人工维护还容易出错；而且很难说清回答依据了哪条信息，合规审计做不了。

RAG 的做法正好对应：只检索必要的知识交给模型；知识独立存在外部库里，更新只需改库；回答附带引用来源，可追溯。原教程总结它为企业解决了五个问题：时效性、专业性、幻觉、可解释与可审计、算力成本。流程分两段：索引阶段把文档切成语义片段、用 Embedding 模型变成向量写入索引；检索生成阶段把问题也变成向量，找出最相近的片段，和问题一起组成提示词交给大模型。

一个“苹果”知识库：检索、阈值与拒答

原教程 RAG 入门 第 3 节

原教程用一个只有三段的知识库把机制拆开：A 是苹果公司 1976 年创立，B 是水果苹果富含维生素 C，C 是苹果公司 2007 年推出 iPhone。每段被 Embedding 模型转换成高维向量（常见 768、1024、1536 维），存进向量数据库（Pinecone、Weaviate、FAISS 等）。向量的每个维度大致对应某种语义特征，所以“公司创立”和“iPhone 发布”的向量彼此接近，和“水果营养”离得远。

提问时，问题也被转成向量，和每个片段计算余弦相似度，取 Top-K。关键在于第三个问题“今天天气怎么样”：它和三段都不相关，但 Top-K 仍然会返回分数最高的两段（0.18 和 0.10）。所以实际系统要配合最低相似度阈值，低于阈值就返回空召回。另一道防线在系统提示词：要求模型严格依据参考信息回答，参考信息里没有答案就明确说“根据现有资料无法回答”，不要编造，并注明依据。原教程的总结：系统指令定角色和规则，检索证据提供可信素材，用户问题明确任务，这种结构化输入正是 RAG 约束幻觉的关键。

选一个问题，调阈值，看哪些片段被送进模型，模型最后会怎么回答（相似度为原教程的示意值）。

你是一个专业的问答助手。请严格根据用户提供的“参考信息”来回答问题。

如果参考信息中不包含问题答案，请明确告知用户“根据现有资料无法回答该问题”，切勿自行编造信息。

三代 RAG

原教程 RAG 入门 第 4 节

RAG 的雏形可以追溯到 2017 年的 DrQA，2020 年 DPR 用神经网络做语义检索替代 TF-IDF、BM25 这类词频方法，2021 年前后系统化。原教程把演进分成三代。Naive RAG 三步走：固定长度切块、向量化入库；问题向量化后 Top-K 检索；把检索结果和问题简单拼接交给模型。它低门槛地证明了“先查再答”有效，但切块粗糙（把一段话拦腰截断或把多个主题混在一块）、检索信号单一（只有向量相似度，不看关键词、时间、来源可信度、权限）、结果不经治理（噪音、重复、矛盾的片段原样塞进上下文）。

Advanced RAG 在检索前后做精细化。检索前：索引端改为按章节段落句子的语义分块、分层和多粒度索引，给每块加来源、时间、作者、类型等元数据；查询端对问题做改写、扩展、拆分。检索后：用 Rerank 模型或 LLM 重排，筛选去重压缩，必要时微调让模型更倾向依据证据作答并给出引用。Modular RAG 不再是固定流水线，而是可插拔的模块按需编排：查询理解与路由（错误日志走代码库、监管新规走搜索或法规库）、多源检索与融合（向量库、全文检索、关系数据库、知识图谱、搜索引擎）、记忆与个性化、任务适配与治理（同一批证据给产品经理出 PRD、给法务出审查意见，并强制引用）。它还可以多轮往返检索和生成，或者让模型自己判断什么时候需要检索。

从 Demo 到企业级：三个模块和三类模型

原教程 RAG 入门 第 5.1–5.2 节

原教程强调，企业实际数据质量参差、格式混乱，要在预处理和导入上投入更多精力。完整系统分三个模块：版面分析与知识采集（PDF、Word、Excel、PPT、HTML、扫描图片、录音，按格式解析：区分标题正文表格页眉页脚、恢复阅读顺序，图片做 OCR、语音做 ASR，保留文档名、章节、页码等元信息）；知识库构建（合理切分并保留来源元数据、Embedding、建向量索引，如 Faiss、Milvus）；在线问答（问题向量化粗排出 Top N，Rerank 精排出 Top K，配合系统提示词拼接后生成，附引用）。

三类模型的选型要点：Embedding 参考 MTEB 榜单（8 大类任务、56 个数据集），关注两个参数：维度（越高语义刻画越细、区分度越强，适合医疗法律等精准检索；越低越省存储、越快，适合千万级高并发）和上下文长度（超出部分被截断，短问答 512–1024 就够，论文报告要 2048 以上）。原教程的实用建议是：选大模型厂商自带的或云平台部署的 Embedding 大概率不会错，中文可看 BGE、Qwen 系列，混合检索可看 bge-m3。Rerank 可参考专门的重排榜单，要同时看排序质量和延迟，只追精度不顾速度会损害体验。LLM 按任务复杂度和成本选。

框架上，低代码平台（Dify、Coze、n8n、擅长复杂版面解析的 RAGFlow、中文友好的 FastGPT）适合快速上线；代码框架（专为 RAG 设计、数据连接器丰富的 LlamaIndex，通用但学习曲线陡的 LangChain）适合深度定制。也可以混合：先用低代码验证，再用代码框架做生产级。

效果评测：检索准不准，生成忠不忠

原教程 RAG 入门 第 5.3 节

原教程说，企业落地 RAG 最大的挑战往往不是构建而是调优：检索和生成都是非确定性的，传统软件测试不适用，必须建立可量化的评测。入门做法是 LLM-as-a-Judge：让一个模型从知识库采样出“问题 + 参考答案”合成评测集，让 RAG 系统作答，再让另一个模型对照参考答案判分，形成“评测 → 优化 → 再评测”的循环。

指标分两组。检索：Recall@K（前 K 条里找回了多少比例的相关文档，覆盖面）、Precision@K（前 K 条里有多少是相关的，准确度）、F1；排序质量看 MRR（第一个相关文档排名的倒数，适合只要一个正确答案的问答）、NDCG@K（考虑相关程度分级和位置衰减，最全面）、MAP。原教程推荐工程上用 Recall@K + MRR@K 组合：如果 Recall@10 有 80% 而 MRR@10 只有 0.3，说明相关文档找到了但都埋在后面，该优化重排了。生成：EM 精确匹配（太严，“2020年1月1日”和“2020-01-01”算不匹配）、ROUGE / BLEU / METEOR（词汇重叠，只看表面）、BertScore 或向量相似度（语义层面）、以及最关键的 Faithfulness / 幻觉率：让模型逐句核查答案能否在检索文档里找到依据。评测框架有 RAGAS、ARES 等。

下面是一次检索返回的前 8 条结果，知识库里一共有 3 篇相关文档。点击标出哪些是相关的，调 K，看指标怎么变。

易混辨析：Recall@K vs Precision@K vs MRR

Recall@K 的分母是知识库里所有相关文档数：3 篇相关、前 K 条找回 2 篇，就是 67%，问的是“漏了多少”。Precision@K 的分母是 K：前 5 条里 2 篇相关，就是 40%，问的是“混进了多少噪音”。MRR 只看第一篇相关文档排第几：排第 3 就是 1/3，问的是“用户要往下翻多久”。K 调大，Recall 只增不减，Precision 往往下降。

从竞赛和开源教程里学什么

原教程 RAG 入门 第 6–7 节

原教程建议：遇到具体问题时，按关键词（PDF 解析、多模态检索、低延迟）去找相关竞赛，读获奖方案。它挑了几个。语义缓存（Hugging Face 教程）：生产环境里大量重复问题（“如何退款”）每次都检索加生成，又慢又贵；在用户查询和向量库之间加一层缓存，相似问题直接命中。一个细节值得记：它缓存的是检索结果，而不是最终回答，否则“用简单语言解释”这类个性化要求会失效。多格式解析（Unstructured）：PDF、PPT、EPUB、HTML 统一解析成带元素类型（正文、标题、表格）的结构，按标题分块。

Enterprise RAG Challenge 冠军方案：2.5 小时内解析 100 份最长上千页的年报，回答 100 个必须给出页码引用的精确问题。几个做法很有代表性：用擅长复杂表格的 Docling 解析并修补表格结构；300 token 分块、50 重叠；每家公司单独建一个向量库，避免查 A 公司 CEO 时检索到 B 公司；检索 Top 30 块后回溯到父页面并去重，再用小模型对页面重排，向量分数与重排分数按 0.3 : 0.7 混合；按答案类型（数字、布尔、名称）用不同提示词，数字题走识别指标、定位表格、提取、核对单位、交叉验证五步；多公司比较题拆成单公司子查询。原教程提到它即使用 8B 小模型也能超过八成参赛者。AIOps 竞赛的经验是给每块加知识库路径等元信息，召回率提升了 2%；图片先 OCR 再用多模态模型生成描述。

未来方向上，原教程列了 Graph RAG（用关系网络做深度检索）、多模态 RAG、Late Chunking（先对长文档整体编码再切块，保留上下文）和 Agent 时代的 RAG（检索变成 Agent 可以按需调用的工具）。

用 LangGraph 做客服 Agent：补问、查询、升级

原教程 企业级客服 Agent 实战

原教程用一个在线教育平台的客服举例，开篇一句话：企业级客服 Agent 的目标不是“多回答一点”，而是“在该自动时自动，在不确定时补问，在高风险时转人工”。设计要从业务出发：哪些问题最高频、哪些规则明确最适合自动化、哪些风险太高不能自动决定、哪些必须接业务系统不能只靠知识库。用户晚上十点说“我明明付了钱，为什么课程还是打不开”，成熟的系统不会立刻编答案，而是先判断这是支付、权限、退款还是账号问题，订单号和账号是否齐全，该查知识库还是查业务系统，是普通请求还是高风险投诉。

LangGraph 适合客服，不是因为它更会聊天，而是因为客服本身就是状态流转问题。每个请求最终落到四种去向之一：补信息、查知识库、查业务系统、转人工。有两类信息要分开：知识规则（FAQ、SOP、退款规则）查知识库，实时状态（订单、权限、支付）查业务系统。用户明确要人工，或出现重复扣费、投诉、法务、隐私、情绪激烈，直接标记高风险转人工，并附带上下文，人工不必重问一遍。上线还要有审计追踪（事后能复盘为什么这样路由）和覆盖常见、边界、高风险问题的离线评测集。

用 LlamaIndex 做企业知识库：持续治理的循环

原教程 企业级知识库实战

如果说 LangGraph 解决“Agent 应该怎么跑”，LlamaIndex 解决的是“企业知识应该怎样被接入、组织、检索和回答”。原教程的一句话：企业级知识库不是“把 PDF 塞给模型”，而是“把分散知识变成一个可维护、可检索、可追溯的入口”。场景是给客服、销售、实施团队用的内部产品知识助手，问题像“企业版能不能配置多个审批流”“为什么我记得以前写的是 100 人上限，现在好像不是了”。

真实企业知识有五个特点：来源多（不只 PDF）、更新频繁（旧答案很快过时）、可信度不同、有些在数据库或配置表里、有些要结合实时系统。所以要解决的不是“有没有文档”，而是：去哪里找、哪份最可信、怎么避免旧版本干扰、怎么稳定地组织成回答。原教程的结构是一个循环：知识来源 → 接入与解析 → 按知识域拆分索引 → 检索与重排 → 证据化回答 → 业务同学使用 → 反馈与治理 → 回到接入。它还点出一个容易忽视的事实：用户怎么问，和企业文档怎么写，往往不是同一种语言，所以第一步是做问题理解和知识路由，判断问题属于产品功能、套餐定价、FAQ、内部 SOP 还是版本更新，新旧版本冲突时优先最新版，超出能力就说明需要查系统或人工确认。

这条路由提示词可以直接改用。

你是企业知识库系统里的“问题理解与知识路由助手”。
你的任务：
1. 判断用户问题属于哪个知识域：产品功能、套餐定价、FAQ、内部 SOP、版本更新。

3. 如果问题涉及旧版本与新版本冲突，优先提醒系统关注最新版本文档。
4. 如果问题超出知识库能力，不要编造，明确说明需要查业务系统或人工确认。

回扣开头的三个问题

先自己答，再点开
1. 长上下文时代为什么还要 RAG？

三类问题：成本与效率（上下文越长成本和延迟越高，大部分内容与问题无关是浪费）；注意力与聚焦（长上下文中早期信息被忽略，无关和冲突内容把回答带偏）；知识更新与可控性（知识在参数里要重训，在提示词里难维护，而且说不清依据哪条信息）。RAG 只检索必要知识、知识存在外部库便于更新、回答可附引用来源，解决时效、专业、幻觉、可审计和成本问题。

2. 三代 RAG 各改进了什么？四种查询改写？

Naive RAG：固定切块、向量 Top-K、简单拼接，验证了先查再答。Advanced RAG：检索前做语义分块、分层索引、元数据和查询改写，检索后做 Rerank、去重压缩和引用。Modular RAG：可插拔模块按需编排，查询路由、多源检索融合、记忆个性化、任务适配与治理，可多轮往返检索。四种改写：Query Rewrite（口语化问题标准化）、Multi-Query（多个角度的查询）、Sub-Query（复合问题拆成子问题）、Step-back（先问更宏观的上位问题再回推）。

3. 检索评测看什么？Recall@10 高 MRR 低说明什么？

覆盖面看 Recall@K，噪音看 Precision@K，排序看 MRR、NDCG@K、MAP，工程上常用 Recall@K + MRR@K 组合；生成侧看 EM、ROUGE 等文本相似度、BertScore，以及最关键的 Faithfulness / 幻觉率，也可以用 LLM-as-a-Judge 多维评分。Recall@10 高而 MRR 低说明相关文档找到了但排在后面，应优化重排序（交叉编码器 Rerank、调整多路召回权重）。
