CLI 编码 Agent：只活在终端里的那个 Agent

原教程 二阶段 CLI AI 编程工具

CLI（命令行界面）是用纯文本命令操作软件，不依赖图形界面。工业界大量交互本来就走 CLI（连服务器集群只有终端）。原教程打了个比方：CLI 编码 Agent 可以看作“特殊的 z.ai”，一个对话入口就能替你执行所有操作；也可以看作把 AI IDE 侧边栏那块 Agent 单独拿出来。没用过命令行也不必怕，照搬前面让 Trae 帮忙的思路，让它替你进目录、搜文件、跑开源项目。

为什么优先用它？原教程引用的对比是：Claude Code 在自动执行任务、多文件操作、Git 一体化、上下文长度、自动化调试上更强；Cursor 这类 IDE 在编辑器集成、实时代码补全、上手难度上更好。CLI 工具通常由模型厂商直接开发（Claude Code 本来就是 Anthropic 内部研发团队用的工具），能支持更长时间的连续工作、更长的上下文、更快的响应，并能接入更多自定义模型。

原教程推荐三款并建议都试一试：Claude Code（可以接官方，也可以通过 GLM 等国内模型的兼容接口转发，降低成本）、Codex（OpenAI 出品，可看作“OpenAI 版的 Claude Code”，可用官方订阅或第三方网关）、OpenCode（开源，可随意切换模型、有免费模型，便于控成本）。模型更新很快，原教程的原则是选当下“效果 / 成本”最好的，某个工具多次试下来效果一般就直接换。

先翻开对照表；再判断几个场景更适合哪类工具。

十个高频技巧

原教程 三阶段 Claude Code 快速上手 · 核心技巧

原教程总结了十个来自实际开发的技巧。回退：按两次 Esc 回到上一轮对话状态，说错话、AI 跑偏时“时光倒流”；原教程特别提醒它回退的是对话，文件改动要靠 Git 恢复，所以大改之前先 commit 或 stash。@ 引用：@src/utils.ts 精准指定上下文，可以引用多个文件、整个目录甚至行号范围，比让它自己去找更准、更省 token。! 执行：!npm test 直接在对话里跑命令，失败了接着说“分析原因并修复”。先规划后编码：超过 30 分钟的任务先让它分析需求、评估现状、列分阶段计划，你确认后再逐阶段执行。

/init 扫描项目结构、配置文件和代码风格，生成一份 CLAUDE.md，这是 Claude Code 的“项目记忆”，每次启动自动读取。/compact 把长对话压缩成摘要（保留已做的决策、已生成的代码、已确认的需求），在对话变长、它开始“遗忘”或要切换子任务时用；/context 查看上下文用了多少。提交流程：先 /diff 或让它解读 git diff，按 Conventional Commits 生成提交信息，你确认后再执行 git commit；想要一条命令提交可以装官方插件市场里的 commit-commands。Shift+Tab 切换自动接受模式，熟悉后让修改直接生效（务必配合 Git）。Ctrl+C 是紧急制动，长任务跑偏时立即中断。

原教程在这一章里也提醒了版本变化：一些曾经内置的命令已经移除或标记为弃用，要以官方命令文档为准。这里再补一条读后核对：在较新的 Claude Code 版本里，双击 Esc 打开的回退菜单也可以把代码恢复到某个检查点，而“先规划”对应的是用 Shift+Tab 切换到的 Plan 模式。快捷键和命令以你本机 /help 为准。

建立项目知识库：三份文件

原教程 AI 辅助开发工作流 第 4 节；Claude Code 快速上手 技巧 5

每次开新会话都要重新解释“我们用什么框架、代码怎么写、数据库表长什么样”，既费 token 又容易漏。原教程建议给项目建一个知识库，由三份文件组成。项目说明文件（Claude Code 里就是 CLAUDE.md，可以先用 /init 生成再手改）：项目概述、技术栈、目录结构、代码规范、开发流程、常用命令、常见任务、注意事项、数据库表结构。常见问题记录：开发环境问题（npm install 失败、数据库连不上）和功能问题（刷新就退出登录、图片上传失败），每条写现象、原因、解决办法。技术决策记录（ADR）：每个重要决策一份，按“状态、背景、决策、理由、后果”五段写，比如“ADR-001：选择 PostgreSQL 作为数据库”。

它们的价值是让 AI 和新同事都不用重新摸索：AI 每次启动就知道规范和背景，遇到老问题直接查记录，想推翻一个技术选型时能看到当初为什么这样选、代价是什么。原教程的建议是新项目初始化后立即生成项目说明，之后随项目演进持续更新。

这些信息该记进哪份文件？

# ADR-001: 选择 PostgreSQL 作为数据库
## 状态
已采纳（2026-10-24）
## 背景
需要存储用户、订单和支付记录，订单与支付之间要求强一致。
## 决策
使用 PostgreSQL（通过 Supabase 托管）。
## 理由
支持事务和外键；Supabase 提供 Auth 与 RLS；团队熟悉 SQL。
## 后果
复杂统计查询需要注意索引；若未来日志量极大，日志单独放到其他存储。

AI 擅长什么，不擅长什么

原教程 AI 辅助开发工作流 第 1、5 节

原教程把 AI 比作“很聪明但需要明确指令的助手”。它擅长有明确规则、可以自动化的工作：根据描述快速生成代码框架、几秒钟读完几千行代码找到目标位置、发现明显的语法错误和常见安全漏洞、批量重命名、格式化、写文档注释。它不擅长的是：不了解你的业务逻辑（除非你详细告诉它订单流程怎么走）、做不了技术选型和架构这种需要权衡的决策、不知道团队的特殊规范（“所有 API 都要加日志”）。最重要的一条：AI 生成的代码不能直接用，必须审查和测试，它会写出看起来对但有问题的代码，也会漏边界情况。

于是分工很清楚：你负责想清楚要做什么、做决策、把关质量；AI 负责执行具体编码、查找信息、发现明显问题。就像带一个执行速度极快、但判断力不如人的初级开发者。原教程给的三条效率技巧也由此而来：描述要清晰具体；一次只做一件事；及时验证结果，每一步完成都跑一下，而不是攒一堆再看。

四类项目，四种策略

原教程 AI 辅助开发工作流 第 2 节

全新项目没有历史包袱：先让 AI 推荐技术栈、设计目录结构、规划数据库表，再搭基础框架，然后按优先级逐个实现功能。关键是一开始就建立代码规范，让 AI 按规范生成；每完成一个模块就测试，及时更新文档。成熟项目代码量大、有历史规范：先让 AI 分析整体结构、找到相关代码，再找项目里类似功能的实现作为参考（要加优惠券，先看满减和折扣是怎么做的），让它模仿现有风格和目录结构；先理解再动手，避免破坏架构。

快速原型追求速度：直接描述需求、快速迭代（“加个搜索”“改成深色主题”），不必在意代码质量，验证成功后再重构。维护项目以修 Bug 为主：先定位（现象 + 报错 + 位置），再分析根因（数据从哪来、什么情况下为空），最后修复并加防御性代码和友好提示；改动要谨慎，修完充分测试，并把问题和解法记进常见问题文件。

四种任务：每一步谁来做

原教程 AI 辅助开发工作流 第 3 节

原教程把四种常见任务都拆成了五步左右，并明确标出每一步是你自己完成、让 AI 帮你、还是和 AI 一起。开发新功能：理解需求（输入输出、边界、性能安全要求）由你完成；了解现有代码交给 AI；实现计划和 AI 一起定；实现由 AI 生成、你审查；测试验证（主流程、边界、权限，比如不能删别人的评论）由你完成，也可以让 AI 写自动化测试。

修 Bug：收集信息（报错、复现步骤、何时出现、影响范围）你来；定位交给 AI；分析根因一起；修复 AI 生成你审查；验证修复并思考别处是否有同类问题你来。原教程的对话示例很典型：刷新就退出登录，AI 发现 token 存在 sessionStorage 里，刷新被清空。重构：重构目标和可接受风险你定；方案一起定；先让 AI 写测试当安全网；再让 AI 逐步重构、你逐步验证；最后跑全部测试。代码审查：让 AI 总结 PR 改动、检查安全（SQL 注入、XSS）、性能（N+1 查询）、明显 Bug 和规范；业务逻辑、边界、更好的实现和反馈由你完成。

以“开发新功能”为例，把五个步骤分给你、AI 或一起。

开发新功能：每一步谁来做（据原教程 3.1 节）

重构的正确顺序（拿掉一步看看后果）

总结一下这次 PR 做了什么改动，主要修改了哪些文件。
然后检查这次改动：
1. 有没有安全问题（SQL 注入、XSS 等）
2. 有没有性能问题（N+1 查询、内存泄漏等）
3. 有没有明显的 Bug
4. 代码风格是否符合项目规范（参照 CLAUDE.md）

CLI Agent 的更多用法

原教程 二阶段 CLI AI 编程工具 · 更多用法

CLI Agent 不只写代码。原教程列了几种用法。具体化需求：大模型需要把抽象需求具体化（“我很饿”→“想吃一个红豆面包配一杯豆浆”），这一步很花精力，可以让 AI 先把一句话想法扩写成完整 PRD（产品介绍、目标用户、用户故事、功能拆解、MVP），审过再开发，比直接开写更少偏差。管理文件夹：整理下载目录、批量重命名。开发新项目和部署开源项目（比如本地把 Dify 跑起来，遇到报错让它自己查）。讲解代码与写文档：读一个陌生仓库，生成架构说明。

原教程还演示了项目约定的写法：在项目说明里列出“项目约定、开发流程、禁止事项”，例如禁止事项写“不要修改 migrations 目录下已有的文件”“不要引入新的依赖而不说明”。这和第 5 篇“第一版不做什么”是同一个思路：告诉 AI 不做什么，往往比告诉它做什么更能防止跑偏。

两条可以直接用的提示词。

Based on my needs, please elaborate and provide a more detailed Product Requirement Document for reference. My idea is: 【一句话想法】
请包含：产品定位、目标用户与痛点、用户故事、MVP 功能拆解（含不做的部分）、关键页面与交互、数据结构。先不要写代码。
## 项目约定
- 前端 React + Vite，组件放 src/components，一个组件一个文件
- 所有接口返回 { code, message, data }
## 开发流程
- 改动前先读相关文件；每完成一步运行 npm test
- 提交信息用 Conventional Commits
## 禁止事项
- 不要修改 supabase/migrations 下已有的文件，只能新增
- 不要在未说明的情况下引入新依赖
- 不要把任何 Key 写进代码，统一读环境变量

回扣开头的三个问题

先自己答，再点开
1. CLI 编码 Agent 强在哪、弱在哪？

强在自动执行任务、多文件操作、Git 一体化、上下文更长、可长时间连续工作、能接入更多自定义模型，多由模型厂商直接开发、编码更稳定。弱在没有图形化的编辑器集成和实时代码补全，学习成本略高。原教程建议 Claude Code、Codex、OpenCode 都试，按效果 / 成本选。

2. 项目知识库三份文件各存什么？为什么要建？

项目说明（CLAUDE.md）存概述、技术栈、目录结构、代码规范、开发流程、常用命令、注意事项、表结构；常见问题记录存环境和功能问题的现象、原因、解决办法；ADR 按状态、背景、决策、理由、后果记录重要技术决策。这样 AI 每次启动就知道背景和规范，老问题直接查，推翻决策前能看到当初的理由和代价，新同事也能快速上手。

3. 新功能、修 Bug、重构里哪些必须你做？

新功能：理解需求和最终测试验证由你完成，了解现有代码交给 AI，计划一起定，实现由 AI 生成你审查。修 Bug：收集信息和验证修复由你完成，定位交给 AI，根因一起分析。重构：目标和可接受风险由你定，先让 AI 写测试当安全网，再逐步重构逐步验证。核心是你负责想清楚、做决策、把关质量，AI 负责执行。
