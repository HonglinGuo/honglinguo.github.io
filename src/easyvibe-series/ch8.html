为什么需要数据库

原教程 第 1.1–1.2 节

数据是信息的载体：联系方式、订单、游戏等级都是。程序里最简单的数据是变量，但变量活在内存里，用户一关浏览器就全丢了，也没法让不同用户共享商品库存、订单记录。数据库就是专门对数据做规范化组织、安全存储、系统管理和高效查询的程序，可以部署在本地，也可以放在云端按需扩容。

原教程归纳了它解决的五个核心问题：持久化存储（写到硬盘，应用关了数据还在）；便捷的查询与分析（用 SQL 这类语言从海量数据里筛选聚合）；高性能与高并发（靠索引、缓存、连接池、分布式架构毫秒级响应成千上万并发）；完整性与一致性（用约束保证年龄必须是数字、订单号必须唯一）；安全性（身份验证、访问控制、加密、备份恢复）。

下面这些问题，分别靠数据库的哪项能力解决？

关系型与非关系型：规范化 vs 聚合

原教程 第 1.3 节

原教程用两个比喻区分两大类。关系型数据库（SQL）像结构严谨的 Excel：每张表事先定义好结构（Schema，比如姓名必须是文字、年龄必须是数字），表与表通过关联字段连起来。好处是数据精确可靠，适合银行转账、库存、订单、账务这类不能出错、需要事务的场景；缺点是改结构麻烦，超大规模时扩展受限。非关系型数据库（NoSQL）像灵活的文件夹：可以存格式各异的文档、键值对，不需要提前定结构，扩展更方便，适合社交内容、日志、物联网写入、推荐特征这类高并发、结构多变的场景，代价是关联查询能力和一致性保障弱一些。

同一个博客平台（用户、文章、评论、标签）在两类数据库里存法截然不同。关系型把它们拆成五张职责单一的表，再用一张 post_tags 表表达“一篇文章多个标签、一个标签多篇文章”的多对多关系，查一篇文章的完整信息要 JOIN 多张表；这叫规范化，换来一致性和最小冗余。文档型则把作者名、评论、标签都嵌进一篇文章的文档里，一次读取拿到全部；代价是冗余：作者改了用户名，要遍历所有包含他名字的文档逐一更新，失败一部分就会出现前后不一致。原教程的结论是看读写比例：读多写少（博客、资讯、商品详情）用少量冗余换极致读取是值得的，写多读少就要慎重。

原教程还说了句很实在的话：初期不必花大量时间纠结选哪种数据库，现在的云数据库已经很成熟，问云厂商要选型建议、或按场景对照厂商的选型表即可。

主键、外键，和 JOIN 的行数乘法

原教程 第 1.3、2.2–2.3 节

关系型数据库有两个核心概念。主键（Primary Key）是每一行的唯一身份证，比如班级表里的班级编号。外键（Foreign Key）是当前表（子表）里的一个字段，它的值引用另一张表（父表）的主键，比如学生表里的“所属班级编号”引用班级表的“班级编号”，于是知道谁在哪个班。查询时用 JOIN 沿着外键把多张表拼起来。

原教程推荐的建表方式是：让大模型生成适配 Supabase 的 SQL，粘贴到 SQL Editor 执行；也可以在 Table Editor 里可视化建表并添加外键。SQL 的基本动作就五个：CREATE 建表结构、INSERT 插入数据、SELECT 查询、UPDATE 修改、DELETE 删除。

原教程给了一条跨五张表查《初识 SQL》完整信息的 SQL。这里补一个原文没展开、但实际很容易踩的细节：一对多的 JOIN 会让行数相乘。这篇文章有 2 条评论、2 个标签，拼完不是 1 行，而是 2 × 2 = 4 行，每条评论都和每个标签配了一次对。所以前端拿到结果要去重，或者分开查评论和标签。

UPDATE menu_items SET price = 0 WHERE id = 3 只改一行；漏掉 WHERE id = 3，整张表的价格都变成 0。DELETE 同理。AI 生成的 SQL 也要先看一眼有没有 WHERE、条件对不对，再执行。原教程的建表脚本出错时，建议先在 Table Editor 里删掉已建的表，或者干脆删掉这个 Supabase 项目重建，说明练习阶段用一个可以随便重来的项目最省心。

BaaS：把常见后端打包成服务

原教程 第 2、5.1 节

选好数据库并不能让应用马上上线。真实项目还要用户注册登录、权限校验、文件上传存储、对外 API、定时任务、实时通知，过去要自己搭服务器、设计 API、处理安全和运维。BaaS（Backend as a Service，后端即服务）把这些常见后端能力打包成云平台，开发者通过 SDK 或 API 直接调用。Supabase 是新一代代表：以 PostgreSQL 为核心，集成了认证、存储、实时、边缘函数、向量等能力，所有用户数据自动同步到 auth.users 表。

为什么选它？原教程的理由是：初创团队既想掌控后端又必须快速上线，自建一整套数据库、实时同步、认证、API、存储、监控要几个月；Supabase 开箱即用，让人把资源集中在核心功能上。和闭源的 Firebase 相比，Supabase 完全开源、支持私有化部署，规避供应商锁定。原教程的选型建议：个人项目或极小范围测试，PocketBase 这类超轻量方案就够；要对接复杂企业身份系统、满足上市公司合规审计，看 WorkOS 这类企业级方案；验证 MVP、承载早期用户，Supabase 足够，还能集成 Stripe、Resend、Cloudflare。

行级安全 RLS：每个人只能看到自己的行

原教程 第 2.4、3.3、5.4.1 节

多用户应用的核心问题是数据隔离：用户 A 只能看自己的订单，看不到 B 的。RLS（Row Level Security，行级安全）允许你给表定义策略，根据请求者的身份精确控制他能访问、修改哪些行。表一旦启用 RLS，所有 SELECT、INSERT、UPDATE、DELETE 都要至少通过一条策略才能执行；没有任何策略允许，就直接拒绝，从数据库底层阻断越权访问。

Supabase 让它很好用：函数 auth.uid() 返回当前发起请求的已登录用户 ID。于是“订单的 user_id 等于当前用户 ID 才能查到”就是一条策略。原教程建议在建表脚本里就把 RLS 一起写好，而不是事后手动配。登录后 Supabase 会建立会话，之后所有请求自动携带身份，RLS 据此把每个人的数据隔开。Storage 的权限同样用 RLS 管：策略写在 storage.objects 上，比如只允许用户上传到以自己 user_id 命名的文件夹。

下面的 SQL 是这类策略的典型写法（据原教程描述补写的示意）：

alter table orders enable row level security;
create policy "只能看自己的订单" on orders
  for select using (auth.uid() = user_id);

切换当前请求者，再开关 RLS，看能查到哪些行。

易混辨析：anon key 能放前端，service_role key 绝不能（补充说明）

第 6 篇说过第三方 API Key 不能进前端，那原教程示例里前端直接带着 Supabase 的 anon_key 请求，岂不矛盾？不矛盾。这一点原文没有展开，这里补充：Supabase 的 anon（公开）key 本来就是设计给浏览器用的，它只代表“一个匿名或已登录的普通用户”，真正的安全边界是 RLS。所以反过来说：只要前端直连 Supabase，每张表都必须开 RLS 并写好策略，否则任何人拿着公开 key 就能读写整张表。另一把 service_role key 会绕过 RLS，只能放在服务端或边缘函数里。

把任意应用接入 Supabase 的四步

原教程 第 3–4 节

原教程用汉堡店的两个示例项目（菜单增删改查、带认证的用户商店）练手，然后总结出一套可以套在任何应用上的标准流程。第一步：需求梳理，告诉 AI 应用现在做什么、要新增什么数据能力，让它列出涉及哪些数据操作、需要哪些表和字段；补上约束（时间戳用 timestamptz、金额用整数存分、待办只有自己可见）；审核它的结果，漏了就补（“你漏了截止时间”）。第二步：生成 init.sql，在 SQL Editor 执行，报错就把错误交给 AI 修。第三步：重构代码，让 AI 基于这份 SQL 改造项目，和 Supabase 通信。第四步：配置与验证，用环境变量配好地址和 key，跑一遍所有数据功能，同时在 Table Editor 里看数据是否真的同步。

加登录系统时，要和 AI 讲清跳转逻辑：登录成功去哪个页面、失败留在当前页并显示错误。验收标准是注册后能在 Authentication 里看到新用户，登录后能进入原本进不去的页面。原教程的案例是给贪吃蛇加在线排行榜和登录；还有两个实用技巧：对话轮次太多想开新会话时，把 init.sql 作为上下文带过去；AI 实现的登录不对劲，就把一个已经能用的项目路径给它，让它参考迁移。

四步都在。拿掉一步，看会出什么问题。

我现有一个本地 React Todo 应用，数据仅存在浏览器本地存储，需新增“数据云端同步”功能并接入 Supabase 数据库。
请帮我梳理：这个应用涉及哪些数据操作（如新增待办、修改状态、删除待办）？需要创建哪些数据表来存储这些数据？
约束：时间戳用 timestamptz；每条待办只有创建者自己可见（请一并写好 RLS 策略）。
基于上述思路和表结构，返回给我在 Supabase 中可以进行初始化的 init.sql 脚本。
（执行成功后）请你根据我的 sql 脚本以及上面讨论的设定，重构项目的代码，让它能够和 Supabase 对应的数据库通信并处理数据。Supabase 地址和 key 从环境变量读取。

第三方登录：OAuth 2.0 的五步

原教程 第 5.2 节

邮箱注册之外，实际产品常用 Google、GitHub 一键登录。背后是 OAuth 2.0 开放授权协议，本质是“授权代理”：用户授权你的应用读取他在第三方平台的公开信息（邮箱、头像），但不必把第三方密码交给你的应用。配置上要去 Google Cloud 和 GitHub 分别申请 Client ID 与 Secret，填进 Supabase 的 Provider 设置，并约定好回调地址。一个完整的认证系统还要有密码重置。

流程中最值得记住的设计是：Google 授权通过后不直接返回用户信息，而是返回一个一次性、短期有效的授权码，由后端（Supabase 托管）拿着授权码去 Google 换 Access Token，再用 Token 拉取信息。这样 Token 不经过前端传输，即使授权码被截获也很快失效。另外，原教程还演示了用 Clerk 做登录、再通过 Webhook 触发边缘函数把用户数据同步进 Supabase 的做法：认证和业务数据库可以由不同服务负责。

走一遍“用 Google 登录”。

实时、存储、边缘函数

原教程 第 2.1、5.3–5.5、6 节

Realtime 让应用即时收到变化，不用反复轮询，通过 WebSocket 推送。三项功能：Postgres Changes 监听表的增删改（可按条件过滤，并遵守 RLS，用户只收到有权看的变更）；Broadcast 让客户端之间通过频道发低延迟的临时消息（聊天、光标、游戏状态）；Presence 追踪谁在线（“当前 3 人正在查看”）。

Storage 管理图片、视频、文档这类非结构化文件。原教程解释了为什么要单独的对象存储：文件体积差异大、数量可能极多，放在业务服务器上会拖慢读写；对象存储（S3、OSS 都是）给每个文件一个 URL，前端直接加载，不经业务服务器中转。Supabase Storage 兼容 S3 协议，基本单位是存储桶（Bucket），每个桶可单独配置策略。取文件地址有两种：公开 URL 永久固定，适合头像这类公开图片；签名 URL 带有效期，适合私有文件。

Edge Functions 是部署在全球边缘节点的服务端函数，不用自己管服务器。核心用途是安全中间层：前端只和你的函数通信，OpenAI、Stripe 这类密钥存在 secrets 里，函数通过环境变量读取（和第 6 篇的 /api 是同一个思路）。它还能识别当前登录用户、遵守 RLS，并适合接收第三方 Webhook（支付成功、Clerk 用户变更）、发邮件、生成报告。原教程最后提醒：Supabase 的每一块在业界几乎都有专业替代品，了解它们能判断“全用 Supabase 是否就够”，以及将来能否把某块单独换掉而不被锁死。

这些需求，各用哪个模块？

原教程列出的替代方案（摘要）一站式 BaaS：Firebase（最成熟但闭源、计费复杂）、Appwrite、Nhost、AWS Amplify、Convex 等。认证：Firebase Auth、Auth0、AWS Cognito、Logto（开源）、Keycloak（开源，运维重）。存储：Amazon S3、阿里云 OSS / 腾讯云 COS、MinIO（开源自建）、Cloudinary（媒体优化）。边缘函数：Cloudflare Workers、Vercel Edge Functions、Netlify、Lambda@Edge。实时：Ably、Pusher、自建 Socket.IO。数据库托管：Neon（Serverless Postgres，支持分支）、CockroachDB、TiDB Cloud、MongoDB Atlas。免费额度和价格变化快，以官网为准。

回扣开头的三个问题

先自己答，再点开
1. 关系型与非关系型各适合什么？规范化与冗余各换来什么？

关系型事先定义表结构、用外键关联，数据精确一致、支持事务，适合金融交易、库存、订单、账务；非关系型结构灵活、易扩展，适合社交内容、日志、物联网写入等高并发多变场景，但关联查询和一致性较弱。规范化（拆表 + 外键 + JOIN）换来一致性和最小冗余；冗余（把关联数据嵌进文档）换来一次读取拿全数据的性能，代价是更新时要改多处，适合读多写少。

2. RLS 解决什么？为什么开了 RLS 才能让前端直连？

RLS 在数据库层按请求者身份控制每一行能否被读写，启用后每个操作都必须通过至少一条策略，否则被拒绝；Supabase 用 auth.uid() 取当前用户 ID 写策略，实现“只能看自己的数据”。前端携带的是公开的 anon key，任何人都能拿到，真正的安全边界是 RLS；不开 RLS，拿着公开 key 就能读写整张表。绕过 RLS 的 service_role key 只能放在服务端。

3. 接入 Supabase 的四步？OAuth 为什么先给授权码？

四步：让 AI 梳理数据操作和表结构并审核补充约束；生成 init.sql 在 SQL Editor 执行；让 AI 基于 SQL 重构代码与 Supabase 通信；用环境变量配置地址和 key，测试并在 Table Editor 核对数据。OAuth 先返回一次性、短期有效的授权码，由后端拿授权码去换 Access Token 再拉取用户信息，这样 Token 不经前端传输，授权码被截获也很快失效，用户密码始终不交给你的应用。
