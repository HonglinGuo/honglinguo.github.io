先问该不该用 AI，让它扮演什么

原教程 产品思维基础 第 4 节

产品思维附录先泼了一盆冷水：不要为了 AI 而 AI。决定之前问两个问题。第一，不用 AI，这个应用是否也成立？把 AI 能力全部抹掉，这件事本身有没有价值，用户愿不愿意持续投入时间。第二，用了 AI 之后具体提升了什么？不接受“提升效率、智能升级”这种泛泛总结，要落到用户自己能感知的一两个维度。登录、支付、保存文件、页面跳转这类有明确规则的事，仍然用普通程序做。

AI 在产品里大致扮演三种角色。大脑：理解和生成文字、在复杂信息间推理，比如从长录音里抓出核心讨论点，或判断学生是没理解概念还是粗心写错；你要做的是把问题问清、上下文喂准。眼睛：处理图像视频，把发票合同变成可搜索文字、看懂草图指出构图问题，让应用开始接触实物世界。手：执行一连串动作，比如读邮件附件、总结、发群、存云盘、建任务，并根据上下文动态决定下一步。

最后要评估 AI 带来的不确定性，原教程给了三问：用户和系统能不能承受（客服理解错了用户能马上纠正，自动财务审批误判就不可接受）；准确率能否达到这个场景的及格线（相册按人脸分类 80% 可以接受，安防漏掉 20% 就是隐患；社交文案 60 分够用，合同条款 95 分都不够）；出错时有没有办法补救（流程确定时可以在关键节点放人工审核，流程本身不确定时风险会急剧上升）。

先把这些功能里 AI 的角色归类；再判断每个场景的不确定性能否承受。

看页面的输入和输出，决定找哪类模型

原教程 初级四 第 1 节

原教程的判断方法很朴素：看一遍页面，用户会提交什么，最后希望看到什么。填商品名称、材质、卖点，返回一段文案，输入输出都是文字，找文本生成模型；上传商品照片识别颜色款式，要图片理解；根据资料做海报，要图片生成；录音整理成纪要，要先语音转文字再交给文本模型；文章做成音频，要文字转语音；让商品图动起来，要图生视频。

不是每个功能都能交给一个模型一次完成。“上传商品照片并生成卖点”要先读懂照片再写文案；“根据公司资料回答问题”要先找到相关内容再组织答案。拆的时候不从模型名出发，顺着用户操作看：哪一步在理解现有内容，哪一步在生成新内容，哪一步只是查资料，需要时把两三种能力串起来。原教程还建议先让用户确认识别出的商品信息，再生成文案，这比直接从图片生成最终文案更容易发现错误。

服务台里还会看到 Embedding、Rerank、Function Calling、OCR、内容审核等接口：做知识库用前两个（第 10、14 篇）、读 PDF 票据用 OCR、让模型调搜索和数据库用 Function Calling。第一次不用学完，先接通一个和页面直接相关的。

服务台四样东西，先在线试格式

原教程 初级四 第 1.2、2–4 节

打开 DeepSeek、SiliconFlow、火山方舟、MiniMax 这类平台，第一次只找四样：API Key（调用凭证）、Model ID（代码里用的准确名字，可能和页面显示的中文名不同）、官方最小示例（curl 或 JS/Python）、额度、价格和调用限制。要分清三个东西：服务平台名称、Model ID、API 地址不是一回事，填代码时以官方示例里的地址和 ID 为准，别把在线体验页的网址复制进去。有的平台还要先选 Region 或创建一个 Deployment 才给 Base URL。

写代码前先到在线体验页试一试，要确认的不是“模型会不会写文案”，而是它能不能按页面需要的格式返回。原教程区分了两类信息：用户只需填商品名称、材质、颜色然后点按钮；固定要求由程序在请求里补上：不要编造价格和销量、标题不要太长、按 title、summary、selling_points 三个 JSON 字段返回，页面才能稳定读取。测试时换几组资料，再故意少填一个字段，看模型会不会擅自补信息。格式不稳就调程序附加的要求，而不是让用户学怎么写提示词。

然后按官方示例在终端发出第一次请求，只替换模型 ID 和测试内容。终端能拿到正常响应，就证明账号、Key、模型本身可用，之后页面报错就能排除这些。发完去 Usage 或 Billing 页面确认出现了调用记录：页面显示了文字不代表它真的来自 API，原型里残留的模拟数据也会产生相似效果。文档太长就把链接交给 AI，让它只按文档写明的参数告诉你最简单的写法。

API Key 放在哪：调用链路

原教程 初级四 第 4.1、5 节

API Key 是应用调用模型的凭证，等同于你的钱包。原教程的规矩：放进本地环境变量文件（如 .env.local，并确保它不会被提交到 Git），不要贴进截图、聊天记录或前端代码；怀疑泄露就立即到服务台撤销重建。

最关键的一条：不要把 Key 写进 Vue、React 或普通 HTML 的前端代码。前端代码最终会下载到每个访问者的浏览器里，任何人打开开发者工具都能看到。正确的链路是三段：浏览器只把业务输入发给你自己的 /api/... 接口；这个接口跑在服务端或 Serverless Function 里，从服务端环境变量读 Key，再去调 AI 平台；平台返回文字、JSON、文件或任务编号，再由你的接口转给页面。

原教程总结的接入顺序是五步：Key 写进不提交的环境文件 → 在服务端或 Serverless Function 里调用模型 → 页面调自己的接口而不是直接带第三方 Key → 给按钮补上等待、成功、失败状态 → 回到 Usage 页面确认产生了真实调用。

易混辨析：VITE_ / NEXT_PUBLIC_ 前缀的环境变量也不安全

很多人以为“写在 .env 里就是安全的”。但 Vite 会把以 VITE_ 开头的变量、Next.js 会把以 NEXT_PUBLIC_ 开头的变量，在构建时直接替换进前端代码，打包后照样出现在浏览器里。这些前缀的含义恰恰是“允许暴露给前端”。能保密的只有只在服务端读取的变量（不带这些前缀，由后端或 Serverless Function 使用）。原教程原话：准备公开部署时，应由后端、Serverless Function 或受保护的网关调用模型。

三种返回方式：同步、流式、异步任务

原教程 初级四 第 3、4.3、5.1、10 节

发请求前要先看清接口实际返回什么，页面写法取决于它：文本通常藏在某个 JSON 字段里，图片可能返回一个 URL（往往有有效期），语音合成可能直接返回音频二进制或十六进制编码，视频则常常先返回一个任务编号。

按返回节奏分三类。同步：短文本、图片理解、短音频识别，一次请求直接拿到结果，页面显示“生成中”即可。流式：对话或实时语音，内容一段一段到达（打开 stream 参数），页面边收边显示。异步任务：图片和视频生成常常要几十秒，第一次请求只拿到 task_id，之后要反复查询状态（排队中、生成中、成功、失败），成功后拿到 file_id 再换下载地址。查询可以由你的程序轮询（要设间隔和停止条件），也可以提供 callback_url / Webhook 让平台完成后主动通知你的服务端。临时下载地址会过期，正式上线要考虑转存。

用量限制也要看：文本接口常标 RPM（每分钟请求数）和 TPM（每分钟 token 数），图片、语音、视频还会限并发。超了通常返回 429，应该稍后重试，而不是不停点。max_tokens、temperature、stream 这些参数第一版先沿用官方示例，输出被截断时再调 max_tokens，需要边生成边显示时再开 stream。

各模态的提示词要点

原教程 初级四 第 6–10 节

原教程把每种模态都接了一遍，示例模型会更新，但提示词的写法是稳定的。文本：在 system 里规定返回字段和禁止编造的内容，用户消息只放业务信息。图片理解（示例用 Qwen3-VL）：页面需要什么就直接问什么，只问“图里有什么”只会得到宽泛描述；还要加一句“看不清的地方直接说看不清，不要猜品牌、价格或销量”。图片生成和修改（示例用 Seedream）：商品图最怕“看起来很好但商品本身变了”，除了背景、构图、光线，要写明哪些地方不能改变（拉链、肩带、口袋），并且不要一上来堆风格词。

语音至少是两条接口：ASR/STT 把音频变文字（上传用 multipart/form-data，和 JSON 请求不同），TTS 把文字变语音（返回音频，不一定是 JSON）。TTS 的“提示词”是朗读脚本和声音参数：先把数字、英文缩写、停顿改成适合朗读的文本，别把 Markdown、URL、按钮文字整段送去读；页面要有试听、停止、重新生成、下载。视频还要说明接下来几秒发生什么：初始位置、运动顺序、镜头方向、时长；动作多时先只保留一个镜头一个主要动作，同时要求旋转、开合、变焦、切场景很难保持商品外观一致。

合规提醒贯穿全章：上传录音前告诉用户用途、保存时间和删除方式；声音克隆必须得到音色拥有者明确授权；用真人照片、声音、商标或版权素材生成视频要确认授权，有些平台的人脸验证和素材登记不是能从前端绕过的技术步骤。

出错了先看状态码

原教程 初级四 第 11 节

原教程把接入 AI 时最常见的现象整理成了一张表：401/403 查 Key 是否正确、有无权限、是否放错请求头；404 查 Base URL、Endpoint 或 Model ID 是否变了；429 查 RPM、TPM、并发或账号等级；400 查必填参数、文件格式、JSON 结构、尺寸限制；5xx 或超时查平台状态、超时设置和重试策略；一直排队查并发、状态查询和额度；页面显示成功却没内容，查响应字段路径、二进制处理、临时 URL 是否过期；本地能用、上线失败，查环境变量、跨域、Serverless 超时和区域网络。

请求失败时先分清三种情况：代码根本没发出去、平台拒绝了、还是账号没额度了。调试时保存四样东西：发生时间、请求类型、HTTP 状态码、Request ID / Trace ID（同一时间请求很多，这个编号能帮你在日志里找到那一次）。日志里不要写 API Key、完整用户音频或敏感业务数据。

让 AI 写后端接口时，你要把关什么

原教程 二阶段 大模型辅助编写接口代码与接口文档

上面的 /api/... 就是一个后端接口。原教程第二阶段专门讲了怎样让大模型写接口，用餐厅打比方：前端是菜单和点餐桌，数据库是后厨仓库，后端 API 是服务员，客人不能冲进后厨自己拿，要把点单（HTTP 请求）交给服务员，服务员核对（参数校验、权限）后去后厨取，再把菜（通常是 JSON 响应）端回来。

AI 写的接口质量取决于你给的上下文：大模型不怕需求复杂，最怕需求模糊。要给出字段定义和约束（商品名和价格必填、价格不能为负、分类只能是汉堡小食饮料、输入不对要提示），还要心里有一个分层结构：路由层定义路径和方法，控制器层处理请求参数，服务层封装数据库交互和业务逻辑，中间件负责鉴权和全局错误捕获，别全塞进一个 server.js。写完还可以让 AI 逆向生成 OpenAPI（Swagger）接口文档、Postman 测试集合（含正常和错误请求）、Jest 单元测试。

即使有 AI，你仍是把关人，原教程列了三条必须审核的准则：RESTful 命名（URL 是资源名词，动作交给 HTTP 方法：GET /api/users、POST /api/users，而不是 POST /api/getUser）；规范的状态码（200/201 成功，400 参数错，401/403 未登录或无权限，404 不存在，500 服务端错，且不要把调用栈直接暴露给前端）；永远不信任用户的输入，所有核心校验在后端再做一次。

回扣开头的三个问题

先自己答，再点开
1. 要不要用 AI 先问哪两个问题？不确定性怎么评估？

两个问题：不用 AI 这个应用是否也成立；用了 AI 之后具体提升了什么（落到用户能感知的一两个维度）。不确定性三问：出错时用户和系统能否承受；准确率能否达到这个场景的及格线（及格线由用途决定）；出错时有没有补救办法，例如在流程确定的关键节点放人工审核。

2. 为什么 Key 不能放前端？正确链路是什么？

前端代码会下载到每个访问者的浏览器，任何人都能看到；VITE_、NEXT_PUBLIC_ 前缀的变量会在构建时被替换进前端代码，同样暴露。正确链路：浏览器只把业务输入发给自己的 /api 接口；接口跑在服务端或 Serverless Function，从服务端环境变量读 Key 去调 AI 平台；平台结果由接口转回页面。Key 放在不提交到 Git 的环境文件里，泄露就立即撤销重建。

3. 视频生成为什么不马上返回？页面怎么处理？

视频生成耗时几十秒甚至更久，接口采用异步任务：创建任务先返回 task_id，之后查询状态（Preparing、Queueing、Processing、Success、Fail），成功后用 file_id 换下载地址。页面要显示这些阶段而不是停在一个不变的“加载中”；程序轮询要设间隔和停止条件，正式产品可以用 callback_url 让平台主动通知服务端；临时下载地址会过期，上线时考虑转存。
