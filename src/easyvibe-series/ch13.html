AI 为什么会过早停止

原教程 让 Claude Code 长时间工作 · 引言、核心原理、方法一

原教程讲了一个故事：2025 年夏天，澳大利亚开发者 Geoffrey Huntley 写了一个只有五行的 bash 脚本，不断重启 Claude Code 并喂给它同一个任务，取名 Ralph Wiggum（《辛普森一家》里那个屡败屡试的角色）。相关项目两周内拿到几千星，流传着“一晚上生成六个完整项目”“几百美元 API 成本完成几万美元合同”这类故事（这些是原教程转述的社区案例）。

它要解决的根本问题是：大模型无法准确判断自己的工作是否真正完成。人的完成标准是客观的（测试全过、功能可用、质量达标），模型只能凭感觉，觉得“差不多了”“输出够多了”或者“不知道接下来干什么”就停。所以要有一个外部系统来判断：让 AI 在循环里工作，每次它想退出时检查“真的完成了吗、符合客观标准吗、还有遗漏吗”，没完成就重新注入任务进入下一轮。

最原始的实现就是 while true; do cat PROMPT.md | claude; done：读任务、启动、干活、退出、重启。极其简单，但它无法判断任务是否真的完成，可能无限空转、浪费调用。原教程给的安全改进版是加最大迭代次数和每轮间隔。

对比两版循环脚本。

Ralph 循环：Stop Hook 加完成标记

原教程 方法二、方法三、方法五

官方插件市场里的 Ralph Wiggum 插件把这个思路做成了正式机制，核心是 Stop Hook：Claude 想退出时，钩子拦截退出信号，检查输出里有没有约定的完成标记；没有就重新注入原始任务开始下一轮，有才允许退出。两个关键参数：--completion-promise 指定完成标记（要明确唯一，如 TODO_API_COMPLETE），--max-iterations 是兜底的最大迭代次数（原教程建议 20–100）。

Prompt 写得好不好决定成败。“写一个 todo API”没有完成标准，AI 写个框架就宣布完成；好的 prompt 分阶段写清要求（CRUD 端点、输入验证、测试覆盖率），列出可以客观验证的验收标准（测试全过、lint 通过、README 有 API 文档），再指定唯一的完成标记。原教程给了测试迁移、UI 统一、批量加类型、TDD 开发、代码风格统一等模板，以及一个用 150 次迭代从零构建 BBS 论坛的完整示例。社区还有增强版：要求完成标记加显式退出信号双重条件、每小时速率限制、连续多次检测到完成就强制退出的熔断器、实时成本仪表盘。

判断一个任务适不适合交给 Ralph，原教程给了三个问题：能定义明确的完成标准吗？有客观的验证方法吗（测试、构建、类型检查）？需要我持续给反馈吗？前两个是、第三个否，才适合。另一个更轻量的工具是后台任务：任务开始后按 Ctrl+B 推到后台，同时让它做别的，用 /tasks 查看。它没有循环机制，只是不阻塞。

走一遍 Stop Hook 的判断；再看哪些任务适合交给 Ralph。

五道安全阀

原教程 安全机制：防止无限循环

任何自动循环系统都必须有保护，否则会失控。原教程列了几层：最大迭代次数是必须的，不管完成没有都停；时间上限（比如最长四小时）；成本预警，花费到 10、50、100 美元时暂停并通知；死循环检测，比如最近五次提交几乎没有代码变化，说明在原地打转，应该停下报警；人工检查点，每十轮停下来问你是否继续。

原教程在 BBS 示例后面也提醒：Prompt 越详细迭代越少；复杂项目要给足迭代次数；TDD 能大幅减少调试；最终必须人工验证，AI 可能漏掉边界情况，尤其是安全相关功能。

Agent Teams：从一个助手到一个团队

原教程 Claude Agent Teams 完全指南

单个实例处理复杂项目有四个瓶颈：串行（互不相关的模块也只能一个个分析）、上下文拥挤（对话越长早期决策越容易被淹没）、单一视角（没有“同事”辩论）、效率天花板。Agent Teams 让多个独立实例像开发团队一样协作：每个成员有完整独立的上下文，可以并行工作、直接互相通信。它在原教程写作时是实验性功能，默认关闭，开启方式以官方文档为准。

它和 Subagent 的区别在拓扑：Subagent 是星型，主代理给每个子代理写任务单，子代理完成后只把结果交回主代理，彼此不交流；Agent Teams 是网状，成员之间可以直接讨论、自主认领任务。团队由四部分组成：Team Lead（拆任务、建团队、分配、综合结果，不直接写代码）、Teammates（独立实例，有完整工具权限）、TaskList（共享任务板，有状态、依赖、完成后自动解锁后续任务、文件锁防冲突）、消息系统（点对点或广播，以 JSON 文件存在本地目录里，状态完全透明）。

原教程总结了七条实践，最重要的是第一条合同优先：并行开工前先定好接口契约（请求响应格式、状态码、错误约定、字段校验），否则后端收 {username, password}、前端发 {user, pass}，只能返工。其余是：Team Lead 用强模型、成员用性价比模型；每个任务 15–30 分钟粒度；不同成员负责不同文件，必须改同一文件时设串行阶段；成员启动时对话是空的，要给足初始上下文；先研究再实现；用分屏或 /tasks 主动监控、及时干预。

先翻开对照表，再点开团队的四个组件。

一笔成本账，顺便验算一下

原教程 Agent Teams · 成本和性能

原教程给的规律是：token 消耗大致随团队规模线性增长（2 人约 2–2.5 倍，3 人约 3–4 倍），再加上每个成员接收初始上下文的启动开销、成员间通信开销、Team Lead 用更贵模型的开销，大致是单实例的 2–4 倍。换来的是时间：它引用的 Anthropic 内部测试是大型重构效率提升约 50%，以及 16 个并行代理约两周写出一个能编译 Linux 内核的 C 编译器的案例。

原教程还算了一个具体例子：Team Lead 用 Opus（50K 输入 + 20K 输出），三个成员用 Sonnet（各 30K 输入 + 15K 输出），对比单实例 Sonnet（100K 输入 + 50K 输出），单价按 Sonnet 每百万 token 输入 3 美元、输出 15 美元，Opus 按原文结果反推为输入 15、输出 75。这里值得自己算一遍：原文写每个成员约 2.7 美元、总计约 10 倍，但按它自己给的单价，每个成员只有约 0.3 美元。数值本身会随价格变化，重要的是练习这个估算方法。

原教程的省钱策略是：混用模型（Lead 用强模型、成员用中等、简单任务用最便宜的）；分阶段调整团队规模；只在最适合并行的阶段（多方案架构设计、多维度代码审查、并行写文档）用 Agent Teams，其余阶段单实例。

用 GitHub Issues 驱动开发

原教程 用 GitHub Issues 驱动 AI 全流程开发

上一篇讲了为什么要 Spec，原教程的这一章用一次真实开发演示怎样落地：起点只有一句“我想做一个 macOS 上的 CRM，用来管理联系人关系，可以先用假数据”，终点是一个原生 macOS 应用 Relationship Compass（搜索筛选、关系档案、CSV 导入、互动记录、自动计算下次跟进），公开仓库里保留了 Spec、Issues、提交和测试。用的是 Matt Pocock 的五个技能：grill-with-docs（讨论到双方理解一致，同步写下项目用词和重要 ADR）→ to-spec（写成需求文档并建一张总 Issue）→ to-tickets（拆成有优先级和依赖的实现 Issues）→ implement（从第一张未被阻塞的任务开始，TDD，每张一个提交）→ code-review（两遍审查）。

这里 GitHub 承担三个角色：项目档案室（Spec、项目用词、技术决定）、任务看板（Issues、优先级、Blocked by 依赖）、完成记录（提交、测试、关闭状态）。聊天结束后这些都还在，下次 AI 不必从头猜，可以沿着记录接着干。拆任务时最容易犯的错是横向切（先建所有模型 → 所有 Store → 所有 UI → 最后补测试），前几张做完用户什么都看不到；应该纵向切片，像切蛋糕每块都有胚、奶油和水果，每张 Issue 同时包含必要的数据、界面和测试，关一张就多一个能演示的小功能。还要分清优先级和依赖：P0 表示重要，依赖表示现在能不能做；所有前置都完成、当前可以开始的那几张叫任务前沿。

最后的两遍审查值得记住。第一遍看代码健康；第二遍重新打开 Spec 和所有 Issues 逐条核对：有没有漏、有没有只做一半、界面在但行为对不对、有没有擅自加功能。这一遍真的抓出了测试没覆盖的问题：CSV 有重复表头时运行时报错、没邮箱的联系人无法按“姓名 + 组织”去重、待跟进列表没用上筛选条件、数据能保存但启动时不恢复。原教程的结论是：测试全部通过，只能证明已经写进测试的行为没出错，不能证明需求一条没漏。

按依赖关系推进任务：点“完成”看哪些任务进入任务前沿（依赖取自原教程的五张 Issue）。

/to-tickets

/code-review

什么时候可以“梭哈”

原教程 GitHub Issues 驱动开发 第 11 节

原教程说的“梭哈”不是完全不看过程，而是需求和安全边界确认后，让 AI 沿着任务清单连续工作，不必每写一个函数都停下来等指令。适合：范围能通过讨论收敛的 MVP；有明确用户行为和验收标准的后台、App、网站；能用测试或构建命令验证的仓库；希望 Agent 跨多个会话持续工作的项目。不适合：需求每小时都在变、无法用测试或构建验证、会直接操作生产数据的任务。

即使连续实现，有四个节点仍然要你亲自确认：需求讨论结束时确认第一版范围没理解错；创建 Issues 前确认没漏项、顺序合理；涉及付费、生产部署、删除数据、账号权限和隐私时确认具体外部操作；完成后亲自打开真实界面，检查构建产物和审查结果。原教程的总结：可靠的自动开发不是把所有决定都交出去，而是你负责目标、边界和最终验收，AI 负责把已确认的事情稳定执行下去。

Agent SDK：把 Claude Code 的能力变成一个库

原教程 Claude Agent SDK 完全指南

基础的 Anthropic SDK 是“你问它答”：要让模型调用工具，你得自己定义工具、自己执行、自己把结果喂回去、自己写循环。Claude Agent SDK 把 Claude Code 的能力（读写文件、执行命令、搜索代码、编辑、浏览网页）封装成可编程的库，内置 agent 循环和上下文管理，原教程的说法是“你下单它干活”。它的运行逻辑一句话：收集上下文 → 执行动作 → 验证结果 → 重复。

两种用法：query() 无状态，适合单次任务；需要多轮时保存 session ID 再 resume（或用有状态的客户端）。通过 allowed_tools 控制能力边界，比如只读 Agent 只给 Read、Glob、Grep，全能 Agent 再加 Edit、Bash。高级功能有 Hooks（在关键节点插入你的逻辑，比如每次改文件都写审计日志）、子 Agent（把大任务拆给专家）、MCP（接 Playwright 操作浏览器、接数据库）。典型场景：自动修 Bug、代码审查、CI/CD 里自动修复、技术调研报告、带浏览器的全栈 Agent。

原教程的选择表：简单对话、生成、翻译、单次工具调用用基础 SDK；自主完成多步骤开发、嵌进 CI/CD、构建能操作文件系统的应用用 Agent SDK；日常交互式开发和一次性快速任务直接用 Claude Code CLI。

回扣开头的三个问题

先自己答，再点开
1. AI 为什么过早停止？Ralph 靠什么判断完成？什么任务不适合？

模型无法准确判断自己是否真正完成，只能凭感觉停下。Ralph 用 Stop Hook 拦截退出，检查输出里是否有约定的唯一完成标记，没有就重新注入任务；最大迭代次数兜底。完成标记必须配合客观验收标准（测试、构建、类型检查）。不适合的是：无法定义明确完成标准、没有客观验证方法、需要人持续反馈的任务，如架构决策、安全相关代码、需求模糊的探索、创意设计，以及简单的一次性任务。

2. Agent Teams 与 Subagent 的区别？用之前最该先做什么？

Subagent 是星型：主代理派任务单，子代理只把结果交回，彼此不交流；Agent Teams 是网状：每个成员有独立上下文，可以直接通信、从共享任务板自主认领任务，由 Team Lead 拆分和综合。用之前最该先做“合同优先”：定好接口契约（请求响应格式、状态码、错误约定、字段校验），再让成员并行开工；同时按文件划分职责、给足初始上下文。

3. 为什么要纵向切片？为什么测试全过还不够？

横向切（先所有模型、再所有 UI、最后补测试）时中间任务完成后都无法单独使用，到最后才知道各层能不能连起来；纵向切片让每张 Issue 都包含数据、界面和测试，关一张就多一个可演示的功能，也便于逐张验证。测试只能证明写进测试的行为没出错，不能证明需求没漏，所以最后要重新打开 Spec 和 Issues 逐条核对，原教程这一步就抓出了测试没覆盖的五个问题。
