本篇要回答的 3 个问题

  1. 模型放到远端更快，什么时候反而让用户等得更久？

从模型运行时间到完整交互时间

原书 12.1.1–12.1.4 节

端侧采集输入并与用户交互，边缘是附近提供计算的工作站或服务节点，云端是远程资源池。原书用三类任务讲同一套分析：图片精修看完整成片何时返回，语音看能否连续播放，截图 Agent 看每轮开销如何累积。

图片精修：Tserial = Su/Bu + R + Tc + Sd/Bd。30 MB 原图、20 Mbit/s 上行、5 MB 成片、100 Mbit/s 下行、R = 0.1 s、Tc = 0.3 s，共 12.8 秒，上传占 94%。处理只占约 2.3%，消掉也只缩短 2.3%——这就是 Amdahl 定律。上行提到 100 Mbit/s 只要 3.2 秒；无损压缩减半、多花 0.15 秒编解码，约 7.0 秒。压缩的收益 ΔT = (Su − S′u)/Bu − Te 随上行变快而缩小：20 Mbit/s 省 6 秒，100 省 1.2 秒，800 Mbit/s 时收益归零。分三块独立处理，前两块的处理和回传藏进后续上传，约 12.36 秒；要全局曝光就只能等整图到齐。

实时语音写成逐块递推：ci = max(ai, ci−1) + mi，ui = max(ci, ui−1) + si，ri = ui + di；两个 max 分别是数据依赖和资源竞争。播放 pi = max(ri, pi−1 + τ)，第一项更大时差额就是停顿。每块 20 ms，处理 12、发送 1、传播 5 ms，缓冲 40 ms；第三块传播变成 50 ms，晚到 5 ms，后面全部推迟 5 ms；缓冲加到 45 ms 正好避开。长期速率不足是另一回事：256 kbit/s 的 PCM 只收到 130 kbit/s，60 ms 缓冲约 0.12 秒就耗尽——加缓冲只抬高起点，不改斜率。

截图 Agent：下一轮截图必须等上一轮操作完成，等待逐轮累积。30 轮，每轮上传 0.8 MB（6.4 Mbit/s，1 秒）+ 终端 0.3 + 远端模型 2.0 + 往返 0.2 = 3.5 秒，共 105 秒。压到 0.2 MB、多 30 ms 编码，每轮 2.78 秒，约 83 秒；但若文字变糊导致多轮纠错，2.78N′ < 105 → 最多 37 轮，即最多容忍多出七轮。最短传播还能先排除太远的服务器：光纤约 2×10⁸ m/s，单向 10,000 km 往返至少约 100 ms。

端侧执行资源：带宽、容量、能耗三个下界

原书 12.1.5 节

带宽给出每秒 token 的上限。Snapdragon 8 Elite 最高 5,300 MHz、最大 24 GB LPDDR5X，即每引脚 10.6 Gbit/s；一条 x16 通道 21.2 GB/s，按四条计 84.8 GB/s（产品简介没给总线宽度，四通道是原书的计法）。沿用第 4 章的 Qwen3-8B BF16、8K：一步 decode 读权重 15.14 + KV 1.21 ≈ 16.345 GB，约 0.193 s，上限约 5.2 token/s；q4_0（每 32 值 64 → 18 bytes）后每步 5.47 GB、64.4 ms，约 15.5 token/s。MELTing Point 在 iPhone 14 Pro 上实测 Zephyr-3B q4_k 14.8 token/s、Llama-2 7B q3_k 6.0 token/s，量级一致。

容量决定装什么、留多长上下文。预留 4 GB；BF16 常驻 16.38 GB（比每步读取多出约 1.24 GB 的词嵌入表），只有 24 GB 一档装得下、仅够两条 8K；q4_0 权重 4.61 GB，每 token KV 147,456 bytes。

能耗与续航是端侧特有的代价。MELTing Point 实测每 token 0.576–0.756 J，持续功率最高 13.8 W；14.8 token/s × 0.576 J ≈ 8.5 W，在持续功率之内。一次充电约 490–590 个提示。

本地三档：手机 84.8 GB/s；M3 Ultra 819 GB/s、约 50.1 token/s；RTX PRO 6000 1,792 GB/s、约 109.6 token/s。运行时（llama.cpp、Ollama、MLX、Unsloth）不改变这些下界，只决定能多接近；RTX PRO 6000 的实测 decode 是读取下界的 2.83 倍。翻转条件：45 秒期限摊到 20 轮、扣 0.3 秒终端工作，每轮约 1.95 秒，手机 q4_0 每轮最多约 30 个 token，第 12.5 节的任务每轮要 45 个。注意下界的判断不对称：下界已超期则一定不可行，低于期限只说明尚未被排除。

跨设备分工：传图片、传特征，还是传状态

原书 12.2 节

端侧编码不一定减少上传量。压缩图片为紧凑存储，视觉编码器的输出为后续计算。Qwen3-VL-4B 固定配置：640×640 → 400 个视觉 token，最终投影 2560 维 + 三组同宽 DeepStack 特征（漏传就缺了三组输入），SE = 400 × 10240 × 2 = 8,192,000 bytes，是 0.8 MB 截图的约十倍。ΔT = TE,l − TE,r + Tx + (SE − SI)/Bu：编码 1.31 TFLOPs，RTX 4090 约 7.9 ms、H100 约 1.3 ms，6.4 Mbit/s 上行下本地编码约 10.25 秒 vs 远端 1.00 秒。换成同机房 400 Gbit/s 的 ConnectX-7，发送差只剩约 0.15 ms，比的就是编码和排队了。图片、7.8 MiB 视觉特征、56.3 MiB 视觉 token KV（每 token 144 KiB）对应三个不同的重算起点。

会话迁移：G(N) = NΔt − M。80 Mbit/s 传 64 MiB 状态 + 1 秒恢复，M ≈ 7.7 秒；每轮快 0.4 秒，10 轮亏 3.7 秒，20 轮才回本，40 轮净省 8.3 秒；恢复多 1 秒，回本推到 22 轮。连接预热、图编译、模型加载都是同一个式子。

模型内部切分：TP=2 跨两台设备，36 层 × 每层两次归约 × 两阶段环 = 144α。α = 2 μs 时约 0.29 ms；换成 54 Mbit/s 无聚合 Wi-Fi，每次至少一次 134 μs 的短帧交换，约 19.3 ms，是 RTX PRO 6000 一步 decode 读取下界 9.12 ms 的两倍多。流水线并行把通信集中在相邻阶段之间，单请求少等，多请求并行提吞吐。

广域网：建链、窗口、丢包与冗余

原书 12.3 节

建链：30 轮截图任务、RTT 200 ms、建链两次往返——每轮重建累计 12 秒，复用只要 0.4 秒；任务从 105.4 秒变 117 秒。QUIC 把传输握手与 TLS 1.3 合并，会话恢复还能发 0-RTT 早期数据，被拒时客户端重发、服务端靠操作编号去重。

窗口：Buseful ≤ min(Bpath, W/R)。20 Mbit/s、100 ms 要约 250 KB 在途；只有 64 KB，上限约 5.1 Mbit/s，30 MB 至少要 47 秒。新连接从 10 个 1460-byte 段起步、每轮翻倍，约 355 KB 的语音请求要到第五轮才发完。头部与 ACK 让 35 MB 变成约 39.6 MB、完整请求约 14.4 秒；改成每两包确认，字节少了（38.2 MB），完成却晚 43 ms——ACK 一面占链路，一面释放发送额度。

丢包不一定是拥塞。Mathis 上界 B ≤ (MSS/R)·C/√p 的前提是丢包代表拥塞。原书作者的 Queqiao 路径记录：Irvine → 贵阳下载方向，从 1 提到 300 Mbit/s 丢包始终约 14%，反方向 41,663 个报文一个没丢，RTT 最大最小只差几毫秒；到 600 Mbit/s 才升到 44%（膝点约 333 Mbit/s）。代入得 约 0.155 Mbit/s，与实测 0.13–0.47 一致，比路径实际能力低三个数量级。BBR 直接测 max_bw 和 min_rtt：BDP = 333 Mbit/s × 0.2 s = 8.325 MB，cwnd 取两倍；理想有效吞吐 (1 − p) × 333 ≈ 286 Mbit/s，约是 Mathis 上界的 1,850 倍。

但测准带宽，重传尾巴还在：354,640 bytes = 245 个报文，逐轮重传期望 0.756 s（串行预算 238.5 ms 的 3.2 倍），p99 1.24 s。FEC 多发 63 个修复包（25.7%）就能 99.9% 不重传，约 241 ms；丢包 3.6% 时只要 20 个（8.2%）——冗余应随测得的丢包率调整。多流时，FIFO 下图片第 5 秒、音频第 6 秒完成，音频优先则 3 秒和 6 秒；整体有序交付让第 3 秒齐的音频等到第 7 秒（队头阻塞），QUIC 逐流交付第 3 秒就交。

Queqiao 案例（贵阳—Irvine，固定 354,640 bytes 音频，交替运行）：新建连接时直接路径约 1.19 s、Queqiao 约 0.30 s；保持连接并调优后两者都约 0.24 s，差约 4 ms，小于同期 RTT 约 8 ms 的波动。差距几乎全部来自实现开销，下界没有错。此后再优化：模型 30 → 3 ms 最多省 27 ms，RTT 200 → 20 ms 省约 180 ms。

无线：空口争用、过期数据与双路径

原书 12.4 节

空口上，上行数据和下行反馈轮流占用同一段时间。端到端 ACK 发给远端发送方，MAC ACK 确认本跳无线帧——承载端到端 ACK 的帧也要自己的 MAC 确认。OFDM 54/6 Mbit/s、无聚合：数据交换 34 μs 接入等待 + 208 μs 数据帧 + 16 μs SIFS + 44 μs MAC ACK = 302 μs；承载 ACK 时数据帧缩到 40 μs，共 134 μs。数据帧短了约八成，整次交换只短了约 56%——94 μs 固定开销还在，合并小报文、减少交换次数更直接。30 MB + 5 MB 共约 30,800 次数据交换和反馈交换，约 13.4 秒空口；ACK 减半能释放约 2.1 秒，但反馈晚了又会拉长窗口停等。TACK 把累积确认合并、把需要即时反馈的事件立即返回。

过期与取消：八块 20 ms 音频与大图共用链路，FIFO 下全部到达却都错过播放时刻，媒体优先时全部按时——收到的字节一样，按时可用的声音分别是 0 与 0.16 秒。取消分两条路：本地清空待播缓冲（用户何时不再听到），远端停止生成（何时不再耗资源）。截图 Agent 的动作提交后会改变环境，重试要先查原操作编号的结果。

双路径（Wi-Fi + 蜂窝）：分流 Tsplit = max(xS/B1, (1−x)S/B2)，最优 x = B1/(B1+B2)：20 和 10 Mbit/s 各传 20、10 MB，各 8 秒，比只用快路的 12 秒少 4 秒；若汇入同一个 24 Mbit/s 出口，至少 10 秒——瓶颈转到共同出口。复制看共同故障：pfail = q + (1−q)p1p2，p₁ = 0.1、p₂ = 0.05、q = 0.02 时约 2.5%，其中 2 个百分点来自共同端点，接入再可靠也降不下去。MPTCP、接入代理和华为 Link Turbo 都按这个思路实现，代理的位置同时决定共享容量、传播与故障域。

云端随上行变化：Tcloud(b) = 11.6 + 128/b，满足期限要 b ≥ 128/33.4 ≈ 3.8 Mbit/s；上行无限大也不低于 11.6 秒，始终慢于附近工作站（每轮 0.2 s 往返比附近的传播 + 上传多 0.1 s，超过 H100 省下的 0.064 s）。门槛 bmin = 128/(D − 11.6) 只在 D > 11.6 时有意义。若按实测 2.83 倍放大模型时间，附近 16.04 s、云端不含上传 14.29 s，上行超过约 73 Mbit/s 云端才更快。上行 4 Mbit/s 只剩 1.4 秒余量，3.5 Mbit/s 就超期；每轮速率不同时 T = 11.6 + Σ6.4/bi，十轮 6、十轮 10 Mbit/s 平均也是 8，却要 28.7 秒（全程 8 是 27.6）。

恢复：云端每轮约 1.57 秒，第十轮执行完、确认未返回时断连，恢复连接 1 秒。前九轮已提交只重做一轮：34.2 s；十轮都丢：48.3 s，超期。附近工作站每轮约 0.54 秒，丢十轮也只要 17.4 秒。独立重试的期望成本 E = C/p。文本 Agent 则相反：少传 56 KB 只省 1.3 ms，主要收益是少做前缀计算（约 0.239 GPU 秒），而 465 MB 状态每秒占 0.0058 GPU 秒，保存约 41 秒后就抵消了。
