本篇要回答的 3 个问题

  1. 把 prefill 和 decode 拆开，什么时候真能涨吞吐？配比怎么定？
  2. EP 越大为什么越不均衡？专家副本要跑几批才回本？
  3. 缓存命中的机器排队 250 ms，没缓存的只等 20 ms，该发给谁？

PD 分离：先算那份要交接的 KV

原书 9.2.1–9.2.2 节

prefill 一次处理很多 token（算力受限），decode 每步只处理一个（带宽受限）。混在一起跑，长 prefill 会推迟已有请求的输出。PD 分离把两个阶段放进不同的池，各有独立队列和配比；代价是要把上下文 KV 从 P 交给 D，而且两个池都要有完整权重。

交接量先算清楚：VKV = 2nLhkvdhb。Qwen3-8B（36 层、8 个 KV 头、头维 128、BF16）每 token 144 KiB，8192 token 是 1.125 GiB，经 25 GB/s 链路 48.3 ms（启动 5 μs 只占万分之一）。MLA 存的是上投影之前的潜变量：V = nL(dc + dr)b，DeepSeek-V3（61 层、512 + 64）每 token 68.6 KiB，8192 token 只有 549 MiB，同一条链路 23.0 ms。

对比很说明问题：若把 V3 的 128 个头也展开保存，每 token 要 4.77 MiB，是紧凑表示的 71 倍；而紧凑 MLA 比只有 8 个 KV 头的 Qwen3-8B GQA 还小，只有它的 0.48 倍。

持续到达时链路还决定队列涨不涨：每秒 8 次 GQA 交接要 9.7 GB/s，16 次要 19.3 GB/s。100 GbE 单向 12.5 GB/s 能撑前者、撑不住后者（每秒积累 6.8 GB）；换成紧凑 MLA，两种到达率都只要 4.6 和 9.2 GB/s，同一个端口都能满足。

配比：同构分离不涨，异构分离涨 1.51 倍

原书 9.2.3–9.2.4 节

每请求的资源需求 dP = Lnew/rP，dD = (G−1)/rD。两种卡恰好强弱相反：A100 是 312 TFLOP/s + 2039 GB/s，H20 是 148 TFLOP/s + 4096 GB/s（算力不到一半，带宽约两倍）。按峰值 50% 的有效能力算 8192 输入 / 1025 输出的请求：

A100 80GB SXM95665800.8561.764
H20 SXM5 96GB453811661.8050.878

同构（八张 A100）分离不划算：共置每请求 0.856 + 1.764 = 2.62 GPU·s，八卡 3.05 请求/s；分离只能按整数分（3 张 P 给 3.50、5 张 D 给 2.83），上限 2.83，反而低 7%——每请求消耗的 GPU 秒没变，整数划分还让两池能力对不齐。同构分离换来的是延迟稳定（否则每 3.2 秒就要插一次 0.86 秒的 prefill，相当于错过 16 个 55 ms 的 decode 步）。而且同构还有更好的办法：分块捎带——A100 一步 decode 访存 55.1 ms、矩阵只要 4.2 ms，空闲算力够处理约 490 个 prefill token，8192 输入分 17 块捎带，首 token 约 0.94 秒而输出间隔不变，八卡上限升到 4.50 请求/s。

异构分离才是正解：μPD = min(μP, μD, Bnet/VKV)。四 A100 做 P（4.67）+ 四 H20 做 D（4.55），链路 20.7，取 4.55 请求/s，是共置 3.02 的 1.51 倍。角色对调（H20 做 P）只剩 2.22，不到一半。H20 一步 decode 的空闲算力只够 85 个 prefill token，分块捎带在异构上替代不了分离（理想捎带 4.17 < 4.55）。

配比一偏就掉：A100 从 P 调到 D，P 降到 3.50（整体被它限制）；H20 从 D 调到 P，D 降到 3.42。最优配比就是让两池能力接近相等。

负载一变配比也得变：前缀命中 6144 个 token 后，A100 的 P 能力从 1.17 涨到 4.20 请求/s，该把两张 A100 调去做 D（5.69 请求/s）；输出缩到 129 个 token 后 D 几乎不是瓶颈，三张 H20 要转去做 P（6.33，但共置已有 5.84，分离只多 8.5%）。三种请求的最佳 P 卡数分别是 4、2、7。

AF 分离：搬权重还是搬激活

原书 9.3 节

AF 在层内切：注意力产出隐状态，FFN 或选中的专家处理它再送回。MoE 特别适合——总权重大但每 token 只用一部分。两条路径：把权重搬给 GPU（花链路带宽换 GPU 算力），或者让 CPU 用本地权重算、只传激活（花 CPU 算力换少得多的流量）。选哪条，看同一个专家这批收到多少行。

原书用 KTransformers 的实验机算这笔账（两颗 Xeon 8452Y 各 36 核 + 1 TB DDR5，MLC 实测插槽内带宽 220 GB/s；PyTorch AVX-512 kernel 最高 1.8 TFLOP/s，KTransformers 的 AMX kernel 最高 21.3 TFLOP/s；A100 40GB PCIe 取峰值 50% 即 156 TFLOP/s、778 GB/s，PCIe 4.0 按 25 GB/s）。Qwen3-235B-A22B 一个专家 BF16 36 MiB。

八个热点专家各处理一个 token（权重 288 MiB）：CPU 路径读主存 1.37 ms + 激活交接 ≈ 1.46 ms；搬到 GPU 光传权重就 12.1 ms，加启动和计算约 12.5 ms。低复用时，避免搬大块权重比提高矩阵算力更值钱。行数多起来之后，天平才倒向 GPU。

调每个专家的行数，看两条路径谁快。

CPU 本地算 vs 搬到 GPU 算

CPU 路径 = max(权重读取 / 220 GB/s, 计算 / CPU 算力) + 激活交接；GPU 路径 = 权重经 PCIe 25 GB/s 搬入 + 计算 / 156 TFLOP/s。每专家 36 MiB、每行 6×4096×1536 FLOPs、激活 8 KiB/行。

大 EP：每卡专家越少，越不均衡

原书 9.4.1 节

最忙的卡决定一层什么时候算完：max(Fr/Cr, Wr/Br)。512 次分派放到八张 H100（按峰值 50% 即 494.7 TFLOP/s）：均分时每卡 2.42 GFLOPs、4.9 μs；八个热点专家都在一张卡上时该卡 19.3 GFLOPs、39.1 μs，八倍。集中路由把权重读取从 4.5 GiB 降到 288 MiB（利于读取受限），却把最忙卡的计算放大八倍（不利于计算受限）——先确定瓶颈，再决定追求复用还是分散。

EP 越大，同一个热点越被放大。n = 1024、k = 8、E = 256（8192 次分派、平均每专家 32 行），假设一个专家收到 128 行（4 倍）：EP8 每卡 32 个专家，热点卡只多 8%；EP32 每卡 8 个，多 36%；EP256 每卡就一个，热点卡 128 行是平均 32 行的 4 倍。小 EP 里热点被同卡的其他专家冲淡，大 EP 里它独占一张卡。

就算没有热点也一样：均匀随机选择时，固定种子模拟 1000 批，EP8 的最忙卡只比平均多 4%，EP256 多 52%。两种效应同源——EP 越大，每卡上能相互抵消的专家越少，要等的卡却越多。（DeepSeek 公开的 decode 部署用 EP144、每卡 2 个路由专家，正在曲线右端，所以它额外配了 32 个冗余专家按负载调副本。）

专家副本：跑几批才回本

原书 9.4.2–9.4.3 节

复制热点专家不改变 top-k 规则（只要权重相同、路由权重用对、合并无误）——改专家选择规则是改模型行为，两件事要分开评价。但副本占显存：每卡每层加一个 36 MiB 专家、94 层要 3384 MiB（3.30 GiB）；只给八个最挤的层各加一个，只要 288 MiB，差近 12 倍。

回本公式：Nmin = ⌊Tcopy/Δt⌋ + 1。原书例 9.6（八张 H100，一批 128 token 全选卡 0 上的八个热点专家，复制七个到卡 1–7 共 252 MiB）：卡 0 每批从 0.550 降到 0.309 ms，省 0.240 ms；经 NVLink（450 GB/s）复制 0.622 ms，第 3 批回本，持续 16 批净省 3.2 ms、64 批净省 14.8 ms。但原副本若在另一台服务器上，经 50 GB/s 网卡要 5.32 ms，得到第 23 批才回本——热点只持续 16 批反而净亏 1.5 ms。

CRAFT（SGLang v0.4.8、8 × p4de.24xlarge A100）按层分配副本预算，报告端到端吞吐平均 1.14 倍、最高 1.2 倍。原书提醒：这说明应把副本预算优先给收益大的层，不表示随便复制热点都有这个增幅。

还有两件实现层的事决定 MFU 为什么达不到峰值。补齐：八个本地专家收到 [32,16,8,4,2,1,1,0] 共 64 个有效行，每个非空专家补到 32 行要执行 224 行，全按最大值补要 256 行——3.5 到 4 倍。争用：均衡分布下 dispatch 0.336 + 计算 0.156 + combine 0.336 = 0.827 ms，分两个 micro-batch 流水理想情况 0.581 ms（省 0.246）；但如果网卡 DMA 和 GEMM 抢 HBM 让两次通信各慢 49%，流水就回到 0.827 ms——通信确实重叠了，整批却没变快（反过来专家计算要慢 3.1 倍才会抵消同样的收益）。

KV 分布：缓存键、多级存储与重启后的页

原书 9.5.1–9.5.3 节

“相同文本”不足以确定能复用：模型和 adapter 版本、token 序列、位置索引、状态格式、编码配置都要进缓存键——同样的 token 配不同 adapter 投影出的 K、V 就不同；同样的后缀接在不同前文后面，注意力看到的上下文也不同。滑动窗口和递推状态还要带上对应的 token 位置索引和更新时刻。

容量相加不等于共享。两个实例各有 4 GiB 私有主机缓存时，同一份 1.125 GiB 前缀两边各存一份共占 2.25 GiB，而且谁也用不了对方那份。接到同一个共享存储后端才能一份服务两边（但各自生成前可能还要取回本地）。还要分清目录（缓存标识 → 位置的映射）和对象（实际 KV 字节）：GPU 副本被淘汰时 CPU 副本可能还在，事件遗漏或延迟会让记录的位置不再可用。

重启后恢复有个很细但很重要的点：某请求读了 64 页（1024 token），但可连续接上的前缀只有 63 页，多读的那一页占 2.25 MiB 却没省下相应重算。原书的说法比"读 144 MiB 用上 142 MiB"更准确：读入 64 页、用上 63 页——限制发生在读取之后，磁盘读得再快也改变不了那末页要重算。

页面缺失时该等还是该重算：A100 上重算整段 8192 token 约 0.856 秒，如果为取回一个不可用对象已经等了 1 秒，这次等待就已经超过整段重算。原书的截断页实验里，无条件等待的请求 60 秒都没完成，允许放弃等待后靠重算拿到了结果。

路由：比的是完成时间，不是命中率

原书 9.5.4 节

有缓存的机器可能正忙，没缓存的可能先做完。所以比的是 Tfirst = max(Q, R) + C（Q 是 GPU 最早可执行时刻，R 是状态就绪时刻，C 是状态可用后的剩余计算）。依赖关系比字节数更要紧：Q = 80 ms、取回 60 ms、剩余计算 10 ms，并行就绪只要 90 ms；等 GPU 空闲再启动取回要 150 ms——计算量和传输量完全一样，差 60 ms。

例 9.7：请求带 8192 token 前缀 + 256 token 新输入。A 实例本地命中但要排 250 ms；B 实例只等 20 ms 但没缓存。按 A100 峰值 50%（156 TFLOP/s）：完整重算 8448 token 要 138.4 TFLOPs ≈ 887 ms，命中后只算 256 个新 token ≈ 30.9 ms。

八卡部署：能不能在 60 秒内排空

原书 9.7 节

例 9.8：四 A100 + 四 H20，每秒到达 3.5 个请求（8192 入 / 1025 出），从停止状态启动、10 秒就绪，要求持续处理新请求，并在开始启动后 60 秒内消除启动积压。

容量先过一遍：每请求 1024 次 decode 后 KV 覆盖 9216 token ≈ 1.27 GiB；H20 按 batch 32 驻留共 40.5 GiB + 1.125 GiB 接收缓冲 + 15.3 GiB 权重 ≈ 56.9 GiB，放得进 96 GB。A100 一侧只需同时保存正在计算和正在发送的两份，2.25 GiB。
