附录 A：高级提示技术

原书附录 A

原书先给了五条核心原则：清晰具体、简洁、善用动词（“总结以下文本”胜过“考虑总结一下”）、指令优于约束（说该做什么，比罗列不许做什么有效）、实验与迭代（温度、top-p、措辞都会影响结果，要记录）。基础技术是零样本、单样本、少样本：少样本通常给三到五个例子，例子要准确、多样；分类任务要打乱不同类别示例的顺序防止过拟合；长上下文模型还能做“多样本学习”，放几百个例子。

结构上有系统提示、角色提示、分隔符、上下文工程，以及结构化输出：要求 JSON，再用 Pydantic 解析校验，原书称之为在组件边界执行“解析而非验证”。推理类技术：零样本 / 少样本 CoT（答案放在推理之后；单一正确答案的任务把温度设为 0）；自一致性（高温度生成多条推理路径，多数投票，代价是多次调用）；后退提示（先问一般原则，如“好侦探故事的要素”，再做具体任务）；思维树。行动类：工具调用和 ReAct。高级类：APE / DSPy（用金标准集 + 目标函数，自动优化少样本示例和指令）、迭代改进、谨慎使用负面示例、类比、分解式认知、RAG、用户画像（描述受众，区别于给模型分配角色）、Google Gems、用 LLM 改进提示。

把例子和技术对上号。

易混辨析：角色提示 vs 用户画像；自一致性 vs 思维树

角色提示告诉模型“你是谁”（经验丰富的旅行博主）；用户画像告诉模型“听众是谁”（没有物理基础的高中生）。

自一致性是同一个问题独立跑多条完整推理，最后对答案投票；思维树是在一次推理过程中分叉、评估、回溯，探索中间步骤。前者在终点汇总，后者在过程中搜索。

附录 C：框架怎么选

原书附录 C

原书把框架按抽象层级排开。LangChain 的核心是 LCEL，用管道符把组件连成链，面向有向无环的线性流程：简单 RAG、摘要、数据提取。LangGraph 构建在 LangChain 之上，把工作流定义成节点 + 边的图，支持循环，显式管理持久状态：多智能体、计划—执行—回看、等待人工输入。选择口诀：A → B → C 不回头就用 LangChain；要推理、规划、循环、反思就用 LangGraph。

Google ADK 抽象掉了大部分底层建图工作，提供 SequentialAgent、ParallelAgent 这类预置模式，状态和会话管理更隐式；原书比喻 LangGraph 是设计单个机器人复杂接线的工具箱，ADK 是生产一整支协同机器人舰队的装配线。CrewAI 用智能体（角色、目标、背景故事）、任务、团队三个概念模拟人类团队，流程是顺序或层级型，开发者“设计团队章程”而不是写状态机。其他框架：AutoGen（对话驱动，路径较难预测）、LlamaIndex（数据框架，擅长摄取和检索）、Haystack（生产级搜索管道）、MetaGPT（按 SOP 模拟软件公司）、SuperAGI（全生命周期管理）、Semantic Kernel（插件 + 规划器，适合 .NET / Python 企业代码）、Strands Agents（AWS 轻量 SDK，原生 MCP）。

按需求选框架。

附录 E：命令行里的四个编码智能体

原书附录 E

原书强调，这几个工具的很多用例彼此都能做，区别在于结果的质量、效率和精细度。Claude Code：对项目架构有全局理解，像结对编程一样先说明计划再执行，适合大规模重构（例如把会话 cookie 认证改成无状态 JWT）；深度集成 Git，通过 MCP 扩展自定义工具。Gemini CLI：开源，Gemini 2.5 Pro、超大上下文、多模态（看截图写组件），免费额度慷慨，内置 Google Cloud 集成。Aider：开源、与模型无关，直接改文件、跑测试、每个成功变更自动提交，适合 TDD 和精确修 bug。GitHub Copilot CLI：深度集成 GitHub，可以被分配 issue，自动建分支、写代码、提 PR。

评测方面，Terminal-Bench 用来衡量智能体在命令行中完成复杂任务的能力：初版 Terminal-Bench-Core-v0 有 80 个人工精选任务，用一个极简智能体 Terminus 作为不同模型的标准测试台。

附录 G：人类主导的编码智能体团队

原书附录 G

原书认为 vibe 编码适合越过“空白页”、探索陌生 API、快速出原型，但构建稳健、可维护的软件需要更结构化的方式。它引用了 2025 年初 Sundar Pichai 的说法：Google 内部超过 30% 的新代码由 Gemini 辅助或生成。附录 G 的框架有三条原则：人类主导编排（人决定调用哪个智能体、提供上下文、对所有输出有最终裁决权）、上下文至上（人工准备完整的“任务简报”：相关代码、外部文档、目标与规范，避免黑盒式自动检索）、直接访问前沿模型（避免经过会截断上下文的中间平台）。

团队里的专门智能体其实是同一个前沿模型配不同的角色提示：脚手架（写新代码）、测试工程师、文档编写、优化 / 重构顾问、流程 / 质量监督（先做初步批判，再对自己的批判做“深度反思”，过滤琐碎意见，给人一份高层可执行摘要）。落地清单有四条：至少两家前沿模型的 API（便于对比、防单点）、本地上下文编排器（用 context.toml 之类的配置声明哪些文件进提示）、在仓库里建 /prompts 目录把提示当代码做版本管理、用 pre-commit 钩子自动触发审查智能体。

按原书的框架给每件事找负责人。

附录 B：从操作界面到感知真实世界

原书附录 B

智能体—计算机界面（ACI）让 AI 像人一样通过 GUI 的“前门”操作软件，而不必依赖 API。四个阶段：视觉感知（截屏）→ GUI 元素识别（分清可点的按钮和静态横幅）→ 上下文理解（放大镜图标代表搜索）→ 动态执行与响应（控制鼠标键盘，持续观察加载状态、弹窗、报错）。代表产品：ChatGPT Operator、Google Project Mariner（Chrome 里的研究原型）、Anthropic 计算机使用、开源的 Browser Use（通过 DOM 控制浏览器）。

再往外是真实世界：Project Astra（通过摄像头和麦克风理解环境）、Gemini Live（低延迟语音、可打断、可共享摄像头和屏幕）、GPT-4o 与实时 API、ChatGPT Agent（浏览、执行代码、操作第三方应用，敏感操作需用户明确授权）、微软 Seeing AI（为视障用户描述环境）。附录 B 末尾还介绍了 vibe 编码：对话式提示、迭代精炼、AI 作为创意伙伴、关注“目标”而非“方法”、可选记忆库。

    附录 D、F 与常见问题

    原书附录 D、F，FAQ

    附录 D（AgentSpace）：Google 面向“智能体驱动型企业”的平台，对文档、邮件、数据库做统一搜索，构建企业知识图谱，提供无代码的 Agent Designer，可连接 Calendar、Gmail、Workday、Jira、Outlook、ServiceNow，智能体之间用 A2A 协作，带基于角色的访问控制和加密。

    附录 F（推理引擎内部）：作者向 Gemini、ChatGPT、Grok、Kimi、Claude、DeepSeek 提了同一个问题“请逐步解释你是如何推理的”，把回答原样列出。值得注意的是 Claude 的开场白：它说自己对自身运作的认知有限，就像人能描述思维过程却无法追踪每个神经突触。读这一附录时要记住：这些是模型的自我描述，不等于对内部机制的实证。

    FAQ 里有几条正文没展开、但很实用的区分：工具 vs 技能（工具是外部资源；技能是结合工具和推理的更集成的能力，如“订机票”）；反思的两种形式“工作自查”和“内部评审”；HITL 的四个典型介入点：计划审批、工具授权、歧义消解、最终输出审核；为非确定性系统写测试的办法：检查响应是否包含关键信息、是否以正确参数调用了某工具，并在测试环境用模拟工具；以及提示泄漏：系统提示内容意外出现在给用户的回答里，可以把推理和最终答案生成分开来防范。

    FAQ 小测。

    回扣开头的三个问题

    先自己答，再点开
    1. 指令优于约束，那何时用负面示例？自一致性 vs 思维树？

    一般优先告诉模型该做什么；需要明确边界、防止某类特定错误时，可以谨慎加入负面示例（原书例子：列巴黎景点但不要埃菲尔铁塔）。自一致性是多条完整推理后投票；思维树是推理过程中分叉、评估、回溯。

    2. LangChain vs LangGraph？ADK 与 CrewAI 的抽象层级？

    线性、无回环用 LangChain（LCEL）；需要循环、状态、规划反思用 LangGraph。ADK 提供预置的多智能体模式、隐式状态管理，是面向生产的“装配线”；CrewAI 用角色、任务、团队来模拟人类团队协作。

    3. 人类主导的编码团队里，人和智能体各负责什么？

    人：定目标和架构、准备完整任务简报、选择调用哪个智能体、对所有输出做最终裁决。智能体：脚手架编码、测试、文档、优化建议、质量审查（批判 + 反思摘要）。
