工具调用：模型只出主意，框架去执行

原书第 5 章

LLM 的知识是静态的，也不能自己做事。工具使用模式通常借助函数调用（Function Calling）实现，原书拆成六步：工具定义（名称、用途、参数及类型）→ LLM 决策（要不要用、用哪个）→ 生成调用（一个指定工具名和参数的 JSON）→ 工具执行（由框架或编排层拦截并真正执行）→ 观察结果 → LLM 处理（据结果回答，或决定下一步，可能再调另一个工具）。要点在第 4 步：执行的不是模型，是框架。

原书建议把“函数调用”理解得更宽，叫工具调用：工具可以是普通函数、复杂 API、数据库查询，甚至是发给另一个专门智能体的指令。这样看，主智能体就是一个在数字资源和其他智能体之间做编排的角色。框架方面，LangChain 用 @tool 装饰器定义工具，ADK 自带 Google 搜索、代码执行、Vertex AI 搜索等预置工具。

走一遍原书金融智能体的例子：查股价，再算利润（价格为示意）。

模式卡 · 工具使用

问题

做法

MCP：通用插座，但插座不保证电器好用

原书第 10 章

原书用了一个比喻：函数调用像给 AI 一套特定的扳手和螺丝刀，适合任务固定的车间；MCP（Model Context Protocol）像标准化电源插座，本身不提供工具，但任何厂商的兼容工具都能插上用。函数调用是专有的、一对一的，模型被明确告知可用哪些工具；MCP 是开放协议、客户端—服务器架构，客户端可以动态查询服务器有哪些能力，服务器可被任何兼容应用复用。

MCP 服务器暴露三类东西：资源（静态数据，如 PDF、数据库记录）、工具（执行操作的函数，如发邮件、查 API）、提示（指导模型如何与资源或工具交互的模板）。本地用基于 STDIO 的 JSON-RPC，远程用可流式 HTTP 和 SSE。交互流程：发现 → 模型制定请求 → 客户端发标准化调用 → 服务器鉴权、校验、执行 → 返回标准化响应、更新上下文。

原书这一章最值得记的是两条提醒。其一，MCP 只是“智能体接口”契约，效果取决于底下的 API：把一个只能逐条取完整工单的老 API 原样包一层，智能体要总结高优先级工单时会又慢又不准，应该先给 API 加上过滤、排序这类确定性功能。原书原话的意思是：智能体不能神奇地替代确定性工作流，反而常常需要更强的确定性支持。其二，MCP 不保证数据格式对智能体友好：文档库返回 PDF 而智能体解析不了，接上也没用，先提供 Markdown 文本版更好。

先分清三类原语，再判断几个设计决策。

RAG 基础：先查资料，再回答

原书第 14 章

RAG（检索增强生成）的流程：查询不直接发给 LLM，而是先在外部知识库里做语义搜索，取出最相关的“块”，把它们增强进原始提示，再交给 LLM。原书把它概括为把模型从“闭卷”变成“开卷”。好处有四个：用上最新信息、减少幻觉、用上企业私有知识、能给出引用。

几个核心概念：嵌入是文本的向量表示，含义相近的文本在向量空间里靠得近。原书举了二维的例子：cat 在 (2, 3)，kitten 在 (2.1, 3.1)，car 远在 (8, 1)；实际维度是几百到几千。分块是把 50 页手册按章节、段落切开，让“故障排除”和“安装指南”成为不同的块。检索方法有向量搜索（按语义）、BM25（按词频，不懂语义）和二者结合的混合搜索。向量存在专门的向量数据库里，用 HNSW 这类算法在数百万向量中找最近邻。

原书也列了 RAG 的难处：答案散落在多个块或多个文档里时，检索器可能凑不全；检索到无关块会引入噪声；来源互相矛盾时难以综合；知识库要预处理、持续更新；整体增加延迟、成本和 token。

模式卡 · 知识检索（RAG）

Knowledge Retrieval / Retrieval-Augmented Generation

问题
模型知识静态，不含实时信息和私有领域数据，回答可能过时或缺乏上下文。
做法
检索相关片段 → 附加进提示 → 生成有依据、可引用的回答。
何时用
基于特定、最新或专有信息回答：内部文档问答、客服机器人、需要引用的应用。
代价
知识库预处理与更新成本；延迟、token 增加；碎片化与矛盾信息难处理。
变体
GraphRAG：用知识图谱的实体关系跨文档综合，适合金融关联分析、基因—疾病研究；但建图维护成本高、更不灵活、延迟更高。Agentic RAG：见下一节。

Agentic RAG：检索结果先过一道“守门人”

原书第 14 章

标准 RAG 被动地接受检索结果。Agentic RAG 加了一个推理和决策层：智能体主动质疑检索结果的质量、相关性和完整性。原书给了四个场景，正好对应四种能力：来源验证（按元数据挑出最新、最权威的文档）、协调冲突（两个数字打架时优先更可靠的来源）、多步分解（把比较类问题拆成多个子查询再综合）、发现缺口并用工具（内部库没有就调网络搜索）。

代价同样明确：复杂度、成本和延迟显著增加；而且智能体本身可能成为新的错误来源：推理出错时会陷入无用循环、误解任务，或错误地丢掉相关信息。

      A2A：智能体之间的“名片”和“工单”

      原书第 15 章

      A2A（Agent2Agent）是 Google 发起的开放协议，让用 LangGraph、CrewAI、ADK 等不同框架做的智能体能够协作。三类参与者：用户、A2A 客户端（代表用户发请求的应用或智能体）、A2A 服务器（远程智能体，以“不透明”方式运行，客户端不需要知道其内部）。

      Agent 卡片是智能体的数字身份，一个 JSON：名称、端点 URL、版本、能力（是否支持流式、推送通知）、技能、默认输入输出模式、认证要求。发现卡片有三种方式：放在标准路径 /.well-known/agent.json、发布到精选注册表（适合企业集中管控）、直接配置（紧耦合的私有系统）。

      通信围绕异步任务组织：每个任务有唯一 ID，经历已提交、工作中、已完成等状态（还有需要补充信息的 input-required）；消息由属性（元数据）和若干部分（文本、文件、JSON）组成；任务产出叫工件，可以流式返回；contextId 把相关任务串起来保持上下文。全部走 HTTP(S) + JSON-RPC 2.0。安全上靠双向 TLS、审计日志、卡片里声明认证要求、凭据放在 HTTP 头里。

      四者分工：谁连谁

      原书第 5、10、14、15 章

      原书第 15 章明确说 A2A 是 MCP 的补充：MCP 管智能体和外部数据、工具之间的交互，A2A 管智能体和智能体之间的发现与委托。把这一篇的四个模式放在一张表里：

      连接的两端解决什么关键概念
      工具使用模型 ↔ 外部函数 / API让模型能行动、取实时数据工具定义、结构化调用、框架执行
      MCP应用（客户端）↔ 工具服务器工具接入的标准化、动态发现、复用资源 / 工具 / 提示；STDIO、HTTP + SSE
      RAG模型 ↔ 知识库让回答有依据、可引用嵌入、分块、向量库、混合检索
      A2A智能体 ↔ 智能体跨框架委托任务、协作Agent 卡片、异步任务、四种交互机制

      回扣开头的三个问题

      先自己答，再点开
      1. 工具调用的六步里，真正执行工具的是谁？

      是智能体框架 / 编排层。模型只负责决定要不要用、用哪个，并生成包含工具名和参数的结构化调用。

      2. 原书对 MCP 提了哪两条设计提醒？

      一是底层 API 要对智能体友好：老 API 原样包装（例如只能逐条取工单）会又慢又不准，应先补过滤、排序等确定性能力；二是数据格式要可读：返回 PDF 而智能体解析不了就没用，先提供 Markdown 文本版。

      3. Agentic RAG 比标准 RAG 多了哪四种能力？代价是什么？

      来源验证、协调冲突、多步分解、发现缺口并调用外部工具。代价是复杂度、成本、延迟上升，而且智能体本身可能成为新的错误来源（陷入循环、误解任务、错误丢弃信息）。
