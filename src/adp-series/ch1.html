提示词链：一次只让模型做一件事

原书第 1 章

把“分析市场研究报告、总结发现、找出趋势、再起草一封邮件”塞进一个提示词，模型很可能把总结写得不错，却漏掉数据或邮件。原书列了单个复杂提示词的五种典型毛病：指令忽略、上下文偏离（忘了最初的上下文）、错误传播（早期错误被放大）、上下文窗口不够、以及认知负荷带来的幻觉。

提示词链（Prompt Chaining，也叫管道模式）的做法是分而治之：第一步只总结，第二步拿摘要找出三个趋势和支撑数据，第三步拿趋势写邮件。每一步还可以换一个角色（市场分析师、贸易分析师、文档撰写者）。原书特别强调两点：一是步骤之间传递的数据要用 JSON、XML 这类结构化格式，否则下一步拿到含糊的输入就会出错；二是链的好处不只是拆分，还能在两次模型调用之间插入确定性逻辑：校验输出、条件分支、调用外部工具。

上下文工程：比措辞更重要的是给模型看什么

原书第 1 章末节

原书在第 1 章末尾插了一节上下文工程（Context Engineering），把它定义为：在模型生成 token 之前，系统地设计、构建并提供完整信息环境的学科。它的主张是，输出质量较少取决于模型架构本身，而更多取决于上下文有多丰富。传统提示工程主要优化用户当前那句话的措辞；上下文工程把范围扩展到多层信息：系统提示词（“你是一名技术作家，语气必须正式精确”）、检索到的文档、工具输出（查日历得到的空闲时间），以及隐式数据（用户身份、交互历史、环境状态）。

原书的例子：一个做过上下文工程的智能体在回复会议邀请前，会先整合日历空闲（工具输出）、和收件人的工作关系（隐式数据）、上次会议的笔记（检索文档）。“工程”二字指的是要建管道在运行时取数、转换，并用反馈循环持续改进上下文质量，比如用 Vertex AI 提示优化器这类工具，按样本输入和评估指标自动调整系统指令。

路由：先判断是什么，再决定交给谁

原书第 2 章

提示词链是一条固定的路。真实系统常要按情况选路：客服智能体先给请求分类，“查订单”交给能查订单库的子智能体，“产品信息”去搜目录，“技术支持”去查排障指南或升级给人工，意图不清就转到澄清环节。这种把控制流导向不同函数、工具或子流程的条件逻辑，就是路由。

原书列了四种实现。基于 LLM：让模型只输出一个类别名，系统据此分发。基于嵌入：把查询转成向量，和每条路由的代表向量比相似度，适合按语义而不是关键词分流。基于规则：if-else、关键词、正则，更快、更确定，但对细微或新颖的说法不够灵活。基于机器学习分类器：在小规模标注数据上做监督微调的判别模型，路由逻辑编码在权重里；LLM 可以帮忙造训练数据，但不参与实时决策。

路由的位置也不只在入口：可以在开头给主任务分类，在链的中间决定下一步，也可以在子程序里从一组工具中挑一个。LangGraph 用状态图显式定义节点间的跳转；Google ADK 则多半把能力定义成工具或子智能体，让框架根据模型判断自动委托。

模式卡 · 路由

Routing

问题
线性流程无法应对多样的输入，没有机制为不同情况选择合适的工具或子流程。
做法
先分析输入（意图、状态），再把控制流导向最合适的工具、函数或子智能体。
何时用
智能体要在多个工作流、工具或子智能体之间做选择，典型是客服机器人区分销售、技术支持、账户问题。
四种实现
LLM（灵活）· 嵌入相似度（语义）· 规则（快、确定、脆）· 微调分类器（权重里编码路由）。
相关
多智能体里的“协调者”本质是路由（第 6 篇）；按成本挑模型的路由器见“资源感知优化”（第 6 篇）。

并行化：不互相等的，就别排队

原书第 3 章

研究一个主题，顺序做法是：搜 A、总结 A、搜 B、总结 B、再综合。并行做法是：A、B 同时搜，都回来后同时总结，最后综合（综合这一步仍要等前面全部完成）。核心是找出工作流里不依赖彼此输出的部分。等待外部 API、数据库这类 I/O 时收益最明显，因为可以一次发出多个请求。

原书的用例很广：公司调研时同时查新闻、股价、社媒和内部库；对一批反馈同时做情感分析、关键词抽取、分类、紧急识别；旅行规划同时查航班、酒店、活动、餐厅；同时生成三个标题做 A/B 选择。框架层面，LangChain 用 RunnableParallel 把多个链放进一个字典并发执行；Google ADK 有 ParallelAgent，常和 SequentialAgent 组合成“先并行研究、再合并”的流水线。

两个容易忽略的提醒：原书指出 Python 的 asyncio 提供的是并发而不是真并行，单线程事件循环在等待网络时切换任务，受 GIL 限制；以及并发会给设计、调试和日志带来显著的复杂度和成本。

模式卡 · 并行化

Parallelization

问题
纯顺序执行时，总耗时等于所有子任务之和；外部 I/O 等待成为主要瓶颈。
做法
识别互不依赖的子任务，并发执行，在汇聚点等全部完成后再进入下一步。
何时用
需要从多个 API 取数、处理不同数据块、生成多个片段供后续综合时。
代价
设计、调试、系统日志都更复杂，成本也更高。
实现
LangChain RunnableParallel；LangGraph 从一个节点分出多个分支；ADK ParallelAgent + SequentialAgent。

三块积木组合起来

原书第 1–3 章

原书在第 1 章就举了组合的例子：自动研究智能体先检索大量文章，从每篇里提取要点可以并行；但提取完之后，整合、起草、审校这几步彼此依赖，必须顺序。所以复杂操作常常是“并行做独立的数据收集，链式做有依赖的综合与打磨”。第 3 章结尾也说，把并行（并发）、链（顺序）和路由（条件）结合起来，才能搭出高效的复杂系统。

易混辨析：提示词链 vs 规划

提示词链的步骤是开发者事先写死的；规划（第 2 篇）的步骤由模型按请求动态生成，遇到障碍还能改。原书第 6 章的判断标准同样适用于这里：方法已知就用固定的链，方法需要被发现才用规划。

回扣开头的三个问题

先自己答，再点开
1. 单个复杂提示词有哪五种典型毛病？提示词链除了拆分，还带来了什么能力？

指令忽略、上下文偏离、错误传播、上下文窗口不足、幻觉。除了拆分，链还允许在两次模型调用之间插入确定性逻辑：校验输出、条件分支、调用工具；步骤间用 JSON / XML 结构化传递数据。

2. 路由有哪四种实现？规则路由的弱点是什么？

基于 LLM、基于嵌入、基于规则、基于监督微调的分类器。规则路由快且确定，但对细微或新颖的说法不够灵活，换个说法就可能认不出来。

3. 并行化在什么情况下收益最大？Python 的 asyncio 算真并行吗？

等待外部 API、数据库等 I/O 时收益最大。asyncio 是单线程事件循环上的并发，不是真并行，受 GIL 限制；并发还会让设计、调试、日志更复杂。
