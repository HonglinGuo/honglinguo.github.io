把三个脚本，收拢成一个框架

第四篇的三个智能体各写各的：各有一个 LLM 客户端、一套工具管理、一份历史记录。第七章把它们收拢成一个小框架 HelloAgents：底层是统一的 LLM 接口、消息、配置和 Agent 基类，中间是四种范式的 Agent，旁边是一套工具系统。这一篇按“框架怎么搭起来”的顺序走：先看设计理念和目录，再看 LLM 怎么自动认出服务商，然后是三个基础类，最后是 Agent 和工具。后面几篇的记忆、RAG、上下文、协议，都是往这个框架里加工具。

本系列是开源教程《Hello-Agents：从零开始构建智能体》（Datawhale 社区编写的开源教程，CC BY-NC-SA 4.0 协议；本笔记依据 2026 年 10 月 14 日的仓库版本）的学习笔记。原书十六章，按“概念 → 手写范式 → 平台与框架 → 自研框架 → 记忆、上下文、协议、训练、评估 → 综合案例”展开，代码量很大。这里重排成十三篇，用自己的话重讲：代码只保留能看清机制的骨架，做成可以逐行走读、可以填空回忆的互动；每篇末尾配原书面试题清单里的相关题目做口述演练。每节标出对应的原书章节，演示数值标“示意”。笔记同样按 CC BY-NC-SA 4.0 共享。

为什么自建，按什么原则建

原书 7.1.1–7.1.2 节

原书先数落了现有框架的四个问题：过度抽象（LangChain 完成一个简单任务也要先懂 Chain、Agent、Tool、Memory、Retriever 十几个概念）、迭代太快不稳定（升级后代码跑不了）、黑盒化（核心逻辑封得太严，难以深度定制，社区不活跃时问题没人管）、依赖复杂（包大，易和别的项目冲突）。自建的价值则是从使用者跃迁为构建者：真正理解原理、完全掌控每一行、锻炼模块化与接口设计能力；何况金融、医疗等垂直领域本来就常要二次开发。

HelloAgents 的四条设计理念：轻量与教学友好（核心代码按章节组织，除 OpenAI SDK 和几个基础库外不引重依赖，出问题能直接读到源码）；基于标准 API（OpenAI 接口已是事实标准，不另造抽象，迁移和集成成本低）；渐进式学习（每章代码对应一个可 pip 安装的历史版本，比如本章对应 0.1.1）；万物皆为工具（除了 Agent 本身，Memory、RAG、RL、MCP 都抽象成工具，学习者回到“智能体调用工具”这一个核心逻辑上）。

“万物皆为工具”是这本书后半部分的主线，先翻牌想清楚它的利弊（原书习题 1）。

整体架构：三层目录

原书 7.1.3 节

框架遵循“分层解耦、职责单一、接口统一”：core/ 是核心层（Agent 基类、统一 LLM 接口、消息、配置、异常）；agents/ 是实现层（Simple、ReAct、Reflection、PlanAndSolve 四种 Agent）；tools/ 是工具层（工具基类、注册表、工具链、异步执行器和内置的计算、搜索工具）。依赖方向是单向的：agents 依赖 core 和 tools，core 不依赖任何上层。

点每个文件，看它负责什么、在本篇哪一节讲。

统一 LLM 接口：自动认出服务商

原书 7.2 节

第四篇的 HelloAgentsLLM 只认一组 LLM_* 环境变量。框架版做了三件事：多服务商（ModelScope、OpenAI、智谱等，新服务商通过继承并重写初始化逻辑加入，think 等方法直接继承）；本地模型（vLLM 和 Ollama 都提供兼容 OpenAI 的接口，原书示例用 vLLM 起 Qwen1.5-0.5B-Chat 在 8000 端口，Ollama 默认 11434 端口）；自动检测，遵循“约定优于配置”。

自动检测由两个方法配合：_auto_detect_provider 推断服务商，_resolve_credentials 按服务商去找对应的密钥变量并补上默认 base_url。推断按优先级：① 特定服务商的环境变量（MODELSCOPE_API_KEY、OPENAI_API_KEY、ZHIPU_API_KEY……有一个就定了，最可靠）；② 解析 LLM_BASE_URL（域名匹配云服务商；localhost 或 127.0.0.1 再看端口，11434 是 Ollama、8000 是 vLLM，其他算 local）；③ 分析 LLM_API_KEY 的格式（如 ms- 前缀是 ModelScope，可能有歧义，只作辅助）；都不行就返回 auto，用通用配置。

勾选环境变量、填 URL 和密钥，看检测逻辑一条条怎么走。试试原书习题 2：同时设置 OPENAI_API_KEY 和 localhost:11434。

    三个基础类：Message、Config、Agent

    原书 7.3 节

    Message 用 Pydantic 的 BaseModel 定义，role 用 Literal["user", "assistant", "system", "tool"] 限死四种取值，正好对应 OpenAI 规范；除了 content 和 role 还带 timestamp 和 metadata，给日志和扩展留余地；to_dict() 只输出 role 和 content 交给 API。原书概括为“对内丰富，对外兼容”。

    Config 把散落在代码里的参数集中起来（默认模型、温度、max_tokens、debug、日志级别、最大历史长度），每项都有默认值保证零配置可用，from_env() 允许用环境变量覆盖，换部署环境不改代码。

    Agent 是继承 ABC 的抽象基类：构造函数明确核心依赖（名称、LLM、系统提示词、配置），自带 _history 和 add_message、clear_history、get_history 这些通用方法，最重要的是 @abstractmethod run()，强制每个子类都有统一的执行入口。这就是“接口统一”的落点：调用方只认 agent.run(text)，不关心背后是 ReAct 还是 Reflection。

    合上书，补全 Agent 基类。

    Agent 的框架化

    原书 7.4 节

    SimpleAgent 是最基础的对话智能体，也是理解框架的入口。它把消息拼成 OpenAI 格式（系统提示词 + 历史 + 当前输入）；没工具就直接 llm.invoke；有工具就在系统提示词后面追加“可用工具”和调用格式 [TOOL_CALL:工具名:参数]，然后进入 _run_with_tools 循环：调模型 → 正则抠出所有工具调用 → 执行 → 把去掉标记的回答作为 assistant 消息、把工具结果作为一条 user 消息追加 → 再调模型，直到不再出现工具调用或达到 max_tool_iterations。另外提供 stream_run 流式输出和 add_tool、list_tools 等便利方法。

    ReActAgent 核心逻辑和第四篇一样，改进有三：工具来自统一的 ToolRegistry（而不是专用的 ToolExecutor）；提示词更严谨（强调每次只执行一步、只有确信信息足够才 Finish、工具信息不够就换参数再查）；可以用 custom_prompt 整体替换模板，跑满步数也会返回一句明确的失败信息并记入历史。Reflection 和 Plan-and-Solve 的默认提示词改成了通用版本（不再只针对代码或数学），通过 custom_prompts 字典按角色（initial / reflect / refine，或 planner / executor）定制。

    0.2.8 之后加了 FunctionCallAgent：不再靠提示词约束格式，而是把工具转成 OpenAI 函数 schema，调用 chat.completions.create(tools=…, tool_choice=…)，由模型原生返回结构化的函数名和 JSON 参数，框架只需解析 JSON 并做类型转换。原书说这比提示词约束的方式更鲁棒。

    工具调用协议的四次演进

    原书第 1、4、7 章对照

    这本书前七章里，“模型怎么告诉程序要调哪个工具”换了四种写法，放在一起看最清楚。前三种都是文本协议：模型写一段约定格式的字符串，宿主用正则抠出来；第四种是原生 Function Calling：工具以 JSON Schema 交给 API，模型返回结构化的调用对象。从前到后，宿主的解析工作越来越少，格式出错的机会也越来越少，但对模型和服务商的要求越来越高。

    先想一想右列，再翻开。

    易混辨析：Function Calling 让模型执行了函数吗

    没有。Function Calling 只是把模型的输出从“一行约定格式的文本”换成了“结构化的 tool_calls 对象”（函数名 + JSON 参数）。执行仍然是你的代码：解析参数、调用函数、把结果作为 role 为 tool 的消息追加回去，再请模型继续。和第一篇说的“Observation 是你的代码写的”完全一致。

    工具系统

    原书 7.5 节

    Tool 基类只有 name、description 和两个抽象方法：run(parameters: dict) → str（统一执行接口）和 get_parameters() → List[ToolParameter]（自描述：我需要哪些参数）。ToolParameter 记录参数名、类型、描述、是否必需、默认值。有了自描述，就能自动生成文档、做参数校验，以及用 to_openai_schema() 把工具转成 Function Calling 需要的 JSON Schema（必需参数进 required 列表；OpenAI schema 不支持 default 字段，所以默认值写进描述；数组类型补 items）。

    ToolRegistry 是管理中枢，两种注册方式：register_tool(Tool) 适合复杂工具，有完整参数定义；register_function(name, description, func) 适合简单函数，快速接入。get_tools_description() 生成塞进提示词的工具清单，execute_tool() 按名字执行。

    两个示例工具各有一个值得记的工程细节。计算器不用 eval，而是用 ast.parse 解析表达式，只认常数、四则运算和白名单函数（sqrt、pi），其他节点一律拒绝，避免模型生成的“表达式”执行任意代码。多源搜索的 hybrid 模式：优先 Tavily（为 AI 优化的搜索），失败降级到 SerpApi，都不可用就明确提示配置哪个密钥，结果统一格式化成“AI 摘要 + 前三条标题、摘录、来源”。原书还给了工具链（多个工具顺序执行，前一步输出按模板填进后一步输入）和异步执行器（线程池并行跑多个工具）。

    面试演练

    题目取自原书 Extra01 与第 7 章习题

    LLM 是如何学会调用外部 API 或工具的？请从 Function Calling 的角度解释。Extra01 · Agent 第 5 题

    • 训练侧：模型在包含“工具描述 + 何时调用 + 调用参数”的数据上做指令微调，学会在需要时输出结构化的调用而不是直接回答。
    • 接口侧：开发者在请求里用 JSON Schema 描述工具（名称、描述、参数类型与必需项）；模型返回 tool_calls（函数名 + JSON 参数）或普通文本；tool_choice 控制是否强制调用。
    • 执行侧：宿主解析参数、执行函数，把结果作为 role=tool 的消息追加，再请模型继续，直至给出最终回答。模型本身不执行任何东西。
    • 对比文本协议：不用正则、格式更稳，但依赖模型与服务商支持；描述写得好坏仍然决定选得对不对。

    “万物皆为工具”的设计有什么优势和局限？原书第 7 章习题 1

    • 优势：概念统一，学一个“调用工具”就够；Agent 主循环不用为记忆、检索、协议各写一套分支；新能力即插即用，按需加载。
    • 局限：有些能力不该由模型“决定是否调用”，比如每轮都要注入的上下文、必须执行的安全检查、对话结束后的记忆写入，做成工具可能被模型漏调；工具多了会挤占上下文、增加选错概率；跨工具的状态共享不自然。
    • 折中：确定性的步骤放在框架的固定流程里（钩子、中间件），需要模型判断的才做成工具。

    Agent 基类公开 run、把具体逻辑留给抽象方法，这是什么设计模式？配置为什么常做成单例？原书第 7 章习题 3

    • 模板方法模式：基类在公开方法里固定流程骨架（记录历史、计时、异常处理），把可变步骤交给子类实现的抽象方法；保证所有 Agent 行为一致，子类只关心核心逻辑。
    • 单例：全局只有一份配置实例，各模块读到的设置一致；避免重复读取环境变量，也避免某处修改后其他地方仍用旧值。代价是全局状态不利于测试，可用依赖注入替代。
    • Pydantic 的好处：类型校验、默认值、序列化，错误在构造时就暴露。

    动手练（原书习题 4、6）

    1. 给 ReflectionAgent 加“质量评分”：分数达标就提前停。
      思路

      反思提示词要求输出 JSON：{"score": 1–10, "feedback": "..."}，解析失败时按 0 分处理并记录；score ≥ 阈值直接返回当前版本。比找“无需改进”这几个字可靠，也能画出每轮分数曲线。

    2. 实现一个 Tree-of-Thought Agent。
      思路

      继承 Agent，run 里维护一个候选队列：每步让模型对当前状态生成 k 个下一步思路，再让模型（或规则）给每个思路打分，保留前 b 个继续扩展（束搜索），到达深度或得到满意解时返回。注意成本是 k × b × 深度次调用。

    回扣开头的三个问题

    先自己答，再点开
    1. 四条设计理念？万物皆工具的利弊？

    轻量与教学友好、基于标准 OpenAI API、渐进式学习（每章一个可安装版本）、万物皆为工具（Memory、RAG、RL、MCP 都是工具）。好处是概念统一、主循环简单、能力即插即用；代价是必须执行的步骤可能被模型漏调、工具多了挤占上下文和增加误选，因此确定性的步骤更适合放进框架的固定流程。

    2. 自动检测的优先级？

    先看特定服务商的环境变量（MODELSCOPE_API_KEY、OPENAI_API_KEY、ZHIPU_API_KEY……），有就直接确定；再解析 LLM_BASE_URL（域名识别云服务商，localhost 加端口识别 Ollama 11434、vLLM 8000、其他 local）；再看 LLM_API_KEY 的格式（如 ms- 前缀）；都不行返回 auto。之后 _resolve_credentials 按服务商找密钥并补默认 base_url。所以同时设了 OPENAI_API_KEY 和 localhost:11434 时会判成 openai。

    3. 协议怎么演进？工具怎么变成 schema？

    第 1 章 Action 写 Python 调用风格 get_weather(city="北京")；第 4 章 Search[输入]；第 7 章 SimpleAgent 用 [TOOL_CALL:工具名:参数]，三者都靠正则解析；FunctionCallAgent 改用原生 Function Calling，模型返回结构化 tool_calls。to_openai_schema() 遍历 ToolParameter：每个参数生成 type 与 description，required 的进 required 列表，默认值写进描述（schema 不支持 default），数组补 items，外层包成 {type: function, function: {name, description, parameters}}。
