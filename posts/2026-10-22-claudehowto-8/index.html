插件不是新能力，是一个包

前面几篇讲的命令、Skills、Subagents、MCP、Hooks，各自都是复制几个文件就能用。问题在于团队里二十个人各自复制，版本就乱了。插件把这些组件装进一个带清单的目录，一条命令安装、可以版本化、可以通过 marketplace 分发。所以学插件的重点不是“它能做什么”，而是“怎么组织、怎么装、怎么让团队用上同一套”。原教程目录里带了三个完整的示例插件：pr-review、devops-automation、documentation。

本系列是开源教程《Claude How To》（luongnv89 与社区贡献者编写，MIT 协议；本笔记依据 2026 年 10 月 20 日的仓库版本（commit 188f468），原文标注对应 Claude Code v2.1.302）的学习笔记。原教程按十个模块（01-slash-commands 到 10-cli）组织，配了大量可复制的模板。这里重排成十二篇：先用一篇讲清七种扩展机制的分工，再逐个拆开，每个功能按“它解决什么问题、最小可用配置放在哪个路径、什么时候不该用”来写，并配上“读配置猜行为”、模拟器和场景判定题。功能与字段取自原文（主要依据英文原版，中文版是它的缩写译本），每节标出对应的原文目录；为演示设的场景和数值标“示意”。Claude Code 更新很快，原文里带版本号的细节以原文和官方文档为准。

它解决什么

原文 07-plugins「Overview」「Standalone vs Plugin」「Plugin Features Comparison」

原文的定义：插件是把斜杠命令、子代理、MCP 服务器、hooks 等定制打包成一个整体、一条命令安装的集合，是最高层的扩展机制。它和单独配置的差别，原文用一张对比表说得很直白：命令、Skill、子代理都是“手动复制、手动版本管理、复制文件分享”；插件是“一条命令安装、自动版本、用安装 ID 分享、可以走 marketplace”。

命名上也有区别：单独配置的命令叫 /hello，插件里的叫 /插件名:hello（没有冲突时可以省前缀）。原文的建议是：个人的快速工作流用单独配置；要打包多种功能、分享给团队、或者公开发布时，用插件。v2.1.157 起还有一个轻量路径：claude plugin init 名字 在 ~/.claude/skills/名字/ 下搭一个插件骨架，下次会话自动加载为 名字@skills-dir，不需要 marketplace。

目录与清单

原文「Plugin Definition Structure」「Plugin Structure Example」「LSP server configuration」

清单在 .claude-plugin/plugin.json，必要的是身份字段（name、description、version、author，可选 homepage、repository、license）；另外可以声明 dependencies（依赖的其他插件，可带语义化版本约束）、keywords（marketplace 搜索用）、userConfig（用户可配置项）、lspServers、outputStyles、experimental.monitors 等，用来指向默认目录以外的组件。

组件按目录约定放：skills/（推荐）、commands/（旧做法，官方建议新插件用 skills/）、agents/、hooks/hooks.json、.mcp.json、.lsp.json（给 Claude 提供诊断、跳转定义、查引用等代码智能）、bin/（插件启用时加进 PATH，排在你自己的 PATH 之后，所以覆盖不了系统命令）、settings.json（只有 agent 和 subagentStatusLine 两个键生效）。插件根目录只有一个 SKILL.md、没有 skills/ 子目录时，整个插件就是一个 Skill（v2.1.142）。

安装与生命周期

原文「Installation Methods」「Testing a Plugin」「Plugin CLI Commands」「Auto-Update」

开发阶段用 claude --plugin-dir ./my-plugin 直接加载本地目录（可重复写多次加载多个；也接受 .zip；--plugin-url 从网址取一个 zip 只用于本次会话）。改了文件用 /reload-plugins 热重载。原教程自己的三个示例插件就是这样用的，因为这个仓库本身不是 marketplace，/plugin install 用不了。

正式安装走 marketplace：/plugin marketplace add 所有者/仓库 加一个市场，/plugin install 插件@市场 安装（v2.1.275 起可以一步写成 /plugin install 插件 --marketplace 所有者/仓库）。从 v2.1.221 起安装通常立即生效：看安装摘要最后一行，“Plugin is now active.” 就不用管，“Run /reload-plugins to activate.” 才需要重载。官方市场默认自动更新，第三方和本地市场默认不自动更新；marketplace update 只刷新目录，不更新已装插件，更新插件用 claude plugin update 名字。装之前可以在 /plugin 的浏览页看每个插件每轮大约要多占多少上下文，装好后 claude plugin details 名字 也能看。

marketplace

原文「Plugin Marketplace」「Marketplace definition schema」「Plugin source types」「Strict mode」

市场本身就是一个带 .claude-plugin/marketplace.json 的仓库：必填 name、owner、plugins 数组，每个插件条目写 name 和 source。来源有七种：相对路径、GitHub（可用 ref 或 sha 锁版本）、git URL、git 子目录（monorepo 里的某个包）、npm、压缩包（只允许 HTTPS，可带 sha256 校验，上限 256 MiB）、命令（由本地工具打印插件目录路径）。官方市场是 anthropics/claude-plugins-official，首次交互启动时自动注册；社区市场 anthropics/claude-plugins-community 要手动添加，收录的插件经过自动校验并锁定到具体提交。

组织管控用托管设置：strictKnownMarketplaces（只允许名单内的市场；空数组表示全部禁止）、blockedMarketplaces（黑名单，可按主机名或路径正则）、enabledPlugins 里把某个插件设为 false（任何层级都装不了）、disableCommandPluginSources（禁用命令来源）。这些在安装、更新、刷新、自动更新的每个环节都会检查。市场条目的 strict 决定谁说了算：默认 true 时插件自己的 plugin.json 为准、市场条目只做补充；false 时市场条目就是插件的全部定义。

安全边界

原文「Plugin Security」「Plugin Options」「Persistent Plugin Data」「archive source」「Mods」

插件里的子代理定义有四个字段会被忽略：hooks、mcpServers、permissionMode、initialPrompt。子代理文件本身照常加载，只是这些键无效。理由是防止插件借一个子代理文件悄悄注册事件处理、接入外部服务或提升权限；插件真要带 hooks 和 MCP，就在插件层面（hooks/hooks.json、.mcp.json）明明白白地声明。

其他几条：插件的 userConfig 里标了 sensitive: true 的值存进系统钥匙串，不落明文配置文件；${CLAUDE_PLUGIN_DATA} 是插件专属的持久目录（~/.claude/plugins/data/<id>/），升级保留，最后一处卸载时删除（--keep-data 可保留）；压缩包来源不是你自己构建的就一定要锁 sha256，否则谁控制那个网址谁就控制在你会话里跑的代码。v2.1.287 起还有一类叫 Mod 的插件，能改界面、拦工具调用、调用模型，原文明确说它以你的权限运行，只从信任的作者和市场安装。

这些说法对不对？

什么时候做插件

原文「Plugin Use Cases」「Publishing a Plugin」「Best Practices」

原文的用例表把答案说得很清楚：新人上手、框架配置、企业规范适合做插件（一次装好全部配置、集中分发、版本可控）；快速任务自动化、单一领域知识、专项分析、实时数据接入不适合（分别用命令、Skill、子代理、MCP）。判断的关键是两个问题：是不是多种组件一起才成立？是不是要给很多人用同一个版本？

发布流程原文列了九步，核心是：组织好目录、写 plugin.json 和 README、用 --plugin-dir 本地测试、claude plugin validate 校验、claude plugin tag ./my-plugin 按 plugin.json 里的版本打 名字--v版本 标签、提交到市场。最佳实践里我觉得最值得记的两条：用语义化版本、保持向后兼容；不要把不相关的功能捆在一起。

这几件事，该做成插件吗？

回扣开头的三个问题

先自己答，再点开
1. 插件能放哪些组件？清单在哪？commands/ 还是 skills/？

清单在 .claude-plugin/plugin.json。组件：skills/、commands/（旧做法）、agents/、hooks/hooks.json、.mcp.json、.lsp.json、bin/（加进 PATH）、settings.json（只有 agent 和 subagentStatusLine 生效），以及主题、监视器、输出风格等。新插件用 skills/，commands/ 只是保持兼容。

2. 本地插件怎么测？装完何时还要 /reload-plugins？

claude --plugin-dir ./my-plugin（可多次、可 zip），改了用 /reload-plugins 热重载。从 marketplace 装（/plugin marketplace add + /plugin install 名字@市场）后看摘要最后一行：“Plugin is now active.” 不用管，“Run /reload-plugins to activate.” 才需要重载（v2.1.221 起）。marketplace update 只刷新目录，更新插件用 claude plugin update。

3. 插件子代理哪些字段被忽略？哪些场景不该做插件？

hooks、mcpServers、permissionMode、initialPrompt 被忽略，防止插件借子代理注册事件、接外部服务或提权；需要的话在插件层声明。快速小任务（用命令）、单一领域知识（用 Skill）、专项分析（用子代理）、实时数据（单独配 MCP）不该做插件；不相关的功能也别捆在一起。
