没有度量，就没有改进

构建完成不等于构建正确。用什么模型、挂哪些工具、记忆怎么存、Harness 加哪些约束，这些选择大多没有显而易见的答案，只能靠评估来回答。这一篇按原书的四个环节走：什么算成功、任务从哪来、由谁验证、分数怎样变成决策。

本系列是开源书《深入理解 AI Agent：设计原理与工程实践》（李博杰 著，Apache-2.0 协议）的学习笔记。不逐段复述原书，而是用自己的话把关键概念讲一遍，配上能动手点的小实验；原书的实验代码和思考题推荐对照阅读。

评估的对象是模型 + Harness

原书 7 章引言

评估靠两种实验：对比实验（改一个变量看效果）和消融实验（逐个关掉组件看整体掉多少）。原书强调一个关键认识：评估的对象不应只是模型，而是模型与 Harness 的组合体。同一个模型换个 Harness，表现可能天差地别，所以评估体系要能区分“模型能力不足”和“Harness 设计缺陷”。

区分它们的常用手段是模型替换实验：固定 Harness，只换更强或更弱的模型。换强模型分数不涨，瓶颈在 Harness；分数随模型能力大幅波动，表现主要由模型决定。它和消融不同：消融定位 Harness 内部哪个部件重要，替换区分瓶颈在模型还是 Harness。

有了自己的评估集还有两个好处：新模型在公开榜上更好，不代表在你的任务上更好，可能反而退化，只有在自己的集合上跑才能决定升不升级；更进一步可以为未来的模型开发产品，先把产品和评估集做好，等模型达到门槛立即上线。

看几组实验结果，判断瓶颈在哪。

解剖一条评估任务：τ²-bench telecom

原书 7.1 节

原书拿 τ²-bench（Sierra 的开源项目）telecom 领域的一条真实任务开刀：用户手机在法国上不了网，状态栏显示 No Service。任务定义分四部分：给 Agent 的工单、给用户模拟器的行为规范、运行前的初始状态、评分标准。

四处设计值得学。显式建模用户的认知边界：known_info 只有姓名、号码、所在国家，真正的故障原因（飞行模式开着、漫游关着）用户自己也不知道，Agent 只能靠提问和引导去发现。防止模拟器被 Agent 忽悠：只有测速为 excellent 才算解决，关于设备的回答必须以工具结果为依据，否则评估会退化成两个模型互相确认。双方都不具备完全信息：运营商侧漫游已开通，Agent 查数据库只会得出“配置正常”，故障在它看不见的用户设备侧，这就是双控，模拟用户也有自己的一套工具。多维度校验：终态断言、关键动作、信息告知。

原书还分析了一条满分轨迹里的瑕疵：政策写着“一次只调用一个工具”，Agent 却同时发了两个，验证器没管，因为这题只看终态。这不是疏漏，而是二元奖励的固有代价：用过程颗粒度换跨模型可比的单一数字。

一条任务的四个组成部分

技术奇观看 Pass@k，业务可靠看 Pass^k

原书 7.2 节

五条任务过了四条，0.8 算好还是差？取决于场景。原书区分两种口径。Pass@k：同一任务跑 k 次，至少一次通过就算过（连续得分取最好的叫 Best@k）。它衡量“原则上做得到”，适合科研发现、漏洞挖掘、开放创作，人可以从 k 条候选里挑最好的。原书称之为技术奇观阶段：Manus 让人第一次看到 AI 像人一样操作电脑干半小时，OpenClaw 让人感到“活人感”，早期成功率并不高，但较高的 Pass@k 和社交网络上的传播是它们成功的关键。

Pass^k（读作 Pass consecutive k）：同一任务连续跑 k 次，每次都要通过，且不能触发安全、合规、幻觉这类一票否决项。它回答“能否稳定交付”，才接近支付、退款、生产部署的要求。若每次独立、单次成功率为 p，则 Pass@k = 1 − (1 − p)k，Pass^k = pk。报告要写清 k 次是同一任务独立采样还是流水线上连续 k 个任务；有副作用的操作不能“重试到成功”，要在沙盒里采样并把每次失败都计入。

拖动单次成功率和 k，看两条曲线如何分道扬镳。

同一个 p，两种口径

0
Pass@k：至少一次成功
0
Pass^k：k 次全部成功

原书的例子：p = 0.6、k = 5 时，Pass@5 ≈ 99.0%，Pass^5 ≈ 7.8%。

环境五要素，和不被糊弄的验证器

原书 7.3–7.4 节

一个可重复运行的评估环境需要五个要素：数据集（每条用例打包初始状态、工单、模拟器规范、验收标准）、环境状态（必须可重置，每次回到同一起点）、工具接口（原子操作，不能有“解决用户上网问题”这种高层工具，否则规划被工具吸收）、评分标准、执行协议（交互顺序和终止条件，沟通效率太低也算失败）。没有对话对象的工具调用型任务（写代码、数据分析、数学）可以省掉用户模拟器，Verifiers 框架按是否保持状态、是否需要隔离分成四类环境。

Agent 很容易写一篇洋洋洒洒的报告说全做完了，所以验证器必须核实机器可独立复核的事实，而不是 Agent 的自我陈述。SWE-bench Verified 把“修好了”拆成两个命题：FAIL_TO_PASS（修复前失败修复后通过）和 PASS_TO_PASS（修复前后都通过）；只验前者，Agent 可以删断言蒙混。OSWorld 用 134 个评估函数直接查数据库、DOM、cookie。Terminal-Bench 要求从源码编译 Linux 内核并在启动日志里看到自定义 printk，没法伪造。

防泄漏有几招：GAIA 的题要组合多个信息源，还配了互联网上不存在的附件；AndroidWorld 用参数化模板每次随机生成实例；Terminal-Bench 在题面里嵌金丝雀 GUID，模型能吐出它就说明进了训练集。质量维护也很重：SWE-bench Verified 发布前请 93 名开发者筛掉 71% 的原始任务；OSWorld 发布后 15 个月暴露了 300 多个问题。生产中的评估集有三个来源：公开基准（粗筛和借鉴）、自建业务集（选型依据）、生产轨迹回流（成本最高也最准，上线后会成为主体）。

把设计手法配到对应的基准上。

Rubric + LLM-as-a-Judge

原书 7.5 节

确定性验证器便宜、可复现，但只能说对不对，说不出错在哪；而且“这封投诉回复是否得体”根本写不成断言。所以生产评估要沿着“可机械验证程度”的谱系往右走：用 Rubric 把“好不好”拆成可分别打分的维度，用 LLM-as-a-Judge 在没有确定性判据时打分。能写成断言的仍然用断言。

原书引用 Scale AI 的 Rubric 四准则：基于专家指导；全面覆盖（包括要避开的陷阱项）；按重要性加权（必要、重要、可选、陷阱，并支持一票否决，如客服场景的幻觉）；评价标准自包含（不写“展示了深刻理解”，写“引用了至少两个权威理论并准确解释”）。要主动防奖励作弊：惩罚幻觉、讨好、关键词堆砌、回避难题。

评判模型自身有偏差。长度偏差：偏爱更长的回答，可在 Rubric 里惩罚冗长、定期审计分数与长度的相关性。位置偏差：配对比较时偏向先出现的候选，要交换顺序各评一次。同源问题：Agent 与评判模型同一家族时，Agent 会学会钻评判者的空子，这就是古德哈特定律，缓解办法是多源异构评判。

用原书的用户记忆 Rubric 给四个回答打分。问题是“我女儿的儿科医生是谁？”，记忆里第一次对话说“女儿叫 Lily”，第二次说“带 Lily 去看了 Dr. Chen”。

    失败归因：找首个错误，不是最后一个报错

    原书 7.5 节 · 失败归因与回归任务

    端到端评估只说成功或失败。要驱动修复，得对每条失败轨迹做失败归因：标出错误类别、首次出现不可接受行为的那一步、对应的工具调用或模型输出，并附可复核的证据。后面的错误往往只是连锁反应。问题案例来自三类信号：用户明确纠正、用户点踩、事后由状态检查或 LLM 评审发现。原书提醒，归因可以借助 LLM 规模化，但不能完全依赖它，因为失败归因往往反映的是产品问题。规则先筛嫌疑轨迹、LLM 再定位首错，比全部喂给 LLM 更便宜也更准。

    一类容易被总分掩盖的问题是“做对了但说错了”：环境状态全对，告诉用户的信息却错了。τ²-bench 公开基线里，有信息告知要求的 704 次运行失败 240 次，其中 80 次环境状态正确但告知错误。另一个案例来自 AndroidWorld 的纯文本 Agent T3A：把图片里的开销录入记账应用，32 步没有任何报错，验收却失败。往回看，第 8 步它自己写道“我其实看不到图片里的开销”，却没停也没报告，第 11 步凭空编出了四条数据。根因不是“模型不会 OCR”，而是它的观察空间里根本没有图像像素：Harness 缺了观察通道。记成模型能力问题，就会去换模型、做训练，修错方向。

    归因之后，把修复目标写成回归任务。端到端回归从初始状态跑完整任务，最接近生产，但难以定位；轨迹前缀回归冻结首错之前的上下文和环境状态，只让 Agent 做下一步，答案是一个“可接受动作集合”加禁止动作。原书认为，对高可靠的生产 Agent，前缀回归集往往比端到端集更重要。

      Coding Agent 的错误类别

      分数怎样变成决策

      原书 7.6–7.8 节

      选型不是“选最强的”。要看延迟（TTFT 由排队加 prefill 决定，思考时长由 decode 速度决定，还要看 p95 尾延迟）、成本（便宜但成功率低、要频繁重试的模型可能更贵）、性能（日常看 Pass@1，关键操作看 Pass^k，探索看 Pass@k）、速率限制和可靠性。还要看预算—能力曲线：RE-Bench 里 2 小时预算下最佳 Agent 约为人类专家的 4 倍，但 8 小时人类略超，32 小时约为 Agent 的 2 倍。原书还提到行为策略差异：固定 Harness 下，有的模型改代码前读得多，有的读少数文件就动手、靠测试补齐认识。

      成本要在完整任务里实测。原书实验在一个八轮客服退款任务上分别开关“稳定前缀”和“压缩历史”：单开前者省 28.3%，单开后者省 17.5%，两个一起只省 30%，因为压缩也缩短了能命中缓存的前缀。几项优化的节省比例不能直接相加。

      最后是统计显著性。n 个用例测得成功率 p，标准误约为 √(p(1−p)/n)：100 题、70% 的 95% 置信区间约 ±9 个百分点，73% 对 70% 不足以支持切换。同一批任务比较两个配置要做配对分析（逐题看谁赢，McNemar 检验或配对 bootstrap），每个配置跑 3–5 个随机种子。分差要超过噪声、配对分析成立、能复现，才值得据此切换。

      从 Benchmark 报告到系统改进

      原书 7.9–7.11 节

      原书的第一条原则：看到表现下降，先检查评测系统本身，再动 Agent。资源不足导致进程被杀、验证器有 bug、测试与生产脱节，在数字上都和模型退化一模一样，只有看完整轨迹才能区分。

      然后是一次真实的 AndroidWorld 调优。116 项任务总成功率约 88%，但四项 Wi-Fi 设置任务里失败了三项。可能是不知道入口，也可能是界面信息不完整。原书只在这四项上做配对实验，每轮只改一个变量，从最便宜的改法开始。

      评估最终要嵌进产品工程。原书以 OpenClaw 和头部 Coding Agent 为例：消融开关（一个总开关同时禁用思考、压缩、记忆等特性，看每个特性是真有用还是只是感觉有用，定期发现“特性债务”）；AB 测试要多臂、要设护栏指标，最重要的是区分机制指标和目标指标（缩短计划文件长度是机制，降低会话成本才是目标，计划太短反而可能增加编辑循环）；双层特性开关；把渲染后的系统提示词纳入版本快照和回归测试；从一开始就把隐私约束设计进分析系统。评估环境再往前一步就是仿真环境：验证器即奖励函数，但训练还要求可靠的 reset 和高得多的吞吐（第 8 篇）。
