上下文就是一个消息列表

原书 2.1–2.2 节

原书开篇用了一个比喻：一位天才工程师加入你的团队，却对产品架构、业务规则、团队约定一无所知，他再聪明也发挥不出价值。Agent 就是这个“永远的新员工”。模型的智力只是基础，上下文的质量才是 Agent 能力的关键；中等模型配上组织良好的上下文，常常胜过顶级模型在信息匮乏下的摸索。这也是个组织问题：对远程协作友好、文档化程度高的团队，往往也对 Agent 友好。

技术上，上下文就是一次 API 请求里的消息列表。每条消息有一个角色：system（开发者写的规则）、user（用户输入）、assistant（模型之前的回复，含工具调用请求）、tool（框架执行工具后的结果，用 tool_call_id 对应到具体调用）。工具定义不是消息，而是请求顶层的 tools 字段。四种角色加 tools 字段，正好覆盖第 1 篇说的五个组成部分。

两件事一定要记住。一是 API 是无状态的：模型不记得上一次请求，框架每次都要把完整历史送回去。二是模型只发出调用请求，真正执行工具的是框架：模型负责决策，框架负责执行。原书说，Agent 框架的核心工作就是管理这个消息列表，本章后面所有技术，本质都是在优化这个列表的内容和结构。

用原书的“温哥华现在几点、天气如何”走一遍两次 API 调用，看列表每一步多了什么、是谁写进去的。

两次 API 调用里的消息列表

为什么两个工具能并行？查时间要的时区、查天气要的城市都能直接确定，两者互不依赖，所以模型在一次回复里同时发出两个调用。如果后一个工具的参数要用前一个的结果，就只能分两轮串行。

工具清单是静态的。无论用户问天气还是订机票，发出去的都是同一份 tools。并不是框架先把问题拆成两个子任务再生成工具描述，拆解发生在模型一侧，就是响应里的 tool_calls。

小模型也能用工具。原书实验 2-1 用 0.6B 参数的 Qwen3 在 M2 芯片上跑，超过每秒 100 token，合理设计提示词后就能可靠地调用工具。

它在请求的哪个位置

改一个空格，账单翻倍：KV Cache

原书 2.3 节

原书讲了一个故事：某团队的客服 Agent 每天 10 万次对话，工程师为了让它“知道时间”，在系统提示词里加了一行 Current time: {{now}}。第二天首 token 延迟从 0.5 秒涨到 3–5 秒，月度账单几乎翻倍。代码没错，模型没换，问题出在缓存。

模型生成每个新 token 时，都要用它的 Query 去和前文每个 token 的 Key 做匹配，再按匹配度加权取各自的 Value。前文 token 的 K、V 算过一次就可以存起来复用，这就是 KV Cache。API 服务商在多次请求之间复用相同前缀的 KV，叫 Prompt Cache，缓存读取通常只要首次计算的十分之一左右的价钱。复用有个前提：前缀必须逐 token 相同。模型是多层串联的，第 k 个 token 一变，它之后每一层的表示都会变，所以缓存只能保留到第一个不同的 token 之前。

时间戳放在系统提示词里，等于每次请求都在最前面改了一处，后面几乎全部要重算。原书给不想深究原理的读者三条结论：系统提示词和工具定义定下来就别改；动态信息永远追加到末尾；用标准 API 格式，不要自己拼字符串。

注意力在找什么

读到“怎么样”时，模型给前面每个词打的注意力权重（原书图 2-6 的示意值）。

权重总和必须是 1（softmax 保证），模型没法表达“谁都不关注”，所以真实模型常把多余的权重倒给第一个 token，叫注意力储存池（attention sink）。另外，开头和结尾的信息更容易被注意，中间的更容易被忽视。

“改前缀”不只是多花钱。原书提到，Claude 新模型的“保留思考”机制用签名把每个 thinking block 绑定到它产生时的前缀上，前缀一改，这段思考和之后的思考全部失效，模型只能从头想。于是“只追加、不改写”从性能建议变成了正确性要求。

缓存是架构约束。Claude Code 把系统提示词用一个缓存边界分成两半：边界前跨用户全局缓存，边界后放用户和会话相关的内容。每个放在边界前的二值运行时条件都会让缓存变体翻倍，3 个条件就是 8 种。

信封格式：Chat Template

原书 2.3 节

API 里的消息是结构化的 JSON，模型真正读的却是一条线性的 token 流。负责翻译的是 Chat Template：用 <|im_start|>system、<|im_end|> 这类特殊 token 标出每条消息的角色和边界。原书把它比作信封格式，不同模型家族的“信封”写法不同，vLLM、Ollama 等服务端会自动套用，开发者一般不用手写。

理解它有两个实际用处。第一，它解释了为什么不能自己拼消息。以 Qwen3 为例，多轮工具调用中，模型会保留之前 <think> 里的推导，就像草稿纸；但模板一检测到新的用户提问，就认为换了话题，把草稿清掉。如果你把工具结果当成 user 消息传进去，就会误触发清理，模型算到一半草稿被收走。第二，它解释了 KV Cache 为什么对前缀敏感：系统提示词和工具定义被翻译成固定的 token 序列放在最前面，多一个空格，序列就变了。

各家对“历史思考要不要回传”的规定也在变：DeepSeek R1 时代要求剥离历史思考，V4 则反转为只要带 tools 就必须原样回传 reasoning_content，否则直接报 400；Kimi K2、GLM-5 也采用同样的协议。使用前要查各家最新文档。

切换两种传法，看模型实际读到的 token 流有什么不同。

系统提示词：一份员工手册

原书 2.4 节

原书给系统提示词的检验标准很朴素：如果一个聪明的新员工读完还不知道该怎么做，Agent 也不知道。几条经验：语气上可以用大写的 “NEVER” 强调关键约束，但用多了会被稀释；格式上用 Markdown 标题给人看层次、用 XML 标签给模型精确语义；组织上用流程驱动（像新员工 SOP：第一步验证、第二步分类……），而不是上百条零散规则堆在一起。

原书实验 2-4 在 Tau-Bench 的航空和零售客服场景里做了消融：换语气（甚至换成夸张自信的“特朗普风”）对完成率影响有限；打乱规则的组织结构，成功率掉 30% 以上，“先验证身份再退款”被拆散后，Agent 会跳过验证直接退款；去掉工具的描述文字，工具调用错误率增加 45%。

最容易被忽视的是业务规则细化，这是产品问题，不是技术问题。原书举了打电话帮用户办账单的计费例子：“根据任务情况选择合适的计费类型”这种模糊规则会让 Agent 行为飘忽，“退衣服”算省钱吗？“取消 Netflix”算省钱吗？必须写到可执行，比如“NEVER use percentage_based for refunds and service cancellations”。原书认为，好的 Agent 公司里提示词通常由产品经理设计，工程师负责准确编码。

提示工程消融（实验 2-4）

规则写到可执行：这单怎么收费

规则：按省钱提成只用于“通过谈判降低现有账单”；退款、取消服务一律不按提成；成功率很低的任务预收款。

Few-shot 示例什么时候给？输出难用规则说清时（文案风格、报告格式、客服分寸），两三个覆盖边界情况的示例胜过一大段定义；模型本来就擅长的任务，示例只是浪费 token。示例位于上下文靠前，应当固定，按请求动态挑“最相关”的示例等于每次改前缀。

提示注入怎么在上下文层防？帮模型分清“指令”和“数据”：外部内容用 <external_content source="webpage"> 这类标记包起来；严格按角色传消息；过滤“忽略之前指令”之类短语（容易被绕过，只能辅助）。这一层只能降低成功率，执行层和数据层的防线见第 1、4、5 篇。

按需加载：Agent Skills

原书 2.5 节

Agent 覆盖的场景越多，系统提示词越长：退款规则、代码规范、文档格式全塞进去，既浪费 token，又稀释注意力。Agent Skills 的做法是把能力拆成可按需加载的知识包，用渐进式披露分三层：第一层只有元数据（SKILL.md 开头的 name 和 description），作为目录常驻；Agent 判断需要时才加载第二层完整的 SKILL.md；正文里再引用第三层的细则子文档和脚本，用到才读。

description 是路由的关键。它要短，但写法要像路由条件而不是功能介绍：写清“何时用我、何时不用我”，给几条反例。“help with backend” 这种描述等于任何后端工作都能触发。原书引用宝玉的建议，一份 Skill 包含四部分：角色与读者、三到五条核心原则（配正反例）、禁止清单（写清例外）、参考资料。

Skill 正文被调用时追加到轨迹里（Claude Code 作为一条 user 消息注入），不回头改写前缀，所以对缓存友好。但原书提醒“友好”不等于“零成本”：目录和正文首次进入时都要计算一次。还有安全面：第三方 Skill 本质是“把外部内容当指令加载”，装之前要像审代码一样审它。

选一个任务，看三层里加载了哪些；再拖滑块，比较“全塞进系统提示词”和“渐进式披露”的常驻成本。

    哪条 description 更好

    让模型瞥一眼就知道：Agent 状态栏

    原书 2.6 节

    原书的场景：系统提示词规定每个商家最多打 3 次电话，可打完 3 次后 Agent 常常数不清，又打了第 4 次，甚至反复拨同一个号。原因在于注意力的一个特性：上下文学习更像检索而非推理。原书的说法是“上下文窗口是一台只有一半的检索引擎”：查找某条原始记录很强，但没有“提炼层”，“一共打了几次”这种结论每次都要从原始记录里现算，内容越多越容易算错。

    Agent 状态栏就是由框架把隐式状态提炼成显式信息，追加在上下文末尾：已调用次数、当前时间、TODO 进度、工作目录等。它像手机顶部的状态栏，不是主内容，但随时能瞥一眼。放在末尾还有一个好处：离即将生成的 token 最近，注意力权重最高。原书引用的实验显示，有了提前算好的状态栏，较小开源模型的准确率可以接近前沿大模型，每轮思考 token、延迟、花费约降一个数量级。

    两条维护纪律：状态栏尽量用代码维护，因为模型几乎无条件相信它，写错了就会照错的做，这也意味着状态栏可以被投毒；谨慎删除原始记录，状态栏是一次有损投影，只算了你预想会被问到的维度。

    先看有无状态栏时模型怎么决定要不要打第 4 次电话，再算一笔“每轮替换 vs 持久追加”的缓存账。

    做减法：压缩与隔离

    原书 2.7 节

    压缩有三个动机。最直观的是长度和成本：工具结果动辄几万字符，几轮就能撑满窗口。更深一层是提升思考质量：原书的宠物店例子里，100 个笼子 90 黑 10 白，问“37 号笼是什么猫”是查找，注意力很擅长；问“一共几只黑猫”是统计，要遍历全部记录。提前总结成“黑猫 90、白猫 10”，就把需要思考才能得到的结论变成了可以直接检索的知识。第三是缓解上下文焦虑：模型觉得窗口快满时会提前收尾。

    还有一种更隐蔽的问题叫上下文腐化（Context Rot）：窗口远没满，Agent 却找不到关键信息、反复纠结已解决的问题。溢出是“装不下”，腐化是“装得下但找不到”。

    压缩和 KV Cache 并不矛盾：系统提示词和工具定义永远不动，压缩的对象是对话历史里的工具结果，替换点之前的缓存仍然有效。所以要接近阈值时批量压，别每轮都压。比压缩更彻底的是隔离：把“在代码库里大范围搜索”这种会产生海量中间内容的活交给子 Agent，主上下文只多两条消息，一条任务、一条结论。

    六种压缩策略（实验 2-10）

    任务：追踪 OpenAI 联合创始人的职业状态，上下文限制在 128K。

    生产级的五层压缩（以 Claude Code 为参照）

    层做法要点
    1 工具结果预算大输出存磁盘，模型只看摘要预览替换字符串首次出现就冻结，保证缓存一致
    2 噪声直接删只被用了几行的搜索结果直接移除对噪声做摘要是浪费 token
    3 API 层微压缩让服务端从前缀里移除指定工具结果移除点之后仍要重建缓存，适合快溢出时用
    4 归档式摘要逐轮结构化摘要，像 git log 而非 git squash保留逻辑脉络
    5 全量压缩LLM 驱动的完整压缩，先压会话记忆再全量配熔断器，避免在反复压缩失败的会话上烧钱

    压缩最容易丢的是早期架构决策、约束背后的理由和失败的路径。原书建议让 Agent 定期把进展写进文档，而不是只留在执行历史里。
