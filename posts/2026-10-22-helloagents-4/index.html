边想边做、先谋后动、做完再改

这是全书最该吃透的一章。原书不用任何框架，从零写了三个智能体：ReAct 边想边做，靠每一步的观察修正方向；Plan-and-Solve 先拿出整张蓝图再按图施工；Reflection 先交初稿，再自己当评审、自己改。三者都跑在同一个 LLM 客户端上，区别只在“思考”和“行动”怎么组织。读完要能做到两件事：合上书写出每个范式的主循环，拿到一个任务能说出该用哪种、或者怎么组合。

本系列是开源教程《Hello-Agents：从零开始构建智能体》（Datawhale 社区编写的开源教程，CC BY-NC-SA 4.0 协议；本笔记依据 2026 年 10 月 14 日的仓库版本）的学习笔记。原书十六章，按“概念 → 手写范式 → 平台与框架 → 自研框架 → 记忆、上下文、协议、训练、评估 → 综合案例”展开，代码量很大。这里重排成十三篇，用自己的话重讲：代码只保留能看清机制的骨架，做成可以逐行走读、可以填空回忆的互动；每篇末尾配原书面试题清单里的相关题目做口述演练。每节标出对应的原书章节，演示数值标“示意”。笔记同样按 CC BY-NC-SA 4.0 共享。

为什么要手写，三种形状

原书第 4 章导言、4.1 节

已经有 LangChain、LlamaIndex，为什么还要“重复造轮子”？原书给了三个理由：高度抽象的框架不利于理解背后的机制；框架替你处理了输出解析、调用失败重试、防死循环这些工程问题，自己处理一遍才会真正有系统设计能力；最重要的是，懂原理才能从框架的“使用者”变成“创造者”，标准组件不够用时能自己改、自己造。

准备工作很简单：把模型 ID、密钥、地址放进 .env，封装一个 HelloAgentsLLM 客户端，只暴露一个 think(messages, temperature=0) 方法，内部用流式调用兼容 OpenAI 的接口。注意默认温度是 0：智能体要稳定地按格式输出，这和上一篇说的“产出 Action 的步骤用低温”是一回事。三个范式都只依赖这一个方法，差别全在提示词怎么写和循环怎么组织。

先把三种形状放在一起看一眼，后面逐个拆开。

ReAct侦探：走一步看一步

  1. Thought：分析现状
  2. Action：调用一个工具
  3. Observation：拿到结果
  4. 回到 1，直到 Finish
每一步一次 LLM 调用

Plan-and-Solve建筑师：先画蓝图

  1. Planner：一次生成完整计划
  2. Executor：按顺序执行每一步，带上历史结果
  3. 最后一步的结果即答案
1 次规划 + n 次执行

Reflection作者兼编辑：先交初稿

  1. 执行：生成初稿
  2. 反思：评审员挑问题
  3. 优化：按反馈改稿
  4. 回到 2，直到“无需改进”
1 + 每轮 2 次

ReAct：推理指导行动，行动修正推理

原书 4.2.1–4.2.3 节

ReAct 由 Shunyu Yao 在 2022 年提出。在它之前有两类做法：纯思考的思维链，推理强但碰不到外部世界，容易事实幻觉；纯行动的方法直接输出动作，缺乏规划和纠错。ReAct 的洞察是两者相辅相成：推理让行动更有目的，行动为推理提供事实依据。形式化地说，每一步策略 π 根据问题 q 和之前所有的（行动, 观察）对，生成当前的思考和行动：(tht, at) = π(q, (a1, o1), …, (at−1, ot−1))，工具执行后返回 ot = T(at)。它最适合需要外部知识、精确计算、与 API 交互的任务。

工具要有三要素：名称（Action 里怎么叫它）、描述（什么时候该用它）、执行逻辑（真正干活的函数）。原书特别强调描述是整个机制里最关键的部分，因为模型只靠这段文字决定用不用、用哪个。搜索工具用的是 SerpApi，并做了“智能解析”：优先返回答案框和知识图谱，其次才是前三条搜索摘要，喂给模型的信息越干净越好。多个工具由 ToolExecutor 统一注册、查找，并用 getAvailableTools() 拼成一段工具清单塞进提示词。

和第一篇相比，这一版有三个工程上的改进：提示词模板里的 {tools} 由执行器动态生成；Action 格式改成 工具名[输入]；历史只记录 Action 和 Observation（Thought 不进历史，节省上下文）。max_steps 是防止无限循环的安全阀。

ReAct 的长短与调试

原书 4.2.4 节

ReAct 的三个优点：高可解释性（Thought 链让你看到它为什么选这个工具）、动态规划与纠错（搜索结果不理想，下一步换个关键词）、工具协同（LLM 运筹帷幄，工具解决具体问题）。四个局限：强依赖 LLM 能力（推理、指令遵循、格式输出任何一项不行，流程就断）、效率低（每步一次调用，串行累加延迟和费用）、提示词脆弱（措辞微调都可能改变行为，并非所有模型都稳定守格式）、局部最优（没有全局规划，可能被眼前的观察带偏，甚至原地打转）。

原书给的调试顺序很实用：先打印完整提示词（追溯决策源头）；解析失败时打印原始输出（分清是模型没守格式还是正则写错了）；检查工具的输入输出（参数格式对不对，返回的东西模型能不能读懂）；频繁出错就加一两个完整的 TAO 成功示例（少样本）；最后才是换更强的模型或把温度设为 0。

易混辨析：文本协议解析 vs Function Calling

本章用正则从纯文本里抠 Search[...]，好处是任何模型都能用、过程透明；坏处是格式稍有偏差就失败（多行、嵌套方括号、模型自己写了 Observation）。原书习题 2 问更鲁棒的方案：让模型输出 JSON 并用解析器校验；或者用模型原生的 Function Calling，由 API 返回结构化的工具名和参数。第 7 篇自建框架时会两种都实现。

Plan-and-Solve：先画蓝图再施工

原书 4.3 节

Plan-and-Solve 由 Lei Wang 在 2023 年提出，动机是思维链在多步骤复杂问题上容易“偏离轨道”。它把流程解耦成两个阶段：规划，P = πplan(q)，一次 LLM 调用把问题分解成 n 个步骤；执行，si = πsolve(q, P, (s1, …, si−1))，每一步都看得到原始问题、完整计划和之前所有结果，最后一步的结果就是答案。适合结构强、可清晰分解的任务：多步数学题、多信息源报告（先定结构再填内容）、代码生成（先定模块再实现）。原书说，今天许多大模型工具的 Agent 模式都融入了这种设计。

规划器的关键是让计划可被代码解析：提示词要求输出一个用 ```python 包起来的 Python 列表，代码用 split 取出中间部分，再用 ast.literal_eval 安全地转成列表（不用 eval，避免执行任意代码）。解析失败就返回空计划、终止任务。执行器的关键是状态管理：用一个 history 字符串累积“步骤 i：… 结果：…”，每次连同问题、完整计划、当前步骤一起交给模型，并要求“仅输出当前步骤的答案”。PlanAndSolveAgent 只是一个协调者，组合 Planner 和 Executor，原书称之为“组合优于继承”。

易混辨析：Plan-and-Solve vs ReAct

两者都是多步，区别在计划何时确定。ReAct 每一步才决定下一步，适合路径依赖中间结果的探索任务；Plan-and-Solve 一开始就定好全部步骤，目标一致性更好，但计划是静态的，执行中发现某步做不了也不会改（原书习题 4）。补救办法是动态重规划：执行器发现失败或结果不符合预期时，把已完成的步骤和失败原因交回规划器，生成剩余步骤的新计划。

Reflection：执行、反思、优化

原书 4.4 节

前两种范式交出答案就结束了，答案可能有错、可能不够好。Reflection 加了一个事后自我校正循环，灵感来自人写完初稿会校对、解完题会验算，代表工作是 Shinn 在 2023 年提出的 Reflexion。三步：执行（用任何方法产出初稿 O0）；反思（另一个提示词扮演评审员，从事实错误、逻辑漏洞、效率、遗漏约束等维度给出反馈 Fi = πreflect(Task, Oi)）；优化（结合初稿和反馈产出新版 Oi+1 = πrefine(Task, Oi, Fi)）。循环到评审员说“无需改进”或达到迭代上限。

它的价值在于有了内部纠错回路，不再只依赖工具反馈，能修正更高层的逻辑和策略错误；并且整个“初稿—反馈—修订”轨迹本身就是一份短期记忆。原书的例子是“写一个找出 1 到 n 所有素数的函数”：评审员提示词被刻意写成“极其严格、专注算法效率、如果已最优才能回答无需改进”，于是它没有满足于能跑的试除法，而是指出 O(n√n) 的瓶颈、建议埃拉托斯特尼筛法；第二轮面对 O(n log log n) 的筛法，提了分段筛等方向后判断“无需改进”，循环收敛。

代价同样清楚：每轮至少多 2 次调用、串行导致延迟显著增加、要为三个角色分别设计提示词。所以它是以成本换质量，适合对质量要求高、对实时性要求宽松的场景（关键代码、技术报告、决策支持）。

对比、组合与选型

原书 4.5 节，表 4.1，习题 1、4、7

原书的总结是：ReAct 的核心优势是环境适应性与动态纠错，适合探索性、需要外部工具输入的任务；Plan-and-Solve 的优势是结构性与稳定性，适合逻辑路径确定、内部推理密集的任务；Reflection 的价值是显著提升质量，适合对准确性和可靠性要求极高的场景。

它们不是互斥的。原书习题反复追问组合：Plan-and-Solve 的每一步可以用 ReAct 执行（计划定方向，ReAct 应对每步的不确定）；任何一个的输出都可以再过一遍 Reflection；规划也可以分层，先出高层计划，每个高层步骤再细化子计划。习题 7 的客服场景就是组合的好例子：查订单、查物流用 ReAct 调工具，退款判断按固定政策步骤走，置信度低时触发 Reflection 给出更审慎的建议。

面试演练

题目取自原书 Extra01 与第 4 章习题

请详细解释 ReAct 框架。它是如何将思维链和行动结合起来的？Extra01 · Agent 第 2 题

  • 动机：CoT 只推理不行动，会事实幻觉；纯行动缺规划和纠错。ReAct 让二者交替：推理指导行动，行动结果修正推理。
  • 机制：提示词规定每步输出 Thought + Action；解析器抠出 Action 调用工具，结果作为 Observation 追加到历史；循环直到 Finish 或达到最大步数。公式 (tht, at) = π(q, 历史)，ot = T(at)。
  • 优点：可解释、动态纠错、工具协同。局限：依赖模型能力、串行调用慢且贵、提示词脆弱、易局部最优或打转。
  • 工程要点：工具描述最关键；最大步数兜底；解析失败把错误作为 Observation 回填；温度设 0。

有哪些主流方法可以赋予 LLM 规划能力？（例如 CoT、ToT、GoT）Extra01 · Agent 第 3 题

  • CoT：一条线性推理链，“一步一步想”。
  • Plan-and-Solve：显式先生成计划再逐步执行，减少 CoT 中途偏航。
  • ToT（思维树）：每步生成多个候选思路，评估后用搜索（BFS / DFS）选择和回溯；GoT（思维图）允许思路合并与复用，形成图结构。
  • 与行动结合：ReAct（边想边做）、分层规划、动态重规划；以及 Reflection 对计划本身做事后修正。

本章用正则解析模型输出，有哪些脆弱点？更鲁棒的方案是什么？原书第 4 章习题 2

  • 脆弱点：模型多输出了几对 Thought-Action；Action 换行或参数里有方括号；模型自己编了 Observation；中英文冒号、大小写不一致；Finish 内容里嵌套括号。
  • 方案：要求 JSON 输出并用 schema 校验，失败时把错误回填让模型重试；使用模型原生 Function Calling / 结构化输出；约束解码（受限语法）。
  • 取舍：文本协议通用、透明但脆；JSON 稳定但仍可能格式错；Function Calling 最稳但依赖模型和服务商支持。

电商客服智能体（理解退款理由、查订单物流、判断是否退款、发邮件、低置信度时反思）用什么架构？原书第 4 章习题 7

  • 架构：外层按固定流程走（理解 → 查询 → 判断 → 回复），查询环节用 ReAct 调工具，判断后计算置信度，低于阈值触发 Reflection 复核，仍不确定转人工。
  • 工具：query_order(订单号)、query_logistics(运单号)、get_refund_policy(品类)、send_email(收件人, 内容)，退款执行动作需审批。
  • 提示词：把公司政策作为硬约束写清，判断必须引用具体条款；语气要求友好，拒绝时给出理由和替代方案。
  • 风险：误批退款、被用户话术诱导（提示词注入）、编造政策、邮件发错人。对策：金额阈值和高风险动作走审批，工具层做权限校验，全程日志可审计。

动手练（原书习题 3、4、5）

  1. 给 ReAct 加一个计算器工具，算 (123 + 456) × 789 / 12。
    思路

    注册 Calculator，描述写清“仅用于数学表达式计算”，执行逻辑不要用裸 eval，可以用 ast 解析只允许数字和四则运算。模型会把表达式作为输入，Observation 是精确结果，避免 LLM 自己算错。

  2. 工具多到 50 个甚至 100 个时怎么办？
    思路

    全塞进提示词会挤占上下文且让模型选错。可以按类别分组、先让模型选类别再展开；或对工具描述做向量检索，每轮只放最相关的几个（第 9 篇上下文工程、第 10 篇 MCP 都会用到这个思路）。

  3. 反思用更强的模型、执行用更快的模型，会怎样？终止条件能不能更聪明？
    思路

    强模型做评审能发现更深的问题，执行用快模型省成本，但要防止评审提出执行模型做不到的建议。终止条件可以改成结构化评分（如 1–10 分，达到阈值停）、连续两轮无实质改动停、或用测试用例通过率判断，而不是依赖字符串“无需改进”。

回扣开头的三个问题

先自己答，再点开
1. 三种范式的本质区别与适用任务？

ReAct 把思考和行动交织在每一步，下一步由当前观察决定，适合需要外部信息、路径不确定的探索任务；Plan-and-Solve 先一次性规划全部步骤再按序执行，适合结构清晰、可分解的推理任务；Reflection 在任务完成后加入评审与修订循环，适合对质量要求高、对延迟宽松的任务。三者可以组合：计划定方向、ReAct 执行每步、Reflection 把关结果。

2. ReAct 主循环几步？哪里容易出错，怎么调？

格式化提示词（工具清单 + 问题 + 历史）→ 调用 LLM → 解析 Thought / Action → Finish 则返回，否则解析工具名与输入并执行 → 把 Action 与 Observation 追加到历史；max_steps 兜底。易错处：输出格式不守、正则写错、工具参数格式不对、工具返回模型读不懂、反复调用同一工具打转。调试顺序：打印完整提示词、打印原始输出、检查工具输入输出、加少样本示例、换模型或温度设 0。

3. 执行器为何带状态？Reflection 何时停、几次调用？

计划中后面的步骤依赖前面的结果（周三销量依赖周二），执行器用 history 累积每步结果并在每次调用时传入，否则模型不知道之前算出了什么。Reflection 在评审反馈含“无需改进”或达到最大迭代次数时停止；调用次数为 1（初稿）+ 每轮 2（反思 + 优化），若在第 k 轮反思时停止则为 2k 次，最多 1 + 2 × max_iterations 次。
