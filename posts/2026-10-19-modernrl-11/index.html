训练单位从一段回答变成一整条轨迹

单轮 GRPO 里，模型读题、写完、拿分。智能体则要搜索、读网页、写代码、跑测试、再根据结果决定下一步——动作改变了环境，环境的返回又成为下一步的输入。原教程第五部分把这件事还原成序贯决策：状态里藏着看不见的环境，token 流里混着模型的动作和环境的观测，一个最终奖励要拆回到十几轮决策上。前面十篇的工具在这里全部用上，同时冒出了新的系统问题。

形式化：POMDP、动作 token 与观测 token

原文 docs/chapter22_agentic/overview.md、formulation.md（19.1–19.2 节）

原文先指出：单轮 GRPO 其实是一个退化的 MDP——状态是已生成的 token，动作是下一个 token，转移是确定的拼接，奖励在末尾给一次，而且所有 token 都由模型生成，所以都参与梯度。多轮交互打破了这个假设。原文采用 AppWorld 论文的 POMDP 形式化：状态 zt = [s0, c, x1:t]——s0 是隐藏的初始环境状态（数据库快照、文件系统、REPL），模型看不到，只能通过工具调用间接观测；c 是任务上下文（用户请求、system prompt、工具说明）；x1:t 是到目前为止的 token 历史。

token 流分两类：普通文本（思考、代码片段）只把自己拼到上下文；结构化的工具调用会触发环境执行，再把 k 个结果 token 拼回上下文——这 k 个是环境的观测，不是策略的动作。所以轨迹概率只在模型生成的位置上连乘：ρθ(x) = 𝕀(s0, x)·Πt∈a(x) pθ(xt | c, x<t)，策略梯度也只在 a(x) 上求和。这就是 action mask：让网页内容、API 返回参与梯度，等于教模型“预测环境会返回什么”，污染策略梯度。Search-R1 用四类标签把 token 分段：<think> 和 <search> 是动作，<information> 是观测（mask 掉），<answer> 是动作。原文也提到 Agent-R1 的发现：对环境 token 另加一个 SFT 损失（学着预测环境）未必是坏事——边学策略边学世界模型。

奖励也不只是“答案对不对”。原文引用的入门资料把它分成四类：Outcome（最终答案或最终环境状态是否满足任务——订票是数据库里真的多了一张符合约束的订单）、Format（动作能否被环境解析执行）、Cost（轮数、调用次数、API 花费）、Process（中间步骤是否真的推进了任务）。入门时先做 Outcome + Format，确保训练能跑通。工程上还要用步骤级记录保存轨迹（每步的状态、原始动作 token、观测、奖励），避免“解析成消息再重新分词”导致的 retokenization drift。

信用分配：从轨迹成败到每一轮、每一个 token

原文 docs/chapter22_agentic/credit-assignment.md（19.3 节）

一条轨迹失败了，信号要经过三层才落到权重上：轨迹奖励 R(τi) 只说这一局成没成；步骤优势 Ai,1 … Ai,T 回答“第 t 轮该不该被奖励”——这是信用分配真正要做的事；token 梯度把 Ai,t 乘到这一轮动作 token 的 log-prob 上（观测被 mask）。原文的判断是：当前 GRPO 式 Agentic RL 的很多工作，本质上都在构造更好的 Ai,t。

两个极端：ORM 只在终点给分，简单便宜（可验证任务连 RM 都不用），但一条 10 步轨迹只有 1 个信号，失败时连做对的步骤也被惩罚；PRM 每步打分，信号密集，但标注量放大 T 倍。中间路线之一是 SALT：同一 prompt 的多条轨迹构成一张图，被很多成功轨迹共享、很少出现在失败轨迹里的步骤得到正优势——只需要最终的二元结果。

另一条是“同状态下比较动作”，代表是 GiGPO：如果同一任务的几条轨迹在中途来到了相同的环境状态 s，就把它们在 s 上采取的动作放进一个组，用“从这一步往后的折扣回报”做组内相对优势 AS，再和轨迹级的相对优势合起来：A = AE(τ) + ω·AS(at)。原文的 WebShop 例子：三条轨迹都来到同一个搜索结果页，点正确商品（很快成功，R = 1.00）、点错商品但后来补救（R = 0.73）、点下一页（最终失败，R = 0）——组内均值 0.58，三者的步骤优势分别是 +0.42、+0.15、−0.58。模型学到的不再是“成功轨迹里一切都好”，而是同一局面下动作之间的细分偏好。原文也提到 HGPO 的修正：当前状态相同不一定代表决策上下文相同，还要看历史。

算法卡 · GiGPO

Group-in-Group Policy Optimization

解决什么问题
多轮智能体只有轨迹级成败，GRPO 的组内比较只能告诉你“哪条轨迹好”，不能告诉你“哪一步好”；训练 PRM 又太贵。
核心做法
外层：同一任务的轨迹之间做相对优势 AE；内层：把不同轨迹中相同的环境状态聚成组，用后续折扣回报做相对优势 AS；两者加权相加。
关键公式
Rt = Σk≥tγk−trk；AS = (Rt − meanGS(s)R)/Fnorm；A = AE + ω·AS
何时用
环境状态会在不同轨迹中重复出现（网页、游戏、工具环境），且只有结果奖励时。
代价与坑
需要能判断“状态相同”；当前状态相同不代表历史相同（HGPO 的修正）；状态很少重复时内层组太小。
相关
GRPO（第 9 篇）；PRM（第 10 篇）；SALT 的轨迹图方法。
ORMPRM同状态比较 / 轨迹图（GiGPO、SALT）
信号稀疏，只有终点密集，每步步骤级，但只用最终结果构造
额外成本几乎没有步骤标注 / 训练 PRM多采轨迹、识别相同状态
适用可验证任务复杂推理、需要精细指导状态会重复出现的交互环境

四个系统挑战，以及 GPU 为什么在空等

原文 overview.md“四个系统级挑战（来自 RAGEN）”、tool-use-agents.md“为什么 Agentic RL 跑不快”

原文借 RAGEN 等系统论文总结了四个挑战。长程决策：早期动作改变后续的状态分布——query 写得差，后面读到的全是错误证据；训练信号很晚才出现，真正起作用的决策却可能在很早的位置。奖励方差：搜索结果会变、网页会更新、工具会失败，同一 prompt 这一轮 8 条里成功 2 条，下一轮可能是 5 条——不能只看单次 reward 曲线，还要看方差、梯度尖峰、轨迹分布是否塌缩。rollout 设计：初始状态要多样（否则学成模板）；交互粒度太粗难以归因，太细则轨迹过长；每个任务采几条也直接影响能否比较。浅层策略：只给结果奖励，模型可能学会模板化 query、证据不足时提前作答、调用了工具却不用它的返回——表面上会搜、会读、会答。

系统层面，Agentic RL 的循环不再是纯 GPU 的：每个工具调用都要等 CPU、沙箱或网络返回，延迟从毫秒到秒不等，而且要在沙箱里执行（代码可能删文件、读环境变量）、结果还不可复现。原文的结论是要异步并发：多条轨迹同时等工具，训练进程有数据就更新（AReaL 等框架做的就是这件事）。代价是数据略微“过期”，又回到 off-policy 的老问题——原文第 4.2 节附录里提到的 M2PO 等工作正是在研究“过期数据能用到什么程度”。

各类智能体：动作、奖励与陷阱

原文第 20–24 章：chapter23_rl_based_swe、chapter24_deep_research、chapter25_computer_use、chapter26_vlm 等

代码智能体（SWE-RL）：读 issue、搜文件、改代码、跑测试，测试结果当奖励。原文的小例子很说明问题：修“空购物车求平均值除零”时，模型第一版用 try/except Exception 吞掉所有异常——空列表测试通过了，却把传入 None 这类真正的错误也掩盖了；加了回归测试才暴露。可执行测试是很好的验证器，但覆盖不全时，奖励会奖励“让测试通过”而不是“修对”（第 12 篇会看到更极端的：直接改测试）。原文还介绍了 SWE-bench、代码世界模型与自博弈。

Deep Research 与浏览器智能体：动作是搜索、点击、阅读，难点是构建可训练、可复现的浏览器环境和评测（答案正确性、引用是否真的支持结论）。Computer Use / GUI 智能体：从截图到可执行动作；最大的新风险是间接提示注入——网页或工具返回里藏着“忽略之前的指令”。原文给的思路是指令层级（system > user > tool 内容）写进训练数据和多目标奖励，再在模型之外加动作白名单、高风险动作二次确认、沙箱与审计日志。

多模态：VLM 的 GRPO（几何题 GeoQA、计数题）用规则验证答案，另加“看没看图”的奖励防止模型只靠文字猜；音频、具身（VLA）和视觉生成（如 DanceGRPO）把 RLVR / RLHF 搬到新的状态表示和奖励来源上。原文第六部分的共同主题是：状态表示变了、奖励来源变了，但“策略、优势、约束、评测”这套骨架不变。

智能体动作常见奖励典型陷阱
搜索 / Deep Research写 query、读网页、作答答案正确 + 格式；引用是否支持模板化 query、证据不足提前作答、引用不支持结论
代码（SWE）搜索文件、编辑、运行测试单元测试 / 回归测试通过吞异常、硬编码、改测试；环境不可复现
工具调用 / 函数调用选工具、填参数格式 + 参数正确 + 执行结果只学会调用格式，不用返回结果
GUI / Computer Use点击、输入、滚动任务最终状态提示注入、越权操作、不可逆动作
VLM看图推理、作答规则验证答案 + 视觉相关性不看图、只靠文本先验猜答案

算法卡 · 多轮 Agentic RL

Search-R1 / Agent-R1 / RAGEN 一类的做法

解决什么问题
让模型学会在多轮中调用工具、利用观测修正计划，而不只是模仿示范（SFT / prompting 学不到“哪一步该做什么”）。
核心做法
在沙箱环境里在线采多条轨迹 → 结果 / 格式 / 成本奖励 → 组内或步骤级优势 → action mask 只在动作 token 上做 PPO / GRPO 更新。
关键公式
∇J = 𝔼[R(x) Σt∈a(x) ∇log pθ(xt|c, x<t)]；Δθ = Ai,t·Σk∈ai,t∇log π(yk)
何时用
搜索问答、代码修复、工具调用、网页与 GUI 操作等多步任务。
代价与坑
环境搭建与沙箱成本高；奖励方差大；GPU 等工具；只有结果奖励时学到浅层策略；安全边界（提示注入、越权）。

易混辨析：动作 token、观测 token 与 Agent 的“环境”

动作 vs 观测：模型自己采样的 token（思考、工具调用、回答）是动作，参与策略梯度；工具 / 网页 / API 返回的是观测，要 mask 掉。

轨迹奖励 vs 步骤优势：前者是环境给的全部信号；后者是算法构造出来的、分给每一轮的功劳。

单轮 RL 的“环境”vs Agent 的环境：前者只是把 token 拼到上下文；后者有隐藏状态 s₀，会随动作改变，可能随机、可能失败、需要沙箱。

指令 vs 数据：网页、工具返回里出现的“指令”是数据，不是用户或系统的命令——这是对抗提示注入的核心原则。

回扣开头的三个问题

先自己答，再点开

本篇公式卡

状态：z_t = [s₀, c, x_{1:t}]（隐藏环境、任务上下文、token 历史）
轨迹概率：ρ_θ(x | s₀, c) = 𝕀(s₀, x) · Π_{t∈a(x)} p_θ(x_t | c, x_{<t})
action mask 梯度：∇J = 𝔼[R(x) Σ_{t∈a(x)} ∇log p_θ(x_t | c, x_{<t})]
三层信号：R(τ_i) → A_{i,t} → Δθ = A_{i,t} Σ_{k∈a_{i,t}} ∇log π_θ(y_k | h_{i,t}, y_{<k})
GiGPO：A = A^E(τ) + ω·A^S(a_t)，A^S = (R_t − mean_{同状态组} R) / F_norm
1. 状态由哪三部分组成？为什么观测 token 不能参与梯度？

隐藏的初始环境状态 s₀（模型看不到）、任务上下文 c、到当前为止的 token 历史 x₁:t。轨迹概率只在模型生成的位置连乘，环境返回的内容由环境决定，不是策略采样的；让它参与梯度等于训练模型去预测网页 / API 的返回，污染策略梯度。实现上用 action mask，把观测位置置 0。

2. 成败信号经过哪三层？GiGPO 怎样不训练 PRM 也得到步骤优势？

轨迹奖励（这一局成没成）→ 步骤优势（每一轮该不该被奖励）→ token 梯度（乘到该轮动作 token 的 log-prob 上）。GiGPO 把不同轨迹里相同的环境状态聚成组，用各动作之后的折扣回报做组内相对优势，再与轨迹级优势加权相加；只需要最终结果信号。

3. 为什么奖励方差大、GPU 空等？只给结果奖励会学到什么？

环境本身随机（搜索结果变、工具失败），加上长程决策让早期小差异被放大，同一 prompt 的成功数在轮次之间波动很大。工具执行在 GPU 之外且延迟长尾，同步批处理要等最慢的那条，所以要异步并发。只给结果奖励时，模型可能学到模板化 query、证据不足就作答、调用工具却不利用返回结果等“看起来会”的浅层策略。
