先问三个问题

原教程 如何选择你的应用该开发的平台 第 1 节

很多人有了想法先问“该用 Flutter、Electron 还是小程序”，原教程说这个顺序反了：平台不是技术偏好题，它取决于用户在哪里打开软件、任务发生在什么设备上、软件需要多深的系统权限。同样是“售后服务”，消费者入口适合小程序，客服和运营要网页后台，维修工程师可能还要一个能拍照、扫码、离线填写的移动端。业务只有一个，入口可以不止一个。

三个问题：用户会从哪里打开它？从搜索、链接、企业门户进来，优先网站或 PWA；从微信群、公众号、线下二维码进来，优先小程序；每天长时间使用、窗口一直开着，优先桌面端；工作本来就在浏览器或编辑器里，优先浏览器插件或 IDE 插件。需要哪些设备能力？相机、扫码、定位不一定非要原生；真正拉开差距的是长时间后台运行、蓝牙和串口通信、本地大文件处理、系统级快捷键、设备驱动和严格的性能要求。需要的权限越深，越该靠近操作系统。谁来长期维护？一套代码发多个平台能减少重复，但商店审核、登录、支付、通知、权限、文件系统、窗口行为最后仍要分别测试。

原教程把这三个问题压成一句口诀：能用链接解决的，先做 Web；用户就在微信里，先做小程序；需要后台运行、硬件或系统权限，再考虑原生；同一业务有多种角色，就让多个客户端共用一个后端。

回答三个问题，看第一版该选哪个平台。

十条常见架构路线

原教程 选平台 第 2–3 节

原教程逐条讲了十条路线，每条都说了企业里常拿它做什么、最大代价是什么。网站 / PWA：点开就能用，适合 SaaS 后台、CRM、看板、知识库、预约，代价是系统权限有限；PWA 仍然是网站，只是多了安装到桌面和离线缓存。微信小程序：优势不是比 App 高级，而是用户不用安装，适合会员、点单、报名、预约、售后工单，受微信环境和审核约束。iOS / Android 原生：离系统最近，后台定位、蓝牙、健康数据、音视频、复杂动画支持最完整，代价是两端各自的工程和发布成本。Flutter / React Native：大部分界面和业务共享，适合两端业务大体相同的电商、销售拜访、现场服务，平台差异仍要单独处理。

Electron / Tauri：用 Web 技术做桌面软件，适合协作客户端、AI 桌面助手、内部工具；Electron 自带 Chromium 和 Node.js、生态成熟，Tauri 用系统 WebView、安装包更轻。Qt / 原生桌面：不只是工厂大屏，常用于设备控制台、医疗影像、汽车诊断、实验室和交易终端，要连串口、Modbus、CAN、仪器，在 Windows、Linux、嵌入式上长期稳定运行。浏览器插件：功能就发生在网页旁边，适合客服知识助手、销售线索补全、合规检查。VS Code 插件 / CLI：开发者工具放进开发流程，插件负责交互，CLI 负责进脚本和 CI。多端企业系统：不同角色不同入口，共用后端。Godot 等游戏引擎：实时画面、输入、碰撞、动画、关卡都现成，比在网页里重搭游戏循环合适。

这些产品，第一版最该选哪条路线？

多端组合：界面可以不同，后端应当统一

原教程 选平台 第 2.9、4、6 节

企业业务很少永远停在一个平台。原教程给的常见组合：零售与会员，消费者用小程序查积分领券申请售后，店员用移动端核销，总部在 Web 后台配活动看数据；现场服务与售后，客户从小程序报修，工程师在移动端接单拍照离线记录，调度在 Web 后台派单，要连检测仪器再加一个 Qt 或原生桌面工具；企业知识与 AI 助手，知识库和权限放后端，员工在浏览器里就给侧边栏插件，在 VS Code 里就给 IDE 插件，批量处理再给 CLI。

这里真正要共享的是业务规则和数据，不是强求每个端的界面代码一样：统一身份、业务 API、数据库、文件存储、审计日志。多端产品最怕每个客户端各写一套会员、订单、权限规则。原教程还列了四个常见误区：“一套代码”不等于“一次测试”（跨端框架替你共享代码，但替不了权限、支付、通知、窗口、商店和真机兼容测试）；企业软件不等于工控软件（CRM、审批、排班、售后都是企业软件，只有真的连设备协议、实时数据或本地大文件才轮到 Qt）；不要第一天就做全平台（同时做五端，容易得到五个都不完整的版本）；客户端不同，后端仍应当统一。

点开售后服务这套多端系统的每一层。

几个端各自的关键边界

原教程 带后端的微信小程序、浏览器 AI 插件、PWA 等各端教程

各端教程的操作步骤会随工具更新而变，但每篇里都有一两条不变的边界，值得单独记住。带后端的小程序：原教程的一句话是“前端负责让用户操作，后端负责让业务可信”。AppSecret、支付密钥、AI Key，用户身份和工单归属，价格库存积分订单状态，内容审核和防重复提交，这四类都不能为了省事放在前端。它用 CloudBase 给一个“会员 + 售后工单”小程序逐项接后端，每接一项就同时去小程序页面和控制台确认结果。

浏览器插件：只有三个核心部分，Content Script 读取当前页面可见文字，Service Worker 接收事件组织流程，Side Panel 展示按钮、加载状态和结果。原教程对比了 Glean（侧边栏查公司资料，仍遵守原系统权限）、Grammarly（建议直接出现在句子旁边，平时安静）、Edge Copilot（读当前页面要用户知情、管理员可管）三种入口，结论是：侧边栏只是入口，员工身份、文档权限、搜索服务和审计在后端；插件只申请真正需要的站点和能力，共享密钥放企业后端；开发先从不联网的本地版本开始。PWA：首先还是网页，适合想马上打开、网络偶尔断、没必要装几十兆客户端的轻量产品（原教程举了 Starbucks 点单），菜单和购物车可以弱网可用，提交订单和付款时明确要求联网；它不等于拥有原生 App 的全部系统能力。

发布上架：能运行和发布给用户是两回事

原教程 如何把开发好的程序发布上架

无论用什么技术，最后都要走这段路：确定渠道 → 固定应用身份 → 构建 Release 包 → 签名 → 内测 → 准备商店资料 → 提交审核 → 灰度发布 → 监控与更新。常被混称为“上架”的其实是四件不同的事：打包（生成正式安装包）、签名（证明包来自你且没被篡改）、分发（通过什么渠道交到用户手里）、审核（平台检查是否符合规则）。第一款作品不必同时上六个平台，先选用户最集中的一个渠道做通一次完整发布。

所有平台共用的发布前检查：用组织身份持有资产（开发者账号、域名、签名证书、云服务、收款资料不要绑在外包或某个员工的私人账号上，并开双重验证）；尽早固定应用身份（Android 包名、Apple Bundle ID 是“身份证”，发布后改了会被当成全新应用，旧用户无法升级；别再用 com.example.myapplication）；区分版本号和构建号（用户看到的是 1.2.0，商店识别的是每次上传的构建号，哪怕只是重打同一版本也要加构建号）；准备真正的 Release 环境（生产域名和 HTTPS、客户端里没有服务端密钥、没有测试账号和调试菜单、崩溃监控可用、数据库升级不清空旧数据）；隐私声明与真实行为一致（最常见的问题不是没有隐私政策，而是代码、权限弹窗、商店申报、隐私政策四者互相矛盾）；给审核人员一条走得通的路径（专用测试账号，不能要求短信验证码）。

各平台要点：Android 面向 Google Play 用 .aab，keystore 放团队密码库、绝不进 Git，先走内部或封闭测试轨道再逐步放量；中国大陆没有单一 Android 商店，要分别上华为、小米、OPPO、vivo 等，并按规定办理 APP 备案，多市场保持包名一致、签名兼容、版本号只增不减。iOS 在 Xcode Archive 后上传，先 TestFlight 内测，提交时先点 Add for Review 再点 Submit for Review，只做前一步不等于送审；被拒后改代码要加构建号重新归档。Windows 可走 Microsoft Store（MSIX）或官网分发（要受信任的代码签名证书）；macOS 官网分发要 Developer ID 签名、提交 Apple 公证并 staple 票据；Linux 常用 Flathub、Snap Store；Web 没有上架按钮，部署到 HTTPS 域名就是发布。

先走一遍发布流程；再勾一勾你的发布前检查。

用手机远程指挥编码 Agent

原教程 三阶段 Claude Code 手机远程开发

原教程收了一个很实用的话题：通勤路上想到修复方案、排队时收到线上故障，能不能用手机让编码 Agent 干活？手机直接开发有四个限制：输入、屏幕、环境（跑不了完整工具链）、连接（移动网络易断）。所有方案的核心思想都是瘦客户端架构：手机只是“控制台”，负责输入指令、查看输出、审查改动；真正运行 CLI、执行代码、访问文件的是家里的主机或云端。

原教程比较了几种做法：官方移动端和 Remote Control（官方集成、可访问本地环境，有订阅和地区限制）；Happy Coder（扫码配对、跨平台、端到端加密，但依赖第三方中继，社区反馈断线较多）；HAPI（本地优先、可自建中继、支持多种编码 Agent，搭配 Tailscale 更稳）；SSH + Tailscale + tmux（Tailscale 组虚拟局域网免内网穿透，tmux 让会话在断线后继续运行，功能最完整但配置稍复杂，电脑要常开）；Android 上的 Termux 本地运行；没有电脑就用云端开发机。安全上要想清楚中继服务器能看到和能做什么：元数据、端到端加密实现不当时的明文、配置不当时的 API Key，甚至注入命令。对稳定性和安全要求高时，原教程推荐自建中继或官方方案。

回答几个问题，看哪种方案适合你。

用 AI 搭一个属于自己的个人主页

原教程 三阶段 如何构建属于自己的个人网页与学术博客

原教程最后一篇回到个人：个人主页是你在互联网上的一块“私有领地”，不依赖平台算法、不会因为平台倒闭而消失，能被搜索引擎索引。对外它是“永不过期的名片”，对内是“第二大脑”，对未来意味着别人搜你的名字时，排在前面的是你定义的内容。在 Vibe Coding 模式下，你的角色从写代码的人变成网站主编：你决定调性和内容，AI 负责把指令变成代码，GitHub Pages 提供免费托管。

建站有四种方式：从零手写（最灵活、门槛最高）、可视化建站（Wix、WordPress，简单但常要付费、难深度定制）、基于 GitHub 模板（Fork 成熟的 Jekyll / Hugo 学术模板，只改配置和内容，原教程最推荐）、AI 视觉生成（截一张喜欢的网页让 AI 照着写）。它的实操路线是：Fork 模板 → 拉到本地预览 → 用 AI 分阶段修改内容（为了避免隐私顾虑，先拿公众人物的公开资料当测试数据）→ 定制风格 → 推送到 GitHub Pages。关键技巧是先发一条统一前置约束给 AI 立规矩：每步只做当前阶段目标、不改站点结构不引新插件、改动必须能被模板正常构建，防止它自由发挥把网站结构弄坏。进阶玩法是让 AI 从零“手搓”一个风格鲜明的主页。

这一节正好也是这个博客的来历：本系列就是用编码 Agent 写成、部署在 GitHub Pages 上的。

这条前置约束可以直接复用。

你现在是一个“GitHub Pages + Jekyll 学术主页模板”的站点维护者。
当前仓库是一个 Jekyll 驱动的学术主页（含 _config.yml、_data、_layouts 等）。
你的修改必须满足以下原则：
1. 每一步修改只做“当前阶段目标”，禁止提前做后续阶段内容
2. 不修改站点结构、不引入新插件、不改主题风格（除非我明确要求）
3. 所有内容必须可被 Jekyll 正常构建，改完告诉我本地预览命令
4. 每次只列出改了哪些文件、改了什么，不要大段重写无关内容

回扣开头的三个问题

先自己答，再点开
1. 选平台的三个问题？何时才值得做原生或 Qt？

用户会从哪里打开它（链接、微信、长时间桌面使用、浏览器或编辑器里）；需要哪些设备能力；谁来长期维护。相机、扫码、定位不一定要原生；只有需要长时间后台运行、蓝牙串口、本地大文件、系统级快捷键、设备驱动、严格性能时，才值得靠近系统做原生；Qt 适合真的要连设备协议、实时数据、离线长期运行的桌面软件，普通企业管理后台用 Web 更易部署维护。

2. 多端产品共用什么？为什么一套代码不等于一次测试？

共用统一身份、业务 API、数据库、文件存储、审计日志等业务规则和数据；各端界面可以不同，按角色和工作环境设计。跨端框架能共享代码，但权限、支付、通知、窗口行为、应用商店审核和真机兼容在每个平台上都不一样，仍要分别测试；所以先做最重要的一个入口，后端边界稳定后再扩展。

3. 打包、签名、分发、审核各解决什么？版本号和构建号的区别？

打包生成正式安装包；签名证明包来自你且未被篡改（keystore 等签名材料要放团队密码库，不能进 Git）；分发决定通过哪个渠道交给用户；审核是平台检查是否合规。版本号是用户看到的 1.2.0；构建号是商店识别每次上传的编号（Android 的 versionCode、Apple 的 Build），即使重打同一版本也必须递增。
