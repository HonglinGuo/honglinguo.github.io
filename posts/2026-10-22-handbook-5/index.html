模型此刻应当看见什么

长任务每推进一轮，Harness 都要重新回答这个问题。全塞进去，成本、延迟上升，关键约束被淹没；只留最近几轮，又会丢掉目标变更、已确认事实、副作用和恢复位置。窗口有限而任务世界持续增长，原书因此要求一套独立的信息系统：把多来源信息编译成本轮 Context，把历史压缩和卸载，把任务事实存在窗口之外，把 Memory、Knowledge、Skill 在正确权限下按需提供。

本系列是开源白皮书《AI Agent Handbook（企业级 Agent 白皮书）》（阿里云团队编写的开源白皮书，Apache-2.0 协议；本笔记依据 2026 年 10 月 21 日的仓库版本）的学习笔记。原书按“架构 → 构建 → 运行 → 治理 → 调优 → 实践”组织三十章，这里重排成十五篇，用自己的话重讲，并把关键表格做成可以点、可以分类、可以走流程的互动。概念与结论取自原书，每节标出对应章节；为演示设的场景和数值标“示意”。原书由阿里云编写，涉及阿里云产品的方案与数字属于厂商自述，文中会单独标出。

System Context 是“编译”出来的

原书 5.1 节

生产级 Agent 的 System Prompt 不该只是仓库里的一个长字符串。每轮模型实际收到的输入，要根据 Agent 版本、任务阶段、用户身份、工作区规则、剩余预算、可用工具和选中的 Skill 动态生成：多个来源按优先级合并、处理冲突、超预算的压缩或移除，更像一次编译。原书把它分成 System Context（平台策略、Agent 契约、租户与项目规则、运行时提醒、选中的 Skill、工具描述）和 Task Context（目标与纠偏、Plan / Todo、最近交互、压缩历史、检索到的 Memory 与 Knowledge、工作区引用）。

分层解决的是责任问题：平台策略不能被项目文档覆盖；用户最新要求能改变方向，但不能突破安全边界；Memory 里的历史偏好不能替代当前业务事实；工具返回的外部内容不能自动升级为系统指令。全部拼成一层文本，就说不清冲突来自哪里，也无法分别版本化和回归。

Context Builder 在每次调用前跑一条确定性管线：读取任务状态 → 解析身份与作用域 → 收集候选 → 权限与可信度过滤 → 相关性排序与去重 → 分配 Token 预算 → 压缩、截断与引用化 → 按层级编译 → 生成 Manifest。顺序很要紧：不能为了排序方便，先把跨租户内容交给检索器或模型。

Token 预算与 Context Manifest

原书 5.1 节

Context 不能只按相似度排序。原书的优先级函数同时看七个因素：约束强度（平台政策与明确业务规则高于经验建议）、任务相关性、时间有效性（当前环境事实高于过期结论）、来源可信度（权威系统事实高于未确认的模型摘要）、执行依赖（即将调用的工具说明和验收条件优先）、信息增量（重复的合并或移除）、Token 成本（同等价值选更紧凑、可引用的表达）。

窗口可以划成预算区：不可覆盖规则、当前目标和状态有固定下限；最近交互、检索知识、Skill、工具 Schema 分动态额度；还要给模型输出和后续 Observation 留空间。预算不是静态百分比：进入工具密集阶段，工具定义和环境状态权重上升；进入最终综合阶段，证据和验收条件更重要。

每次调用都应生成一份 Context Manifest，记录模型究竟看到了什么：来源与 ID、作用域、版本、可信等级、为何有权读取、为何被选中、占多少 Token、做了什么变换、内容哈希。它不保存敏感内容本身，却能支撑三件事：开发时解释模型为什么遗漏某项信息、评估时比较两个版本的 Context 差异、审计时确认某条敏感内容为什么进了模型。层级、检索范围、预算、压缩阈值、工具披露、敏感内容处理统一定义为 Context Policy，与 Agent 版本绑定，把“偶然看见了什么”变成可测试、可回放的工程行为。

压缩、卸载与续行

原书 5.2 节

原始历史保存在外部，按阶段构造一个 Active Context：稳定的目标与约束、当前任务状态、需要精确理解的最近原文、更早过程的结构化摘要、本轮相关的检索结果、可按需读取的 Artifact 引用。“最近”不只按时间：用户对目标的最新修改、未解决的工具错误、待审批动作、验收失败证据，即使产生得早也属于活动状态；已完成且能由 Artifact 证明的探索，可以退出窗口。

对话压缩不是普通摘要，它要支持下一轮继续执行，必须保留目标与约束、已确认事实及来源（区分事实、假设、建议）、决定与被否决方案、已执行行动与副作用、Plan / Todo / 阻塞、Artifact 与外部对象 ID、偏好、审批与权限模式、失败尝试。摘要用结构化 Schema、带覆盖范围和来源；高风险事实最好从 Task State、工具结果、审批记录中确定性提取，只让模型压缩叙述性内容。四步是 Commit（先把结构化事实提交到权威状态）→ Compact → Rebuild → Validate。顺序的道理：任何会影响后续行动的事实，先进权威状态，才允许从窗口移除，否则一次不准的摘要就能改写任务真实状态。

大结果（几万行的日志、扫描报告）不应反复进入每轮 Context：原文写进 Workspace 或 Artifact Store，窗口里只留摘要、关键片段、类型、大小、来源工具、权限和稳定且受权限保护的引用（临时 URL 恢复时可能已失效），会变化的还要记快照版本。多次压缩仍不够、或进入新大阶段时可以 Context Reset，新窗口从 Continuation Package 和权威状态重建，不重放全部对话。压缩质量也不能只看省了多少 Token：事实保留率、继续成功率、矛盾率、引用可用率、成本收益要一起衡量。

Call、Session、Task 与 Workspace

原书 5.3 节

三个经常被统称为“会话”的边界：Call 是一次请求或恢复动作（秒到分钟，带请求 ID、身份、临时凭证、返回游标）；Session 是某个调用方与 Agent 的连续交互边界（分钟到数天，参与者、Channel、消息、偏好）；Task 是围绕可验收目标持续存在的执行对象，可以跨 Call、Session、进程和节点。一个 Session 可以发起多个 Task，一个长 Task 也可以在多个 Session 中被查看和恢复。把 Task ID 绑成消息线程 ID，会限制后台执行、多人协作和跨渠道续接。

任务状态有三种互补表示：Event Log 记录发生过什么（追因果、审计、重建），Snapshot 记录某一时刻的聚合状态（快速读当前视图），Checkpoint 表示可以安全恢复执行的位置（除快照外还包含 Continuation、幂等和环境依赖）。三者不能互相替代：只有日志，恢复成本随任务长度增长；只有快照，说不清状态怎么来的；把每次保存都叫 Checkpoint，会掩盖某些工具事务仍在进行、不能安全重放。Harness 面向逻辑状态接口编程（append_event、commit_task_patch、create_checkpoint、read_range 等），本地映射到文件，分布式映射到外置服务。

Workspace 是可寻址、可检查、可逐步修改的外部工作记忆，和 Memory 的区别在于它服务当前任务、内容通常用户可直接查看编辑。原书把它分成 inputs、scratch、state、artifacts、evidence、manifest：生命周期和责任不同，不能因为都在文件系统里就用同样的保留和权限策略。Artifact 有自己的生命周期 Draft → Validating → Ready → Published / Rejected → Archived / Deleted，模型写出文件不等于产物完成。

Memory 提供经验，Knowledge 提供事实

原书 5.4 节

Memory 不是无限增长的历史数据库，而是 Harness 有选择地写入、检索、更新、遗忘的信息。原书分四类：Working（当前任务的临时事实，直接来自 Task State）、Episodic（过去任务的经验片段，要保留当时条件和 Outcome，免得把偶然成功当规律）、Semantic（稳定事实、偏好、实体与关系，要有来源与更新时间）、Procedural（已验证的方法，稳定后最好升级为受版本治理的 Skill）。

“每次任务结束自动总结写入 Memory”很容易造成污染。写入前要过六问：未来是否有可预期价值？是验证过的事实还是推测？属于哪个用户 / 项目 / 租户、保留多久？是否含敏感数据？新增、合并、更新还是标冲突？将来错了谁能纠正、派生索引怎么清理？检索到也不代表能直接进 Context：要按当前身份和目的过滤，并标记为历史经验而不是当前事实。新旧冲突时不静默覆盖；长期未用、未验证或持续导致错误的要衰减、复核或遗忘。

Knowledge 由组织维护，权威责任在内容所有者，风险是过期、权限泄漏、来源冲突；Memory 由 Agent 积累，风险是污染、错误固化、跨用户混淆。知识接口应返回结构化证据（内容、来源与 ID、版本或生效时间、所有者与权威等级、ACL 作用域、检索理由、时效、引用），实时经营数据和强一致事实优先查权威工具而不是离线索引；权限过滤不能靠向量库里的自然语言标签推断。AgentScope 的做法是双层记忆：当日事实追加到 memory/YYYY-MM-DD.md，周期性合并去重到 MEMORY.md，压缩前先 Flush 关键事实。

Skill 与渐进式披露

原书 5.5 节

Tool 告诉 Agent “能做什么动作”，Skill 告诉 Agent “在某类任务里怎样正确使用若干动作”。一个 Skill 包由 manifest（名称、版本、所有者、适用条件、所需工具 / 权限 / 环境、输入输出与验收契约）、指令、脚本、模板、示例、参考资料和测试用例组成。它不直接拥有额外权限：当前用户、任务和环境允许时，相关能力才能执行。

企业积累几百个 Skill 后，全部注入每轮 Context 会耗尽窗口，也让模型选错能力。渐进式披露分三层：发现层只看名称、简述、适用条件和主要风险；选择层由 Harness 按任务、权限、环境解析候选并加载完整 Manifest；执行层真正需要某一步时才读详细指令、脚本和参考。选择不只靠语义匹配，还要查模型兼容、工具依赖、环境、租户许可、数据范围和版本状态：要写生产系统的 Skill 在只读探索阶段可以被发现，但不能进入可执行状态。

Skill 中稳定、重复、可编码且失败代价高的步骤（格式转换、固定校验、权限查询、跑测试）沉淀为脚本或工具，模糊目标、方案比较、异常解释留给模型。一次成功不等于可复用能力：要从 Trace 提取稳定步骤、去掉任务 ID 和临时路径、给脚本补测试，再走 Draft → Test → Review → Publish → Observe → Update / Deprecate / Rollback。评估看启用前后的成功率、步骤数、工具错误、人工修改量、成本与安全事件，而不只是被选中没有；生产 Trace 必须能定位到具体 Skill 版本，latest 指针只适合开发。

拖动 Skill 数量，比较“全量注入”和“渐进式披露”的窗口占用（每项 token 数为示意）。

易混辨析：Skill vs Tool vs Prompt vs Procedural Memory

Tool 是一个动作；Skill 是某类任务的方法，可以调用多个工具和脚本，但不带额外权限；Prompt 只是一段指令文本，没有脚本、测试、版本和评估；Procedural Memory 是自由文本形式的方法经验，稳定且可复用后应升级为 Skill，进入测试、评审、发布与回滚。

作用域、污染与真正的删除

原书 5.6 节

Context、Memory、Knowledge、Skill 都可以跨任务复用，但不能默认全局可见。原书的作用域模型从大到小是 Global、Tenant、Project、User、Session、Task。检索和 Context 构建必须先确定调用身份、租户、项目和任务，再查询允许的作用域；不要先跨作用域召回、再在生成端“提醒模型不要泄漏”，内容一旦进了模型输入，隔离就已经失败。每项资产带最小治理元数据：来源、所有者、作用域、版本、时间、权限、敏感级别、保留周期、摘要、派生关系、状态。

要防三种污染：记忆污染（错误推测、失败轨迹、恶意输入被长期写入）、指令污染（外部文档、工具结果、Memory 里的文字被提升为高优先级规则）、跨租户污染（索引、缓存、摘要、Artifact、评估数据把一个租户的信息带进另一个）。防护覆盖写入（来源识别、验证、敏感检测、作用域绑定、冲突检查）和读取（身份过滤、信任标记、指令与数据分离、最小披露、输出审查）两端。

“遗忘”有时是权重衰减，有时是彻底删除，二者必须在策略中区分：需要撤回的数据不能只降检索分数。资产变更（Context Policy、Memory、Knowledge、Skill）也要走和代码一样的发布链：结构与权限校验 → 受影响用例分析 → 离线回放与安全评估 → 灰度 → 监测 → 保留、修订或回滚，并按场景、租户、风险分层评估。

回扣开头的三个问题

先自己答，再点开
1. 为什么先过滤权限、再排序？Manifest 有什么用？

内容一旦交给检索器排序或进入模型输入，跨租户隔离就已经失败，“提醒模型别泄漏”不是隔离。Manifest 记录每轮输入的来源、作用域、版本、可信等级、读取依据、选择理由、token、变换和哈希，用来解释遗漏、比较版本差异、审计敏感内容为何进入模型，而只存拼接后的 Prompt 文本做不到。

2. 压缩前为什么先 Commit？三种状态表示有何区别？

任何影响后续行动的事实（审批、工具提交结果、Plan 状态、Artifact、外部对象 ID、预算、用户变更）必须先进入权威状态，才能从窗口移除，否则一次不准确的摘要就会改写任务真实状态。Event Log 记过程（审计、重建），Snapshot 记某时刻聚合视图（快速读取），Checkpoint 是可安全恢复的位置（含 Continuation、幂等与环境依赖）。

3. 信息该去哪？删除为什么不只是删向量？

只服务当前任务、须精确恢复的 → Task State / Workspace；可复用但需来源与验证时间的经验 → Memory 候选；组织维护的制度和事实 → Knowledge；验证过的稳定方法 → Skill 候选（测试、版本化后发布）；未验证的推测 → 不写入。删除要禁止新读取与注入、删除或隔离原文、清理索引缓存摘要等派生数据、更新引用它的 Manifest 和 Skill、保留最小化的审计证明、触发受影响 Agent 版本的验证。
