先写契约，再挑框架

构建 Agent 的主要工作，是为模型建立与任务结构、风险等级相匹配的 Harness。企业不必从零写模型之外的全部系统：可以用高代码框架自己搭，可以复用 Coding Agent 那样的产品化 Harness，可以把 Harness 连同运行一起交给托管服务，也可以在云产品里组合预置能力。四条路的差别不在模型，而在于 Harness 的通用行为由谁实现、Runtime 与 Sandbox 由谁提供、企业还要补哪些责任。

本系列是开源白皮书《AI Agent Handbook（企业级 Agent 白皮书）》（阿里云团队编写的开源白皮书，Apache-2.0 协议；本笔记依据 2026 年 10 月 21 日的仓库版本）的学习笔记。原书按“架构 → 构建 → 运行 → 治理 → 调优 → 实践”组织三十章，这里重排成十五篇，用自己的话重讲，并把关键表格做成可以点、可以分类、可以走流程的互动。概念与结论取自原书，每节标出对应章节；为演示设的场景和数值标“示意”。原书由阿里云编写，涉及阿里云产品的方案与数字属于厂商自述，文中会单独标出。

Harness 是什么，不是什么

原书 3.1.1 节

这一章给了 Harness 一个更工程化的定义：模型之外、围绕 Agent Loop 组织上下文、能力、状态、环境与控制机制，把模型判断转化为可执行、可恢复、可验证任务过程的代码、配置和执行逻辑。原书用三个“不是”来划界：它不是更长的 System Prompt（Prompt 只是它每轮生成的输入之一，状态机、工具注册、权限检查、错误恢复、完成验证都是确定性逻辑）；它不是某个 Framework 的同义词（框架可以帮你实现，CLI / SDK 可以提供现成的，托管服务可以连运行一起托管）；它也不是 Runtime 或 Sandbox。

为什么需要它？一次模型调用没有可靠的跨轮状态，不知道任务是否已在别处推进；窗口有限；工具调用只表达意图，不等于用户已授权；模型可以声称完成，却证明不了文件已生成、测试已通过、订单已提交。Harness 的工作就是把概率性的判断嵌入确定性的边界。

原书把责任分五层：Model（能理解推理到什么程度）、Harness 编排（Agent 如何工作）、Runtime（如何持续运行）、Sandbox / Environment（在哪里行动、影响多大）、Agent Platform（如何规模化交付和治理）。一个 SDK 可以同时包含 Harness 和本地 Runtime，托管服务可以同时提供三者，但设计时仍要保留边界，否则说不清故障归属、数据位置、迁移成本和最终责任。

下面每件事归哪一层负责？

八个构建对象，从任务契约开始

原书 3.1.2 节

从开发者视角，构建 Harness 不是罗列功能，而是让八个工程对象在同一个任务生命周期里协同：Agent Contract（为谁工作、目标、允许与禁止）、Execution（循环、规划、等待、委派、结束）、Context & State（每轮看什么、事实存哪）、Capability（Tool、MCP、Skill、Subagent）、Environment（在哪里运行）、Control（以谁的身份、哪些要拒绝或审批）、Interaction（进度、干预、恢复）、Quality（怎么证明完成、新版本是否更好）。最小 Agent 可以只实现一部分，进生产后每一项都要有明确责任人。选构建路径，本质上就是决定哪些对象自己开发、哪些复用产品、哪些交给托管平台。

原书强调，构建不能从选框架或打开工具开始，而应先固定任务契约：为谁工作、接受什么输入、交付什么结果、允许影响哪些系统、哪些动作必须拒绝或审批、什么证据证明完成。同一个“修复高危依赖漏洞”的目标，可以只出分析报告，可以在隔离环境里改代码跑测试，也可以创建合并请求；除非契约明确授予发布权限并规定审批条件，这些 Agent 都不应把“修复完成”解释成“已经发布生产”。

四个构建入口：谁实现 Harness，谁提供运行

原书 3.1.3 节，表 3-2

选入口之前先判断路径由谁控制：步骤、分支、异常在设计时已明确的用 Workflow；路径要按中间结果动态决定的让 Agent 持有部分决策权；主流程稳定但局部判断复杂的用 Hybrid，由 Workflow 固定审批、交易、发布边界，Agent 负责检索、分析、方案。注意，这三者描述的是路径控制方式，和 Single / Long-Horizon / Multi-Agent 不是并列的形态。

然后是四类入口：高代码 Framework 自主构建（AgentScope、LangChain 等，企业直接控制 Loop、Context、规划、状态语义和验证逻辑）、产品化 Harness（Coding Agent CLI / SDK、工作区助手，复用规划、工具执行、Session、事件和过程干预）、基于模型构建 / Managed Agents（Qoder Cloud Agents、Claude Managed Agent，约定范围内的 Harness 连同隔离执行和云端资源一起托管）、基于云产品构建（阿里云 AgentCore，用产品预置的模型、知识、工具、运行环境组合）。任何一种形态都可以从任一入口构建，入口也可以混用：框架写的 Agent 可以跑在托管 Runtime 上，产品化 Harness 也可以被平台调度。

回答四个问题，看哪个入口更合适。

厂商案例说明原书以 AgentScope、QwenPaw、Qoder Cloud Agents、阿里云 AgentCore 分别代表四种入口，它们都来自阿里系产品。本笔记保留原书总结的责任边界，产品具体能力以官方文档为准。

高代码框架：从成功标准反推能力

原书 3.2 节

Framework 路径的核心价值是任务语义控制：每轮 Context 怎样组成、哪些错误可以重试、计划何时生成和更新、何时请求审批、怎样创建子任务、什么证据算完成。相应地，框架只提供构建材料，不会自动补齐多租户隔离、状态恢复、Sandbox、安全策略、评估基线和业务验收。“自主构建”指团队用框架设计 Harness，不是 Agent 自己生成 Harness。

原书的建议是不要一次性打开所有能力，而是从任务成功标准反推。漏洞修复 Agent 至少要读代码、生成补丁、跑测试、做安全扫描；计划未经确认不能改代码，就需要 Plan Mode 与 Permission；分析和评审能并行，就需要 Subagent；任务跨多次调用，就需要外置状态和可恢复 Workspace。一条分工原则贯穿始终：稳定、确定的步骤沉淀为 Tool、脚本或策略；需要理解目标、权衡方案的部分留在 Agent Loop；可能影响外部世界的动作统一经过权限和 Sandbox。这样的 Harness 才有可测试的边界，而不是一组由 Prompt 驱动的隐式行为。

走向在线服务时，实例不能靠进程内消息历史恢复任务：要把 Session、Task、Plan、子任务、Artifact 映射到共享状态，给同一任务设并发写入或执行租约，Worker 失效后从安全点恢复，按租户创建或复用 Sandbox，用短时身份访问企业工具。

产品化 Harness：复用工作方式，补齐企业责任
原书 3.3 节

  

    
Coding Agent 和工作区助手已经形成一套可复用的工作模式：检查工作区、制定计划、调文件和命令工具、维护 Session、请求权限、生成 Artifact、长任务中接受用户干预。CLI 适合开发者直接在工作区操作，SDK 适合把同一套 Harness 嵌入既有应用，工作区助手强调跨入口的连续使用和个人化状态。三者区别不是模型能力，而是 Harness 由谁发起、状态由谁保存、事件由谁消费。

    
原书的 SDK 示例值得细看：tools 限定可用工具集合，allowedTools 只预授权读取和检索，需要确认的修改或命令交给 canUseTool 回调由宿主应用审批，拒绝、取消、超时都应终止操作。提示词里写了“不要发布”，真正落实它的是：cwd 指向受控 Workspace、不注入生产发布凭据、用身份与网络策略阻断发布通路。result 只是运行结果，业务 Outcome 要依据变更文件、测试、安全扫描和业务状态另行确认。

    
封装成多租户服务时，外部 Session Store 能让另一台主机凭 session_id 继续执行，但它只保存对话记录，不保存认证状态、文件 Checkpoint 或保留策略。Worker 失效后要先确认原行动和工作区状态，再决定 Resume、Retry 还是转人工，不能因为 Session 能读到就重放最后一次工具调用。工作区助手同理：原书举 QwenPaw 为例，官方文档注明后台 Subagent 不可恢复、Sandbox 在未启用约束时不提供隔离、多实例 Hub 不构成面向陌生用户的强多租户边界，所以“功能可用”不等于“生产责任已满足”。

易混辨析：Session Store vs 企业任务存储

    
Session Store 镜像的是 Session Transcript（对话历史），让别的主机能接着对话。企业任务存储还要分别管理 Task State、Artifact、Sandbox Snapshot、凭证和业务 Outcome，并保证租户隔离、追加顺序、幂等写入和并发控制。前者能续聊，后者才能续任务。

  

  






  
托管 Agent：用四个对象委派任务
原书 3.4 节

  

    
托管路径把通用 Harness 和运行基础服务化：平台承担基础 Agent Loop、Session 推进、工具运行和 Serverless 隔离环境，企业的工作从“组织一次次执行”转向定义目标、处理干预、验收成果。原书以 Qoder Cloud Agents 为例，核心对象只有四个：Agent（可复用定义：模型、System Prompt、工具、Skill）、Environment（容器环境：依赖、资源、环境变量、凭证）、Session（一次具体任务）、Event（输入与实时执行事件）。一个 Agent 定义可以被多个 Session 复用，每个 Session 有独立的隔离环境。

    
事件流有几个工程细节：新的 SSE 连接（不带 Last-Event-ID）只收建连之后的事件，所以要先确认订阅建立，再提交任务；处理成功后保存事件 ID，断线时用 Last-Event-ID 续接并按 ID 去重；提交超时要先核对服务端状态再决定是否重试，避免重复执行。session.status_idle 只表示当前回合结束，不表示任务成功。

    
托管越多，越要把责任写成机器可执行的契约：Agent 能看见什么工具、Environment 能访问什么资源、凭证以谁的身份发放、哪些事件需要人工参与、什么 Outcome 才能让企业 Task 完成。原书的话很直接：否则“只是把不明确的 Agent 行为转移到了云端”。

Agent Platform：统一对象，不抹平实现
原书 3.5–3.7 节

  

    
云产品入口（原书以阿里云 AgentCore 为例）与托管 Agent 的区别主要在控制面：托管服务侧重把已定义的 Agent 持续执行，云产品还负责创建、资源装配、版本管理和发布配置。原书提醒，在产品界面里完成了配置，不代表所有能力属于同一个架构层；平台侧的“已发布”只说明定义可以被调用，不说明业务任务已完成。建 Agent 也应从任务契约反推资源，而不是把所有模型、知识、工具都挂上去。

    
当多个团队、多种 Agent 并存，每个项目各建模型接入、工具目录、凭证、Session、Sandbox、观测和评估，就会重复投入并形成 Agent、数据、权限的孤岛。Agent Platform 要接入框架写的 Workload、SDK 封装的 Worker、托管或 SaaS Agent，统一的是身份、资源、版本、任务和质量事实，不要求它们改用同一种 Harness。纳管多源 Agent 至少满足三个条件：版本与归属可追溯（不只是一个名字）；Event、Artifact、Trace 关联 Task、Identity、Tenant；远程 Agent 不能只回一段自然语言结论，要提供可验收的 Artifact、事件或环境事实。

    
原书小结里最值得记的一句：无论选哪个入口，都要区分 Task 与 Session、Event 与 Trace、Artifact 与 Outcome，把权限与验证落实为确定性机制，并让模型、Harness 配置、能力、环境、策略、评估基线共同受版本控制。

回扣开头的三个问题
先自己答，再点开

  

    
1. Harness 不是什么？它和 Runtime、Sandbox、Platform 怎么分工？
不是更长的 System Prompt，不是某个框架的同义词，也不是 Runtime 或 Sandbox。Harness 决定下一步给模型什么、允许模型提出什么行动、怎样推进任务；Runtime 负责持续承载（进程、调度、并发、等待、恢复）；Sandbox 把行动限制在可控环境（文件、网络、Secret、资源）；Platform 负责多租户、发布、网关、配额、观测、评估、安全和运营。

    
2. 四类入口的根本差别？为什么不是成熟度阶梯？
差别在 Harness 的通用行为由谁实现、Runtime 与 Sandbox 由谁提供、企业还要补齐哪些控制和验收责任，而不是模型能力或应用形态。它们可以混用（框架 Agent 跑在托管 Runtime 上、产品化 Harness 被平台调度），企业应按任务结构、定制深度、数据边界、环境影响、团队能力和交付方式选最低充分方案。

    
3. 为什么 Session 能续上不等于任务能恢复？三对概念各是什么？
Session Store 只存对话记录，不存认证状态、文件 Checkpoint、业务状态；恢复前要先核对原行动、工作区、幂等键和外部系统状态，再决定 Resume、Retry 或转人工，不能直接重放最后一次工具调用。Task 是企业业务任务、Session 是某个 Agent 实现里的一次执行会话；Event 是执行过程中的实时消息、Trace 是可观测与审计用的结构化执行轨迹；Artifact 是交付的产物、Outcome 是经验证后的业务结果判定。
