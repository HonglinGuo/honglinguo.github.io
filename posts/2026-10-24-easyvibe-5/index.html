原型的价值不由功能数量决定，由范围清不清楚决定

有了问题定义，原教程第一阶段用一个贯穿案例把它做成产品：一家店铺的运营想“用 AI 辅助制作商品图片和文案，让上新准备时间更短”。这句话直接丢给 AI，只能得到一个靠猜的页面。这一篇沿着原教程的路线走：先向业务提问、收敛范围、写成一页需求说明，再交给 AI IDE 生成原型；然后不加新功能，把四个容易卡住的时刻补好，请别人用一次，按真实卡点改一遍，最后整理成别人打开就能用的作品。

本系列是开源教程《Easy-Vibe：Vibe Coding 产品实战教程》（Datawhale 社区编写的开源教程，CC BY-NC-SA 4.0 协议；本笔记依据 2026 年 10 月 22 日的仓库版本（f2239c6））的学习笔记。原教程分“新手入门、第一阶段产品原型、第二阶段全栈、第三阶段进阶”三段，加一个上百篇的附录知识库，图文和操作截图很多。这里只取三阶段正文，重排成十五篇，用自己的话重讲：操作步骤压缩成要点，把方法论和容易混的概念做成可以动手的互动；每篇配原教程里最值得留存的提示词模板，以及一份可以勾选的动手清单。每节标出对应的原教程章节，演示数值标“示意”。笔记同样按 CC BY-NC-SA 4.0 共享。

写代码前，写一页需求说明

原教程 初级三 第 1 节

原教程先分清两个词：需求描述用户希望取得的进展和当前的阻碍（“运营希望缩短每个商品准备首版图文的时间”）；业务是用户每天实际在做的事（上架、改价、做图、看数据）。理解业务，才能判断功能该放在哪个环节、是否真的减少了工作量。于是第一步是带着问题去访谈：“效率高一点”是更快、更少重复还是更高转化？现在怎么上架？哪件事最不想做？

访谈得到的事实很具体：一个人管好几个店，在上架、改价、做图、看数据之间来回切；内容不是一次做好，而是先用厂家图和旧素材快速上架、花点小钱推广看有没有人买，卖得好的才认真做。问题被归成节奏、效率、内容三类，第一版只选内容；再往下挖出两个具体阻碍：批量制作要重复操作，好用的旧方案找不到、复用不了。于是范围定为两件事：批量生成图文草稿，把好用的方案存成模板。

原教程建议把结论写成一页需求说明，六项：给谁用、在什么场景用；要解决的问题（直接用 JTBD 句式）；第一版只做的核心流程；第一版不做什么；怎样算验证成功（写成能观察到的结果）；还没确认的问题。它有两个用处：先和自己对齐范围，再作为交给 AI IDE 的输入，AI 不用再猜。两个常见误区：写成功能清单（只列上传、生成、编辑、导出，没写给谁用、解决什么，AI 会照单全收）；只写做什么、不写不做什么。“不做什么”交给 AI IDE 时还能提醒它别自行补功能。AI 让开发变快了，但第一版仍要足够小，正因为快，才能先满足一群人、拿去测试、小步快跑。

先判断访谈里冒出来的这些想法，第一版做不做；再用模板写一份你自己的需求说明。

一页需求说明（原教程 1.3 节模板，“填入示例”是原教程的电商案例）

易混辨析：第 1 项按什么细分人群

原教程给了三步：先列出互不重叠的参与方（店铺运营、买家、设计师，需求各不相同，别混写）；选一类参与方后，按行为或动机细分，而不是按年龄、性别这类人口属性（“同时管好几个店、要批量上新”和“只管一个店、精细打磨每个商品”是两类运营）；最后从“影响”（人多不多、问题频不频繁）和“未被满足程度”（现在的办法有多麻烦）两个角度打分，只挑一个群体。

把需求交给 AI IDE：三种起步方式

原教程 初级三 第 2–4 节

原教程给了三种起步方式，按准备程度选。从口述开始：用自己的话把想法说一遍（哪怕很粗糙），交给通用对话模型，让它整理成业务逻辑文档和一份给 AI IDE 的实现说明；它常会反问你没想到的问题（“要不要支持批量上传？”），你再删掉不需要的。直接交业务文档：已经写好一页需求说明，就按“输入 / 输出 / 期望的使用方式变化”的格式直接交给 AI IDE，并说明“先做第一个功能，模板库后面再加”。提示词的提示词：让通用模型先写一份给编码 Agent 的提示词，要求包含页面布局、数据结构和交互、技术栈、核心功能点，再拿去生成。

生成后的节奏和第 2 篇一致：先单页面跑通核心流程，再让 AI 对照需求列出还只有外观、没有行为的入口，按优先级逐个补成多页面；每补一页都实际点一遍。两个实用技巧：让 AI 加一个“载入示例”入口，准备一组正常数据和几组边界数据（信息缺失、图片格式不对），每次刷新后都能一键复现同一条流程；让 AI 做需求对照检查，列出哪些已完成、哪些没实现或体验不足。但原教程强调：AI 可以生成检查清单，最终仍要你亲手操作确认。

报错时的原则也一样：先保留一个能运行的版本，再把现象、错误信息、预期行为交给 AI。发送日志前检查里面有没有 API Key、账号等敏感信息。改了很多次还不行，就回退到能运行的版本、换模型，或者把“当前代码 + 错误日志 + 预期行为”打包一次性交给 AI 整体重构那一块。

从截图复刻：练眼力，也练描述

原教程 从截图复刻：第一次模仿练习

原教程在 AI IDE 和原型之间插了一节“临摹课”：找一张喜欢的产品截图（官网首屏、SaaS 看板、小游戏画面），拖进聊天框，只说一句“照着这张图帮我做一个网页，做好后帮我打开看看”。截图已经替你说明了颜色、间距和布局的大半，文字只需告诉它要把图变成网页。如果只想参考样子，加一句“样子参考这张图，名字和内容换成新的”。

它想练的是 Vibe Coding 里很重要的一项能力：看出画面细节，并说出哪里不像。做完把作品和参考图并排放，看自己能模仿到五成、七成还是九成。第一版先做到“能看”：页面能打开、主要内容出现、按钮能点；不要因为字体差一点就推倒重来，一次只指出一个最明显的问题（“中间的标题再大一点”）。

原教程里有个很好的反例：老师拿 Minecraft 截图说“帮我做一个像这样的方块小游戏”，结果得到一个 2D 横版游戏，因为没说要 3D，AI 选了更简单的做法；加上“3D、可以转动视角”之后才得到第一人称方块世界。你没说清的维度，AI 会替你选一个省事的。

四个时刻：开始、等待、成功、失败

原教程 初级五 第 1–2 节

原型接上 AI 以后，原教程的第一阶段收尾课明确说：这一章不加新功能。先像用户一样从第一页用到拿到结果，哪一步还需要你在旁边解释，哪一步就是要改的地方。开发久了页面里总有上次的数据，所以要开无痕窗口或清空本地数据，做三次测试：空白打开一次（什么都不填直接点）、正常生成一次、模拟出错一次（传不支持的文件或让请求失败）。

问题通常集中在四个时刻。刚打开时：只有一个输入框不够，要有一句说明、一组示例或支持格式的提示；字段多就只留必填，其余放进“更多设置”。等待 AI 时：按钮显示“生成中”并防止重复提交，已填内容不消失；图片视频要排队可以显示阶段，不要编造一个看似精确的百分比，除非接口真的给了进度。拿到结果后：AI 返回不是终点，至少要能编辑、复制、下载或重新生成；模型无法确认的信息直接标出来。失败时：不给普通用户看整段报错，但要说清这次没完成，保留输入并提供重试；刷新会丢一大段输入的话，可以用 LocalStorage 存草稿，但别存 API Key 和敏感资料。

请别人用一次，再改一遍

原教程 初级五 第 3–4 节；产品思维基础 3.4 节

自己做的页面怎么看都顺。找一个没参与开发的人（最好是真可能用它的人），测试开始时只说目标：“请用这个工具，根据这张商品图片生成一版标题和卖点，把你认为可以继续修改的版本复制出来。”然后只看不教，记录他停顿、返回、重复点击、向你提问的位置。你一开口解释，本该由页面解决的问题就被掩盖了。用完再问三个问题：哪一步最不确定？结果里哪些会直接用、哪些一定要改？下次还愿不愿意用、为什么？不要只问“好不好用”，礼貌的“挺好的”指导不了修改。用真实素材测试前，要说明内容会发给哪类 AI 服务。

试用后会记下一堆问题，原教程给了五级优先级：① 无法完成任务（按钮无效、请求失败、结果带不走）；② 结果明显不可信（编造信息、无法核对）；③ 操作容易误解（不知道从哪开始、不清楚当前状态）；④ 使用成本过高（步骤重复、内容丢失、等待无反馈）；⑤ 样式和新增功能。先挑最重要的一到三个，改完自己从头再试，最好请那个人回来看。交给 AI IDE 时把观察到的现象写进去，而不是一句“帮我优化一下”。

产品思维附录补充了更长期的视角。反馈分三类：bug（说好会发生的没发生或发生错了，尽快复现修复并告知受影响用户）、体验问题（流程长度、按钮位置、文案没选到最顺的路径，结合观察判断改不改）、新需求（用户提出你没想到的功能，先看背后有没有共性、是否和你要服务的人群一致，别被分散需求拉到各个方向）。判断要不要继续投入看三个指标：留存（一段时间后还有多少人在用）、复访频率（多久回来一次，和你预期的使用节奏比）、推荐意愿（推荐带个人信用背书，比满意度更能说明问题）。

整理成别人打开就能用的作品

原教程 初级五 第 5 节；在魔搭社区发布

一分钟介绍按这个顺序：谁遇到了什么问题 → 产品怎样帮他 → 接了什么 AI 能力 → 用户怎样完成任务 → 试用后改了什么。先让人听懂你做了什么，再说框架和模型。分享前准备三样东西：可以运行的应用（链接，或写清启动命令）、30 到 60 秒的演示视频（完整展示一次核心任务，不要只快速切页面）、一页项目说明（目标用户、核心问题、主要流程、AI 能力、一次用户反馈和据此做的修改）。原教程还说，不必为了显得原创去做陌生题目，一个来自自己生活工作的小问题，经过真实试用和修改，比功能很多但没人用过的页面更有说服力。

发出去之前最后打开一次分享链接从头用一遍：别人能打开、AI 能返回、页面和截图里没有 API Key、用到的图片声音文档有使用授权。没有服务器的话，原教程附录介绍了魔搭社区的创空间：选 Static 类型上传纯静态网页即可得到公开链接；Gradio、Streamlit、带自定义后端的应用分别选对应类型或 Docker。第 9 篇会讲正式的部署。

用模板写一段一分钟介绍。

一分钟介绍（原教程 5.1 节的五步）

易混辨析：源代码 vs 构建产物

纯 HTML/CSS/JS 写的页面，源代码本身就能被浏览器直接打开。Vue、React、Vite 项目不一样：源代码要先 npm install 装依赖、npm run build 构建，生成 dist 或 build 目录里的静态文件，浏览器才能运行。原教程提醒，往魔搭 Static 空间（以及任何静态托管）上传时，只传构建产物，不要把源代码目录直接当网站传，托管平台不会替你执行构建。

回扣开头的三个问题

先自己答，再点开
1. 一页需求说明的六项？最能防止范围膨胀的是哪项？

给谁用和在什么场景用；要解决的问题（JTBD 句式）；第一版只做的核心流程；第一版不做什么；怎样算验证成功（可观察的结果）；还没确认的问题。最容易被跳过、也最能防止范围膨胀的是“第一版不做什么”，交给 AI IDE 时还能阻止它自行补功能。

2. 开始、等待、成功、失败四个时刻各要什么反馈？

开始：一句用途说明、示例或支持格式提示，只保留必填字段；等待：按钮显示“生成中”并防止重复提交，已填内容不消失，有真实进度才显示百分比；成功：结果可编辑、复制、下载或重新生成，存疑信息标出；失败：说明这次没完成，保留输入，提供重试或返回修改的入口，不向普通用户展示整段技术报错。

3. 请别人试用时该做什么、不该做什么？问题按什么顺序改？

只告诉对方要完成什么，然后只看不教，记录停顿、返回、重复点击和提问的位置，结束后问哪一步最不确定、哪些结果会直接用、下次是否还用；不要边用边解释，也不要只问好不好用。修改按五级：无法完成任务 → 结果明显不可信 → 操作容易误解 → 使用成本过高 → 样式和新功能，先改最重要的一到三个，改完从头复测。
