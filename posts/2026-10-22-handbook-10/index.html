从这一篇进入原书的“治理”篇。Agent 的一次结果由编排、推理、上下文、检索、工具和运行环境共同决定，任何一环偏差都可能表现为变慢、变贵、失败，或者看似合理实则不可用。所以生产运行不能只问“服务是否可用”，还要回答 Agent 实际执行了什么、问题出在哪一步、异常由哪次模型或工具调用引起、应用层现象是否和推理引擎或执行环境有关。

为什么 Agent 需要专门的可观测性

原书 13.1 节

原书的定义：AI 可观测性是通过指标、日志、Trace 和事件，理解 AI 原生应用内部状态和执行行为的能力，在传统可观测性上引入 Agent、模型、工具、上下文和任务等语义。它不等同于模型训练监控，也不同于用 AI 分析传统运维数据的 AIOps。OpenTelemetry 已把模型调用、Agent 操作纳入生成式 AI 语义约定，但规范仍在演进，平台要兼容标准也要能扩展语义。

挑战有六类：异常与任务质量难界定（同样输入可能走不同路径；错误规划、无效检索、工具误用、表面完成实则不对，“请求成功”不等于“任务成功”）；动态路径难还原（多轮调用、并行工具、子 Agent、异步回调，固定拓扑表达不了）；外部依赖可见性有限（托管模型、第三方工具只暴露有限信息）；跨步骤跨会话难关联（单次调用没问题，放进任务里可能是重复调用或异常循环）；异构场景难统一（语言、框架、SDK、协议、运行形态各不相同）；完整性、成本与安全难平衡（Prompt、响应、工具参数体量大，还可能含用户数据和凭证）。

“看什么”分四个维度：运行表现（任务是否完成、输出是否符合预期）、稳定性与性能（错误、超时、重试、异常循环、延迟）、成本与效率（Token、调用成本、资源效率）、行为审计（关键操作能否追溯主体、过程、结果）。“看哪里”分三层：任务与交互层、Agent 执行层、AI 基础设施层（网关、推理引擎、沙箱、Pod、GPU）。

这些问题分别属于哪个观测维度？

采集接入：多种入口，统一语义

原书 13.2 节

AI 应用的技术栈差异大，很难靠一种探针覆盖：自研 Agent 可以在代码和框架里埋点；Coding 与通用 Agent 只能用 Hook、插件、会话日志或本地数据库；网关和推理引擎提供服务端指标与访问日志；工具、沙箱、Pod、GPU 要靠运行时事件、节点采集和 eBPF。原书的四层架构：被观测对象层 → 采集接入层（多种方式可组合，组合时按原生调用 ID、时间边界和来源去重，避免同一次操作重复建 Span 或重复累计 Token）→ 统一处理层（以 OTLP 接收，做协议适配、语义规范化、采样、过滤、脱敏，并保留“实际值还是估算值”）→ 存储与分析层（Trace、Metrics、日志、事件各进合适的存储，通过共同标识联合查询）。

高代码应用有三种接入方式：手动埋点（语义最强，能表达目标、阶段和业务结果，原书以开源的 LoongSuite GenAI Utils 为例，默认不采集 Prompt 和回复正文）、进程启动时自动插桩（改启动命令即可覆盖 HTTP、数据库、受支持的模型 SDK 和框架，但推断不出“为什么调用”“属于哪个业务阶段”）、K8s 集群自动注入（解决探针交付和配置治理，兼容边界与进程探针相同）。生产常用“探针采集通用依赖 + 手动补业务语义”，但要避免对同一次调用重复建模。建议的层级是 ENTRY → AGENT / WORKFLOW → STEP → LLM / RETRIEVAL / TOOL；流式响应和生成器不能在函数返回迭代器时就结束 Span。

Coding Agent 只能从外部采：原生插件回调、生命周期 Hook（不能假定每个 Hook 都带模型用量）、本地 transcript / 日志 / 数据库。原书介绍的 LoongSuite Pilot 用“Agent 侧适配器 + 独立 Daemon”：适配器取证据，Daemon 做增量读取、跨来源合并和上报。几个要点：按原生调用 ID 配对，时间接近只是辅助；缺失和估算的信息明确标出，不能用零值或猜测值补齐；模型结束不等于轮次结束；游标已保存不代表后端已收到。eBPF 则从内核侧无侵入地补“实际发生了什么”：模型调用表现为网络请求与响应（可算 TTFT、TPOT），工具调用表现为进程、文件、网络事件，按进程关系和内核时间戳拼成轨迹。

链路模型：Session、Trace、Span 与执行语义

原书 13.3.1–13.3.2 节

不区分关联范围和执行边界，就会出现两种错：把整个长会话记成一条持续很久的链路，或者把相关的多次执行割裂成互不相干的请求。原书用三层：Session 是一段连续会话的关联范围，可以跨多次请求、多条 Trace 和很长的时间间隔，不宜记成一条长时间不结束的 Trace；Trace 记录一次外部输入触发的活跃执行（用户消息、审批结果、回调、异步恢复），Agent 返回结果、转入跨请求等待或因错误中断时结束；Span 是有明确开始、结束和结果的基本执行单元，嵌套表示调用关系，同一父节点下时间重叠表示并行。

边界规则：内部重试、模型回退、工具重试如果没有结束当前活跃执行，留在同一 Trace，每次实际调用分别记录；流式输出覆盖到消费完成或被中断；AskUserQuestion 或 HITL 如果在同一进程内等待且没有释放控制权，可以沿用当前 Trace，如果已经返回请求、持久化状态或进入长等待，就结束当前 Trace，恢复时建新 Trace，用相同 Session 标识和前序关系或 Trace Link 关联。

原书给出十二种执行语义：ENTRY、AGENT、WORKFLOW、STEP、LLM、RETRIEVAL、MEMORY、TOOL、GUARDRAIL、COMPACTION、HITL、INTERRUPT。几条关键约定：TOOL 表示一次实际发生的工具执行，不表示模型生成的调用意图，审批等待不计入工具耗时；STEP 只在能可靠识别 ReAct 轮次时记录；由 LLM 自主发起的检索或记忆操作要放在对应 TOOL 之下；MEMORY 只记录明确的记忆读写，模型读取已组装的上下文不算；COMPACTION 下的摘要 LLM 调用挂在它下面，Trace 只留压缩事实和结果引用；预期的用户打断不一定是系统错误，但也不应标记为正常完成。Trace 的父子结构反映真实调用关系，不要为了得到固定的树形人为拼接；语义优先记录能直接观察和验证的事实，而不把拿不到的模型内部思维当必需字段。

错误延迟、Token 成本与输出质量

原书 13.3.3–13.3.5 节

错误要分类：模型调用错误、检索失败、工具执行错误、参数校验失败、权限拒绝、超时、人工终止，并记录错误首次出现的步骤和后续传播；工具失败但 Agent 继续执行时，工具步骤的失败状态和任务最终状态都要保留。错误率只统计可直接观测的执行错误，不把“任务是否正确完成”混进来。延迟分请求端到端（P50 / P95 / P99、首个用户可见输出）和步骤耗时（各语义的分位数），用户可见首输出与模型首响应分开统计；模型性能看调用耗时、TTFT、TPOT、输出速率。

Token 分别记录输入、输出、缓存（读取、写入）和可获得时的推理 Token；能拿到服务端用量就以它为准，估算要标明口径、与计费数据区分。成本要汇总到 Trace、Agent、Session，有稳定任务标识时再到任务层，并保留模型、供应商、Token 类型、计价版本、币种以便重算审计。缓存命中率可以按缓存读取 Token 占输入 Token 的比例计算，但不同供应商口径不一致。效率看每条 Trace 的步骤数、LLM 调用数、工具调用数、重复步骤占比：只有把成本和任务结果放在一起，才能区分合理的高成本任务和重复调用、异常重试造成的浪费。指标标签用应用、Agent、操作类型、模型、供应商、工具类型、结果、环境等低基数字段，Session ID、Trace ID、用户 ID、动态 Prompt 留在 Trace 或日志里下钻。

质量不能从运行指标推断，要在 Trace 上额外做规则校验、模型评估或人工判断，分三层：最终结果、关键步骤（检索内容、工具选择、参数、子 Agent 路由）、执行轨迹。通用评估器有正确性、相关性、完整性、有据性、指令遵循、检索质量、工具调用正确性、轨迹质量、安全与合规；有明确答案的优先用确定性规则和业务系统校验，语义质量用 LLM-as-a-Judge，高风险或主观的结合专家复核。评估记录要保留评估器名称与版本、对象、分数、理由和证据，并关联到 Trace 或 Span。原书也提醒：通用评估器只给基础信号，替代不了面向具体业务目标的效果评价。

审计：可复核的证据链

原书 13.4 节

Agent 审计是在可观测数据之上，对身份、授权、执行行为和外部影响进行持续记录、检查和追溯。它要回答：谁在什么权限下、通过哪个 Agent 发起了什么任务，调用了哪些模型、数据、工具，实际影响了哪些对象，是否越过用户意图、组织策略或合规边界，结论能否复核。四者分工：可观测性还原发生了什么，评测衡量效果，审计判断是否合规、责任归谁、证据是否完整，Guardrail 在执行前或执行中允许、拒绝、脱敏、审批、限权。事后审计能发现风险，撤销不了已经发生的修改或泄露。

最小证据链包括四部分：主体与范围（用户、Agent、子 Agent、服务身份，租户、会话、任务、Trace 标识）、意图与授权（目标、指令来源、可用工具、权限范围、审批、当时生效的策略版本）、执行事实（模型、检索、记忆、工具参数与结果，以及进程、文件、网络、凭证使用等实际副作用）、结果与证据（状态、受影响对象、风险命中位置、原始事件引用、规则或模型版本）。eBPF 补充的是“实际发生”的证据，但缺少用户目标和业务授权，对加密流量可见性有限，要与应用埋点、Hook、网关日志、策略记录互证，不能单独据此认定越权或攻击。原始事实追加写入，检测结论以引用证据的派生记录存在，不为修正结论去改原始事件；审计数据本身也是高敏资产，完整审计不等于无边界地保存全部内容。

检测链路分层：原始事实 → 候选信号 → 上下文研判 → 已确认事件。研判结果至少区分三种：证据足以确认风险；证据足以说明风险链不成立或仍在授权范围内；关键证据缺失、暂时无法判断，第三种不能当成安全结论。严重性与置信度分别记录。模型可以辅助理解长上下文、降噪，但送进模型的审计材料本身可能含注入，要隔离数据与指令、限制工具、结构化输出，模型解释也是待验证输出。确认后进入有负责人、状态、处置动作、证据、关闭原因的事件响应；实时阻断的策略必须确定、低延迟、可解释、可回放，并有影子运行、灰度和回滚，开放式语义判断更适合异步调查。

AI 基础设施：网关、推理引擎、工具沙箱

原书 13.5 节

AI 网关集中代理模型、MCP、工具访问，提供相对统一、稳定的观测入口，补应用侧埋点参差的问题。模型访问侧看请求与服务状态、性能分段（网关处理、上游等待、首个响应 Chunk、流式持续）、路由（请求模型 vs 实际模型、重试、Fallback、熔断）、用量与成本、调用身份与策略结果、安全策略执行、Trace 关联；MCP 侧还要区分初始化、能力协商、工具发现、资源读取，不应把所有 MCP 流量都归为 TOOL。同一次调用在 Agent 侧和网关侧各有记录：前者描述任务语义，后者描述代理、鉴权、路由过程，靠 Trace 上下文串起来。

推理引擎（vLLM、SGLang 等）只看 HTTP 耗时或 GPU 利用率都不够。模型级指标看流量与可靠性、用户体验（E2E、TTFT、TPOT）、吞吐与负载形态（Token 吞吐、Prompt / 输出长度分布）、调度与缓存（Waiting / Running、队列时间、Prefill / Decode 耗时、KV Cache 使用与命中）；再下钻到 Pod 判断负载是否均衡，关联 GPU 的 SM Active、Tensor Active、显存带宽。端到端耗时可以近似拆为“队列等待 + Prefill + Decode + 框架及网络开销”，指标要联合解读而不是逐项设阈值。单条 Trace 只展示这个请求的经历，在 Continuous Batching 下，同批次的其他请求会共享计算与缓存，一个长 Prefill 或并发突增都可能拖慢它，所以要配合并发视图：以时间为横轴画出每个请求的 Wait、Prefill、Decode，沿某一时刻画竖线就是当时的执行快照。原书的排障闭环：指标发现 → Trace 找慢请求 → 并发分析还原现场 → Pod / GPU 验证根因 → 同流量同长度分布下对比验证。

工具与沙箱：模型的 tool call 只表示计划调用，经过参数校验、权限检查、审批、策略拦截后可能被拒绝、取消或改写。要同时记录“计划做什么”和“实际发生什么”：工具调用事实、沙箱生命周期（调度、创建、冷启动、休眠、恢复、销毁）、命令与进程（退出码、信号、OOM）、资源使用、文件网络等副作用、策略与隔离结果，用 Trace 上下文、tool-call ID、沙箱实例 ID、Pod、进程 ID 关联。策略拒绝发生在执行前时，记录判定事件，不伪造命令执行 Span。

回扣开头的三个问题

先自己答，再点开
1. Session、Trace、Span 是什么？等用户补充信息时怎么处理？

Session 是连续会话的关联范围，可跨多条 Trace；Trace 是一次外部输入触发的活跃执行，返回结果、转入跨请求等待或中断时结束；Span 是有明确起止和结果的基本操作单元。若在同一进程内等待且未释放控制权，可沿用当前 Trace；若已返回请求、持久化状态或长时间等待，就结束当前 Trace，用户回答时建新 Trace，用同一 Session 标识和前序关系 / Trace Link 关联。

2. 为什么高基数字段不做标签？tool-call 为什么不能记成 TOOL？

Session ID、Trace ID、用户 ID、tool-call ID 等是高基数字段，作为指标标签会导致时序数量失控，应保留在 Trace 或日志里下钻，指标用应用、模型、工具类型、结果等可控维度。模型生成的 tool-call 只是意图，可能被校验、权限、审批、策略拒绝或改写；TOOL 表示一次实际发生的执行，要由执行回调或结果记录确认，审批等待也不计入工具耗时。

3. 审计研判三种结论？TTFT 升、TPOT 稳，查哪里？

证据足以确认风险；证据足以说明风险链不成立或在授权内；关键证据缺失、暂无法判断（不能当成安全结论），严重性与置信度分开记录。E2E 与 TTFT 同时上升而 TPOT 稳定，优先查 Waiting 请求数、Queue Time、Prompt 长度和 Prefill，再用并发视图看是否并发突增排队或长 Prompt 进入，用 Pod / GPU 指标验证是否单实例倾斜。
