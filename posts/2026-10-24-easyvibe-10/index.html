从对话到智能体，从智能体到工作流

原教程 Dify 第 1.1–1.2 节

原教程开头点出纯对话 AI 的局限：聊天机器人本身并不能做事。它能描述周报该包含什么，却不能汇总项目数据并发邮件。要从聊天伙伴升级为数字员工，需要三项能力：专属知识（读懂你的产品文档、客户资料、内部制度）、工具调用（操作数据库、调 API）、结构化执行（按预设逻辑一步步完成，而不是自由发挥）。原教程也坦白：业界说的简单“智能体”，大多是 LLM + 工具 + 知识库的增强型应用，还不是能自主规划的智能体（第 13 篇讲后者）。

最简单、最广泛的形态是知识库问答机器人：很多业务的核心诉求不是让 AI 执行复杂操作，而是基于企业自己的资料准确回答。难点是几千页文档里每轮对话怎样找到最相关的内容，答案是 RAG（检索增强生成）：提问时先从知识库检索出语义最相关的片段，注入到模型输入里，让它基于真实资料作答，减少幻觉，还能保持客服口径（第 14 篇深入讲 RAG）。

更复杂的业务光有知识库还不够。原教程的例子：“把上个月面向客户的新功能整理成文案发给市场部”，要检索发布记录、过滤客户相关特性、改写成客户语言、推送邮件。让模型一次自由推理，容易漏信息、混术语、格式不稳。更关键的是，企业需要可审计、可复用、可监控的标准化执行路径。于是有了 AI 工作流：把任务拆成有序、可配置、可自动执行的子步骤，用可视化或代码编排条件、循环、并行，把“如何用 AI 完成某件事”的经验固化成模板。原教程的一句话：智能体让 AI 从会聊天走向能做事，工作流让 AI 从偶尔做成一件事迈向稳定、规模化地完成一类事。

Dify、Coze、n8n 怎么选

原教程 Dify 第 1.3、2.1 节

低代码平台用可视化拖拽、预置模板替代大量手写代码，把 AI 应用从创意到上线的周期从几周缩到几小时，而且都能把搭好的应用发布成标准 API。原教程比较了三个最常用的：Dify 定位为 LLM 应用开发与运营平台，开源可私有化部署，知识库和 RAG 能力突出，支持多模型，适合企业知识库问答、定制 Agent、API 服务；Coze（字节）以极致易用为核心，插件丰富，一键发布到豆包、飞书、微信公众号，私有化能力有限，适合社交机器人和快速原型；n8n 是通用的可编程工作流自动化引擎，数百种 SaaS 和数据库集成节点，可视化加 JS / Python 代码，可自托管，适合跨系统数据同步和 AI + 传统 SaaS 自动化。大厂方案（百度千帆 AppBuilder、阿里百炼、腾讯 TI）适合已在相应云生态里、合规要求高的企业。

原教程的建议是：它们核心逻辑相同，都是可视化地编排和连接能力模块，掌握一个就能迁移到其他。学习直接用 Dify 官方云的 Sandbox 免费方案，不必先买服务器自部署；确实需要控制实例时，再按官方 Docker Compose 指南部署（至少 2 核 4G），自部署不代表服务器和模型调用免费。

按场景选平台。

建知识库：六个参数

原教程 Dify 第 2.4 节

在 Dify 里上传 PDF、TXT 后进入知识库设置。第一组是文本切分：长文本必须切成小块（chunk）才能检索。最大切分长度可以试 512、2048、4096 并预览效果；切片重叠决定相邻片段保留多少相同内容，适当重叠可以避免一句关键信息被切到两块里谁也说不全。还有个选项是让大模型把部分内容转成问答对再存储，某些场景下能明显提升检索效果。

第二组是模型。Embedding 模型把文本转成数字向量，语义相近的文本向量也相近，于是能按意思而不是关键词找内容；它的选择显著影响检索效果（原教程推荐先用 Qwen 的 0.6B Embedding，再换 4B、8B 对比）。Rerank 模型对初筛出的候选做二次精排，把最匹配的排到前面，就像搜索引擎先粗筛一千条再精选前十。

第三组在召回测试里调：Top K 是返回最相似的前 K 个片段；Score Threshold 是相似度阈值，低于它的片段不返回，用来过滤相关度低的内容。设置完点保存，Embedding 模型把所有切片向量化，之后可以逐个查看、编辑、删除不合适的切片，再把知识库挂到应用上，对话时能看到每次命中了哪些来源。

先调切分长度和重叠，看一段文字怎么被切开（高亮是重叠部分）；再调 Top K 和阈值，看哪些片段会被送进模型。

易混辨析：Embedding 检索 vs Rerank 精排

Embedding 检索把问题和每个切片都提前变成向量，比较向量距离，速度快、能处理海量切片，但只是“大致语义相近”。Rerank 把问题和每个候选片段放在一起交给一个更精细的模型重新打分，准但慢，所以只用在初筛出的少量候选上。实际流程是先用 Embedding 粗筛出几十条，再用 Rerank 选出最好的几条送进大模型。

Dify 节点与一条意图分类工作流

原教程 Dify 第 2.1、2.6–2.7 节

搭工作流像拼积木：LLM 节点负责理解和生成；工具节点执行具体动作（搜索、查数据库、发邮件）；数据节点读写信息。原教程把常用节点分成三类。推理类：LLM、Knowledge Retrieval（知识检索）、Answer（输出）、Agent（可自主选工具的多步决策）、Question Classifier（问题分类）。流程控制类：IF/ELSE 条件分支、Iteration（无状态的批量并行处理）、Loop（有状态的循环，每轮依赖上一轮结果）。数据类：Code、Template、变量聚合与赋值、文档提取、参数提取、HTTP Request、列表操作。工具则有 Tavily 搜索、JSON 处理、Markdown 导出等，插件市场可扩展。

为什么要分类再分流？原教程的餐饮场景：用户的输入从来不是规范参数，有人下单、有人抱怨、有人闲聊、有人跑题。全交给同一个模型会出两个问题：回复风格不稳定（同样是抱怨，有时道歉有时解释）和业务逻辑不可控（你要求“抱怨必须先道歉”，模型未必每次遵守）。工程化的做法是：先做意图分类（buy_food、complain、chitchat、other），再按意图分流到各自的提示词和角色，最后统一封装输出。原教程还建议多用现成模板：工作流可以导出导入（DSL 文件），找官方推荐的工作流案例直接导入，比自己从零搭省时间。

易混辨析：Iteration vs Loop

Iteration 是无状态的批量处理：子任务之间没有依赖（批量翻译段落、并行审核多条内容），节点把输入数组分片并行跑同一条链路，结果自动聚合成数组；配置重点是并行度和失败重试。Loop 是有状态的循环：下一轮依赖上一轮的输出（反复修订文案直到满意），要先初始化状态变量、每轮更新，并且必须定义终止条件（最多 10 次、评分大于 9、收到停止信号）和超时，否则可能无限循环。

把 Dify 当作 API 中枢

原教程 Dify 第 2.8–2.9 节

Dify 搭好的应用可以发布成 API，让它成为你产品的“大模型中枢后端”。做法和第 6 篇接模型 API 是同一个套路：应用里点 Publish → Access API Reference，找到 “Send Chat Message”，复制右侧的 Request 和 Response 示例，再拿到 API Key。有了 Key、请求示例、返回示例这三样，就可以让 AI IDE 写调用代码，并按返回结构提取需要的字段。原教程在第二阶段的一个前端项目（霍格沃茨画像）里就是这么做的：前端页面负责展示和交互，Dify 工作流负责“画像人物”的对话和情绪判断。

要注意的仍然是第 6 篇那条规矩：Dify 的 API Key 同样不能放在前端，由你自己的后端或边缘函数转发。

这条提示词把三样东西一起交给 AI IDE。

我在 Dify 里发布了一个知识库问答应用，想做一个自己的网页聊天界面。
下面是 Dify 的 “Send Chat Message” 接口文档里的请求示例和返回示例：
【Request 示例】
【Response 示例】
请帮我：
1. 做一个简洁的聊天页面，支持多轮对话（用返回的 conversation_id 续接上下文）；

工作流平台的局限

原教程 Dify 第 6 节

原教程对低代码平台的评价很中肯：“低代码”往往也是一种“高代码”，用户仍要理解平台的概念、规则和操作逻辑，这本身就是新的学习成本。很多简单工作流本质上就是几个大模型调用前后串起来，几行代码就能写完，包了一层平台反而让调用变麻烦。在 Vibe Coding 快速发展的今天，让 AI 直接生成代码有时更高效。

但它仍然值得掌握：像办公软件一样，在业务团队里非常普遍；非技术同事能直接看懂、修改流程；调试、追踪、复用都有现成界面。原教程预告第三阶段会用代码级的工作流和 RAG 框架（LangGraph、LlamaIndex）实现同样的事，届时可以对比两种方式在复杂度和灵活性上的差别。

回答几个问题，看这次该用平台还是直接写代码。

第二阶段大作业：按一份真实 PRD 交付产品

原教程 Stage 2 综合实战（八个项目与 PRD）

第二阶段的收尾是八个综合项目，每个都附一份真实风格的 PRD（产品需求文档），要求把前面学的前端、后端、数据库、支付、部署全部串起来，交付一个可运行的产品原型。它们各自训练一种常见的产品形态：AI 营销文案 SaaS（Supabase + Stripe 的完整商业闭环）、类 Midjourney 生图 SaaS、类 Dify 智能体平台（多角色、多模块的“平台感”）、智能旅游规划 Agent（让 AI 输出结构化、可操作的行程而不是一大段文字）、在线考试系统（Express，多角色权限）、Spring Boot 电影推荐（内容 + 行为 + 可解释推荐）、生鲜电商微服务（服务拆分、API 网关、跨服务一致性）、Go 交通数据平台（数据接入 → 聚合 → 告警 → 可视化）。

以营销文案 SaaS 的 PRD 为例，一份能直接开发的 PRD 包括：项目定位（一句话定义 + 系统总览图 + 技术选型 + 竞品借鉴点）、目标用户与核心目标（“5 分钟内注册并完成第一次生成”这种可验证的目标）、MVP 范围（做什么、不做什么）、角色与权限（游客、注册用户、管理员）、页面架构（3 套入口 www / app / admin，共 10 个页面，每页列核心功能）、关键链路与状态流（游客 → 用户 → 付费用户，生成中 → 成功 / 失败）、后端模块与数据表、后台指标与监控、接口草案、非功能要求（历史只能自己可见、支付状态与套餐一致、移动端可用）、开发顺序。

原教程给每个项目的开发流程都是四个阶段：需求分析（读 PRD，答清几个入口、每页核心功能、有哪些模块和表、支付和免费额度怎么设计、MVP 做什么；答不清就不要开始写代码，需求不清是返工的最常见原因）→ 搭骨架（让 AI 按 PRD 生成所有页面的结构和假数据，先不接真实接口，“风格要像现代 SaaS，不像课堂 demo”）→ 后端集成（鉴权、数据库、模型调用、支付）→ 联调上线（端到端跑通，部署，准备演示）。

勾掉 PRD 的某一部分，看开发时会出什么问题；再看八个项目各自练的核心难点。

回扣开头的三个问题

先自己答，再点开
1. 数字员工需要哪三项能力？为什么企业更需要工作流？

专属知识（基于企业资料回答，靠 RAG）、工具调用（操作数据库、调 API）、结构化执行（按预设逻辑一步步完成）。让模型自由推理容易漏信息、混术语、格式不稳，而企业需要可审计、可复用、可监控的标准化执行路径，非预期结果可能带来严重损失；工作流把任务拆成可配置的有序步骤，把经验固化成模板。

2. 知识库六个参数各管什么？

最大切分长度决定每个片段多长；切片重叠让相邻片段共享一段内容，避免关键信息被切断；Embedding 模型把文本变成向量，按语义检索；Rerank 模型对初筛候选做二次精排；Top K 决定最多返回几个片段；Score Threshold 过滤掉相似度低于阈值的片段。

3. PRD 的组成？按 PRD 开发的四个阶段？

项目定位与技术选型、目标用户与可验证的核心目标、MVP 范围（做与不做）、角色与权限、页面架构（入口与每页核心功能）、关键链路与状态流、后端模块与数据表、后台指标与监控、接口草案、非功能要求、开发顺序。四个阶段：需求分析（答不清不写代码）→ 按 PRD 用假数据搭全部页面骨架 → 后端集成（鉴权、数据库、模型、支付）→ 端到端联调、部署、演示。
