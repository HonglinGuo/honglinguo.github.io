难的不是列组件，是划边界

第 1 篇说 Agent = Model + Harness。这一篇把 Harness 拆开落位：哪些能力属于哪个责任域、在哪个平面运行、由谁负责、怎样随版本演进。原书反复强调，架构的难点在于责任边界：边界不清的问题在演示阶段不会暴露，会在任务变长、工具变多、租户变多之后集中出现。

本系列是开源白皮书《AI Agent Handbook（企业级 Agent 白皮书）》（阿里云团队编写的开源白皮书，Apache-2.0 协议；本笔记依据 2026 年 10 月 21 日的仓库版本）的学习笔记。原书按“架构 → 构建 → 运行 → 治理 → 调优 → 实践”组织三十章，这里重排成十五篇，用自己的话重讲，并把关键表格做成可以点、可以分类、可以走流程的互动。概念与结论取自原书，每节标出对应章节；为演示设的场景和数值标“示意”。原书由阿里云编写，涉及阿里云产品的方案与数字属于厂商自述，文中会单独标出。

三个视图：同一套系统的三个侧面

原书 2.1.1 节

原书要求设计时同时用三个正交视图看系统。组件视图回答“由什么组成”，避免能力遗漏，尤其是把上下文管理、状态持久化、结果验证当成实现细节；平台视图回答“在哪里运行、由谁负责”，避免责任混乱；生命周期视图回答“怎样从决策走到运行、再被治理和改进”，避免把一次演示当成可运营系统。

三个视图不能互相推导：组件齐全不代表责任清晰，责任清晰也不代表变更可控。同一个 State Store，在组件视图里是任务事实的持久化能力，在平台视图里属于数据与资源面，在生命周期视图里是运行阶段产生、调优阶段反复读取的证据来源。

下面每个问题，该打开哪个视图来回答？

五个能力责任域

原书 2.1.2–2.1.3 节，图 2-1

组件视图把参考架构分成五个责任域。这里的“层”用来组织责任，不是严格的调用栈，也不是建设顺序。业务与应用层定义目标、交互和验收条件，不实现通用 Agent 能力；Agent 构建与编排层把 Model、编排逻辑、Context、Memory、Knowledge、Skill 和 Tool / Protocol 的能力定义组合成任务循环，但浏览器、Shell 等真实执行环境不在这一层；生产运行层承载跨时间跨请求的任务；治理与控制层回答哪些版本和动作被允许；调优层从运行证据中产出候选变更，它不直接改生产，变更要回到构建层形成新版本、过治理门禁再上线。

Security 不属于某一层，而是横跨五层：业务层定风险与验收边界，构建层实现约束，运行层提供隔离，治理层定义身份、策略、审计，调优层用红队和仿真验证这些措施是否有效。

原书由此归纳了五条相对稳定的设计原则：Model 与 Harness 解耦；编排层与 Runtime 解耦；状态外置、执行实例可替换；自主性与权限和可验证性匹配（工具、网络、数据、凭证越多，影响半径 Blast Radius 越大）；可观测、安全、评估是运行前提，不是上线补丁。五条原则不要求把系统做大，只要求被授予的自主性都有匹配的边界、证据和验证手段。

Harness 编排层：谁持有任务语义

原书 2.2.1–2.2.2 节

先说 Model。原书建议从五个维度持续评估：领域能力；长上下文中的指令遵循与抗干扰；工具参数生成、结果理解和多步调用的稳定性；延迟、价格、并发、区域；数据保留、隐私、合规。前三项决定能不能完成任务，后两项决定能不能规模化。复杂应用可以用 Model Router 按任务类型、预算和负载路由，但每条路由和降级都会改变 Agent 行为，必须和完整 Harness 一起回归。原书点名一种失败：降级模型在协议层能正常返回工具调用，却在多步任务中丢了中间约束，得到一次结构合法却结果错误的执行。

广义 Harness 包含 Runtime、Sandbox、Observability、Governance，太宽了，责任无法归属。原书把其中直接组织任务循环的子域称为 Harness 编排层：位于模型与运行环境之间，构造上下文、组织循环、提供能力、约束行为、验证中间结果的代码、配置与执行逻辑。它决定模型看到什么、能调用什么、什么时候停、交付前要过哪些验证。

编排层和 Runtime 的分工：编排层管语义（下一步做什么、要不要审批、上下文怎么重建、任务是否达成），Runtime 管物理保障（在哪个实例执行、排队限流、从哪个 Checkpoint 恢复、资源回收）。二者的接口应当是任务与状态，编排层一旦依赖某个 Runtime 的内存结构，原则二就被破坏了。编排层也不是一次定型的：Anthropic 发现模型变强后，旧脚手架可能反而限制新模型；LangChain 则在模型固定时，靠 Trace 分析、错误聚类、完成前验证和循环检测提升了完成质量。

取消勾选编排层的某项能力，看生产中会怎样失效（原书表 2-2）。

不要用一个上下文包含一切

原书 2.2.3 节，表 2-3

上下文窗口是模型当下能看到的内容，而 Agent 要管理的信息远超一个窗口。原书要求至少区分五类对象：Context（这一次调用该看到什么，单次调用级、不断重建、不作为事实来源）、State（任务已经发生了什么、从哪里恢复，任务级、强一致）、Memory（过去哪些交互经验有用，跨会话、需要写入门槛与遗忘）、Knowledge（组织已有哪些可检索的知识，要随源系统同步权限与时效）、Skill（某类任务该怎么做，作为版本化资产发布、复用、回滚）。

Memory 和 Knowledge 分开，是因为风险不同：Memory 由 Agent 运行中生成，怕的是错误经验被反复沿用；Knowledge 来自组织内容，怕的是权限越界和信息过期。放进同一个向量库，两类治理能力往往一起丢掉。Context Engineering 的本质也不是把窗口塞满，而是在正确的时间选正确的信息；同时可恢复任务的真实状态必须放在上下文之外：如果压缩、截断或误读能改变任务事实，任务就失去了可恢复性。

把这些内容放进它该去的对象。

易混辨析：Context vs State

Context 是给模型看的“这一帧画面”，每次调用都会重建，可以压缩、摘要、截断；State 是任务的“账本”，记录已经发生的事实，必须持久、强一致。把不完整的对话历史当成任务事实，是原书点名的第三类边界问题。

从接口调用到受控行动

原书 2.2.4 节

Tool 是 Agent 可以请求的一项能力，Protocol 定义能力如何被描述、发现、调用、返回，Environment 是能力真正产生影响的空间。三者失效方式不同：Tool 常是描述不清或缺参数校验，Protocol 常是把能力发现和权限授予混为一谈，Environment 常是影响范围超出预期。Function Calling 提供结构化调用，MCP 把工具、资源和 Prompt 抽象成可跨应用复用的协议能力，A2A 用于 Agent 之间的发现、委派和状态交换；Browser Use、Computer Use、Shell、Code Interpreter 让 Agent 能处理没有 API 的系统，也明显扩大了影响半径。

原书的三句话值得记住：能力被发现，不等于被授权；参数符合 Schema，不等于意图符合用户目标；命令在 Sandbox 里成功运行，不等于结果可以安全影响生产。所以一次受控行动至少经过六个环节，分布在编排层、Gateway、Sandbox 和控制面，缺任何一环，模型建议的动作就直接变成了系统执行的事实。

示意场景：Agent 想执行“清理过期的测试数据表”。拿掉一环看看。

三个平面：执行面、数据与资源面、控制面

原书 2.3 节

任务从秒级拉长到小时、天、周级，同一个 Agent 服务多个租户，又拿着文件、网络、数据库和企业凭证，问题就从“一个进程里的循环”变成分布式系统、安全隔离和企业治理问题。原书把平台划成三个平面（不叫“数据面”，以免和业务数据、记忆、任务状态混淆）：执行面真正跑 Loop 和工具，可弹性、可失败、需隔离，尽量不持有唯一真实状态；数据与资源面保存可恢复事实并提供 Agent 可访问的能力；控制面定义版本、身份、策略、部署、配额。

控制面不该成为每次调用的强同步依赖。更稳的做法是策略集中定义、判定点分布执行：Middleware、Gateway、Runtime、Sandbox 在请求路径上按已下发的策略判定，审计事件异步送回。代价是策略有传播延迟，所以凭证吊销、租户封禁这类高风险策略要靠强制刷新、短期凭证或集中校验兜底。

Runtime 管任务生命周期：把请求变成 Task，绑定 Harness 版本、身份、租户、预算和环境，处理排队、暂停、取消、超时、重试、Checkpoint、Recovery，并假设任何一步都可能被打断。Sandbox 限制行动的影响范围：文件、进程、资源、包安装、网络、Secrets、数据出站。AI Gateway 按治理粒度分三层：LLM Gateway 管模型调用，MCP Gateway 管工具调用，Agent Gateway 管任务（这是原书为区分粒度做的归纳，不是某厂商的产品定义）。

把这些对象放进它所在的平面。

Gateway 层治理粒度处理什么
LLM Gateway一次模型调用协议适配、路由、限流、降级、容灾、Token 成本
MCP Gateway一次工具调用Server Registry、凭证托管、工具级 ACL、审计
Agent Gateway一个任务Agent 路由、会话连续性、租户配额、预算

三者可以是同一个 Gateway 的不同能力，但治理对象和粒度必须分开，否则模型成本、工具权限和任务预算会在同一处策略里互相覆盖。详见 08 AI 网关。

易混辨析：Sandbox 管什么、不管什么

Sandbox 约束的是行动的技术可达范围：进程级隔离便宜但边界弱，容器适合大多数通用任务，微虚拟机、独立虚拟机或独立账号适合不可信代码和高敏感数据。它不回答三个问题：这个动作是否获得授权（工具权限判定）、是否符合业务意图（业务审批）、结果是否正确（结果校验）。

部署形态：平台给默认路径，应用保留组合权

原书 2.3.5 节，表 2-5

参考架构不要求第一天就建一个大而全的平台。原书列了四种常见形态：应用内嵌 SDK 直连（简单快，但状态、密钥、观测、策略散落在各应用）、托管 Harness 与 Runtime（持久执行、隔离、扩缩容由平台提供，代价是厂商绑定）、托管控制面 + 私有执行面（管理与执行解耦，数据和工具留在域内，但跨域审计更复杂）、全自托管或混合云（完全可控，建设和运营成本最高）。

选型先问哪些是自己的差异化资产：业务特有的 Prompt、Skill、Tool、评估标准、人机协作流程；模型接入、任务托管、沙箱、状态存储、身份、可观测、评估基础设施、安全策略更适合平台化。原书的平衡点：平台封装所有差异，会退化成只能满足最低共同需求、业务绕开自建；平台只给计算不给策略、状态、观测、评估，每个应用又要重复解同一批治理问题。

回答四个问题，看哪种部署形态更合适。

生命周期：Agent Release 与五阶段闭环

原书 2.4 节

Agent 的行为不只取决于代码，还取决于模型、Prompt、Context、Memory、Knowledge、Skill、Tool、编排逻辑、预算和运行环境，任意一项变化都可能改变轨迹和结果。所以最小发布单元应当是可复现的 Agent Release，至少绑定六类要素。只有它们可追踪，才能回答“生产中这个任务用的是哪个版本”、复现失败、证明质量是提升了而不只是变了。反过来，如果 Prompt 能在生产里随手改、不留版本，任何评估结论只对那一刻成立。

生命周期是架构设计 → 构建 → 运行 → 治理 → 调优的闭环。架构设计被单列为第一阶段，因为形态、自主性、责任域和权限边界一旦确定，后续成本区间基本锁定；治理和调优指回架构设计的虚线，是给“风险来自形态或权限模型本身”留的显式通道，这时该重新设计，而不是继续叠补丁。调优产出的 Prompt、Memory、Skill、Harness 补丁都只是候选变更，要回到构建、经过评估、安全检查、版本化、灰度、可回滚发布才能上线；调优指向运行的虚线只是在线评估的观测通道。治理既是一个阶段，也是横切约束：如果某项治理要求只能上线后靠流程和人工补齐，规模化后很可能失效。

易混辨析：受控自进化 vs 自我修改

原书说的调优不等于让 Agent 在生产中自由修改自己。由模型、反馈或轨迹生成的补丁都是候选变更，必须经过可复现评估、安全检查、版本化、灰度和回滚能力才能进入生产。“可控的改进比无审批的自我修改更符合企业级自进化的定义。”第 14 篇的受控自进化会展开。

回扣开头的三个问题

先自己答，再点开
1. 五条设计原则是什么？“编排层与 Runtime 解耦”指什么？

Model 与 Harness 解耦；编排层与 Runtime 解耦；状态外置、执行实例可替换；自主性与权限和可验证性匹配；可观测、安全、评估是运行前提。编排层管语义（下一步、审批、上下文重建、是否完成），Runtime 管物理保障（实例、排队、恢复、配额），二者以任务与状态为接口，这样能换 Runtime 而不重写任务逻辑，也能在换进程、节点、区域时恢复同一任务。

2. 五类信息对象各管什么？为什么不放进同一个向量库？

Context：这次调用看什么，不断重建，不是事实来源；State：任务发生了什么、从哪恢复，强一致；Memory：跨会话的经验，需要写入门槛与遗忘；Knowledge：组织的可检索知识，需要权限过滤与时效；Skill：某类任务怎么做，版本化发布回滚。它们的一致性、生命周期和治理风险不同：Memory 怕错误经验被沿用，Knowledge 怕越权和过期；混在一起会同时丢掉这些治理能力。

3. 为什么最小发布单元是 Agent Release？补丁为什么不能直接进生产？

Agent 的行为由模型、编排、Prompt / Context / Skill / Knowledge、工具与权限、运行环境、评估基线共同决定，任何一项变化都可能改变结果，只有把六类要素绑在一起版本化，才能复现失败、证明改进。调优产出的补丁只是候选变更，要回到构建并经过评估、安全检查、灰度和回滚门禁；否则就是无审批的自我修改。
