模型只能申请完成

模型的一次输出只是离散判断，企业任务却是一个持续过程：先理解环境、再定计划、连续调工具、关键动作前等审批、把一部分委派出去、失败了要恢复，最后用环境事实证明目标达成。这一篇讲 Harness 的执行内核怎样把一次次判断组织成有状态、可控制、可恢复的任务。全篇用原书的同一个案例：修复支付服务的高危依赖漏洞并形成可审批变更。

本系列是开源白皮书《AI Agent Handbook（企业级 Agent 白皮书）》（阿里云团队编写的开源白皮书，Apache-2.0 协议；本笔记依据 2026 年 10 月 21 日的仓库版本）的学习笔记。原书按“架构 → 构建 → 运行 → 治理 → 调优 → 实践”组织三十章，这里重排成十五篇，用自己的话重讲，并把关键表格做成可以点、可以分类、可以走流程的互动。概念与结论取自原书，每节标出对应章节；为演示设的场景和数值标“示意”。原书由阿里云编写，涉及阿里云产品的方案与数字属于厂商自述，文中会单独标出。

Agent Loop 与权威任务状态

原书 4.1 节

Agent Loop 是 Harness 最稳定的内核：不要求模型一次给出答案，而是重复“判断—行动—观察—再判断”，直到任务被验证完成、进入等待、失败或取消。原书把它抽象为五个阶段：Prepare（读取权威状态、确定本轮目标、请 Context Builder 装配输入）→ Model（判断下一步是行动、委派、询问、等待还是申请完成）→ Act（交给 Action Plane 做参数、身份、策略、审批、执行）→ Observe（把结果标准化并更新任务事实）→ Verify（不接受“我已经完成”作为唯一依据）。浏览文件、跑代码、调远程 Agent 都只是 Act 的不同实现，核心 Loop 保持不变。

消息历史记录的是交流过程，不该是任务状态的唯一来源。Harness 至少要维护一份可机读的权威状态：目标、阶段、Plan 与 Todo、已确认事实、阻塞项、子任务、Artifact、剩余预算、等待原因、完成依据。模型看到的是由这份状态生成的任务视图，而不是从几百条消息里猜进度。状态显式化以后，Runtime 才能在等待期间释放资源并准确恢复，界面才能说明 Agent 在等什么，观测才能区分执行慢、审批慢和工具慢。

Loop 还必须有外部终止边界：步骤数、总时长、Token 与费用、工具调用次数、子任务并发、高风险动作次数都进预算。接近阈值时让模型收敛范围、停止新委派、优先完成可交付部分；耗尽时给出明确终态和未完成清单，而不是悄悄截断。

Planning、Todo 与阶段门禁

原书 4.2 节

Planning 的价值不是展示模型隐藏的思考，而是把任务结构外部化为可读、可改、可验证的控制对象：阶段目标、依赖、正在执行哪一步、用什么证据判完成。原书按复杂度给了三种方式：轻量 Todo（目标明确、步骤少、反馈快）、Plan Mode（只读探索 → 写计划 → 确认后执行，适合影响面大、需审阅、环境不清楚）、Planner–Executor（Planner 管阶段与依赖、Executor 逐项执行，适合长任务、多依赖、可并行）。计划必须允许修订，但每次重规划要说明触发事实、保留已完成项，不能靠改写目标掩盖失败；Todo 只记录会改变可交付状态的事项。

长任务不应到最后才验证。原书把修复案例分成五个阶段，每个阶段都有门禁。门禁既减少在错误方向上继续投入，也为上下文压缩、人工接管、跨窗口续行提供稳定边界。好的阶段描述要回答输出是什么、证据在哪、谁来确认，而不是“分析问题”“处理代码”“确保质量”。

Plan Mode 是“Prompt 约定”与“Harness 控制”的典型对比：Prompt 可以要求“先规划再修改”，但只有权限模式、工具白名单、持久状态、HITL 同时生效，“计划获批前不可写”才是真约束。AgentScope 的实现里，探索阶段只开放只读工具和 plan_enter / plan_write / plan_exit / todo_write，plan_exit 触发人工确认，计划写进 plans/PLAN.md，都能跨调用恢复。

    Subagent：委派的是任务，不是责任

    原书 4.3 节

    Subagent 的价值不是把一个 Agent 包装成多个角色，而是解决三个具体问题：上下文隔离（子任务只加载相关内容，主窗口不被探索过程占满）、能力隔离（不同模型、指令、Skill、工具与权限）、并行执行（互不依赖的检索、实现、验证同时推进）。任务很短、步骤高度依赖、共享对象频繁变化时，委派只会增加通信和合并成本。

    主 Agent 负责全局目标、计划、预算、依赖和最终结果，不把“任务完成”的责任交出去。每个子任务都要带一份可机读契约：目标与边界、已知上下文（哪些决定不可自行改变）、能力与权限、预算、输出与证据、失败语义、验收条件。子代理默认不继承父任务的全部上下文和权限：父任务有权委派，不等于子 Agent 自动获得同等授权。案例里，依赖分析可以只读并行；修复要基于已确认的目标版本、在隔离分支上写；评审必须读取固定的差异和测试结果，不与执行者共享未提交的中间判断。多个执行者改同一工作区，要用隔离分支、对象级锁或补丁合并，不能靠“大家小心别冲突”。

    子任务的产物不是主 Agent 可以直接复述的“答案”，而是新的 Observation：经过 Schema 校验、版本检查（防止基于旧代码得出的结论）和父任务验收，才能进入权威状态。失败策略也要事先定义：关键分析失败 FAIL_FAST，非关键探索 BEST_EFFORT，瞬时故障 RETRY_OR_REASSIGN，需要业务决定 ESCALATE。

    易混辨析：Delegation vs Handoff

    Delegation（委派）：父任务保留责任，把有边界的子任务派出去，结果返回后由父 Agent 整合和验收。Handoff（移交）：任务控制权转移，接收者成为当前责任人，拿到继续推进所需的目标、状态和恢复位置。两者都不能只靠一条自然语言消息实现，至少要有任务关系、状态与责任变更记录。

    异步任务与长程续行

    原书 4.4 节

    企业任务常常比一次 HTTP 请求、一个终端进程、一个上下文窗口活得更久。所以 Harness 要把任务身份与当前连接分离：调用方提交后拿到稳定的 task_id，可以持续消费事件，也可以断开；任务进入等待或后台运行时，Runtime 释放计算资源；条件满足后从权威状态恢复，不依赖原进程还活着。后台任务、事件和恢复共用一套契约：任务 ID、父任务 ID、状态、创建者与执行者、输入与 Artifact 引用、事件序号、超时、取消与幂等语义、结果位置、错误分类、Continuation。

    暂停前，停止创建新行动、处理可中断操作、保存最新状态；恢复时重新检查目标、外部条件、工具是否实际执行过、权限是否仍有效、工作区是否变化、剩余预算。取消要沿父子任务传播，但已发生的外部副作用不能假装消失，要保留事实、必要时补偿。Context Reset 只负责控制语义：旧窗口结束前形成一致的继续点，新窗口从权威状态重建任务视图；Continuation 应包含目标、当前 Plan、已确认事实、失败尝试、Artifact、等待项、剩余预算和权限模式。

    用 SDK 嵌入时，多实例下 Session 放共享存储，凭 session_id 在任意实例 resume；但 Session Store 只解决会话接续，任务队列、并发控制和业务幂等仍要企业服务层负责。托管服务（原书以 Qoder Cloud Agents 为例）降低了执行内核的建设成本，目标、工具与数据边界、审批人、成功标准仍归企业。

      Middleware 与执行内核测试

      原书 4.5 节

      一个常见的演进问题：每加一种能力（压缩、计划、权限、路由、观测），就往 Loop 里塞一组条件分支，短期直接，长期让状态迁移不可预测。原书推荐稳定内核 + 可插拔能力：核心 Loop 只定义阶段与状态迁移，Middleware、Hook 或 Ability 在明确的生命周期点读取 Runtime Context，返回放行、修改、短路或追加。扩展本身也要有顺序、读写范围、冲突规则、失败语义和可观测性，最好返回结构化的 Decision 或 Patch，由核心 Loop 统一提交，而不是各自改共享对象。

      Harness 测试不能只看最终回答。执行内核至少要四类确定性测试：状态迁移（只接受合法事件，暂停、取消、失败正确传播）、扩展顺序（时机确定，冲突与短路稳定）、恢复（任意安全点中断后能重建且不重复副作用）、预算与边界（到阈值按设计收敛）。模型输出可以用固定样本、录制回放或模拟器替代，专门测 Harness 的确定性控制；真实模型的端到端效果属于 Evaluation。原书举例：在“补丁已写入但测试结果未返回”时强制中断，恢复后应先查原测试任务，而不是再改一次文件或重复启动发布。

      按失败类型恢复，由证据决定完成

      原书 4.6 节

      “Agent 失败了”不是可执行的诊断。瞬时模型或网络错误适合有界退避；参数错误要修正；环境缺失要重建；权限拒绝应等待或终止；重复探索要重新规划；业务条件不满足要明确缺口。盲目重试只会增加成本和风险。有副作用的行动（发布、通知、写库）重试前必须先回答“上一次究竟有没有发生”：超时可能只是响应丢了。Harness 要生成幂等键、记录请求与结果、优先查状态；无法证明未执行时，不应直接重复。

      无进展检测比最大步数更早发现问题：连续调用相同工具且参数相似、反复得到同一错误、Plan 长时间不变、工作区没有新事实、在少数动作间打转。检测到后先让模型依据结构化证据重新规划，再逐步缩小任务、切换能力、开独立评审或转人工。

      最关键的一条：模型只能提出完成申请，Harness 才能提交完成状态。验证强度与风险匹配，原书分五级：结构验证、环境验证、确定性验证、独立模型验证、人工验收。Verifier 返回结构化缺口和失败证据，验证失败是新的 Observation，不是简单结束。Verifier 是单次任务的完成门禁；跨版本判断 Harness 是否更好，属于 Evaluation。

      回扣开头的三个问题
      先自己答，再点开
      
  
      
    
      1. 为什么任务状态不能只靠消息历史？WAITING、PAUSED、VERIFYING 说明什么？
      消息历史会被压缩、截断、误读，模型要从中猜进度；权威状态是可机读的目标、阶段、Plan / Todo、事实、阻塞、子任务、Artifact、预算、等待原因和完成依据，能驱动 Runtime 释放和恢复资源、界面说明在等什么、观测区分慢在哪里。WAITING 不是失败（缺输入、等审批、等事件），PAUSED 不是结束（主动暂停，可恢复），VERIFYING 表示模型申请了完成、正在用证据核验。
      
    
      2. 什么时候值得用 Subagent？Delegation 和 Handoff 有什么不同？
      当上下文隔离、能力隔离或并行执行的收益超过通信与合并成本时；任务很短、步骤强依赖、共享对象频繁变化时不值得。Delegation 父任务保留责任、负责整合与验收；Handoff 是控制权转移，接收者成为责任人。两者都需要任务关系、状态与责任变更记录。
      
    
      3. 有副作用的操作超时了，该直接重试吗？“完成”由谁说了算？
      不该。超时可能只是响应丢失，要用幂等键、请求与结果记录先查状态；无法证明未执行时不应重复。完成由 Harness 依据证据提交：模型只能申请，Verifier 按风险选结构 / 环境 / 确定性 / 独立模型 / 人工验收，并返回结构化缺口。
