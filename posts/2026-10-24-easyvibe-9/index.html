Git 与 GitHub：版本检查点和远程仓库

原教程 Git 和 GitHub 工作流

每次和 AI 对话都会生成一版新代码，想回到之前某一版怎么办？这就是版本控制要解决的问题。Git 是本地的版本控制工具，给代码打检查点、在版本间切换；GitHub 是基于 Git 的远程“代码仓库云盘 + 协作社区”，提供 Issues、Pull Requests 等协作功能，也是全球最大的开源社区。安装后先用 git config --global 设好用户名和邮箱，它们会写进每次提交记录。

建仓库时两个文件值得留意：README 是仓库的说明书；.gitignore 告诉 Git 哪些文件不跟踪不上传（依赖包、临时文件、大文件，以及放密钥的 .env）。连接 GitHub 推荐用 SSH：本地生成一对密钥，公钥像一把可以公开的锁，交给 GitHub；私钥是你的钥匙，留在本机 ~/.ssh/，绝不分享。推送时本机用私钥签名，GitHub 用你绑定的公钥验证，于是不用每次输密码。多台电脑各生成一对，分别绑定；私钥泄露就立刻在 GitHub 删掉对应公钥。

原教程的日常操作都交给 AI IDE：克隆（clone）别人的仓库、修改前先拉取（pull）最新更改、改完让它提交并推送（commit & push）。提示词里要写清仓库文件夹路径，避免推错仓库。Git 的命令和分支、合并这些机制，博客里已有一篇可以动手玩的图解。

选部署平台：先回答三个问题

原教程 一键发布；VPS 部署 第 0–1 节

为什么不直接买服务器？原教程列出了手动部署的五步，每步都可能踩坑：准备服务器（选地区配置、学会 SSH 连接）、配置环境（Node.js / Python 版本不匹配就起不来）、上传代码、启动并测试（访问不了可能是防火墙没放行端口，也可能是程序有 bug）、维护更新（每次改代码重新上传重启，宕机后要进程守护）。这里顺带解释了两个词：IP 是设备的门牌号，端口是同一设备上不同应用的房间号，合起来 IP:port 定位一个网络服务。Vercel、Cloudflare Pages 这类平台把这五步全包了：连上 GitHub 仓库，它自动拉代码、识别类型、配环境、给你一个公网地址，还能绑域名。

选平台前原教程建议先问三个问题：需要 24 小时在线吗？文档站、博客、普通网站是用户访问才响应，选静态托管或 PaaS；定时任务、爬虫、聊天机器人、WebSocket 需要常驻，选常驻型 PaaS 或 VPS。需要 GPU 吗？只调用 OpenAI、Anthropic 的 API 不需要；自己跑开源模型、生成图片视频才需要 GPU 云（Modal、Replicate、AutoDL）。用户在哪里？国内优先评估国内云并实测访问，海外看 Vercel、Railway、Fly.io，都有就用 CDN。

几个平台的定位：Vercel 是 Next.js 官方平台、前端首选；Cloudflare Pages 托管静态站和构建产物，支持本地上传和 Git 自动部署；Render 能跑独立的 Node / Python 后端，但免费实例闲置 15 分钟会休眠；Railway、Fly.io 适合常驻进程和数据库组合；CloudBase 国内访问快、与微信生态整合；Dify 官方云注册即用，不必先自部署。原教程反复提醒：免费额度和试用不等于长期免费，以官网当期为准；学完要记得停止和删除不用的项目。

自己买 VPS：一次请求经过哪几层

原教程 VPS 部署 第 2–5、9.3 节

需要常驻、想完全控制、或者想省钱时，可以买一台 VPS（腾讯云 / 阿里云轻量应用服务器、Vultr、Hetzner 等）。国内服务器有一件绕不开的事：备案。在中国大陆资源上对外提供网站服务需要按接入商要求办理，原教程特别澄清“不是换个端口就不用备案”；香港及境外地域通常不按大陆 ICP 备案处理，但普通 Cloudflare 免费服务也不等于“免备案且有大陆加速”。

买完第一件事是安全组（云厂商控制台里的防火墙）：只放行 22（SSH，最好限制为自己的 IP）、80（HTTP）、443（HTTPS）；应用自己的端口（比如 3000）不要直接对公网开放，而是由 Nginx 在本机代理。服务器内部再用 ufw 开一层防火墙。登录方式改成 SSH 密钥，确认能登录后再考虑关掉密码登录。

原教程的三种部署场景对应三种结构：纯前端静态站，Nginx 直接托管构建产物；Node.js 后端，用 PM2 守护进程（崩了自动拉起），Nginx 反向代理到应用端口；全栈项目，用 Docker Compose 一键起前端、后端、数据库。最后买域名、把 A 记录解析到服务器 IP，用 Let's Encrypt 免费证书一键开 HTTPS。安全加固清单：fail2ban 封暴力破解、开自动安全更新、密钥和 .env 不进 Git、定期备份数据库并在独立环境验证能恢复。

云厂商服务全家福

原教程 VPS 部署 第 6–7 节

买过一台服务器后，会发现云厂商控制台里有几十种服务。原教程把它们归成几类，并给出国内和海外的对应名字：计算（跑代码的地方：云服务器 ECS / CVM / EC2，Serverless 函数，容器服务）、存储（对象存储 OSS / COS / S3 最常用，云硬盘，文件存储 NAS）、数据库（云数据库 RDS，缓存 Redis）、网络（CDN 内容分发、负载均衡、DNS 解析、SSL 证书、VPC 私有网络），以及域名、邮件、短信、监控日志等。

原教程还单列了 AI 专用的部署平台：Modal（Python 的 Serverless GPU，按秒计费）、Hugging Face Spaces（AI Demo 首选，Gradio / Streamlit 一键托管）、Replicate（把模型变成 API）、国内的 AutoDL（便宜的 GPU 租用）。

让 AI 当运维助手

原教程 VPS 部署 第 8 节

原教程称这是 Vibe Coding 时代最重要的部署心法：不需要记住所有命令，AI 就是运维助手。有两种协作方式。方式一：本地生成，手动执行：让编码 Agent 生成部署步骤清单、所有配置文件（Nginx、PM2、Dockerfile、compose）、部署脚本和环境变量检查清单，你先检查路径、启动命令、端口、环境变量是否和项目匹配，再在测试环境执行。方式二：AI 直接 SSH 到服务器操作：具备终端权限的编码 Agent 在你授权后调用本地已有的 SSH 配置去执行，更省事，但前提是你先在本地终端确认能登录。

原教程的安全提醒很具体：先在测试服务器练手；重要数据定期备份；用独立的部署用户并限制可执行的管理命令（有不受限 sudo 的用户等于有 root）；AI 执行危险命令前先看一眼；删除数据、改登录方式、产生云费用前要求它先说明影响。真实私钥和密码留在本地凭证里，环境变量只给名字，真实值通过服务器密钥配置注入，不要粘贴到对话里。出问题时先看日志（Nginx 错误日志、pm2 logs、docker compose logs、journalctl），去掉密码和 Token 后连同配置一起发给 AI。

支付三原则：前端负责跳转，后端负责定价和确认

原教程 如何集成 Stripe 等收费系统 第 1–6 节

原教程说，第一次接支付的人常把注意力放在“怎么跳转到付款页”，但决定系统是否稳定的是整条链路：谁决定价格、谁确认支付成功、谁更新数据库、谁回收权限。它让你只记三条：① 价格必须由后端决定，不能相信前端传来的金额；② 真正让权限生效的是 Webhook，不是 success 页面；③ 你自己的数据库必须保存支付状态，不能只依赖支付平台后台。边界对了，从 Stripe 换成 PayPal、支付宝、微信支付，都只是“接口换了，架构不变”。

为什么不能让前端直接连 Stripe 省掉后端？浏览器发出的请求用户可以随意修改（价格被改）；密钥和开通逻辑会暴露；跳到成功页不代表数据库记上了；用户说“我付了钱”你却查不到。所以分工是一句话：前端可以负责跳转，后端必须负责定价和确认。前端只传套餐名和用户信息，后端把套餐映射成 Stripe 里事先建好的 priceId，用密钥创建 Checkout Session（Stripe 托管的付款页），返回链接让前端跳转。

Stripe 适合海外 SaaS、订阅会员、数字产品和 AI 积分包；主要用户在中国大陆则优先支付宝、微信支付。原教程的选型顺序是：先按主要用户所在地选一条主支付链路，跑通最小版本，再按真实用户来源补第二种。

走一遍最小可行支付链路。

请你帮我把当前项目接上 Stripe 支付，我希望做一个最简单能跑起来的会员收费功能。
我的要求：

Webhook、幂等与订阅事件

原教程 Stripe 第 8 节、附录 A–D

原教程用一个真实场景解释为什么 success 页面不等于支付成功：如果你在 success.html 里写“到了这页就开通会员”，那么没付钱、付到一半关掉页面的人，直接在地址栏输入这个网址也能开通。success 页面是用户浏览器发起的跳转，可以伪造，不一定代表付款成功；Webhook 是 Stripe 服务器发给你后端的正式通知，带签名，后端验签通过后才更新数据库。前端刷新后从数据库读状态，才显示会员功能。

最容易踩的四个坑：把 success 页面当成支付成功；让前端传金额；Webhook 路由被 express.json() 提前解析（Stripe 验签需要原始请求体）；没做幂等。最后一条要特别记：Webhook 可能因为超时等原因被重试，同一事件可能到达多次，每次都给用户加会员或加积分就会出事故。所以要记录已处理过的事件 ID（或订单状态），重复的直接返回成功、不再执行。

订阅制要监听四个事件：checkout.session.completed（首次开通，创建本地订阅记录）、invoice.paid（续费成功，延长有效期）、invoice.payment_failed（扣费失败，标记风险并提醒）、customer.subscription.deleted（订阅取消，回收权限或到期失效）。状态在“未开通 → 有效 → 扣费失败待恢复 → 已取消”之间流转。本地联调用 Stripe CLI 的 stripe listen 把事件转发到本机。

先翻开 success 页面和 Webhook 的对照；再给事件配上该做的动作。

易混辨析：支付网关 vs MoR（记录商户）

原教程附录的对比表里有一列“税务处理”。支付网关（Stripe、PayPal、支付宝、微信支付、Adyen）只负责收钱，你是卖家，销售税、增值税这些要自己处理。MoR（Merchant of Record）如 Paddle、Lemon Squeezy，法律上由它们作为卖家向用户销售，再和你结算，代你处理全球税务，抽成更高。面向全球卖数字产品、不想研究各国税务的独立开发者，原教程建议看 MoR；按地区选：大陆用支付宝 / 微信，香港看 Stripe 加 Airwallex / Adyen，海外 SaaS 用 Stripe 或 Paddle。

回扣开头的三个问题

先自己答，再点开
1. 选部署平台的三个问题？什么项目需要 VPS 或常驻平台？

需要 24 小时在线吗；需要 GPU 吗；用户主要在哪里。用户访问才响应的文档站、博客、普通网站用静态托管或 PaaS（Cloudflare Pages、Vercel）；定时任务、爬虫、聊天机器人、WebSocket 这类需要常驻进程的，用 Railway、Fly.io、Render 付费实例或自己买 VPS；自己跑模型才需要 GPU 云。

2. VPS 上的请求路径？502 和刷新 404 说明什么？

用户输入域名 → DNS 把域名解析成服务器 IP → 云厂商安全组和服务器防火墙放行 443 → Nginx 终止 HTTPS，静态文件直接返回，API 请求反向代理到本机应用端口 → 由 PM2 或 Docker 守护的应用处理并访问数据库。502 通常是后端没启动、端口不对或 proxy_pass 写错；刷新 404 是单页应用没在 Nginx 配 try_files 回退到 index.html。

3. 支付三原则？success 页面为什么不等于支付成功？

价格由后端决定、权限以 Webhook 为准、支付状态保存在自己的数据库。success 页面只是用户浏览器的跳转，任何人都能直接访问这个网址，关页、断网时也可能没到达；Webhook 是支付平台服务器发给后端、带签名的正式通知，验签后更新数据库才可靠。处理 Webhook 还要读原始请求体验签，并做幂等防止重试导致重复开通。
