Git 是工具，GitHub 是平台

  

    
这两个名字经常被混着说，其实是两层东西。Git 是装在你电脑上的版本控制工具，提交、分支、合并、标签、查历史，全都可以离线完成，不需要注册任何账号。GitHub 是托管 Git 仓库的网站，它在服务器上替你保存一份普通的 Git 仓库，再在上面加了一层协作功能。

    
分清这两层，很多困惑会自然消失。比如 Pull Request 并不是 Git 的概念，Git 里没有一个叫 PR 的对象。它是平台提供的“请求合并”页面，讨论、审查意见、自动测试结果都存在平台的数据库里，不会写进 Git 历史。Git 自己只有一个 git request-pull 命令，作用是生成一段“请来拉取我这个分支”的文字，PR 这个名字就是从这儿来的。同样，fork、Issue、Release、Actions、分支保护，也都是平台功能。

    
所以同一个 Git 仓库，可以放在 GitHub、GitLab、自建的 Gitea 上，也可以只在本机用。换平台，Git 命令不用变，变的只是协作那一层的名字和操作方式。

    
先来分一分：下面每个词，你觉得属于 Git 还是 GitHub？

一个文件，同时有好几个版本

  

    
很多人每天 add、commit、push，却说不清这三步分别把文件送到了哪儿。原因在于，Git 里同一个文件往往同时存在好几份：磁盘上你正在改的那份（工作区），你挑好、准备提交的那份（暂存区，也叫 index），已经存档的那份（最新提交），还有服务器上的那份。

    
暂存区是 Git 最容易被忽略、又最有用的设计，它让你决定“这次到底交什么”。AI 修一个 bug 时顺手动了十个文件，你可以只挑和 bug 有关的几处提交，剩下的留着或扔掉。代价是要多理解一层：add 选中的是文件在那一刻的内容，之后再改，暂存区不会自动跟上。

    
编辑器里的“保存”只是写磁盘，不会替你生成提交；commit 只存在本机，不会自动上传；只有 push 才会把提交送到服务器。

分支只是一张能挪的标签

  

    
Git 并不是记录“改了哪几行”，而是每次提交都给整个项目拍一张快照。没变的文件直接复用上一次的内容，所以快照并不占多少空间。每张快照都记着自己接在哪张后面，也就是父提交；把这些连起来，就是一张有方向的图。

    
分支在这张图里只是一张贴在某个提交上的标签。叫 main 还是 feature 没有区别，main 之所以“永远能用”，靠的是团队约定，不是 Git 本身。HEAD 则记着你现在站在哪张标签上。

    
理解了“提交是点、分支是标签”，后面的命令都只是在挪标签或加点：快进合并是标签往前挪；合并提交是新加一个有两个父提交的点；rebase 是把一串点复制到别处，复制出来的点编号都是新的；reset 是把标签往回拽，被甩下的点没人指着，但并没有立刻消失。

想撤销？先回答两个问题

  

    
“撤销”这个词在 Git 里至少对应四件不同的事：放弃文件里的修改、把文件从暂存区拿出来、让分支退回以前的提交、用一个新提交抵消旧提交。命令不同，风险也完全不同。

    
选哪个，看两件事。一是改动现在在哪：还在工作区、已经暂存，还是已经提交。二是提交有没有给过别人：只在自己电脑上的提交可以随意改写；已经推送、别人可能在它上面继续开发的，就只能用 revert 追加一个反向提交，不能动历史。

    
还有一条底线：Git 只保护提交过的东西。从没提交过的修改，一旦被 restore 或 reset --hard 覆盖，就真的没了。所以动手前先跑一次 git status，拿不准就先建个备份分支。

    你电脑上的 origin/main，是一份旧记忆
    
  
    
    
    把 GitHub 上的仓库 clone 下来以后，main 这个名字其实对应三样东西：GitHub 服务器上的 main；你电脑里的 origin/main，它记的是“上次联网时看到的服务器 main”；还有你正在改的本地 main。
    
    
    关键在中间那份。origin/main 不会自己更新，只在 fetch、pull、push 时同步。所以 git status 说“与 origin/main 一致”，只说明和你上次看到的一致，并不代表刚刚确认过服务器。同事刚推上去的提交，你的电脑可能完全不知道。
    
    
    更稳的做法是把“拿”和“合”分开：先 git fetch 看看服务器多了什么，再决定怎么合。只想跟上主线就用 --ff-only，有分叉时它会停下来提醒你，不会悄悄生成合并提交。push 被拒绝也一样，先 fetch，再 merge 或 rebase，别直接强推，那可能把别人的提交挤出历史。

    同一个 PR，三种合法的合并方式
    
  
    
    
    团队协作时，代码一般不直接推到 main，而是走 Pull Request。前面说过，PR 是 GitHub 这类平台的功能，不是 Git 命令：在功能分支上提交、推送，再到 GitHub 上发起“请把这个分支合进 main”的请求。讨论、代码审查、自动测试都在 PR 里完成，按意见改完再推一次，PR 会自动更新。
    
    
    没有写权限的开源项目也是这么参与的：先 fork 到自己账号下，在 fork 里开分支、推送，再向原仓库发 PR，合不合由维护者决定。仓库还可以设置分支保护，要求测试通过、审查完成才能合并。
    
    
    审查通过后，GitHub 提供三种合并方式。合进去的代码完全一样，区别在主线留下什么样的历史：保留每个提交外加一个合并点，压成一个提交，或者复制成一条直线。团队通常会统一选一种。

    概念
    Pull Request
    请求把 compare 分支合进 base 分支，附带讨论、代码审查和自动检查。
    Draft PR

    三种合并
    Merge 保留提交并加合并点；Squash 压成一个新提交；Rebase and merge 逐个重放成直线。
    分支保护

    Actions

    上周还好好的：用二分法找出元凶
    
  
    
    
    Git 的历史不只用来回滚，也是排错的线索。想知道一段代码为什么写成这样，可以用 git log -S 找某个字符串是哪次提交加进来的，用 git blame 看每一行最后是哪次提交改的，再用 git show 读那次提交的完整上下文。blame 适合找线索，不适合拿来追责。
    
    
    最头疼的一类问题是“上周还好好的，现在坏了”，中间却隔着几十上百个提交，一个个往回试太慢。git bisect 用二分法：你给它一个好版本和一个坏版本，它每次挑中间那个让你测，测完标 good 或 bad，范围就砍掉一半。1000 个提交，最多测 10 次。
    
    
    来玩一局：每次先看测试结果，再标记。

    记下来
    
    
    
      
    概念
    二分查找
    每测一次排除一半。n 个提交最多测 log₂n 次。
    good 和 bad
    你告诉 bisect 当前版本好还是坏，它据此挑下一个版本。
    .gitignore
    只对未跟踪文件生效。已经跟踪的文件要 git rm --cached 才会停止跟踪。
    大文件
    GitHub 拒收超过 100 MiB 的普通文件。二进制要版本管理用 Git LFS；删掉当前文件不会让历史变小。
    泄露的密钥
    先去服务商那里撤销或轮换，再考虑清理历史。
    
      
    命令
    git log -p -- <文件>
    某个文件的历史补丁
    git log -S '字符串'
    找这个字符串出现次数发生变化的提交
    git blame <文件>
    每一行最后是哪次提交改的
    git bisect start
    开始二分
    git bisect bad / good <提交号>
    标记坏版本、好版本
    git bisect run <脚本>
    自动测：退出码 0 好，125 跳过，其他 1–127 坏
    git bisect reset
    结束，回到出发前的分支
    git rm --cached .env
    停止跟踪但保留本地文件
    
    
    
  
    

    



    
  
    下次让 AI 改代码，先过一遍这张单子
    
  
    
    
    AI 写代码越快，越需要一套固定动作把风险框住。思路很简单：每次只让 AI 在一个干净的新分支上做一件事，做完自己看 diff、跑测试、挑着提交。改坏了，大不了删掉分支重来，主线始终能跑。
    
    
    需要几个 AI 同时干活时，用 git worktree 给同一个仓库开几个工作目录，各自检出不同分支，互不干扰。不过目录分开了，端口、数据库、密钥这些运行环境还得另外安排，否则照样会打架。临时被别的事打断，就用 git stash 把手上的改动先收起来，处理完再拿回来。

    记下来：并行与发布
    
    
    
      
    概念
    stash
    临时收起没提交的改动，去处理别的事，回来再拿出来。
    worktree
    同一个仓库开多个工作目录，各自检出不同分支，共用对象库。适合几个 AI 并行干活。
    标签 tag
    钉在某个提交上的固定名字，不会随提交往前走，常用来标版本号。
    Release、Packages、Pages
    版本下载页、软件包和镜像仓库、静态网站托管。
    
      
    命令
    git stash push -u -m "说明"
    收起改动，-u 连未跟踪文件一起
    git stash list / apply / drop
    查看、恢复（保留记录）、删除
    git stash pop
    恢复并删除记录
    git worktree add -b feature/ai ../todo-ai main
    从 main 开新分支，放到另一个目录
    git worktree list / remove <目录>
    查看、删除工作目录（分支保留）
    git tag -a v1.0.0 -m "说明"
    打带说明的版本标签
    git push origin v1.0.0
    标签要单独推送
