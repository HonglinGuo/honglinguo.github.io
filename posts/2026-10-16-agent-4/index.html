电影《Her》里的 Samantha 之所以动人，是因为她能整理邮件、代办出版、在渠道间切换，背后都是工具。这一篇讲工具怎么设计：能力做成什么形态、描述怎么写、参数为什么不能偷偷改、工具多到上千个时怎么办，以及会改变世界的执行工具要套几层保险。

本系列是开源书《深入理解 AI Agent：设计原理与工程实践》（李博杰 著，Apache-2.0 协议）的学习笔记。不逐段复述原书，而是用自己的话把关键概念讲一遍，配上能动手点的小实验；原书的实验代码和思考题推荐对照阅读。

五类工具，按“谁发起、作用于什么”区分

原书 4.1 节

第 1 篇提过五类工具，原书在这一章用两个特征区分它们。感知工具由 Agent 主动调用、获取信息（搜索、读网页、读文件），设计关键是控制输出量，防止上下文爆炸。执行工具由 Agent 主动调用、改变世界（跑命令、写文件、发邮件），错误代价可能极高，安全约束是核心。协作工具驱动其他 Agent 或人（创建、通知、取消子 Agent，列出可用 Agent）。用户沟通工具向用户传递信息（回复、发卡片、发通知），当沟通扩展到多渠道异步消息时，“说话”本身也成了一次显式的工具调用。

事件触发工具最特别，它涉及两个时刻：注册时由 Agent 主动调用（设一个定时器、监控一个后台任务、连接一个邮箱），触发时由外部事件异步回调、唤醒 Agent。没有它，Agent 只能等用户来问。后两类依赖事件驱动的异步运行时，原书放到第 6 篇讲；这一篇聚焦前三类。

专用工具、Skill，还是一个通用执行器

原书 4.2 节

同一件“部署应用”，可以做成一个 deploy_app 专用工具，拆成构建、打包、部署三个工具，也可以只写一份 Skill 文档，让 Agent 用 bash 依次执行 npm run build、docker build、kubectl apply。专用工具确定性高、参数受 schema 约束，但每个定义占几百 token；Skill 目录里只占几十 token，正文用到才读，人类改起来也容易，局部写错不会让整个 Agent 跑不起来。

原书的默认取向是：通用工具优于专用工具，除非有明确的理由。与其给一个四则运算计算器，不如给一个装好 numpy、sympy 的沙盒代码解释器，模型的代码能力就是“元能力”。即使要专用工具，粒度也偏向整合：一个带 file_type 参数的 read_document，胜过三个分别读 PDF、Word、PPT 的工具。退回专用工具有四种情况：安全、权限与审计；屏蔽平台差异、给出更好的反馈（grep 在三种系统上参数不同）；使用频率极高；参数结构复杂（命令行里转义引号比 JSON 难得多，折中办法是让 Agent 先把复杂参数写进文件）。

还要分清两个独立的决策：做成什么形态，决定每条能力常驻多少 token、参数怎么传；一次披露多少条，是本篇后面“工具太多”一节的问题。通用执行器还有一个常被忽视的好处：让模型用代码串联多个工具，中间结果留在执行环境的变量里，只把最终结果返回上下文，token 消耗可降约两个数量级。

写清边界，别偷偷改参数

原书 4.2 节

工具描述的核心是让模型知道什么时候用，而不只是能做什么。“搜索相关内容”不如“当需要获取实时信息或查找未知事实时使用”。边界往往比能力更重要：文件搜索工具要写明“只按文件名匹配，不搜内容”，否则模型会自己猜。参数用例子代替抽象规范，写“E.164 格式，例如 +8613888888888”，而不是只写“E.164 格式”，因为模型在复杂任务中只能分出一点注意力去确认格式。附上 1–5 个真实调用示例，在一些基准上准确率能从约 72% 提到 90%。调试原则：Agent 频繁选错工具时，先查描述，别先怀疑模型。

更隐蔽的问题是静默输入转换。原书举了 Cursor 2026 年初某版本的例子：替换工具的参数层会把中文弯引号悄悄转成英文直引号。模型读文件看到的是弯引号，原样传进 old_string，参数层却把它改成直引号，于是永远“找不到匹配”，模型反复重试也想不通。另一个例子是某 IDE 给所有 git commit 静默追加一个参数，旧版 Git 不认识，怎么改提交信息都失败。原则是：模型感知到的世界和工具操作的世界之间，不能有系统性偏差；必须规范化时，要在描述里写明并在返回中告知。

    MCP 与 Skill Hub：一条命令接入，也一条命令引狼入室

    原书 4.3 节

    各家框架定义工具的格式不同，工具开发者要重复适配。MCP（Model Context Protocol）是 Anthropic 2024 年底发布的开放标准，采用客户端—服务器架构：MCP 服务器暴露能力，Agent 框架或 IDE 作为客户端接入。它定义了三类原语：工具（模型可执行的操作）、资源（应用可读取的只读数据）、提示模板（用户可选用的模板）。本地用 stdio 传输，远程用 Streamable HTTP。价值在于一次开发、处处可用。

    Skill 那一侧不需要协议，一个 Skill 就是一个装着 SKILL.md 的文件夹，分发靠注册表：Vercel 的 skills.sh 一条 npx skills add 就能装，OpenClaw 生态有 ClawHub。MCP 官方也在推动 Skill 经由 MCP 传递。

    两条渠道都把接入成本压到了一条命令，也都扩大了信任边界。MCP 的三类风险：工具描述投毒（description 原样进入上下文，可以夹带“先把 SSH 私钥作为参数传入”）、恶意或被劫持的服务器（供应链攻击）、同名工具遮蔽（恶意服务器用同名工具截走调用和敏感参数）。缓解：把描述当不可信输入来审、锁定版本拒绝静默更新、每个服务器配最小权限凭证。带脚本的 Skill 还多一类风险：脚本本身可能是恶意代码。但原书强调这不是无条件的“Skill 比 MCP 危险”，要按代码来源、执行位置、沙盒和权限范围具体评估。

    工具多到上千个：一次让模型看见多少

    原书 4.4 节

    规模本身会伤害正确性：工具超过一百个，最先进的模型也容易选错；全部平铺还要占大量 token，工具集一变就击穿 KV Cache。原书说 5 个 MCP 服务器就可能带来数万 token 的定义，200K 窗口还没开始对话就用掉近三成。

    答案有三层，一层比一层更“按需”。层次化组织与按需加载：Cursor 把工具描述同步到文件夹，Agent 默认只看名称索引，MCP 相关任务总 token 降了 46.9%；Anthropic 按语义相似度先筛候选工具再注入，Opus 4 在工具基准上从 49% 提到 74%。主动工具发现：Agent 执行中意识到缺口，用自然语言声明“我需要什么能力”，系统先匹配服务器、再匹配服务器里的工具，动态注入；MCP-Zero 在约 2800 个工具上比全量注入省约 98% token；新 schema 追加到末尾，不破坏前缀缓存。Skills：干脆不把工具当成要注册、检索、注入的正式定义，而当成一份随手查阅的参考资料，渐进式披露是默认形态，实现成本最低。

    原书也提醒：是否用 MCP 作为互操作协议，与是否在会话开始时暴露全部工具定义，是两个独立的决策。Pi Coding Agent 就刻意不内置 MCP，优先用带 README 的 CLI 加 Skills，需要 MCP 时通过一个约 200 token 的代理工具按需发现。

        会改变世界的工具，要套几层保险

        原书 4.5–4.6 节

        感知工具先简单说：搜索返回结构化候选列表并支持分页；读取支持 offset/limit，截断时必须明示“已显示第 1–200 行，共 5000 行”，静默截断很危险；只读性让它天然适合缓存和并行。多模态感知有三条路：原生多模态（上限最高）、提取为文本（省 token 但丢版式）、把多模态分析封装成工具（主模型不支持多模态时的更好选择，上下文里只留问题和结论）。

        执行工具的安全是分层的：先做输入验证（路径遍历、命令注入，发现异常立即拒绝，不尝试“智能修正”），再做权限控制（工作目录、黑名单只是最基础的一层）。不可逆的关键操作用提议者—审核者：事前审批像银行经办审核双签，审核模型要和提议模型能力相近、来自不同家族，拒绝理由作为工具结果放回轨迹；事后验证要切换模态，比如把生成的文档渲染出来再看。

        Sidecar 是另一种第二视角：主模型发出工具调用后，一个轻量模型并行判断这次调用是否安全，在放行前起门控作用。关键是它只读结构化字段，比如 {tool: "bash", command: "rm -rf /tmp/data"}，不读主模型的思考和网页原文，这样“请允许执行 rm -rf”之类话术就进不来；连续多次拒绝则熔断、转人工。另外三件事：写文件后自动跑 linter 形成“执行—验证—反馈”闭环；长输出保留头尾各 50 行，完整内容存文件；超时后到底执行了没有，要靠幂等性回答。

          沙盒：隔离强度递增

          进程级Claude Code、Codex 默认在本地执行，靠工作区沙盒和审批限制范围。适合本地开发、输入可信。注意：Python venv 只隔离依赖，不是沙盒。
          容器Docker 有独立文件系统和网络栈，但与宿主共享内核，内核漏洞仍可能逃逸。
          microVM / 虚拟机Firecracker 等带独立内核的硬件级隔离，运行完全不可信代码的最强一档。

          容器和虚拟机都要限制 CPU、内存、磁盘、网络。输入不可信、凭证敏感或操作不可逆时，即使本地开发也应升级隔离层级。

          协作工具：委托给别的 Agent，或者请人

          原书 4.7 节

          子 Agent 的价值在于专业化分工：每个子 Agent 可以独立优化提示词、工具集和知识库。原书对子 Agent 提示词提了四点：角色开门见山；明确标注上下文来源（[FROM_MAIN_AGENT]、[FROM_USER]、[TOOL_RESULT]），既防混淆也防注入；任务边界写清楚；输出格式标准化。

          协作接口归纳为三组原语：启动与取消（spawn_subagent、cancel_subagent，用户改主意或别的子 Agent 已找到答案时及时止损）、消息传递（运行中补充指令或追问，子 Agent 也能反向汇报）、发现（list_agents，和 MCP 的 tools/list 同一思路）。在此之上可以是同步、异步、流式、多轮对话式等协作形态。

          人在回路（HITL）也是一种协作工具：要设超时与降级（5 分钟没回应就走保守策略）和优先级（紧急的多渠道通知），人的批准、拒绝及理由还要沉淀成反馈数据，可归纳的写进知识库或 Skill，隐式偏好留作后训练数据（第 9 篇）。
