平均够用，为什么还排队

第 2 篇给出了一次调用要多少容量、运算和读取。这一章再加三个问题：工作什么时候到、哪些步骤必须等、什么才算任务完成。原书由此建立排队、状态驻留、关键路径和成功任务成本四个模型，再延伸到训练、强化学习和“训练 + 服务”的全生命周期成本。

本系列是开源书《深入理解 AI Infra：量化分析与系统设计》（李博杰 著，Apache-2.0 协议，初稿持续修订中）的学习笔记。原书的方法是“从约束推导设计”，所以每篇以计算器为主：先自己代入数字估一遍，再对照原书的结论。公式、硬件参数和算例数字都取自原书，为演示设的默认值会标注“示意”。

本篇要回答的 3 个问题

  1. 平均处理能力足够，为什么请求还会大量积压？积压要多久才能排空？
  2. 一个 Agent 任务的时间和成本怎么算？缓存、并行工具、多采样各改变了哪一项？
  3. 训练一个 8B 模型要多少显存和算力？RL 为什么比看上去贵？“训练更久的小模型”何时划算？

先写清楚“什么算完成”，再决定统计什么

原书 3.1.1–3.1.2 节

一次请求恢复 S 个上下文、处理 P 个新输入、返回 G 个 token，就是一次 prefill 加 G − 1 次 decode。prefill 一次处理 BP 行，decode 只有 B 行，这就是“prefill 常受算力限制、decode 常受带宽限制”的来由。时间线上标三个点：到达 ta、首 token t1、末 token tG，得到 TTFT = t1 − ta、完整请求时间 tG − ta、平均 token 间隔 (tG − t1)/(G − 1)。减少排队改善 TTFT，却不会缩短已开始生成后的间隔。

平均值会掩盖慢请求，原书用 p95，按最近秩法取第 ⌈0.95n⌉ 个观测：4 条请求的 p95 就是最大值，480 条是第 456 个。等待期间还占着状态：AM = ∫M(t)dt，1 GiB 驻留 10 秒是 10 GiB·s；任务以 λ/秒到达、各占 M0、平均等 τ 秒，稳定时这些等待任务的平均占用约 λ·M0·τ。工具等待由此变成容量问题。成本则用成功任务成本：所有尝试（含失败）的花费除以成功任务数。

排队：前一分钟的空闲，留不到后一分钟

原书 3.1.3 节

例题 3-1：两分钟内到达 480 条请求（平均每秒 4 条），一半是“长输入”（8192 入 / 256 出），一半是“长输出”（1024 入 / 2048 出）。均匀混合时每秒需要 4,604 步 decode；若前一分钟两类比例 9:1、后一分钟 1:9，则前一分钟每秒 1,736.8 步、后一分钟 7,471.2 步，总量不变。

处理率从硬件下界算：RTX PRO 6000（1792 GB/s）上的 Qwen3-8B 同时跑 64 条序列，一步至少读 15.14 GB 权重加各序列的 KV（平均上下文约 2742 token），共 41.02 GB、22.89 ms，所以一张卡每秒最多约 2,795.66 步，两张约 5,591.33 步。用流体队列 Qk+1 = max(0, Qk + Ak − μkΔt) 递推：后一分钟每秒多出约 1,879.87 步，60 秒积压约 112,792 步，停止到达后还要约 20.17 秒排空。一般地，突发速率 λw 持续 τ 秒，积压 (λw − μ)τ，排空时间 (λw − μ)τ/μ。

原书还在一张卡上真实回放了这两种序列（vLLM 0.23，KV 池 24 GiB，最多 64 条）：完整请求 p95 都约 299.4 秒，但 TTFT p95 分别是 242.9 和 258.9 秒，抢占事件 62 和 24 次。一张卡每秒最多 2,796 步，本来就低于平均需求 4,604 步，两次都严重积压；而 KV 池填满时，即使计算单元有空，新请求也只能等已有请求释放状态。

Agent 任务：前缀复用、成功率、关键路径

原书 3.2 节

前缀复用：第 i 轮输入 Ii，可复用前缀 Ki，则 Pi = Ii − Ki、Si = Ki。原书的四轮代码修复任务累计输入 5,297 token、命中 4,480，prefill 从 76.196 降到 11.976 TFLOPs；代价是旧状态要一直保留。缓存收益还取决于改动发生在哪里：末尾追加 100 token 只多 100 行；改动 2000 个 token 中的第 501 个，最长可复用前缀只剩 500。

成功任务成本：每次尝试成本 c、成功率 p，Csuccess = c/p；新方法更省的条件是 p2/p1 > c2/c1。原书的简单假设：token 单价降到 1/10，每任务用量涨到 20 倍，成功率 50% → 80%，成功任务成本比 = 2 × 0.5/0.8 = 1.25，单价降了、质量升了，成功任务反而更贵。原书还测了同一代码任务：关闭思考 12 轮、765 个输出 token、13.2 秒，仍未修好；开启思考 4 轮、2,733 个输出 token、76.3 秒，原定检查全部通过。

关键路径：串行阶段相加，独立分支取最慢。模型 2 秒 → 工具 6 秒、10 秒 → 模型 3 秒：工具有依赖是 21 秒，独立是 15 秒，工具总工作仍是 16 秒。首轮 36.375 秒的模型计算减半，整任务从 76.510 降到 58.323 秒，Amdahl 加速约 1.31。原书还拆解了 Jev 决策模型：只做 prefill、不生成，所以快；但不确定的请求要转交 LLM，转交比例超过约 0.58%，转交费用就超过决策模型本身。

多模态与实时：数一数 token，算一算缓冲

原书 3.3 节

视觉问答是 编码 E → prefill P → decode D。视觉 token 数 nv = H·W / (ppatch²·r²)：Qwen3-VL-4B 的 640×640 图片按 16×16 切成 1600 块，再 2×2 合并成 400 个视觉 token。同一张截图在三个阶段大小不同：压缩文件 0.8 MB；编码结果 EC（含三组 DeepStack 中间层特征，共 4 × 2560 维 BF16）7.8125 MiB；进入语言模型后的 KV 56.25 MiB（每 token 144 KiB）。EC 只要图片和编码配置相同就能复用；KV 还依赖图片之前的上下文。图片边长加倍，视觉 token、EC、KV 都变四倍。

输出若是声音或图像，迭代方式又不同：Fish Audio S2 Pro 每帧要 10 次快速路径前向；Qwen-Image-2512 生成 1024×1024 图像 50 步去噪、true CFG 每步两支，共 100 次 DiT 前向，约 7.830×1015 FLOPs，总量 = ns·nb·Fstep。

实时播放还要每块按时到：缓冲余量 B(t) = A(t) − P(t)。原书时间线：每 20 ms 一块（24 kHz 单声道 16 位，960 字节），模型 12 ms + 发送 1 ms + 网络 5 ms，第一块 38 ms 到；抖动缓冲 40 ms，于 78 ms 开播。第三块网络延迟 50 ms，123 ms 才到，错过 118 ms 的播放时刻，停顿 5 ms。缓冲加到 60 ms，停顿消失，首播推迟到 98 ms。若平均到达速度长期低于播放速度，有限缓冲终究会耗尽。

训练：每参数 18 字节，和 6ND 漏掉的东西

原书 3.4 节

对 Y = XW，反向要算两种梯度：dX = dY·WT（传回前一层），dW = XT·dY（本层的调整方向），三次矩阵乘法各 2mkn，合计约前向的三倍，累计得 Ftrain ≈ 6ND。冻结的矩阵可以省 dW，但只要更早的层还要训练，dX 照算。为了算 dW，前向的输入 X 要一直留到反向用完；优化器状态则要跨多次更新保留。

例题 3-3：Qwen3-8B 的 8,190,735,360 个参数，保存 BF16 权重 2 字节 + FP32 梯度 4 + FP32 主权重 4 + Adam 两个矩估计各 4，每参数 18 字节，共 147.433 GB，还没算激活就超过 H100（80 GB）、RTX PRO 6000（96 GB）乃至 H200（141 GB），是推理 BF16 权重的九倍。显存放不下完整 batch 时，可以拆成多个 micro-batch 累积梯度再更新一次。

6ND 只是粗算：Qwen3-8B、8192 token 一次前反向，6ND 给 402.591 TFLOPs，逐矩阵累计是 431.368，多出的主要是不对应参数的注意力 QKT、AV（前反向 59.381），而嵌入等参数又不该按 6ND 计入，两项相抵后高约 7.15%。这是第 1 篇说的“模型漏项”。只对 4096 个监督 token 算词表投影，可降到 416.074。序列组成也有影响：8192 token 拆成 4096 + 4096 和 7168 + 1024，一层注意力配对从 1678 万增到 2622 万，约多 56%。

强化学习：生成的样本和用上的样本不是一回事

原书 3.5 节

RL 把生成（rollout）、反馈（规则、测试、奖励模型或教师模型）、学习器更新、权重同步连成一个循环，任何一环慢了下游都要等。DeepSeek V4-Flash 先用 SFT + RL 训练领域专家，再用多教师的同策略蒸馏（OPD）合并，教师前向成了生成与更新之间的一项工作。

关键是区分生成的样本和进入更新的样本：保留 nkeep 条、保留比例 a，平均要生成 nkeep/a 条。采用组内相对优势时，同组回答奖励相同（比如全对），优势全为零，生成、评分、更新做了一遍，却没有学习信号。例题 3-4（Qwen3-8B，8 题 × 4 份，P = 1024，G = 256，保留 16 条）：rollout prefill 465.143 + decode 129.056 + 参考模型 634.944 + 策略更新 952.416 = 2,181.559 TFLOPs。写成 Fcycle(n) = n(fg + fr) + Fu：保留比例从 1/2 降到 1/4，生成 64 条，总量 3,410.701，增加约 56.3%，多出的全部来自生成和参考模型。更新后还要把 16.381 GB 的权重发给每个生成副本，4 个副本独立发送约 65.5 GB。

预算：Scaling Law、GPU 小时和全生命周期成本

原书 3.6 节

固定训练预算 C = 6ND，损失 L(N, D) = E + A/Nα + B/Dβ，求导得 Nopt ∝ Cβ/(α+β)，Dopt ∝ Cα/(α+β)；α = β 时预算翻四倍，参数和数据各翻两倍。Kaplan 早期拟合约 N ∝ C0.73，Chinchilla 认为两者应接近等比例增长（约每参数 20 token）。原书用 datablations 的 8 个 C4 观测做留出检验：6 个拟合、2 个大模型检验，均方根误差约 0.0193 nats/token。

但实际模型远超“计算最优”：7–8B 档的 D/N 从 Llama 1 的 149 增到 Qwen3 的约 4,500，比 Chinchilla 基准高一到两个数量级。原书强调这不是拟合错了，而是目标不同：计算最优只最小化固定预算下的损失，开发者还要计入上线后的服务成本，所以选更小、训练更久的模型。全生命周期：Clife = C0 + QΣwjcj；小模型多花 ΔC0 训练、每个成功任务省 Δc，交点 Q* = ΔC0/Δc。原书例：多训 10 万 H100 GPU 小时，每任务省 0.72 GPU 秒，Q* = 5 亿次。

GPU 小时换日历时间要除以卡数：Llama 1 65B 用 1,022,362 A100 小时，2048 卡约 20.8 天；Llama 3.1 405B 用 30.84M H100 小时，按 16,384 卡约 78.43 天。跨卡型比较要折算：一个 H100 / H800 小时按 BF16 峰值约等于 3.17 个 A100 小时。
