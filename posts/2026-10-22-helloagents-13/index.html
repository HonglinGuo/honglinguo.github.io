把前面学的，拼成能用的东西

原书第四部分用三个完整项目收尾：智能旅行助手、深度研究助手、赛博小镇；第五部分是毕业设计，要求读者自己做一个智能体应用提交到共创仓库。三个项目都用 Vue 或 Godot 做前端、FastAPI 做后端、HelloAgents 做智能体，界面和部署细节占了大半篇幅。这一篇略过前端，只看每个项目里智能体部分的设计决策：为什么拆成几个智能体、它们怎么串起来、成本和延迟怎么压、哪些地方还能改得更好。最后用一个选型助手把前十二篇串起来。

本系列是开源教程《Hello-Agents：从零开始构建智能体》（Datawhale 社区编写的开源教程，CC BY-NC-SA 4.0 协议；本笔记依据 2026 年 10 月 14 日的仓库版本）的学习笔记。原书十六章，按“概念 → 手写范式 → 平台与框架 → 自研框架 → 记忆、上下文、协议、训练、评估 → 综合案例”展开，代码量很大。这里重排成十三篇，用自己的话重讲：代码只保留能看清机制的骨架，做成可以逐行走读、可以填空回忆的互动；每篇末尾配原书面试题清单里的相关题目做口述演练。每节标出对应的原书章节，演示数值标“示意”。笔记同样按 CC BY-NC-SA 4.0 共享。

三个案例的共同骨架

原书第 13–15 章各自的 1 节

三个项目长得很不一样，骨架却相同：前端层（旅行助手和深度研究用 Vue3 + TypeScript，赛博小镇用 Godot 4.5 游戏引擎）负责交互与展示；后端层（FastAPI）负责路由、数据校验与状态；智能体层（HelloAgents）负责任务分解、工具调用、结果整合；外部服务层提供 LLM、地图、搜索、向量库等能力。智能体只是其中一层，这和《AI Agent Handbook》里“模型之外还需要一整套系统”的说法一致。

智能体层的设计各有侧重，正好分别用到了前面几篇的知识：旅行助手是多智能体 + MCP（第 6、10 篇），深度研究是Plan-and-Solve + 笔记 + 搜索（第 4、9 篇），赛博小镇是角色扮演 + 记忆 + 状态驱动的提示词（第 3、8 篇）。

先翻牌对照三个案例。

智能旅行助手：四个专家，一个 MCP

原书第 13 章

为什么不让一个智能体包办？原书给了三条理由：工具调用受限（SimpleAgent 每次 run 只执行一个工具，多次调用之间要手动传中间结果；换 ReAct 又要多轮串行思考，至少三次 LLM 调用）、提示词复杂（一份提示要写清景点、天气、酒店、整合四套规则，难维护、易混淆）、难调试（计划不对时说不清是哪一环出错）。于是像旅行社一样分工：AttractionSearchAgent（按偏好搜景点）、WeatherQueryAgent（查天气）、HotelAgent（按住宿类型搜酒店）、PlannerAgent（不调工具，只整合前三者的输出加上日期、预算，按 JSON 格式生成行程）。每个专家的提示词都很短，核心就是一行 [TOOL_CALL:amap_maps_text_search:keywords=景点,city=北京] 示例加一句“必须使用工具，不要编造”。

工具接入走 MCP：用一个 MCPTool(command="npx", args=[amap-mcp-server], env={AMAP_API_KEY}, auto_expand=True) 自动展开出 16 个高德地图工具，而不是手写 HTTP 调用（手写的话 Agent 无法自主选择、十几个参数难描述、响应难解析、新 API 要改多处）。关键细节是三个专家共享同一个 MCPTool 实例：只起一个 Server 进程，省资源，也便于控制 API 调用频率。数据结构用 Pydantic 模型（TripPlanRequest、TripPlan 等），前后端和智能体之间都按同一套类型传递和校验。

原书的 plan_trip 按顺序调用四个智能体。但景点、天气、酒店三者互不依赖，能不能并行？拖动耗时看看差别（耗时为示意）。

深度研究助手：TODO 驱动的三阶段

原书第 14 章

搜索引擎只回答单个问题，研究要回答一串相关问题。原书的范式叫 TODO 驱动：把“研究”变成规划 → 执行 → 整合。三个智能体各管一段：TODO Planner 把主题拆成 3 到 5 个子任务，每个带 title、intent、query，提示词里放当前日期以便搜到新信息，要求 JSON 输出；Task Summarizer 对每个子任务的搜索结果提炼核心观点和关键数据，每个观点标 [1]、[2] 来源；Report Writer 把所有子任务总结按逻辑整合成最终报告。每个子任务的总结和来源都用 NoteTool 存成笔记，可追溯。

两个工程设计值得记。一是 SearchService 中间层：不让智能体自己决定调不调搜索，而是由服务层确定地执行搜索（选引擎、去重、限制 Token、处理失败），再把结果交给总结智能体，让它专心处理信息，这就是第 7 篇说的“确定性的步骤放进固定流程”。二是 ToolAwareSimpleAgent：继承 SimpleAgent，重写 _execute_tool_call，每次工具调用都回调一个 tool_call_listener；后端把这些事件连同状态、任务列表、每步总结一起通过 SSE（/research/stream）推给前端，用户能实时看到研究进行到哪一步。三个智能体是顺序协作：线性流程、输入输出明确、同一时间只有一个在工作。

看一次研究请求在 SSE 通道里推出的事件（事件内容为示意，结构据原书 14.3.3 节）。

易混辨析：深度研究的 TODO 驱动 vs 第 4 篇的 Plan-and-Solve

骨架相同：先规划出步骤列表，再逐步执行。区别有三：每个子任务的执行不是一次 LLM 调用，而是“确定性搜索 + 总结智能体”；中间结果写进外部笔记而不是只放在 history 字符串里；最后多了一个专门的报告整合阶段。可以把它看作 Plan-and-Solve 加上第 9 篇的结构化笔记、第 8 篇的检索增强。

赛博小镇：会记事、会变熟的 NPC

原书第 15 章

传统 NPC 只会说固定台词或走对话树。赛博小镇里每个 NPC 都是一个 SimpleAgent：系统提示词写身份、职业和性格（Python 工程师张三严谨直接，产品经理李四外向爱问“为什么”，UI 设计师王五温和有审美），配两层记忆：WorkingMemory（最近 10 条、保留 120 分钟，保持对话连贯，比如理解“它是什么颜色”里的“它”）和 EpisodicMemory（SQLite + Qdrant，检索“上次讨论的那个项目”）。每轮对话先取最近 5 条短期记忆、再检索 3 条相关长期记忆，一起交给模型。

降成本的关键是批量生成 + 即时响应的混合模式。后台定期用一次 LLM 调用、以 JSON 格式生成所有 NPC 的“背景对话”（正在调试代码、在看产品文档），原书说成本降到约三分之一，而且同一上下文里生成的台词彼此呼应；玩家按 E 键发起对话时，才调用该 NPC 自己的智能体，结合记忆和好感度生成个性化回复。

好感度分五级：陌生 0–20、熟悉 21–40、友好 41–60、亲密 61–80、挚友 81–100。每轮对话后用 LLM 判断玩家态度：友好 +5、中立 +2、不友好 −3，分数截断在 0 到 100；当前等级对应一句提示词片段注入系统提示（陌生时“保持礼貌但不要过于热情，回复简短专业”，挚友时“无话不谈，回复亲切真诚”），于是 NPC 的语气会随关系变化。

和张三聊几句，看好感度和提示词怎么变。

读设计时值得多想一步：中立也加分

按原书的规则，中立对话也 +2，所以只要不冒犯，好感度就会一直涨：大约 40 轮普通对话就能从陌生聊到挚友，“友好”和“中立”之间只差 3 分的节奏。另外，每轮额外调用一次 LLM 做情感判断也是成本。可以考虑中立记 0、按天衰减、或者把情感判断合并进 NPC 回复的同一次调用里（让模型同时输出回复和态度标签）。这是我的读后想法，不是原书观点。

毕业设计：做一个自己的

原书第 16 章

原书最后一章不讲新技术，而是要求读者做一个完整的智能体应用，以开源项目形式提交到仓库的 Co-creation-projects 目录：目录名用“GitHub 用户名-项目名”（如 jjyaoao-CodeReviewAgent），内容包括可运行的 Jupyter Notebook 或 Python 脚本、requirements.txt、README.md（项目简介、核心功能、技术栈、快速开始），可选演示视频、截图、数据集（大文件放外部链接）；通过 Fork、提交、Pull Request 提交，社区评审通过后合并。选题原则三条：解决真实问题而不是为技术而技术、有限时间内能完成、能清楚展示能力；推荐方向有生产力工具、学习辅助、创意娱乐、数据分析、生活服务五类，原书示例是智能代码审查助手。

做之前，按全书的顺序过一遍决策会很有帮助：先判断要不要 Agent（第 1 篇），选范式（第 4 篇），决定平台、框架还是自研（第 5–7 篇），再定记忆与检索（第 8 篇）、上下文策略（第 9 篇）、协议（第 10 篇），最后是要不要训练（第 11 篇）和怎么评估（第 12 篇）。

面试演练

题目取自原书 Extra01 与第 13–15 章内容

当 Agent 要在真实或模拟环境（机器人、游戏）中执行任务时，它和纯软件工具型 Agent 有什么本质区别？Extra01 · Agent 第 9 题

  • 状态与时间：环境持续变化，有实时性要求；游戏 NPC 要在几百毫秒到几秒内回应，机器人还要满足控制周期。
  • 观察：来自传感器或游戏状态，部分可观察、有噪声，需要感知模块转换成模型能用的描述。
  • 行动后果：行动不可撤销甚至有安全风险，需要底层控制器和安全约束兜底，LLM 只做高层决策。
  • 成本结构：交互频繁，必须像赛博小镇那样批量生成、缓存、分级响应，或用小模型、本地模型。

设计一个多智能体旅行规划系统，你会怎么拆分？有哪些性能优化？

  • 拆分：按信息来源拆成景点、天气、酒店等检索专家，加一个只做整合的规划专家；每个专家提示词短、工具少。
  • 串联：检索专家互不依赖可并行，规划专家等它们完成后执行；中间结果用结构化模型（Pydantic）传递并校验。
  • 优化：共享 MCP Server 实例控制并发与限流；检索结果缓存；规划输出要求 JSON 并做校验与重试；预算等确定性计算放在代码里而不是交给模型。

你认为目前限制 Agent 能力和普及的最大瓶颈是什么？Extra01 · 其它第 1 题

  • 可靠性：多步任务的错误会累积，格式漂移、幻觉、工具误用；需要验证、反思和评估闭环（第 4、12 篇）。
  • 成本与延迟：多次调用串行累加（第 4 篇 ReAct、第 13 篇的串行规划），需要并行、缓存、小模型分工。
  • 上下文与记忆：长任务的信息管理仍然困难（第 8、9 篇）。
  • 安全与信任：权限、提示注入、可审计性（第 9 篇沙箱、第 10 篇协议安全）。答题时选一个展开，结合自己的实践例子。

回扣开头的三个问题

先自己答，再点开
1. 共同骨架？各自如何分工串联？

四层：前端（Vue 或 Godot）、后端（FastAPI）、智能体层（HelloAgents）、外部服务（LLM、地图、搜索、向量库）。旅行助手：景点、天气、酒店三个检索专家 + 规划专家，原书按顺序调用，共享一个高德 MCP 实例。深度研究：TODO Planner 拆 3–5 个子任务 → 每个子任务由服务层搜索、Summarizer 总结并写笔记 → Report Writer 整合，顺序协作，经 SSE 推送进度。赛博小镇：每个 NPC 一个 SimpleAgent，带短期与长期记忆，背景台词批量生成，玩家交互时即时响应。

2. 降成本或延迟的设计？可改进处？

旅行助手共享 MCP 实例、提示词拆小；深度研究用 SearchService 确定性执行搜索、限制 Token；赛博小镇用一次调用批量生成全部 NPC 背景对话，交互时才单独调用。可改进：旅行助手的三个检索专家互不依赖，可以并行；深度研究的子任务也可并行检索；赛博小镇中立也加分会让好感度单调上涨，情感判断可以合并进回复调用。

3. 自己做应用的决策顺序？

先判断是否需要 Agent（Workflow 还是 Agent）；选范式（ReAct、Plan-and-Solve、Reflection 或组合）；选实现方式（低代码平台、框架或自研）；定记忆与检索；定上下文策略（JIT、压缩、笔记、子代理）；定协议（MCP、A2A）；判断是否需要训练（SFT、GRPO）；最后设计评估（基准、过程指标、LLM Judge、持续监控）。提交时备齐 Notebook 或脚本、requirements.txt、README，通过 PR 提交。
