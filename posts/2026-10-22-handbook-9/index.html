完成语义：五层信息，各有权威

原书 10.1 节

原书第 10 章开头先把对象理清：Task 是异步执行的最小业务单元，有独立持久的标识和自己的业务 State，可以跨等待、恢复、审批和多个 Session；Session 只是其中一段执行视图，跨 Session 续跑要由 Runtime 显式装载经授权的 Task State，而不是默认两个 Session 天然共享上下文。业务 State 归业务应用，Session Context 归 Harness / Runtime，Checkpoint 归工作流引擎 / Runtime，Runtime State（心跳、租约、Worker）只活一个执行租约，外部副作用归业务系统。

“任务做完了吗”要分五层回答：执行状态（Runtime 给的 succeeded / failed，回答“这次有没有跑完”）、节点运维状态（Worker 在不在线、租约是否有效）、候选证据（日志、Trace、快照、Artifact、LLM 原始响应）、Evidence（被成功标准明确引用的候选证据）、业务 Outcome（业务应用或获授权 Verifier 依据 Evidence 与标准做的最终判定）。LLM-as-a-Judge 是 Evaluation 的一种实现，不是 Outcome 的天然权威；人工审核也只有被授权才能形成 Outcome。运维侧的“强制标记成功”只能在授权范围内改变执行状态并留下审计，不能跨层直接判定 Outcome。

恢复与幂等也要分清：外置调度能统一触发和故障转移，但仍可能重复投递；Checkpoint 复用的是计算结果，不等于外部副作用幂等：外部写入已提交而 Checkpoint 还没落盘，重跑照样重复。幂等手段（任务唯一键、幂等键、去重账本、outbox / inbox、租约与 fencing token、对账与补偿）按交付语义和外部系统能力选择，没有通用必选项。Watch、回调、轮询只是变化信号，信号缺失时要重新读权威状态对账。

把这些信息放到正确的层级。

异步任务：队列、调度、状态机与同步

原书 10.2 节

同步请求—响应在简单问答里高效，但长时间、跨请求、要操作外部环境的任务会撞上请求超时、上下文溢出、用户必须在线、等待期间持续占资源。请求超时只表示调用方没在期限内拿到结果，不能证明执行已经停止。异步的核心是把执行生命周期与请求生命周期解耦：提交并得到可靠接收确认后拿到 Task ID，后台排队、执行、重试，完成后经 Webhook、消息推送或轮询通知。异步也不会扩大上下文窗口，那仍是 Harness 的事。

生产级异步系统由三类组件协同：任务队列（按优先级、同优先级 FIFO；积压时拒绝新任务并返回结构化错误、对低优先级限速、告警扩容，队列深度本身是核心指标）、调度器（选 Worker、维护租约、重试与故障转移；所有 Worker 都忙时不应继续取任务，这就是背压，常见做法是并发配额、队列水位线、消费速率自适应、租约超时、动态容量的组合）、任务执行状态机（维护合法转换，以数据库为权威存储、内存缓存加速）。原书的状态集合是 waiting、queued、running、hold、succeeded、failed、killed、skipped、mark_succeeded。

状态同步有三种方案：调度器轮询（控制集中，但单次轮询失败不能推断任务异常，网络分区、GC 暂停都可能让查询失败而 Worker 仍在跑，判异常要靠租约 / 心跳）、Worker 回调（实时，但崩溃时可能发不出，要超时兜底；回调带 Task ID、事件序号、Worker 标识、租约 token，以便幂等消费和丢弃迟到事件）、共享存储 + 变更通知（Redis Keyspace Notification 默认关闭且断连期间事件会丢；etcd Watch 落后超过 compaction 会返回 ErrCompacted，要重读全量）。生产通常组合：回调为主、轮询 / 租约兜底、共享存储做权威持久化。HITL 让 Task 进入 hold，等待可能从分钟到数天：内置调度若只有内存状态就得保留进程，外置调度在具备恢复条件时可以释放执行资源；审批结果回传要带 Task ID、审批版本、授权主体、决策结论，接收方据此校验未过期、未重复、与当前状态兼容。

给状态同步的三种情况选处理方式。

定时触发：从被动响应到主动执行

原书 10.3 节

定时任务让 Agent 从“被动工具”变成“主动数字员工”：每天 9 点生成日报、每周一检查服务器健康。它按用户或业务的预授权、按时间规则创建 Task。时间触发有 Cron、ScheduledAt（未来某时刻一次）、FixedRate（固定频率）；事件触发有 Webhook（业务方 → Agent 系统）、消息队列、内部事件。两类触发在执行层走同一条路径：都是向任务队列投递一个 Task，共用调度、并发控制、重试和对账。

定时任务的属性里有几项容易忽略：任务并发数（1 表示串行）与阻塞处理策略（并发满时新触发排队、跳过或合并为最新）；错过策略（调度器宕机导致触发点错过后怎么补）；时区与发生标识（明确时区、夏令时，用调度 ID + 计划发生时间识别同一次触发）。大规模下调度通常外置到专用系统（XXL-JOB、SchedulerX、Airflow 等），原书强调三点：两类触发在执行层统一；外置调度系统不接管业务 State 的权威，它持有的是 Runtime State 与触发计划；幂等是业务设计责任，failover 期间子任务可能执行多次。

工作流：DAG、节点与 Join

原书 10.4 节

编排结构没有收敛到两种：单个 Task 内由 Agent 自主决策（ReAct）、预定义工作流（把计划固化为图）、Multi-Agent 协调（Planner 动态分解），以及它们的组合，比如工作流的某个节点内部是一个完整的 Agent 循环。预定义工作流能减少重复规划、让控制路径易测，但不会消除节点内的模型错误、工具开销和失败重试。原书把工作流限定为 DAG：需要循环时用运行时有界展开（ForEach）、子流程迭代（Loop 设最大次数），图本身保持无环；业务确实需要带环的流转（审批驳回回到起草），应改用状态机或流程图模型，而不是把环硬塞进 DAG。节点分业务节点（Agent 调用、工具调用、代码执行、知识检索、人工审批、通知推送）和逻辑节点（条件分支、并行、汇聚、循环、等待、错误处理、子工作流）。

就绪条件要明确：普通依赖边要求上游 succeeded 或 skipped；AND Join 要求所有入边到达终态且满足策略（全部成功或至少 N 个成功）；OR Join 任一入边满足即就绪，未选分支由引擎显式取消，迟到结果进审计日志、不改变下游已就绪的状态。不显式取消，未选分支会继续消耗资源、产生副作用，和下游基于“先到结果”做出的决策冲突。

工程上还有三件事：步骤级 Checkpoint（节点完成后持久化输入、输出、状态，进程崩溃后从最后一个成功 Checkpoint 继续）；幂等与局部重跑（外部调用先存意图、执行后存结果，故障窗口按后端能力用事务、Outbox、幂等键或对账；邮件、扣款这类已发生操作只能确认或补偿，恢复检查点撤销不了）；可视化运维（节点实时状态、耗时、重试，支持重跑、跳过、强制标记成功、暂停、终止；“查看任意节点输入输出和 LLM 原始响应”应按需授权，而不是默认开放）。

三个并行分支查询同一个问题，比较 AND Join 与 OR Join（耗时为示意）。

多 Agent 团队：接入、组织、分解与接受

原书 11.1–11.4 节

把多个 Agent 放在一起不会自然形成团队。缺少清晰的分工、协作方式和状态管理，参与者越多越容易重复执行、信息不一致、任务遗漏、责任不清。团队需要共同目标，也要知道每项工作谁推进、依赖什么、完成后交给谁、怎样才算结束；编排层把宽泛目标逐步变成可执行、可验收的任务，但不需要介入每个成员的所有执行细节，否则主管 Agent 会变成新的上下文和执行瓶颈。只有专业分工、并行、故障隔离和过程治理的收益覆盖沟通与协调成本时，团队才有价值。

接入异构成员时保留其原有 Harness：能改代码就加协作 SDK 或任务接口；能装插件、控制启动就用插件与适配程序；只能调远程 API 就在外部加适配程序，记录远端任务编号。能逐步返回文本，不代表支持任务查询或中断恢复，要按实际能力安排工作。Coding Agent 内部的子代理不因接入而自动成为团队成员。个人工作区接入要注意：设一个工作目录参数挡不住程序访问其他文件；用户允许某 Agent 处理项目代码，不意味着团队其他成员能借用该用户的账号权限；本地 Agent 只回一个绝对路径，别的机器读不到。

组织拓扑有三种，不是演进阶段：主管—执行（集中协调、分散执行，警惕所有局部决定都等主管）、对等协作（直接协商，但要预先约定分歧怎么解决、谁整合、谁对最终交付负责）、分层编排（按专业小组交付，只有小组能承担相对完整的交付时才值得加层）。专业能力说明擅长什么，组织角色说明负责什么，二者不同；成员关系、参与关系、执行责任、审核责任要分别记录。任务方面，Task 是持续的工作约定，Task Run 是一次实际执行，一个 Task 可以因重试、恢复、改派有多个 Run；消息发送成功不代表任务被承接。团队级停止条件要在根任务开始前约定：总预算、最大委派深度、派生任务数、重试次数、返工轮次、连续无进展时的处理。

    最小充分共享，入站出站分开授权

    原书 11.5–11.7 节

    团队需要的不是所有成员共用一个不断增长的“共享大脑”，而是有边界的信息协作：成员保留独立推理空间，任务模型维护协作状态，产物系统保存成果，团队记忆沉淀可复用知识，每个 Agent 按当前角色和任务取必要信息。团队共享的是上下文来源，不是同一个 Context。Handoff 只需传四类：目标、已知事实、待处理事项、可用引用；完整搜索过程、工具调用记录、未验证的中间推理通常不必原样传。团队记忆只沉淀经过任务结果、外部数据、其他成员或人工确认的内容，并保留来源、适用范围与有效性。消息说明“发生了什么”，Task State 和 Artifact 才记录“当前事实是什么”：收到“任务完成”通知后，仍应读取任务当前状态；收到“报告已生成”，应通过 Artifact 引用读取报告本身。

    身份上，原书区分人员主体、服务主体、Agent / 工作负载主体（每个 Agent 唯一，不与模型或临时容器绑定）、执行主体（实际发起访问的运行实例）、临时凭证（证明身份与范围的载体，凭证不是身份）、委托授权（谁允许 Agent 代办什么，委托也不是身份）。一次动作的有效权限是人员权限、团队边界、Agent 策略、资源策略、委托范围的交集，显式拒绝优先；Agent 间交接不会扩大权限。最关键的一条：入站权限（谁可以调用 Agent、发起什么任务）和出站权限（Agent 可以代表谁访问哪些资源）独立配置、分别校验，调用者能访问 Agent，不等于 Agent 能访问调用者的全部资源。

    观测上，长程任务可能跨多条 Trace，不要强行塞进一棵调用树：用 W3C Trace Context 传播，teamId、taskId、taskRunId、sessionId 作业务关联；能连续传播的用父子 Span，跨 Trace、并行汇合的用 Span Links。评估结论与事实记录分开保存，并写明方法、版本和时间。

    权限判断

    易混辨析：Workspace vs Environment

    Workspace 是 Agent 可直接操作的工作目录及映射其中的获准资源（文件、分支、快照、工具与凭证引用），按任务或项目的持久化策略管理，可以跨运行实例重新挂载。Environment 是本次执行采用的运行条件（计算、网络、文件系统、凭证映射、隔离），随运行实例或部署配置变化。前者让工作文件延续，后者约束每次运行能怎样访问和执行。

    通信：四个通信面 × 四档交互语义

    原书 12.1–12.6、12.8–12.9 节

    进入 Agent 场景，四个前提要重新检查：调用耗时是否有界、会话是否依赖当前连接、等待期间占用哪些资源、通信端点是否会变化。全章的主线是让必要状态独立于连接存在：连接与进程内存里的内容断连即丢；外部状态存储保存任务记录、检查点、结果引用；持久消息通道保存消息、序号、确认位置，超出保留期就有缺口。消息重播不自动恢复进程，也不自动撤销或去重外部操作。

    第一个坐标按通信双方分四个面（原书自己的分类）：人机面（用户与 Agent，AG-UI；要增量可见、随时打断，而前端连接最不可靠）、能力面（Agent 与工具，MCP；毫秒级查询和分钟级任务共用一套协议）、协作面（Agent 与 Agent，A2A；任务天然长跑）、内构面（服务端组件之间，无标准协议；海量会话通道的元数据成本与多租户隔离）。第二个坐标按耦合度分四档：S1 请求—响应、S2 请求域流式（当前流依赖连接）、S3 任务句柄（提交后凭标识查询或订阅）、S4 持久通道（订阅、确认、补读）。它们不是成熟度等级，一个系统可以同时用多档。每段通信都要回答契约六要素：标识、顺序、投递保证、续传点、生命周期、背压。

    两个常被混为一谈的地方：token 流和 SSE 说明结果怎样逐步到达，不说明任务是否独立于连接存在；有任务句柄不一定能重播事件，有事件序号也不自动保证业务可恢复。MCP 与 A2A 走向相反方向，也不是路线之争：MCP 2026-07-28 移除了协议会话和初始化握手，改为逐请求元数据，长任务交给可选的 Tasks 扩展，协议无状态不等于应用无状态，状态责任转移到应用层的显式句柄；A2A 为长时间运行与人在回路设计，强化 Task 生命周期（提交、执行中、需要输入、需要授权、完成、失败、取消、拒绝），流式更新（S2，流完即断）、推送通知（触发“去拉取”）、任务查询（保证结果可寻址）按能力组合。同步也有它难以替代的优点：控制路径直接、进程内调用栈连续、运维和成本结构简单。选型原则仍是每个通信面选最低充分语义。

    易混辨析：流式输出 vs 任务异步

    S2 流式解决“过程可见”，作用域通常是一次请求，流断了就断了。S3 任务异步解决“执行与连接解耦”，断连后凭句柄查询结果。二者要分别检查：有没有独立于连接的任务句柄？有没有事件续传位置？断连是否取消执行、还能否查结果，由服务契约明确，不能从传输形式推断。

    内构面：通道键与手脑分离

    原书 12.7 节

    服务端内部要处理两件事：怎样组织并发会话的消息，以及怎样连接决策循环与工具执行。一种做法是为每个会话或任务开独立逻辑通道，按业务标识发送、订阅、记录消费位置。原书提炼的判据是：通道键决定治理粒度，通道以什么业务标识命名，隔离、限流、观测、回收就以什么粒度进行。三个案例：智能语音交互以会话标识为通道键（请求侧按会话分区保序，响应侧按会话通道回推，路由逻辑下沉到消息中间件，应用节点更接近无状态）；模型网关限流以“用户 × 模型”为键（网关只做粗粒度上限，漏桶从进程内搬到通道阵列，命中限流时只挂起该通道）；资产中心以“用户”为键（消息只带元数据和对象存储索引，单用户突发不牵连他人）。

    规模上去后，“一会话一个标准主题”会让元数据先于业务压垮控制面；广播让单节点能力成为上限；每 Session 一个消费组会让消费组数量爆炸。另一个反模式是把会话和常驻工作进程一对一绑死，原书引用的说法是把 Worker “当成了宠物”。轻量通道（如 RocketMQ LiteTopic）让逻辑通道挂在少量父主题下，只在内存里表现为字符串键，首次发送自动创建、空闲自动回收、单通道挂起不牵连其他。

    决策与执行分离（手脑分离）：决策循环要访问任务状态、等待模型；工具执行要突发计算或更强隔离，分开部署可以分别伸缩。Anthropic Managed Agents 把 Agent 虚拟化为三个抽象：会话（追加式事件日志）、Harness（调模型、路由工具调用的循环，无状态，新实例凭会话标识拉历史续跑）、沙箱（降级为一只普通的“手”，失败表现为工具错误而不是会话中断）；会话不等于上下文窗口，日志完整保留，取用与压缩留给 Harness。原书还详细介绍了 Qoder Cloud Agent 的四层：脑（Agent Runtime）、路（MQ，Session 内有序、跨 Session 并行）、手（Sandbox Worker，完成即释放）、底（Session State），概括为“会话常驻、计算流动、状态可续”。

    回扣开头的三个问题

    先自己答，再点开
    1. succeeded、强制标记成功、Outcome 有何区别？Checkpoint 能防重复副作用吗？

    succeeded 是 Runtime 给的执行状态，回答“这次跑完没有”；强制标记成功只在授权范围内改变执行状态并留审计；Outcome 由业务应用或获授权 Verifier 依据 Evidence 与成功标准判定。Checkpoint 只复用计算结果，外部写入已提交而 Checkpoint 未落盘时，重跑仍会重复副作用；要按外部系统能力选择幂等键、去重账本、outbox、fencing、对账与补偿。

    2. OR Join 为何要显式取消？多 Agent 结果的四个层次？

    不取消的话，未选分支继续消耗资源、产生副作用，并与下游基于先到结果的决策冲突；迟到结果只进审计日志。多 Agent 中：执行者提交 = 候选成果已产生；Leader 或指定审核者接受子任务 = 可用于下游；根任务完成 = 当前有效版本的成果共同覆盖目标、团队执行阶段结束；用户或指定验收者依约定规则确认接受并归档，任务才真正完结，未通过则沿原任务关系继续修订。

    3. 流式 = 异步吗？MCP 和 A2A 为何反向演进？

    不是。流式只说明结果逐步到达，可能只是当前调用的输出；任务异步要求有独立于连接的任务句柄。MCP 主要访问工具、资源，收敛协议会话有利于请求在实例间分配，状态由应用显式句柄承担（协议无状态 ≠ 应用无状态）；A2A 面向 Agent 间长任务交接，需要可查询的任务生命周期。两者可以组合：编排 Agent 经 A2A 委派，专业 Agent 经 MCP 调工具。
