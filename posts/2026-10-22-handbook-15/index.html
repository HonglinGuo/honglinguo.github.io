从一个 Agent，到一层系统

最后一篇收两头。一头是落地：原书开篇的开发者调研给出了现状（近一半在做，不到五分之一上线），实践篇收录了二十多个企业与开源案例。另一头是展望：当一家企业同时运行多个 Agent、多种框架、多个租户，前面每一篇的工程要求都会在每个应用里被重复实现一遍，而且互不一致；原书第 30 章讨论哪些能力应该下沉成所有 Agent 共享的系统层，并把它称为 Agentic OS，同时声明它现在还不是一个已经存在的产品类别。

本系列是开源白皮书《AI Agent Handbook（企业级 Agent 白皮书）》（阿里云团队编写的开源白皮书，Apache-2.0 协议；本笔记依据 2026 年 10 月 21 日的仓库版本）的学习笔记。原书按“架构 → 构建 → 运行 → 治理 → 调优 → 实践”组织三十章，这里重排成十五篇，用自己的话重讲，并把关键表格做成可以点、可以分类、可以走流程的互动。概念与结论取自原书，每节标出对应章节；为演示设的场景和数值标“示意”。原书由阿里云编写，涉及阿里云产品的方案与数字属于厂商自述，文中会单独标出。

2026 Agent 开发者调研

原书《2026 Agent 开发者调研报告》

原书开头附了一份调研：在北京、深圳、广州、上海、杭州等地的线下开发者沙龙回收有效问卷 1906 份，受访者以技术决策者、架构师、一线工程师和产品经理为主。做不做 Agent 已不是议题：暂无开发计划的从去年的 22% 降到 15%，已开发完成或开发中的合计 46%（去年 36%），但真正部署到生产的只有 18%，持续迭代的不到 10%。上线率差距普遍大于开发率差距（上海大型企业已上线 45%，小微企业 16%），原书据此判断卡点不在意愿，而在持续演进 Agent 的工程能力。

几个与前面各篇直接对应的数字：架构上单 Agent 为主 40%、多 Agent 为主 42%、15% 把人在回路当作主要架构原则，是共存不是替代（第 1 篇）；采购 Coding 工具的 57%、用通用 Agent 框架的 78%，近四成两者都用，供应商碎片化，“可迁移的工程抽象比押注某个厂商更有价值”（第 3 篇）；记忆与上下文的痛点里检索不准 54%、更新与遗忘机制缺失 48%，窗口限制只排第三（第 5 篇）；关注或落地 MCP 的 37%，但完成企业内私有部署的只有 9%（第 12 篇）；多模型路由与自动降级是 63% 企业最需要的网关能力，成本归因（50%）比审计合规更早成为观测重点（第 8、10 篇）。

评估是短板：55% 靠人工抽查，基于运行轨迹自动评估的只有 6%，28% 没有系统性评估；任务成功率 90% 以上的约一成，70% 以上的约 55%，16% 根本没量化过成功率。用了评估手段的企业，成功率 70% 以上的比例约为没有评估体系的两倍（第 14 篇）。这些是阿里云开发者沙龙问卷的结果，样本以参会开发者为主。

企业案例里反复出现的做法

原书第 25–28 章及专题

研发效能的几个案例不约而同地讲了同一件事：编码提效不等于交付提效。一个复杂 Feature 从需求到上线约 20 个工作日，编码约 2 天，即使编码快 10 倍，端到端也只从 20 天降到 18.2 天；堵点在需求澄清、评审跟不上上万行的产出、测试排期这些仍由人衔接的节点（云通信团队的说法是“只要交付链路里存在由人衔接的节点，该节点就决定了吞吐上限”）。于是方向从“让 Agent 写代码”变成“让一支 AgentTeam 交付结果”，人只在目标、架构和风险判断上介入。原书也很克制地标注了效果：内部 19 道未参与调优的盲测题 10 道等价、5 道接近、4 道部分完成，交付节奏约一周的观察“样本量仍小”。

其他领域的做法可以归纳成几类：领域化（Kitta 把通用 Code Review 领域化，沉淀项目级专家资产与审查流程，原书引用的数据是龙蜥社区累计审查超 7 万个补丁、门禁准确率 97%；ABACI 把每次内核变更当作测试目标做定向测试）；工作流承载过程（PatchPilot 把补丁移植拆成冲突分类、依赖分析、AI 解冲突、语义审查、交付回检等可观测可恢复的阶段）；让研发系统可被调用、过程可被验证、任务可持续运行（PolarDB-X 的 Loop 工程，7×24 处理报警到自动修复）；先治数据再上工具（畅捷通的“指标陷阱”：底层指标全绿，用户体验已经劣化；吉利的“先治数据、再上工具、以场景建信任”；塔斯汀不到十人的 SRE 支撑万店）；规模化运营（滔搏 4360 家门店：“让今天解决过的问题，成为明天可以复用的能力”）；以及 GenUI（由 Agent 依据本次结果动态组织结论、证据和可执行操作，渲染只用受信组件）、Jev“系统 1 模型”做快速结构化决策与 HiRoute 路由、Personal Agent 的产品与商业观察。

这些案例大多由阿里云团队或其客户撰写，效果数字来自内部评测或生产统计，原书在多处注明“文中数据来源于内部评测与生产环境统计”。读它们更适合取方法，而不是取数字。

开源赛道：把 Agent 放进高风险流程

原书第 29 章

第 29 章记录了 2026 GOAI 世界人工智能开源大赛 Agent Infra 赛道的 15 项决赛作品（847 个提交、覆盖 38 个国家和地区）。赛道要求至少三个职能不同的 Agent、以 Skill 封装能力，覆盖从任务输入、拆解、上下文传递、工具调用、结果验证、证据沉淀、审批与回滚到经验沉淀的完整链路，场景横跨能源电力、金融、建筑设计、零售、财务结算、IT 运维、安全运营、数据工程等。

原书最值得记的是它的总结：15 项作品全部选择了企业内部的高风险流程，这在一年前还普遍被回避；它们给出的共同答案不是提升模型能力，而是重新组织权限：执行与验证分离、授权绑定到具体动作、关键计算交给确定性引擎、拒绝作为合法终态。“这四条都不需要更强的模型，需要的是更清楚的工程设计。”还有一批可迁移的模式，例如“原件只读 + 白名单修复”适用于任何不能损坏原始数据的受控修改，同一套控制面只替换平台工具、阈值与场景能力就能覆盖不同平台。

为什么需要一层 Agentic OS

原书 30.1–30.2 节

原书先回顾全书的五项共识：架构对象是系统而不是一次调用；任务是需要长期管理的对象，状态必须外置、可暂停可恢复；能力动态接入，发现与授权必须分开；自主性必须与权限、可撤销范围和可验证性匹配；证据是变更能否发布的前提。这些在单个应用里能落地，困难出在组织层面，六类约束会在每个应用里被重复且不一致地实现：任务缺统一标识与状态归属；执行环境成为一等资源，按峰值预留浪费、按均值部署拥塞；能力元数据缺“是否有副作用、是否幂等、失败能否安全重试”三类声明；上下文与状态的边界被压缩、摘要、续行侵蚀；授权难以随任务派生、在终止时级联收回；证据采集点分散、口径不一。

但不是所有共性能力都该下沉，把任务语义、业务规则或评估口径塞进系统层，只会得到一个更难替换的框架。原书的三条判据：复用性（多个应用重复实现、差异不产生业务价值，例如工作区快照、沙箱创建、Trace 采集；任务终止条件和验收标准不属于此类）、强制性（必须由被约束方之外的组件执行才生效，例如权限校验、出站控制、预算上限、审计；只写在提示词里、或由被约束的 Agent 自己调用的约束不是强制的）、可验证性（需要独立于执行方的证据来源，Agent 自己上报的结果不构成独立证据）。必须满足复用性，且至少满足另外一条。

由此给出窄定义：Agentic OS 是为 Agent 任务提供公共运行对象、公共能力接入、可强制边界与统一证据的系统层，以任务、环境、能力、授权与证据为核心管理对象，不持有任务语义。三条否定同样重要：它不替代 Harness（模型看什么、调什么、何时停、怎样验收仍留在应用侧）；它不是又一个框架（框架的约束在不用该框架时失效，系统层的约束应在被约束方不配合时仍然成立）；它不必然意味着修改内核（目标是让能力位于被约束方之外，而不是位于尽可能低的层次）。原书还指出两条正在会合的演进线：平台能力向下沉（openEuler Intelligence、RHEL MCP Server、Windows 的 Agent 账户与 workspace），系统承载向上增强（轻量创建、模板预热、写时复制、PSI 与 cgroup v2），会合点正是环境、授权与证据。

用三条判据判断：这项能力该不该下沉？

九类管理对象与三层结构

原书 30.3 节

操作系统的形态由核心管理对象决定。原书归纳了九类：Agent 身份、Run、Session、Workspace、Skill、Tool 与 MCP 端点、Budget Lease（预算租约）、Policy、Evidence。其中三个与传统对象差异最大：Run 与进程不是一个层次，它可能跨进程、副本、区域，或中途挂起等审批，正确性依据是“任务事实是否完整一致”而不是“进程是否存活”；Budget Lease 把配额和最小权限合并成一件事：一次授权同时限定可用资源、可执行操作、有效期限与撤销方式，并可随子任务派生，缺少它，“终止任务”和“收回该任务的全部权限”只能靠多处配置协同；Evidence 必须区分计划中、已发出、已确认结果三种操作状态，它直接决定恢复策略（恢复本地工作区不会把已经重启的远程服务恢复原状，已发出未返回的调用直接重试可能重复产生影响）。

九类对象的管理职责分三层，各对应一条判断标准：Agent 运行服务层解决复用性（Run、Session、Workspace 的生命周期，上下文、记忆、技能的读写接口，并在这些操作上绑定预算租约）；系统承载层解决成本与密度（沙箱与工作区的轻量创建、模板共享、及时回收，按活跃状态分配容量；单纯增加沙箱数量可能让整体服务质量下降）；治理与证据层解决强制性与可验证性（身份、策略、授权集中定义，判定点分布在请求路径上，采集模型调用与系统行为的关联证据，提供恢复与补偿所需的操作记录）。最重要的一条边界是运行服务层与应用侧 Harness 编排层之间：任务语义不下沉。“一旦系统层开始规定任务该如何完成，它就从操作系统退化为框架。”

原书反复引用阿里开源的 ANOLISA 作为组织方式的样本（并说明多数组件仍是 0.x 版本）：Token-less 在 Agent 与模型之间压缩工具 schema 和响应，不改框架代码，被丢弃的项保留可检索标记，是一次“合格下沉”；AgentSight 用 eBPF 观测，提供独立于执行方的证据；Agent Sec Core 的 Skill Ledger 给技能补上签名、漂移检测和阻断状态，说明“Skill 可校验”需要这三样同时存在。

解耦、标准化与互操作

原书 30.4–30.5 节

Agentic OS 能否成立取决于四个解耦面上是否有稳定接口，所谓稳定，是能在不重写任务语义的前提下替换实现，并用同一套评估证明替换前后能力等价。模型与 Harness：接口形态相对成熟，但协议兼容不等于能力等价，模型替换只能用完整 Harness 回归验证；Harness 与运行时：状态外置已成共识，“一次运行”的定义还不一致；能力与协议：MCP 解决了发现与调用，但副作用、幂等性、风险等级缺少可机读声明，不能把“能发现”当成“可执行”；运行时与承载环境：多后端可配置已有实践，缺的是快照语义的边界声明（内部快照能恢复什么、不能恢复什么）。解耦也有代价：版本组合矩阵、不改接口却改变行为的隐式变更（系统更新带来模型变化后要重新验证提示词行为）、评估成本，评估因此从“质量保障手段”变成“解耦的前提条件”。

原书认为具备标准化条件的有六类接口：任务与运行对象模型、身份与授权（委派链、租约的授予与撤销）、能力描述与发现（补充副作用、幂等性、风险等级、前置条件，原书认为这是当前最欠缺、收益最直接的一类）、可观测事件语义、评估与指标口径、执行环境契约。形成机制有上游贡献、多方共建、可复现测评三种。生态化分三层：协议兼容（能互相调用，MCP 在工具接入上已达到）→ 语义一致（相同调用产生相同的可观察后果，包括错误分类、重试语义、状态变更范围，目前普遍未达到）→ 证据可比（运行记录与评估结果能放在同一口径比较）。原书提醒标准化不应先于共性问题收敛，并推荐一种披露口径：数字 + 适用范围 + 测量来源，缺少后两者的单一百分比，数值再高也没有跨实现比较的价值。

这条效能声明披露得够不够？

从可靠执行到可控自治

原书 30.6 节

原书把第 4 篇的完成验证和第 6 篇的权限审批合在一起，得到一条自治阶梯：L1 建议（由人执行）、L2 单步获准执行、L3 有界自主（限定资源、预算、操作集，需要预算租约和完整轨迹）、L4 长任务自主（需要可级联撤销的授权、可回退的工作区，并区分计划 / 已发出 / 已确认）、L5 组织级自治（需要可验证的委派链、跨域强制点和跨组织可审计的责任证据）。隐含的判断是：自治程度的上限不由模型能力决定，而由可撤销范围与可证明范围决定。一项操作既不能撤销、也不能证明结果，无论模型多可靠，交给自主执行都缺少工程依据。

纳管多来源 Agent 时最常见的表述问题，是把“能观测到”说成“能控制住”。一项边界只有同时满足三个条件才能称为强制边界：覆盖全部可用路径（任务入口、凭证获取、网络与 DNS、文件与进程间通信、子进程、原生工具、后台任务与子 Agent、交互控制台）；判定组件不可用时失败即拒绝（fail-closed）；通过负向测试证明绕过尝试确实被拒绝。任一不满足，就只是观测边界。同理，“只读接入”是需要证明的结论：没有“写路径不可达”的负向测试，准确的说法是“未观察到写操作”。接入能力可以分为外部边界强制、包装器中介（强制性取决于被接入方是否绕过）、仅观测、不支持四类，原书用 ANOLISA 说明同一产品的两项能力可能落在不同类别，“是否受控”只能按能力、路径、证据分别回答。

失败处理的最后一块：工作区快照只解决文件状态回退，数据库写入、消息发送、工单创建、远程重启不会随内部回滚撤销。长任务恢复需要三样配合：区分三种状态的操作记录、识别重复提交的幂等键、针对不可逆操作的显式补偿。已发出但结果未返回时，先查实际状态再决定重试或补偿。长期记忆里也可能保留已经失效的结论，恢复时要重新查询当前状态，而不是直接采信历史记忆。

先回答两个问题看自治上限；再判断一个边界能否称为“强制”。

能称为“强制边界”吗？（原书 30.6.2 节）

七个开放问题

原书 30.7–30.8 节

原书为每个尚无公认答案的问题都给了一个判断进展的标志，方便读者在之后一两年里自己校准。这种写法本身值得学：不预测结论，只说清看到什么信号就说明问题有了进展。之外还有一个更基础的问题：面向 AI 负载的基础机制重构能否成立（如 LithOS 重新设计 GPU 资源管理，Agent libOS 在运行时管理授权上限、预算与操作记录），原书判断这类重构更可能先在专用执行域（代码修改与测试、数据分析、工具执行这类依赖和权限范围明确的任务）里被验证。

全书的收尾回到起点：模型是认知核心，但可靠性不能寄托于模型本身。一项能力是否真正成立，原书给的判断依据始终是三个问题：它能否在被约束方不配合时仍然生效；它的效果能否用独立证据证明；它能否在版本演进中被持续维护。Agentic OS 会不会成为稳定的产品品类，取决于这三个问题在多少条路径上得到了肯定回答。

回扣开头的三个问题

先自己答，再点开
1. 在做和上线差多少？为何编码快 10 倍交付只快一点？

调研中已开发完成或开发中的合计 46%，部署到生产的只有 18%，持续迭代的不到 10%；卡点不在意愿和模型，而在持续演进 Agent 的工程能力（评估 55% 靠人工抽查、轨迹自动评估仅 6%）。交付周期由整条链路决定：20 天里编码只占 2 天，编码快 10 倍也只从 20 天降到 18.2 天，上限是 18 天；需求澄清、评审、测试这些由人衔接的节点决定吞吐上限。

2. 下沉的条件？三条“不是”？

必须满足复用性（多应用重复实现、差异不产生业务价值），且至少满足强制性（必须由被约束方之外执行）或可验证性（需要独立证据来源）之一。Agentic OS 不替代 Harness（任务语义不下沉）、不是又一个框架（约束应在被约束方不配合时仍成立）、不必然修改内核（目标是位于被约束方之外，而非层次更低）。

3. 自治上限由什么决定？强制与观测边界如何区分？

由可撤销范围与可证明范围决定，而不是模型能力：既不能撤销也不能证明的操作，不应交给自主执行。强制边界要同时满足：覆盖全部可用路径、判定组件不可用时 fail-closed、通过负向测试证明绕过被拒绝；任一不满足只能称观测边界。“只读接入”也需要“写路径不可达”的负向测试，否则只能说“未观察到写操作”。
