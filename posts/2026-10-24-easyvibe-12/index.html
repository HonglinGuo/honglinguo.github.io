Vibe 没有错，只是有适用范围

原教程 Spec Coding 第 1 节

Vibe Coding 的最大优点是快：你不必先知道正确答案，可以一边看结果一边找方向。半小时后就丢弃的界面草图、试探一个陌生框架能不能做到某个效果、一次性数据脚本、Hackathon 证明想法、调颜色间距文案，这些都适合直接 Vibe。原教程举的指令是“先做一个可点击的通知中心原型，用假数据，只验证列表、未读标记和筛选，暂时不接后端”。

原教程给了七个该转向 Spec 的信号，出现两三项就说明只靠聊天不够了：要改多个模块或很多文件；有权限、支付、隐私、数据安全要求；边界和失败情况很多；需要多人或多个 AI 会话接力；几周后还要维护；你开始频繁说“这个前面不是讲过了吗”；功能能跑，但没人知道是否完整实现。区别在于：只靠聊天时需求散落在多轮对话里、想到什么改什么、AI 凭感觉判断完成、换会话就丢上下文；用 Spec 时已确认的需求集中在仓库文档里、先确认变更影响再改、AI 逐条对照验收标准、新会话先读同一份规格。

原教程的结论是：从 Vibe 到 Spec 不是新方法淘汰旧方法，而是项目从探索阶段进入了交付阶段。

勾出你当前任务符合的信号，看看该用哪种方式。

Spec 是一份关于预期行为的共同约定

原教程 Spec Coding 第 2 节

原教程的定义：Spec 是一份关于预期行为的共同约定，至少要让人和 AI 都能回答三个问题：要做什么（用户最终能完成哪些事）、边界在哪里（哪些规则、异常、非目标不能忽略）、怎样证明完成（能观察或测试到哪些结果）。好的 Spec 不等于长文档，一个小功能一页就够，关键是具体、一致、可验证。“做一个好用的通知中心，界面现代、速度快、支持各种通知、注意安全”看起来写了不少，AI 仍然要猜什么叫好用、多快算快、谁能读通知。

原教程给了一个四层结构：产品目标（为什么做）、用户行为（用户能做什么）、规则与边界（什么情况下怎么处理）、验收证据（怎样证明做完）。技术方案很重要，但应该建立在行为已经明确的基础上。不要一开始只写“创建 NotificationService.ts”，因为文件存在并不能证明用户问题已经解决。

还要分清三个经常被混在一起的文档：spec.md 写期望的行为和验收标准（“用户可以将单条通知标记为已读”）；plan.md 写技术方案（“通过 PATCH /notifications/:id 更新状态”）；tasks.md 写可以按顺序完成的工作（“先实现读取列表，再实现单条已读”）。技术栈变了 plan 可能要重写，但只要用户仍然需要“标记已读”，spec 里的行为就不该变。

先看一段需求从愿望清单变成可观察行为；再把句子分到三份文档里。

通知中心：从愿望清单到可观察行为（原教程 2.1 节）

把一句模糊需求变成规格：四步

原教程 Spec Coding 第 3–4、6.7 节

第一步：先让 AI 提问，不要马上写代码。让它找出会影响产品范围、数据结构和验收方式的问题，每次最多问 4 个并给推荐。通知中心这一轮确认了来源（订单、安全、活动三类站内通知）、渠道（不做手机推送）、偏好（活动可关，订单和安全不可关）、保留周期（列表 30 天，数据 90 天），这些拖到写完代码才确认，数据模型和接口都要返工。第二步：写清做什么和不做什么。“不做什么”不是消极信息，它在保护第一版，防止 AI 看到“通知中心”四个字就顺手搭一整套消息平台。

第三步：把形容词改成验收标准。“实时”“安全”“友好”都无法直接验证，要追问“发生什么操作后，用户应该看到什么”。“未读数实时变化”被定义为：标记单条已读后，列表状态和顶部未读数在同一次操作完成后更新，不要求跨设备同步。第四步：补上失败情况和数据边界，至少检查四类：空状态（一条都没有显示什么）、失败状态（异常时能否重试、不清空已有列表）、权限边界（能不能读改别人的数据）、重复操作（已读的再标记一次会怎样）。不确定的内容放进“未解决问题”，不要伪装成结论。

原教程还推荐了两种写验收标准的句式。EARS：WHEN 发生事件 THE SYSTEM SHALL 产生结果，减少需求句子的歧义。Given / When / Then：给定初始状态、当发生操作、那么应看到什么，几乎可以直接转成测试。其他可迁移的方法还有 ADR（保存技术选择的原因）、纵向切片（每张任务交付一小段完整价值）、验证关卡（不许只凭任务勾选宣布完成）。

判断下面这些句子能不能直接当验收标准。

## 1. 背景与目标

- 希望带来的结果：
- 目标用户：
## 2. 第一版范围
- 用户可以……
- 系统在……时应该……
## 3. 第一版不做
- 暂不支持……
## 4. 业务规则
- 当……时……；只有……可以……
## 5. 边界与异常
- 空状态：
- 失败状态：
- 权限边界：
- 重复操作：
## 6. 验收标准
1. 给定……，当……，那么……
## 7. 已确认的技术约束
- 必须兼容 / 不允许引入 / 性能隐私安全要求：
## 8. 未解决问题
- [ ] 仍需要确认……

易混辨析：EARS vs Given / When / Then

EARS 是写需求句子的格式，强调触发条件和系统义务：“WHEN 用户点击全部已读，THE SYSTEM SHALL 只更新当前账号的未读通知”，Kiro 的 requirements.md 就用它。Given / When / Then 是写具体场景的格式，带着具体数据：“Given 有 3 条未读，When 标记 1 条，Then 顶部显示 2”，更接近一条测试用例。前者定义规则，后者举例验证规则，常常搭配使用。

五段式工作流，和需求变化时的顺序

原教程 Spec Coding 第 5、7–8 节

有了文档不等于进入了 Spec Coding，真正的变化是后续规划、实现、验收都要引用它。原教程建议的仓库结构是：CLAUDE.md 或 AGENTS.md 放整个项目长期遵守的规则（怎么跑测试、哪些目录不能改、金额怎么存）；specs/功能名/ 下放 spec.md、plan.md、tasks.md；具体功能的需求不要全堆进项目总规则。

GitHub Spec Kit 把流程概括为 Specify → Plan → Tasks → Implement，原教程再加一步独立的 Verify。每一步你要检查的东西不同：Specify 看范围、规则、非目标对不对；Plan 看方案是否符合现有项目约束；Tasks 看每项能否独立完成和验证；Implement 看是否只做当前任务、是否持续测试；Verify 看有没有漏项、回归或未经确认的假设。最后一步有个要点：不要根据任务勾选状态判断完成，要重新读 spec 逐条核对，并给出每条要求对应的代码或测试证据。

需求一定会变。原教程的例子：上线后用户提出“安全提醒即使读过也不能被普通用户删除”。正确顺序是先在 spec 里加规则和验收标准，再看 plan 和 tasks 是否要新增任务，然后改代码和测试，最后对照完整 spec 验证旧行为没被破坏。只在聊天里说一句“顺手加上”，下次会话就不知道这条规则为什么存在。同时 Spec 也不是写完就冻结，过时的 Spec 会给 AI 错误上下文，比没有文档更危险。原教程列的常见误区：把 Spec 写成文件清单、让 AI 独自决定权限隐私付费这类关键问题、追求一次写出完美长文档。

逐步走一遍五段式工作流；下面的提示词可以按顺序直接用。

我要实现【功能名称】。先不要写代码。
请先阅读当前仓库和已有项目规则，然后通过提问帮我明确：
1. 第一版范围和非目标；
2. 关键业务规则；
3. 空状态、失败状态和权限边界；
4. 可以验证的验收标准。
每次最多问 4 个真正会影响实现的问题，并说明你的推荐。
根据我们已经确认的讨论，生成 specs/<feature>/spec.md。文档必须包含：背景与目标、第一版范围、非目标、业务规则、边界与异常、验收标准、技术约束和未解决问题。不要把尚未确认的假设写成结论，也不要开始实现。
（确认后）阅读 spec.md 和现有代码。先生成 plan.md，说明数据、接口、受影响模块、风险和验证方式；再生成 tasks.md，把工作拆成有顺序、可独立验证的小任务。现在不要修改实现代码。
按照 tasks.md 的依赖顺序逐项实现。每次只处理一项：先补充能证明当前行为缺失的测试，再实现，运行相关检查，最后更新任务状态并说明对应的验收标准。如果发现 Spec 有矛盾或缺少关键决定，先停下来指出，不要自行扩展范围。
（全部完成后）不要根据任务勾选状态判断完成。请重新阅读 spec.md，逐条核对范围、业务规则和验收标准；同时运行测试、类型检查和构建。列出每条要求对应的代码或测试证据，发现遗漏就修复并重新验证。

主流 Spec 工具怎么选

原教程 Spec Coding 第 6 节（截至 2026 年 8 月的调研）

原教程核对了六个项目的官方文档。它们都在讲“先明确意图再写代码”，但解决的问题不同。GitHub Spec Kit：Specify → Plan → Tasks → Implement，每步生成 Markdown 工件，还有 clarify、analyze、checklist 查模糊点和跨文档矛盾，适合新项目和正式团队流程；需求特别大时先写一份浅层路线图，再让每个子功能各走一轮（Spec of Specs）。OpenSpec：Explore → Propose → Apply → Archive，以“一次变更”为单位维护增量规格，完成后归档并合并回稳定规格，流程轻，适合已有代码库持续迭代。Kiro Specs：Requirements → Design → Tasks，在 IDE 里直接审阅三份文件，需求用 EARS 格式。

Matt Pocock Skills：grill-with-docs → to-spec → to-tickets → implement → code-review，把对话、GitHub / Linear 任务和提交连成一条线，适合让 Agent 跨多个会话持续工作；它的官方说明也提醒，讨论清楚且一个上下文窗口就能完成的工作，直接 implement 即可，不必为形式生成 Spec。Superpowers 不是另一种 Spec 格式，而是用强制技能守住实现质量（见本篇最后一节）。BMAD Method 用产品经理、架构师、开发、测试等角色化技能产出产品简报、PRD、架构、Story，适合从零规划多模块大型产品，给小功能用就太重。

原教程还提醒要事先决定 Spec 的生命周期：Spec-first（开发前用，交付后可丢，Matt Pocock 的快照模式）、Spec-anchored（交付后继续维护作为长期锚点，OpenSpec 的归档接近这种）、Spec-as-source（人主要改 Spec，再重新生成实现）。最后一条警告：不要把几套框架一起装进同一个项目，三个工具各自维护 spec 和完成状态只会制造冲突；选一个做主流程，再借用 EARS、ADR、TDD 这些方法。

回答两个问题，看原教程推荐哪种组合。

Skills：给 AI 的操作手册

原教程 Claude Code Skills 完全指南

没有 Skills 时，每次都要重新解释代码风格、提交信息怎么写；团队经验无法沉淀；不同人用出来的结果不一样。Skills 把专业知识、工作流程和最佳实践打包成可复用的“技能包”：一个目录，里面必须有 SKILL.md，可选 scripts、templates、references、examples。SKILL.md 分两部分：开头的 YAML 元数据（name 只能用小写字母数字连字符，会变成 /name 命令；description 描述什么时候用，越具体越容易被自动匹配），后面是 Markdown 写的使用场景、执行步骤、注意事项。放在 ~/.claude/skills/ 是个人全局技能，放在项目的 .claude/skills/ 是团队共享技能，可以用 Git 管理。

和直接发提示词相比：提示词是临时的、每次重复说、存在对话里占 token、难以共享和版本控制；Skills 写一次反复用、按需加载、团队共享。原教程在“深入阅读”里讲了它的机制：Skills 不是可执行代码，而是在需要时注入上下文的指令。关键是三层渐进式加载：启动时只加载每个技能的 name 和 description（原教程估算每个几十 token）；被触发时才加载完整的 SKILL.md；脚本、模板、参考文档按需从文件系统读取，不占上下文。路由也没有硬编码，所有技能的描述交给模型自己判断该用哪个，所以 description 写得好不好，直接决定会不会被触发。

原教程推荐先装 find-skills（帮你找技能），再试几个现成的；自己写技能可以直接让 Claude 按需求生成，或用官方的 skill-creator。它给的实例有代码审查、Git 自动提交、测试生成、文档生成四个。

# 代码审查
## 使用场景
提交前、合并 PR 前。
## 执行步骤
1. 运行 git diff 查看改动
2. 按清单检查：安全（注入、XSS、密钥）、性能（N+1）、错误处理、命名与规范

## 注意事项
- 只审查改动部分，不重写无关代码

MCP：给 AI 接上工具

原教程 Claude Code MCP 完全指南；Skills 指南 · Skills vs MCP

没有 MCP 的 Claude Code 能读写本地文件、改代码、跑命令，但看不了你的 GitHub Issues、连不了云数据库、调不了外部 API。MCP（Model Context Protocol）是让它连接外部工具和服务的协议，接上之后可以查和建 Issue、PR，查 SQLite / PostgreSQL，访问 Notion、Slack，做浏览器自动化。原教程演示了直接用自然语言让 Claude Code 帮你添加、查看、诊断 MCP 服务器。

配置分两级：用户级（全局，所有项目可用）和项目级（只对当前项目，可以提交到 Git 让团队共享，原教程推荐优先用项目级）。传输方式三种：STDIO（本地进程，用 npx 启动一个服务器）、HTTP（远程服务，带 Authorization 头）、SSE（服务器推送）。四条最佳实践：项目级配置优先；敏感信息环境变量化，配置里只写 $GITHUB_TOKEN 而不是真实 token；版本锁定，npx -y 默认拉最新版，可能突然不兼容或下架，在包名后加 @版本号；在 .claude/README.md 里文档化每个服务器的用途和所需配置。

读后核对一处路径：原教程写的项目级配置文件是 .claude/mcp.json；按当前 Claude Code 官方文档，项目级 MCP 配置放在项目根目录的 .mcp.json（可以用 claude mcp add --scope project 生成）。工具更新很快，路径和命令以官方文档为准。

这些需求，该用 Skill、MCP 还是两者配合？

易混辨析：Skills vs MCP

原教程的比喻：把 Claude 比作一个工作人员，MCP 是给他配的工具（扳手、电脑、访问权限），解决“能用什么”；Skills 是给他的操作手册（怎么做代码审查、怎么提交），解决“怎么做”。Skills 是 Markdown 文件，MCP 是一个运行着的服务器加 JSON 配置。两者互补：代码审查时，Skill 定义审查步骤、清单和输出格式，GitHub MCP 提供读取 PR 和 diff 的能力。

Superpowers：用技能强制工程纪律

原教程 Claude Code Superpowers 工程级开发

Superpowers 是 Jesse Vincent（obra）开发的开源技能框架，要解决的是：怎样让 AI 写出工程级而不是玩具级的代码。原教程的比喻：普通编码助手像聪明的实习生，能写出能跑的代码，但可能没测试、没文档；Superpowers 给他配了一位资深导师，强制走完整流程。它列出的问题正是 Vibe Coding 的老毛病：没规划直接写、先写代码再补测试甚至不写、需求模糊就动手、质量看“心情”。

标准流程是：brainstorming（苏格拉底式提问澄清需求）→ 设计文档（分块展示、等你确认）→ writing-plans（拆成 2–5 分钟的小任务）→ 子代理开发（每个任务一个独立子代理，两阶段审查：是否符合规格 + 代码质量）→ test-driven-development（强制 RED-GREEN-REFACTOR：先看到测试失败，再写最小实现，再重构）→ 代码审查 → verification-before-completion（宣布完成前运行真实检查，不接受“应该已经好了”）。技能有三种触发方式：关键词（说“TDD”“先写测试”）、场景（需求模糊时自动提问，出 bug 时启动 systematic-debugging）、手动调用。

原教程强调它的价值是强化纪律，不是无中生有：不提 TDD 时，模型写不写测试看训练习惯；提了 TDD，就被强制走红绿重构。快速原型和一次性脚本不必强求，生产级、多人协作、长期维护的项目才值得。它和 Spec 工具的关系是：Spec 负责“要做什么”，Superpowers 负责“怎样可靠地实现并证明”。

逐步走一遍 Superpowers 的标准流程。

回扣开头的三个问题

先自己答，再点开
1. 何时转向 Spec？Spec 要回答哪三个问题？

出现两三项以下信号时：改多个模块、涉及权限支付隐私安全、边界和失败情况多、需要多人或多会话接力、几周后还要维护、频繁说“前面讲过了”、能跑但没人知道是否完整。本质是项目从探索进入交付。Spec 要回答：要做什么（用户能完成哪些事）、边界在哪里（规则、异常、非目标）、怎样证明完成（可观察可测试的结果）。

2. spec / plan / tasks 的区别？为什么需求变化先改 Spec？

spec.md 写期望行为和验收标准，plan.md 写技术方案，tasks.md 写有顺序可独立验证的工作；技术栈变了 plan 可能重写，但行为不变 spec 就不变。需求变化先改 spec，再看 plan 和 tasks，然后改代码，最后对照完整 spec 验证旧行为没被破坏；否则新规则只存在于某次聊天里，下次会话无从得知，而过时的 Spec 会给 AI 错误上下文。

3. Skills 与 MCP 各提供什么？为什么装很多 Skills 也不撑爆上下文？

Skills 是操作手册，告诉 AI 怎么做（流程、清单、格式），是 Markdown 文件；MCP 是工具接口，给 AI 能用的外部能力（GitHub、数据库、浏览器），是运行的服务器加配置。Skills 采用三层渐进式加载：启动时只加载每个技能的 name 和 description，被触发时才加载完整 SKILL.md，脚本和参考资料按需从文件读取，所以一百个技能启动时只占几千 token。
