会话结束以后，它还记得你吗

上一篇管的是一次任务之内的上下文；这一篇管跨会话的东西。对单个用户叫用户记忆，让 Agent 成为“懂你的助手”；对所有用户共享的叫知识库，让 Agent 成为“领域专家”。两者共用检索和压缩技术，也共享同样的麻烦：信息冲突、知识过期、检索不准。

本系列是开源书《深入理解 AI Agent：设计原理与工程实践》（李博杰 著，Apache-2.0 协议）的学习笔记。不逐段复述原书，而是用自己的话把关键概念讲一遍，配上能动手点的小实验；原书的实验代码和思考题推荐对照阅读。

记什么，以及怎样算记得好

原书 3.1 节

用户记忆不是把每句对话都存下来。对话结束后，框架会再调用一次 LLM，从对话里提取对未来有用的事实。原书给了三条规则：选择性（丢掉“搜索返回了 3 个选项”这类短期细节）、抽象化（把这次选了靠窗座位归纳成长期偏好）、结构化（用可检索的字段保存）。这和第 2 篇的上下文学习不同：上下文学习只在当前窗口生效，记忆则跨会话持久存在。

怎样算“记得好”？原书在 LoCoMo 等公开基准之上设计了一个更贴合 Agent 的三层评估框架。第一层基础回忆：用户说过会员号，需要时能准确给出。第二层多会话检索：用户有两辆车，说“帮我的车预约保养”时，要找出两辆车的信息并主动问是哪一辆，而不是随便猜。第三层主动服务：订国际航班时，主动想起几个月前存过的护照快过期了。

先替 Agent 做一次记忆提取：下面这段订机票对话里，哪些值得长期记住？

    这属于第几层能力

    放哪里、怎么存、存什么

    原书 3.1 节

    原书把记忆设计拆成三个互相正交的维度。放哪里：轨迹（单次会话的原始记录，只增不改，是流水账）和用户长期记忆（跨会话提炼出的稳定信息，会被反复改写合并，是档案），有的系统还有业务状态（“等待付款”这类任务阶段）。存什么：借用认知科学的分类，情景记忆是具体事件（“订了下周五的 ANA 航班”），语义记忆是抽象出的稳定特征（“用户吃素”），程序记忆是行为流程（“先搜直飞、确认座位、用常旅客号、订餐”）。

    怎么存有四种渐进的格式。Simple Notes 每条一个最小事实，最省但会把“在 TechCorp 当高级工程师负责推荐系统”拆成互不相关的三条；Enhanced Notes 存完整段落，语义完整但冗余难更新；JSON Cards 用“类别.子类别.键”三层结构，可局部更新但强制单一分类；Advanced JSON Cards 再加上来源背景（backstory）、主体（person）、关系（relationship）和时间戳，专门解决消歧：“张医生”是用户自己的牙医，还是父亲的心脏科医生？

    原书的选择建议是混合：关键且少量的数据用 Advanced JSON Cards，大量且非关键的对话事实用 Simple Notes。更进一步的 User as Code 把用户状态写成带类型的对象、把规则写成函数，聚合、冲突检测、约束检查交给确定性代码，而不是让 LLM 心算。

    切换四种格式看同一份信息长什么样；再在右边改日期，看“代码化记忆”如何自动报警。

    情景、语义还是程序记忆

    冲突在写入时解决，还是读取时解决

    原书 3.1 节 · 记忆框架案例

    用户先说“我住在北京”，后来说“我搬到上海了”。记忆系统该怎么办？Mem0 的演进给了两种答案。2025 年论文和 v2 在写入时消歧：抽取候选事实后，向量检索找出相近的旧记忆，再让 LLM 在 ADD、UPDATE、DELETE、NOOP 中选一个，把“住北京”更新成“住上海”。好处是记忆库始终简洁一致；风险是一次错误的更新或删除会不可逆地丢掉历史，而且每条候选事实都要多一次检索和 LLM 判断。

    2026 年的 v3 改成仅追加写入、检索时推理：只做 ADD，两条带时间的事实并存；查询时融合语义相似度、BM25 关键词、实体匹配，再按时间排序找出当前事实。Mem0 报告 LoCoMo 从 71.4 提到 92.5，LongMemEval 从 67.8 提到 94.4。另一个框架 Memobase 则聚焦用户画像（开发者配置的主题槽位）加事件时间线，用缓冲批处理摊薄 LLM 成本。

    逐条喂给两种系统几句话，其中一句容易被误读，看它们的记忆库分别变成什么样。

        检索：语义、关键词，和把两者合起来

        原书 3.2 节

        知识库的核心技术是 RAG：检索相关片段，注入上下文，让 LLM 基于它们生成答案。文档先要分块，常见起点是每块 256–1024 token、相邻重叠 10%–20%；块太小语义不完整（“该公司收入增长 3%”，哪家？），块太大主题混杂、向量被稀释。生产中最常用的是按标题、段落、句子递归切分。

        检索有两条路线。稠密嵌入把文本变成向量，语义相近的向量方向相近，用余弦相似度比较；它懂同义词，但可能漏掉精确关键词（搜“HTTP-403”返回泛泛的“服务器错误”）。稀疏检索以 BM25 为代表，靠关键词匹配：词越稀有权重越高，词频有饱和、文档长度要归一化；它精确，但读不懂同义词（搜“kitty”找不到只写“cat”的文档）。

        混合检索两路都跑。两路得分尺度不同，常用倒数排名融合（RRF）只看排名合并：得分 = Σ 1/(k + 排名)，k 常取 60。之后再用跨编码器做重排序：把查询和候选拼在一起让模型逐词比对，像面试官和候选人深谈，比检索阶段“各自编码再比向量”的双编码器（像猎头看简历）准得多。验收指标看 recall@k（该找的找到没）、MRR（找到得够不够靠前）、nDCG（整个列表的质量）。

        原始案例直接入库，远远不够

        原书 3.3 节

        原书用两个案例说明扁平知识库的硬伤。黑猫白猫：100 个案例文档，90 黑 10 白，问比例时 top-k 只能取回 20 条，模型基于不完整的样本下结论。Xfinity 优惠资格：几百条客服工单，退伍军人 John 通过、医生 Sarah 拿到折扣、教师 Mike 不符合，但没有任何一条写着资格范围本身。护士来问能不能享受时，有三重障碍：最近邻偏置（“护士”离“医生”最近，Sarah 那条排第一）、边界语义缺失（“仅限……其他一律不适用”不存在于任何单条工单，调大 k 也没用）、完整性信号缺失（模型不知道自己有没有看全）。

        结论是要在索引阶段投入计算：把 100 个案例压成统计摘要，把散落的个案提炼成带边界的规则卡。RAPTOR 自下而上聚类、递归摘要成一棵树，适合“从概念逐步钻进细节”；GraphRAG 抽取实体和关系建图，适合多跳问题（“我的医生所在医院的地址”）和实体消歧，但把自然语言变三元组会丢掉条件和时间逻辑。字节开源的 OpenViking 走文件系统范式：每个目录自动生成约 100 token 的 L0 摘要和约 2000 token 的 L1 概览，L2 全文按需加载，前提是文件之间像 Wikipedia 一样互相链接。

          该用哪种组织方式

          把知识库当代码库：每次修改都是一个 PR

          原书 3.3 节 · 知识应该如何更新

          上线运行的记忆和知识库会持续收到新信息。只更新不整理会越来越乱，只定期重写又不及时，所以要两条路径并行：事件触发的增量更新和周期触发的全量整理。

          原书的工程答案是把知识库当代码库，把每次变更当成一个 PR，套用第 1 篇的提议者—审核者模式：Proposer Agent 先检索相关旧知识，提交尽量小而完整的 diff；Reviewer Agent 拿着变更前的知识、diff 和原始证据独立核对，不通过就给出指向具体证据和行号的意见；迭代到批准为止，超出预算转人工，不能默认放行；合入后跑 CI，再从这个版本重建索引。两者都应是能自己搜索、比对、跑检查的 Agent，而不是两次固定的 API 调用，最好用能力相近、来自不同家族的模型互审。

          全量整理做三件事：去重去旧合并、回到原始数据核查（不能只在摘要之间互相改写）、冲突解决与场景限定（两种说法可能在不同时间、对象、地域下都成立，那就把适用条件写清，而不是删掉一条）。共享知识库还要按调用者权限过滤检索、做租户隔离，给内容加生效/失效时间。

          跟着一次知识更新 PR 走一遍。

          一次知识更新

          示意流程，沿用上一节的 Xfinity 例子。

          三层要分开：

          • 原始证据层：对话、轨迹、原始文档，只增不改。
          • 知识层：提炼后的 Markdown 或代码，进 Git，可修订、可回滚。
          • 服务层：从某个已合入版本生成的检索索引，是可重建的派生物。

          每条线上知识都应能回答：从哪条证据来、谁在什么时候批准的。

          让 Agent 自己决定查什么

          原书 3.3 节 · 智能体化 RAG 与上下文感知检索

          传统 RAG 是单向管道：查询直接检索，结果直接注入，模型直接回答。原书比喻为“图书馆里只能搜一次就得立刻写报告”。智能体化 RAG 把检索变成一个工具，Agent 用 ReAct 循环决定查什么、查完够不够、要不要换个关键词再查。简单问题（“正当防卫怎么规定”）两者差不多，传统 RAG 还更快；复杂问题（“醉酒过失致人重伤且有盗窃前科如何量刑”）差距就很明显。

          另一个瓶颈在分块本身：块被切出来后丢了上下文，“该公司第二季度收入增长 3%”不知道指谁。Anthropic 的上下文感知检索在索引前让 LLM 给每块生成一句前缀，如“本段节选自 ACME 公司 2025 年 Q2 财报的关键业绩指标章节”，再连同原文一起索引，同时增强稀疏和稠密两路。据 Anthropic 数据，结合 BM25 检索失败率降 49%，再加重排序降 67%，借助提示缓存每百万文档 token 约 1 美元。注意它和第 2 篇的“上下文感知压缩”不同：一个在索引期做加法，一个在运行期做减法。

          两条线最后汇合成双层记忆架构：Advanced JSON Cards 存少量关键事实常驻上下文，提供全局概览；上下文感知检索按需取回原始对话细节。主动服务之所以最难，是因为它同时需要概览和细节。检索内容也是间接提示注入的载体，要做来源标记，且不能仅凭检索内容就触发转账、删除这类操作。

          走一遍原书的量刑问题，再看一个分块加了前缀前后的差别。

          给分块补上下文

          多模态记忆还在前沿。原书列了三种思路：存原图加文字描述再按描述检索；把人脸或声纹的嵌入存进上下文的一块区域，每个只占约 1 个 token；把嵌入写进 Engram 类模型的哈希槽位（User as Engram），扩展性更强但要模型本身支持。
