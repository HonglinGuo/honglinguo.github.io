接工具、找同伴、进网络

前九篇的智能体都是“单机版”：每个外部服务都要手写一个 Tool 类，能力被预先定死，几个智能体要协作只能手工编排。第十章引入三个协议来打破这三堵墙：MCP 让智能体用统一的方式接入工具和资源，A2A 让智能体之间点对点地派任务、交结果，ANP 让智能体在一个大网络里被注册、发现和路由。原书提醒，协议都还处在早期，这一章以会用为主，不必自己造轮子；但每个协议解决什么问题、核心对象是什么，值得记清楚。

本系列是开源教程《Hello-Agents：从零开始构建智能体》（Datawhale 社区编写的开源教程，CC BY-NC-SA 4.0 协议；本笔记依据 2026 年 10 月 14 日的仓库版本）的学习笔记。原书十六章，按“概念 → 手写范式 → 平台与框架 → 自研框架 → 记忆、上下文、协议、训练、评估 → 综合案例”展开，代码量很大。这里重排成十三篇，用自己的话重讲：代码只保留能看清机制的骨架，做成可以逐行走读、可以填空回忆的互动；每篇末尾配原书面试题清单里的相关题目做口述演练。每节标出对应的原书章节，演示数值标“示意”。笔记同样按 CC BY-NC-SA 4.0 共享。

为什么需要通信协议

原书 10.1 节，表 10.1

第七篇的 ReActAgent 加上计算器和搜索就能干活，但有三个根本限制：工具集成困境（每个外部服务都要手写 Tool 类，不同开发者写的工具互不兼容，HTTP、错误处理、认证代码到处重复）、能力扩展瓶颈（能力限定在预先写好的工具里，无法在运行时发现新服务）、协作缺失（研究员、撰写员、编辑协作只能手工编排）。协议的价值就像 TCP/IP：给出一套标准接口，任何遵循它的服务都能被统一访问，带来标准化、互操作、动态发现、可扩展。

原书用三句话区分三个协议：MCP（Anthropic 提出）解决“如何访问工具”，设计哲学是上下文共享，不只是远程调用，还能提供结构、依赖、历史等上下文；A2A（Google 提出）解决“如何与其他智能体对话”，设计哲学是对等通信，每个智能体既是服务提供者也是消费者；ANP（开源社区维护的概念性框架，生态尚不成熟）解决“如何在大规模网络中发现和连接智能体”，设计哲学是去中心化服务发现。HelloAgents 分三层实现：协议实现层（MCP 基于 FastMCP，A2A 基于官方 a2a-sdk，ANP 是自研的概念模拟）、工具封装层（MCPTool、A2ATool、ANPTool 都是 Tool）、智能体集成层，于是协议对智能体来说仍然只是工具。

MCP智能体 ↔ 工具

Host、Client、Server 三层；Tools、Resources、Prompts 三种能力；JSON-RPC 消息，可走 stdio 或 HTTP。怎么访问工具？

A2A智能体 ↔ 智能体

点对点网状拓扑；核心对象是 Task 和 Artifact；任务有标准生命周期，可以协商。怎么和别的智能体协作？

ANP智能体 ↔ 网络

服务注册、发现、路由；按能力、负载、价格挑选服务。在一大群智能体里怎么找到合适的？

MCP：智能体的 USB-C

原书 10.2.1 节，表 10.2、10.3

原书的比喻是 USB-C：不管用 Claude、GPT 还是别的模型，只要支持 MCP，就能接入同一批工具和资源，不用为每个服务、每家模型的 function call 格式各写一套适配。

架构三层，以在 Claude Desktop 里问“我桌面上有哪些文档”为例：Host（宿主，Claude Desktop）负责用户界面和与模型的对话流程；模型决定需要文件信息时，Host 里内置的 Client 负责连接合适的 Server、收发请求；文件系统 Server 执行真正的扫描并返回列表。关注点分离：开发者只需写 Server。Server 提供三种能力：Tools 是主动的（执行操作，如读写文件、搜索代码）、Resources 是被动的（提供数据，如文件内容、数据库记录，用 URI 标识）、Prompts 是指导性的（预定义的提示模板，如代码审查模板）。

模型怎么决定用哪个工具？五步：Client 连上 Server 后先 list_tools() 拿到名称、说明和参数 schema（工具发现）→ 转成模型能理解的格式放进提示（上下文构建）→ 模型判断要不要调、调哪个（模型推理）→ Client 经 Server 执行（工具执行）→ 结果交回模型生成回答（结果整合）。所以工具描述写得好不好仍然是关键。

MCP 和 Function Calling 不是竞争关系。原书的类比：Function Calling 是你学会了“怎么打电话”（模型知道何时调用、怎么生成参数），MCP 是全球统一的“电话通信标准”（工具怎样被描述、发现和连接）。

下面这些服务器能力，属于 Tools、Resources 还是 Prompts？

易混辨析：MCP vs Function Calling vs 第七篇的 ToolRegistry

Function Calling 是模型能力：看懂工具 schema，输出结构化调用。ToolRegistry 是 HelloAgents 进程内的工具管理：工具代码和智能体在同一个程序里。MCP 是跨进程、跨语言的连接标准：工具住在独立的 Server 里（可能是别人用 Node 写的），任何支持 MCP 的 Host 都能发现和调用它。三者叠在一起用：MCPTool 从 Server 拉来工具清单，注册进 ToolRegistry，再通过 Function Calling 或文本协议交给模型选。

一次 MCP 交互长什么样

原书 10.2.2 节、习题 2

原书习题 2 点出了 MCP 的底层：消息格式是 JSON-RPC 2.0，本地默认通过 stdio（标准输入输出）和 Server 子进程通信。HelloAgents 的 MCPClient 提供异步 API：async with client: 建立并保证关闭连接，await client.list_tools() 发现工具，await client.call_tool("read_file", {"path": "my_README.md"}) 调用，另有 list_resources、read_resource、list_prompts、get_prompt。

传输方式与接入智能体

原书 10.2.3–10.2.5 节，表 10.4

MCP 与传输层无关，同一套消息可以跑在不同通道上。HelloAgents 的 MCPClient 支持五种：Memory（进程内，MCPTool() 不带参数就用内置演示服务器，适合单元测试和快速原型）；Stdio（启动本地子进程，server_command=["python", "my_server.py"] 或 ["npx", "-y", "@modelcontextprotocol/server-filesystem", "."]，适合本地开发调试）；HTTP（连远程服务，适合生产和微服务）；SSE（Server-Sent Events，服务器推送，适合实时流式和长连接）；StreamableHTTP（需要双向流式的 HTTP 场景）。MCPTool 主要封装前两种，远程传输建议直接用底层 MCPClient。

接入智能体时，MCPTool 有一个自动展开特性：把它加给 Agent，它会把 Server 提供的每个工具展开成独立工具，智能体像调普通工具一样调用它们。社区已有大量现成 Server（文件系统、GitHub、数据库、地图等），原书建议优先选大公司背书、持续维护的。

每个场景该用哪种传输？

A2A：智能体之间派任务、交工件

原书 10.3 节，表 10.7，图 10.7–10.8

多个智能体协作，最直观的是一个中央协调器（星型拓扑），但它有三个毛病：单点故障、性能瓶颈（所有通信都过中心）、扩展困难（加减智能体要改中心逻辑）。A2A 采用点对点的网状拓扑，智能体之间直接通信。它与 MCP 最大的区别在于两个核心抽象：Task（一个被委托的工作单元，有状态）和 Artifact（任务产出的工件）。任务有标准生命周期：创建、协商、代理、执行中，最终完成或失败；一次请求要经过代理发现、身份验证、发送消息、流式消息四步。

HelloAgents 里，A2AServer(name, description) 把一个智能体发布成服务，用 @server.skill("research") 装饰器声明技能；A2AClient(url).execute_skill("research", "...") 调用；A2ATool 把远程智能体包装成工具交给协调者 Agent。原书的例子有研究员 + 撰写员的流水线、接待员把问题分给技术专家或销售顾问的客服系统，以及两个 Agent 关于截止期限的协商：提案的 deadline 少于 7 天就拒绝并给出反提案。

走一遍任务的生命周期，切换“协商”和“失败”两条分支。

读代码时注意：别对远端消息用 eval

原书 A2A 示例里，撰写员用 eval(content) 把研究员发来的字符串还原成字典，协商示例也用 eval(proposal_str) 解析提案。在单机演示里无害，但 A2A 的意义恰恰是接收别的智能体、甚至别的组织发来的消息，对它们 eval 等于允许远端执行任意代码。实际使用应传 JSON 并用 json.loads 加 schema 校验。这是我的读码观察；原书习题 5 也在追问协议的安全问题。

ANP：在一大群智能体里找到合适的

原书 10.4 节，表 10.8

网络里有成百上千个能力各异的智能体时，会遇到三个问题：服务发现（新任务来了，谁能处理？）、智能路由（好几个都能处理，按负载、成本选哪个？）、动态扩展（新加入的智能体怎么被别人发现？）。ANP 就是为此准备的一套机制。HelloAgents 的实现是概念模拟：register_service 登记服务（id、名称、类型、能力列表、端点、元数据如负载和价格）；discover_service(discovery, service_type="nlp") 按类型或能力查询；挑选策略由调用方决定，原书示例是 min(..., key=负载)；ANPNetwork 再把服务作为节点连成网络、统计拓扑。原书习题 4 还追问了星型、网状、分层拓扑怎么选，以及关键节点故障时的容错。

自建并发布 MCP 服务器

原书 10.5 节

为什么要自己写 Server？四个动机：封装业务逻辑（把企业内部流程做成标准工具）、访问私有数据（给不能暴露到公网的数据库、API 建一个可控代理）、性能专项优化、功能定制（专有算法、特定硬件）。原书的教学例子是一个天气服务器：用 HelloAgents 的 MCPServer(name="weather-server", ...) 创建，内部调 wttr.in（中文城市名映射成英文），对外提供 get_weather、list_supported_cities、get_server_info 三个工具，返回 JSON 字符串；再用 MCPClient 以 stdio 方式启动它做测试，最后挂给 Agent 使用。

发布到 Smithery（原书称它是 MCP 服务器的发布平台，类似 PyPI、npm）：项目需要 README、LICENSE、Dockerfile（推荐）、pyproject.toml（必需）、requirements.txt、smithery.yaml（必需，写名称、描述、版本、运行方式 runtime: container、构建与启动命令、工具清单）和 server.py。

发布前的检查单：拿掉一项看会出什么问题。

怎么选，怎么组合

原书 10.1.2 节（4），习题 1

原书的选择口诀：要访问外部服务（文件、数据库、API）用 MCP；要多个智能体相互协作用 A2A；要构建大规模智能体生态考虑 ANP。三者不是互斥的：一个智能客服系统里，每个智能体用 MCP 访问订单库和知识库，接待员通过 A2A 把复杂问题委托给技术专家或销售顾问，大规模部署时用 ANP 式的注册发现把请求路由到负载最低的实例。

面试演练

题目取自原书 Extra01 与第 10 章习题

了解 A2A 吗？它和普通 Agent 框架的区别在哪？挑一个最关键的不同点说明。Extra01 · Agent 第 11 题

  • 定位不同：AutoGen、CAMEL 等框架是“怎么在一个程序里编排多个智能体”；A2A 是“不同程序、不同厂商、不同框架的智能体之间怎么通信”的开放协议。
  • 最关键的不同：跨边界互操作。A2A 智能体通过网络端点暴露技能，有标准的发现、认证、消息与流式接口，以及带生命周期的 Task 和 Artifact；框架内的智能体通常共享进程和内存，换个框架就无法对话。
  • 关系：互补而非替代，可以用 AutoGen 写一个智能体，再通过 A2A 把它发布给外部调用（原书习题 3 的思路）。

MCP 用 JSON-RPC 2.0 + stdio 通信，有什么优势和局限？怎么支持远程服务器？原书第 10 章习题 2

  • 优势：JSON-RPC 简单、语言无关、请求响应带 id 易于匹配；stdio 无需网络端口，进程隔离，本地部署零配置，Host 能管理 Server 的生命周期。
  • 局限：只能本机；一个 Host 一个子进程，难以共享和扩容；没有内建的认证与多租户。
  • 远程：同样的消息换成 HTTP / SSE / StreamableHTTP 传输，补上认证（令牌、OAuth）、TLS、限流和会话管理；HelloAgents 中用 MCPClient(url, transport_type=...) 连接。

MCP 服务器提供了删除文件、执行命令这类危险工具，怎么做权限控制？原书第 10 章习题 5

  • 最小授权：只挂载需要的 Server 和工具，文件系统 Server 限定根目录；按工具名配置允许 / 拒绝 / 需确认三档。
  • 人在回路：写操作、外部发送、删除等高风险调用前弹出确认，或走审批流。
  • 隔离与身份：Server 跑在沙箱或容器里，用短时、低权限的凭证；远程 Server 要认证调用方。
  • 审计：记录每次调用的参数和结果；警惕工具描述或返回内容里夹带的提示注入。

回扣开头的三个问题

先自己答，再点开
1. 三个协议一句话区分？

MCP 解决智能体如何以统一方式访问工具与资源（智能体 ↔ 工具，上下文共享）；A2A 解决智能体之间如何点对点地委托任务、交付工件（智能体 ↔ 智能体，对等通信）；ANP 解决大规模网络里如何注册、发现、路由智能体（智能体 ↔ 网络，去中心化服务发现）。

2. MCP 三层与三能力？与 Function Calling 的关系？

Host 是用户交互和模型对话的宿主（如 Claude Desktop）；Client 内置在 Host 中，负责连接 Server、收发 JSON-RPC 消息；Server 提供具体能力。Tools 主动执行操作，Resources 被动提供数据（URI 标识），Prompts 提供预定义模板。Function Calling 是模型“会打电话”的能力，MCP 是统一的“电话标准”，二者互补：MCP 负责发现和连接工具，模型用 Function Calling 决定何时调用、生成参数。

3. A2A 核心对象？ANP 怎样选服务？

A2A 的核心是 Task（带生命周期的被委托工作：创建、协商、代理、执行中、完成或失败）和 Artifact（任务产出的工件）；请求经过发现、认证、发送消息、流式消息。ANP 先按服务类型或能力从注册表发现候选，再按路由策略（负载最低、价格最低或综合打分）挑选，新服务注册后即可被发现。
