Agent 干活的时候，界面谁来画

整页只跟一件事：让 Agent 把周五去上海的航班改到周六上午。一路上会遇到三个协议，AG-UI 管“发生了什么”，A2UI 管“画成什么样”，MCP Apps 让工具“自带界面”。先感受一下，为什么光靠聊天不够。

界面是跟着任务长出来的

Agent 刚流行时，不少人觉得“对话框就是 Agent 的全部界面”。说需求确实是自然语言的强项，一句“把航班改到周六上午”胜过在菜单里点五层。可一旦要比较十几个选项、调一个数量、确认一笔钱，列表、滑块和按钮仍然又快又不容易出错。所以 Agent 的界面通常是对话和图形界面的混合体。

更麻烦的是时机。传统 App 的页面顺序由设计师提前排好；Agent 先调哪个工具、缺什么信息、哪一步要人拍板，往往跑起来才知道。界面得跟着任务按需冒出来，还要在长任务里一直告诉用户它在干什么。再加上 Agent 越来越多地通过 MCP 调外部系统，那些需要持续交互的工具，界面该由谁来提供，也成了问题。

先自己感受一下：勾选几种情况，让 Agent 跑一遍，数数这一趟冒出了几块界面。

传统 App 永远是：搜索列表详情确认完成

    记下来

    概念

    Agent UI
    Agent 应用里自然语言之外的图形界面，用来看信息、补条件、做确认。
    动态 UI
    界面出现的时机和内容由任务进展决定，而不是事先排好的页面路由。
    人在回路
    任务中途需要人查看、修改或拍板的环节，通常配一块确认界面。
    长任务状态
    Agent 跑几分钟以上时，前端要持续显示的进度、当前步骤和正在调用的工具。

    要点

    说 vs 点
    自然语言适合表达意图；比较、调参、确认，用控件更快更不易出错。
    路径不固定
    传统应用的流程是设计好的；Agent 的步骤跑起来才确定，界面要能按需出现。
    三块缺口
    实时同步过程（AG-UI）、现场描述界面（A2UI）、工具自带界面（MCP Apps）。
    耦合问题
    需要持续交互的工具，若界面全在客户端定制，每接一个工具都要改宿主。

    先把“发生了什么”说清楚

    AG-UI

    第一个缺口是“看不见过程”。Agent 一次任务可能跑好几分钟，中间会开始、分步骤、调工具、一个字一个字地吐回复、更新状态，前端要把这些实时同步给用户，用户的确认也要能传回去。过去每个框架各自约定一套格式，换个 Agent 后端，前端就得重写一遍。

    AG-UI（Agent-User Interaction Protocol）由 CopilotKit 发起，把这些来回的消息统一成一套标准事件。它只管“发生了什么”，不管“画成什么样”：卡片长什么样、按钮放哪，仍然是前端自己的事。所以它最适合已经有前端、只缺 Agent 实时过程的项目；后面要讲的 A2UI 描述，也可以装在它的事件里一起送过来。

    下面左边是一串真实结构的事件，右边是两套完全不同的前端。一步步放事件，再切换皮肤，看同一串事件怎么被画成两个样子。

    事件流

    蓝色是 Agent 推给前端的（通常走 SSE），黄色是前端发回 Agent 的。

    • 换皮肤不用改后端。事件里没有一个字关于按钮长什么样，两种界面都是前端自己的代码。
    • 状态可以整包发，也可以只发差量。STATE_SNAPSHOT 发全量，STATE_DELTA 用 JSON Patch 只发改了的字段。
    • 确认按钮是前端画的。用户点了之后，前端带着新消息再发起一轮 run，Agent 才继续。

    记下来

    概念

    AG-UI
    Agent-User Interaction Protocol：Agent 与前端之间实时、双向、结构化通信的开放事件标准，由 CopilotKit 发起。
    事件
    对“运行中发生了一件事”的标准化消息，带 type 和必要数据，不带界面信息。
    run
    Agent 的一次运行：以 RUN_STARTED 开始，以 RUN_FINISHED 或 RUN_ERROR 结束。
    SSE
    Server-Sent Events：服务器沿一条 HTTP 连接持续往下推事件。AG-UI 常用 POST 发请求、SSE 收事件。
    快照与差量
    STATE_SNAPSHOT 发完整状态；STATE_DELTA 用 JSON Patch 只发改动的字段。
    适配器
    把某个 Agent 框架（如 LangChain）的输出翻译成 AG-UI 事件的中间层。

    关键事件

    RUN_STARTED / RUN_FINISHED / RUN_ERROR
    一次运行的开始与结束
    STEP_STARTED / STEP_FINISHED
    任务里一个步骤的起止，做进度列表用
    TEXT_MESSAGE_START / _CONTENT / _END
    流式文本：CONTENT 里的 delta 是增量
    TOOL_CALL_START / _ARGS / _END / _RESULT
    工具调用的起止、参数增量和结果
    STATE_SNAPSHOT / STATE_DELTA
    共享状态的全量与差量更新

    要点

    管通信不管界面
    事件里没有组件；同一串事件可以配完全不同的前端。
    双向
    用户确认、补充信息由前端带着新消息发起下一轮 run 送回 Agent。
    接入成本低
    后端换适配器，前端用 CopilotKit 或 @ag-ui/client，不必换 UI 框架。

    让 Agent 出图纸，前端按目录施工

    A2UI

    AG-UI 解决了“过程看得见”，但界面还是前端事先写死的。如果每单需要的控件都不一样，比如有时要选时段、有时要核对差价、有时要挑座位，前端就得把所有可能提前做好。更自然的做法是让 Agent 现场决定这一步要什么界面。

    A2UI（Agent-to-User Interface）由 Google 发起，就是干这个的：Agent 发一份 JSON，说明要哪些组件、怎么排、绑什么数据，前端渲染器用本地组件照着画。关键是组件目录，也就是一份事先登记好的白名单，Agent 只能点名用里面的组件，不能塞脚本或任意 HTML。于是 Agent 决定画什么，前端仍掌握怎么画、能画什么；同一份描述也能在不同端各自渲染。

    记下来
    
    
    
      
    概念
    A2UI
    Agent-to-User Interface：Google 发起的声明式 UI 协议，Agent 用 JSON 描述界面，客户端用本地组件渲染。
    声明式
    只说要什么组件、怎么排、绑什么数据，不带任何可执行代码。
    surface
    Agent 管理的一块界面区域，用 surfaceId 标识，先创建再更新。
    组件目录 catalog
    客户端事先登记、允许 Agent 使用的组件清单，也就是白名单。
    渲染器
    客户端里按目录校验描述、再映射成原生控件的模块。
    action
    用户在界面上的操作（如点按钮），以事件名加上下文回传给 Agent。
    关键消息
    createSurface
    新建一块界面，指明 surfaceId 和所用的 catalogId
    updateComponents
    发送组件列表：扁平排列，用 id 和 children 组织层级
    要点
    分工
    Agent 决定画什么；渲染、样式和可用能力仍由前端说了算。
    安全边界
    目录外的组件一律不渲染，Agent 没法注入脚本或任意 HTML。
    跨端
    同一份描述可在 Web、移动端复用，前提是支持同一版目录；不保证像素一致。
    传输无关
    可走普通 HTTP，也可装进 AG-UI 或 A2A 的消息里。
    
    
    
  
    

    



    
  
    工具自己带着界面来
    MCP Apps
    
  
    
    
    前两个协议都假设界面由宿主应用来画。可有些交互本来就属于工具方：航司的座位图、地图服务的拖拽地图、CRM 的筛选和下钻表格。让每个接入它们的 AI 客户端各自重写一遍，既费力又跟不上工具更新；只返回 Markdown 文本，又得靠多轮对话来回凑。
    
    
    MCP Apps 是 MCP 的官方 UI 扩展，由 Anthropic、OpenAI 等一起推动：工具在元数据里关联一个 ui:// 资源，宿主读到后把这页 HTML 放进沙盒 iframe 里运行。为了安全，iframe 里的 App 不能直接连 MCP Server，要调工具只能通过 postMessage 交给宿主，由宿主里的 AppBridge 代为转发。这样界面跟着工具走、由工具方维护，宿主只需要支持这个扩展。

    记下来
    
    
    
      
    概念
    MCP Apps
    MCP 的官方 UI 扩展：MCP Server 除了返回数据，还能提供一页交互式 HTML 界面。
    ui:// 资源
    Server 以 MCP 资源形式提供的界面页面，宿主用 resources/read 取回。
    _meta.ui
    工具元数据里的 UI 关联，resourceUri 指向该工具配套的界面资源。
    宿主 host
    承载对话和 MCP Client 的应用，负责加载、隔离、展示 App。
    沙盒 iframe
    App 运行的隔离容器，碰不到宿主页面，也不能自己去连 Server。
    AppBridge
    宿主侧的中转层：接收 App 的请求，审查后经 MCP Client 代为调用工具。
    postMessage
    浏览器原生跨窗口消息 API，App 与宿主之间只走这一条通道。
    关键调用
    tools/list
    发现工具，带 UI 的工具在元数据里挂着 ui:// 地址
    resources/read ui://…
    宿主取回界面 HTML
    app.callServerTool()
    App 内请求调用 Server 工具，经宿主转发
    registerAppTool / registerAppResource
    服务端 SDK（@modelcontextprotocol/ext-apps）注册带界面的工具和资源
    要点
    界面跟着工具走
    由工具方维护，所有支持的宿主自动复用，宿主不写这部分代码。
    向下兼容
    不支持扩展的宿主照样拿到普通工具结果。
    安全
    App 没有直连 Server 的路，每个请求都可被宿主拦截、审查。
    
    
    
  
    

    



    
  
    考考你：这个需求该找谁
    
  
    
    
    三个协议都和“界面”有关，但管的是不同环节。选型时别先问哪个更先进，先问项目缺哪一块：已有前端、只缺 Agent 的进度和回复，看 AG-UI；界面要按任务现场拼、还要跨端，看 A2UI，前提是客户端有对应的组件目录和渲染器；工具需要地图、编辑器这类重交互、希望随工具复用，看 MCP Apps，前提是宿主支持这个扩展。
    
    
    下面六个需求，每个选一个最合适的。答错可以再选，答对后会显示理由。
    
  
    
  
    
    
      
    
      
  
      

      



      
  
      四种拼法，盯住渲染器在哪
      
  
      
    
      三个协议可以单独用，也可以组合。AG-UI 和 A2UI 搭档最直接：A2UI 描述装进 AG-UI 事件，用一个专门的事件类型标明身份，和进度、回复一起流到前端，前端拆开后交给渲染器。A2UI 和 MCP 的组合要多想一层，常见有三种拼法，看起来容易混。
      
    
      分辨它们，只要盯住两个位置：A2UI 的渲染器装在宿主里，还是跟着 MCP App 走进了 iframe；界面里到底有没有 iframe。能改宿主、宿主有渲染器，渲染器就放宿主；改不了别人的宿主、对方只认 MCP Apps，就把渲染器打包进 App。
      
    
      切换下面四种拼法，看渲染器和 iframe 怎么搬家，对照线上实际传的消息；最后用条件选择器反过来推一遍，看你的情况该选哪种。

        记下来
        
    
        
      
        概念
        AG-UI × A2UI
        A2UI 消息装进 AG-UI 事件，和进度、回复一起流到前端，由前端渲染器画。
        ACTIVITY_SNAPSHOT
        AG-UI 的一种事件；用 activityType: "a2ui-surface" 标明里面装的是 A2UI。
        A2UIMiddleware
        AG-UI 提供的适配代码：从 Agent 工具输出中识别 A2UI，封装成事件。
        A2UI over MCP
        MCP 工具返回 A2UI 描述（application/a2ui+json），宿主渲染，不需要 iframe。
        MCP Apps in A2UI
        A2UI 目录里多一个 MCP App 容器组件，在 A2UI 界面中嵌入 iframe 里的 App。
        A2UI in MCP Apps
        渲染器和目录打包进 MCP App；宿主只需支持 MCP Apps，不必懂 A2UI。
        判断依据
        先问两个位置
        A2UI 渲染器在宿主还是在 App 里？界面要不要 iframe？
        能改宿主
        宿主装渲染器，用前三种；要统一各工具的界面风格选 A2UI over MCP。
        改不了宿主
        对方只支持 MCP Apps，就让渲染器跟着 App 走（A2UI in MCP Apps）。
        要看进度
        加 AG-UI，它和另外两个都不冲突。
        要用别家专业面板
        走 MCP Apps：单独用，或嵌进 A2UI 卡片。
        按需引入
        只缺进度就只接 AG-UI；工具只要一页固定界面就只用 MCP Apps。
        
    
        
  
        

        



        
  
        三个一起上：一张改签工作台
        
  
        
    
        真实应用里，三个协议完全可以同时出现：AG-UI 持续传 Agent 的回复和进度，A2UI 画外层的改签单，MCP Apps 承载卡片里航司的选座面板。用户看到的是一张工作台，背后却是三拨人维护的三块东西。
        
    
        拼界面容易，拼状态难。面板里保存了新座位，外层卡片和 Agent 怎么知道？协议只规定各自的接口，不会自动同步。宿主得先确认工具保存成功，再把变化告诉 Agent，Agent 读到最新状态后，才通过事件流更新回复和外层卡片。少了这一环，几块界面就会各说各话。

        记下来
        
    
        
      
        概念
        分区负责
        一个页面里，AG-UI 管运行时消息，A2UI 管外层卡片，MCP Apps 管内嵌工具面板。
        状态衔接
        App 里发生的变化，要由宿主转告 Agent，Agent 再经事件流更新外层界面。
        权威数据源
        同一份数据（如座位）只认一处为准，其他地方都从它同步。
        要点
        协议不管业务同步
        三个协议只定义接口，跨区域的衔接逻辑要应用自己写。
        正确顺序
        App → 宿主 → Server 校验保存 → 宿主确认成功 → 通知 Agent → AG-UI 回传回复和 A2UI 更新。
        失败不打扰
        保存失败就别通知 Agent，免得它基于没生效的状态往下走。
        关键动作前重读
        出票、付款这类不可逆操作前，让 Agent 再读一次最新状态。
        
    
        
  
        


        



        
  
        三个协议，一张表背下来
        
  
        
    
        前面一节一节点过来，这里把三个协议压成一张表：各管什么、谁产出、谁渲染、怎么传、靠什么保证安全。复习时先遮住一列，试着自己说出来。窄屏可以左右滑动。
        
  
        
  
        
    
        
      
        AG-UIA2UIMCP Apps
        
      
        
        管什么Agent 运行时的事件：进度、文本流、工具调用、状态界面长什么样：组件、布局、数据绑定工具配套的一整块交互界面
        
        
        不管什么界面长什么样怎么传输、Agent 怎么跑宿主其余界面
        
        
        谁产出Agent 后端（经适配器）Agent 生成 JSON 描述MCP Server 提供 HTML 资源
        
        
        谁渲染前端自己的代码客户端渲染器，用本地组件宿主把 HTML 关进沙盒 iframe 运行
        
        
        怎么传HTTP POST 请求 + SSE 事件流不限：HTTP、AG-UI、A2A、MCPMCP（tools、resources）+ postMessage
        
        
        安全边界只传数据，不传界面代码组件目录白名单iframe 隔离 + AppBridge 代理
        
        
        发起方CopilotKitGoogleMCP 社区（Anthropic、OpenAI 等）
        
        
        什么时候用已有前端，缺 Agent 的实时过程界面要按任务现拼、要跨端工具需要地图、编辑器这类重交互
        
              
    
        
  
        

  
        聊天适合把事情说出来，按钮、列表、滑块适合把事情办利索。Agent 没让界面消失，变的是界面出现的时机和由谁来决定画什么。
