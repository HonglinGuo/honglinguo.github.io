记忆，是写给未来那次会话的一张便条

Anthropic 的 Lance Martin 在工程博客发表《The components of agent memory》（智能体记忆的组成部分）。文章不是一篇“记忆该怎么分类”的综述，而是一份实验笔记：用 CL-Bench、《宝可梦 红》、Stainless 内部文档和 Harvey LAB 法律任务，观察 Claude 怎么写记忆、哪里写错、怎么修。主线有两条：写记忆是在预测未来，而模型预测不准；所以要有 dreaming（做梦），在会话之外回看转录，修正、重组、提炼记忆。

Life can only be understood backward, but it must be lived forward.

生活只能向后理解，却必须向前过。文章用克尔凯郭尔这句话开头：写记忆的时候只能向前猜，dreaming 让智能体有机会向后看。

原文开头 · 引言

一页读懂：原作的七个观点

  1. 记忆 = 从经验得来、跨会话保留、以后能读回的知识。权重变化、单次对话内的 in-context learning、compaction（用摘要替换旧轮次）都不算。
  2. 记忆有层级。从下到上：可搜索的转录 → Claude 写的笔记 → wiki 等表示 → 每次会话自动注入的顶层上下文。越往上越常用、越要小。
  3. 写下一条记忆，就是押注它将来还用得上。CL-Bench 上，新模型能闭合“犯错—记录—验证—复用”的学习环，Opus 5.5 有记忆后从 0.655 到 0.838。
  4. 该记的是自己推导出来的东西。屏幕上每回合都能读到的状态不用记；策略、计划、试出来的规则不写下来就没了。Sonnet 3.7 写了 413 个文件拿 1 枚徽章，Fable 5 写 9 个文件拿 4 枚。
  5. 告诉 Claude 记忆是干什么的，别规定怎么用。给强模型加“只记录失败”的规则反而让 Opus 5 的增益掉了 0.234；旧模型则需要明确流程。
  6. dreaming 做五件事。对照转录修正错笔记、构建 wiki 等新表示、把关键笔记提到顶层、围绕目标重组、补齐单次会话留下的空白。
  7. 还没解决的：什么时候写记忆、怎么保持更新、怎么在转录搜索之上维护表示又不让错误累积。结论：没有模型能预知未来，所以要给它向后看的机会。

读的时候留意：这是 Anthropic 工程团队的博客文章，不是论文。文中所有数字都来自 Anthropic 自己的实验（本文标为 作者自测），CL-Bench 的总题数和评分细则文中没有给出，《宝可梦》和 Mt. Moon 是单次运行的案例。原文是网页，没有页码，本文按原文小节标注出处。

和转述里的说法不一样：有的新闻摘要把这篇文章概括成“工作上下文、外部存储与检索、跨会话持久化状态”三类组件。原文的层级其实是转录 → 笔记 → 表示（wiki）→ 注入上下文，而且明确把单次会话内的上下文管理（in-context learning、compaction）排除在“记忆”之外。本文以原文为准。

记忆是什么，不是什么

原文 · 引言、Memory notes、记忆层级图

文章先拿人脑做类比。海马体很快记下经历，但只有一部分会在睡眠和安静休息时被“回放”，巩固进新皮层成为长期知识；某些化学信号会给重要的经历打上标记，让它们更常被回放。智能体这边，经历就是会话日志和转录；Letta 与 UC Berkeley 提出的 sleep-time compute，是让模型利用空闲时间整理上下文。作者把“回看日志、修正错误、产生新笔记和新表示”这件事叫作 dreaming。

在这个类比之前，作者先把“记忆”的范围划窄：只算 Claude 从经验中得到、在会话之间保留、之后能读取的知识。经验包括和用户的互动、被分配的任务。很多人平时说的“记忆”其实是上下文管理，原文把它们排除在外。

先判断一下：下面这些按原文的定义，算不算“智能体记忆”？

四层记忆层级

原文用一张图把记忆分成四层，注入上下文在每次会话开始时自动加载，下面几层在 Claude 需要时再去读或搜。越往上越精炼、越常被用到，也越贵；越往下越完整、越便宜，但要花力气找。后面讲的 dreaming，大部分工作就是在层与层之间搬东西。

记忆是对未来需求的预测

原文 · Memory is a prediction

这一节是全文的核心论点。写下一条规则，等于预测它描述的模式以后还会出现；记下一条已核实的事实，等于预测以后的会话可以直接用它、不必再核实一遍。难点在于：写的时候并不知道以后会发生什么，Claude 只能凭当下判断什么重要。

作者用 CL-Bench 1.0 的数据库任务观察不同模型能不能把这个“预测”做好。设置很干净：Claude 依次答题，每题答完会被告知正确答案，可以往记忆里写东西；每道题都在全新会话里做，唯一能延续的是一个持久化的记忆目录。所以分数提升只能来自记忆。

点每个模型，看它的笔记长什么样。注意差距不在“有没有写”，而在“写的东西能不能被下一次会话直接信任”。

原作观点不同模型“闭合学习环”的能力差别很大。Opus 5 是第一个闭合的：多数条目同时写了规则、为什么认为规则成立、之前题目的答案，以及对踩过的坑的明确警告。分数的跃升（0.564 → 0.828）来自笔记质量，而不是笔记数量。

Claude 学会判断什么值得记

原文 · Claude is learning salience

“显著性”（salience）就是判断什么值得记。作者用《宝可梦 红》测：每个模型开局拿到一个可读写的记忆文件夹，然后自己玩。游戏状态一直在变，正好检验“记了会不会过时”。

两个极端很说明问题。Sonnet 3.7 认为什么都可能有用，什么都写，结果记忆跟不上游戏变化，大量时间花在整理记忆上：在大约 17 步里，它新建了 6 个文件、删了 9 个，游戏里一个操作都没做。Fable 5 只写很少的文件，顶层一个像仪表盘的 global.md。

怎么引导 Claude 写记忆

原文 · Steering Claude's memory

作者的经验是一句话：告诉 Claude 记忆是干什么的，但不要规定怎么用。在 CL-Bench 上，只告诉 Opus 4.7 和 Opus 5“有一个记忆文件夹可用”，就足以让它们有效利用记忆、显著提分。

反过来，给它们加一条看似合理的规则“只记录失败”，增益反而下降了。原因是强模型自己判断显著性比固定规则准，规则把它本来会记的东西挡在了外面。但对旧模型，明确的流程帮助很大。

切换看两组结果：规则对强模型是负担，对弱模型是拐杖。

原作观点对前沿模型，作者通常只给一句简单指引：用户要求时、或内容明显值得记住时才建笔记，其余交给 Claude 判断。

Dreaming：向后看的五件事

原文 · Dreaming 相关五节

前面说过，写记忆是在会话中凭当下判断做的预测。笔记可能一开始就写错，也可能随环境变化而失效；下一次会话读到它，往往会直接信任。dreaming 是在会话之外回看原始转录和已有记忆，修正、重组、提炼。原文给了 dreaming 的五种用途，每种配一个实验。

按顺序看，也可以点下面直接跳。

  1. 修正笔记对照转录找出写错的笔记
  2. 构建新表示把散笔记织成互相链接的 wiki
  3. 提到顶层关键笔记每次会话自动加载
  4. 围绕目标按任务需要重组记忆
  5. 补齐空白跨会话补上缺页和断链

① 修正笔记：Mt. Moon 的故事原文 Dreaming can fix memories

Mt. Moon 是游戏里的一个坑：入口在西侧，出口在东侧，入口附近有一段单向悬崖，掉下去会回到来时的路。Claude 拿入口处的宝可梦中心当地标，却在笔记里把它的位置写成了东侧。这一处记错，让它之后的推理全都建立在错的地图上。

位置示意不按比例。结果：dreaming 修正的运行在第 1,935 步到达 Cerulean；原始笔记的运行退回 Pewter；无记忆的运行始终没到 作者自测

② 构建新表示：wiki原文 Dreaming can build new representations

wiki 是 Claude 写并维护的一组页面，一个主题一页，页面互相链接，像一张地图，帮 Claude 快速找到该看什么。作者在 Stainless 的内部文档上做实验：约 35 万个文件、约 4.2 亿 token，出 25 道题。Opus 5 智能体在 128 个会话里探索文件，写或修正互链的 wiki 页面、合并重复、核对来源，会话之间通过共享日志协调。

原作观点wiki 和搜索是组合关系：wiki + 搜索最好，而且每题约省 2 万 token。早期的 Claude 像新员工，wiki 不全，单靠它答不好；dreaming 多了以后，它像熟练员工一样手里有一张更丰富的知识地图。但答案能在单份文档里文本搜到时，wiki 没有明显帮助；wiki 写得和原文一样大时，就成了博尔赫斯笔下“与帝国等大的地图”，失去意义。

③ 提到顶层：自动注入原文 Dreaming can promote notes to the top

dreaming 可以把关键笔记提升到层级最顶，由 harness 在每次会话开始时直接加载进上下文。好处是 Claude 不用去搜，甚至不需要知道这条记忆存在，就已经在用它了。但代价同样明显，作者列了三条：

顶层太大的代价

① 每条注入的记忆都占宝贵的 token，每次会话都要付。

② 一条错笔记被提到顶层，会被带进每一个会话。

③ 加载了不等于会照做：作者引用 Claude Code 文档，指令文件越长，遵循得越差。

所以顶层要小

dreaming 的一项重要工作是把细节往下层搬，在顶层只留链接。

Claude Code 的 auto memory 就是这么做的：会话开始只加载 MEMORY.md 的前 200 行或 25KB，它是一份索引，告诉 Claude 自己知道什么、去哪里找。

原文 “So the top layer of the memory hierarchy has to stay relatively small … by moving some details down the hierarchy and leaving links behind.”

开放问题与结论

原文 · Looking backward and forward

作者没有给出一个“标准记忆架构”，而是列了三个还没解决的问题。读这三条时可以留意：它们都是在线写（及时但分心）和离线整理（专注但滞后）之间的取舍。

  1. 任务中写记忆能当场抓住显著性，但会分散 Claude 对主任务的注意力。dreaming 可以把记忆创建挪到后台，但它的产出不一定能马上被 Claude 用到。
  2. Claude 可能一开始就预测错、写下错规则，记忆也会随环境变化而失效。时时检查所有记忆不现实；可能要重点盯容易变的信息，或按访问频率调整 dreaming 的节奏。
  3. wiki 这类表示和搜索结合有时很有效，但维护表示要花算力，还要防止错误和幻觉在表示里越积越多。
原作结论Claude 对显著性的判断在进步，但没有模型真正知道未来会发生什么。dreaming 让 Claude 能向后看，用算力整理记忆、修正错误、维护表示，让未来的会话更容易用上记忆。随着 Claude 变强，记忆系统还会继续演进。

易混辨析

按原文内容整理的学习材料

易混辨析：记忆 vs compaction

compaction：在一次会话内，用 Claude 写的摘要替换旧的对话轮次，目的是腾出上下文窗口。

记忆：跨会话保留、下次会话能读回的知识。原文明确把 compaction 排除在记忆之外。

易混辨析：记忆 vs in-context learning

in-context learning：单次对话里学到的东西，会话结束就没了。

记忆：必须落到会话之外（例如记忆目录），CL-Bench 每题新开会话，正是为了只测这部分。

易混辨析：写记忆 vs dreaming

写记忆：会话中实时写，及时抓住显著性，但只看得到当前会话，还分散主任务注意力。

dreaming：会话外回看转录和已有记忆，能跨会话修错、重组、补空白，但产出不一定马上可用。

易混辨析：注入上下文 vs 检索

注入：每次会话自动加载，不用搜、不用知道它存在；代价是 token、错误被放大、太长了遵循度下降。

检索：下层（笔记、wiki、转录）按需读或搜，便宜但得想起来去找。

易混辨析：wiki vs 搜索

wiki 强：答案要跨多份文档综合、要判断或计算时（LAB 87% vs 73%）。

搜索够：答案在单份文档里能文本搜到时。最好两者组合（Stainless 54%→61%，仅搜索 53%）。

易混辨析：说用途 vs 定规则

说用途：“有个记忆文件夹可用”，对强模型足够，自主判断更准。

定规则：“只记录失败”会拉低强模型；但“先读记忆、明确检验假设”能让 Sonnet 4.6 几乎翻倍。规则的价值取决于模型。

术语速查

按原文用法改写
智能体记忆（agent memory）
Claude 从经验中获得、跨会话保留、之后可读取的知识。
in-context learning
单次对话内获得的知识，不算记忆。
compaction
Claude 写摘要替换较早的对话轮次，属于上下文管理，不算记忆。
转录（transcripts）
会话的完整事件日志，可搜索，是记忆层级的最底层，也是 dreaming 核对笔记的依据。
记忆笔记（memory notes）
Claude 在会话中写进记忆存储（如一个笔记文件夹）的条目。
记忆表示（memory representations）
在笔记之上组织出来的结构，如 wiki。
wiki
Claude 写并维护的页面集合，一个主题一页、互相链接，帮 Claude 定位知识。
注入上下文（injected context）
每次会话开始时由 harness 自动加载的顶层记忆。
显著性（salience）
判断什么值得记住的能力。
dreaming
在会话之外回看日志和记忆，修正错误、产生新笔记和新表示的过程。
sleep-time compute
Letta 与 UC Berkeley 提出的思路：让模型利用空闲时间整理上下文，是 dreaming 的来源之一。
harness

读后

以下是我的整理，不是原文内容

对照我自己的 Claude Code 记忆

我每天在用的就是文中举例的 auto memory，拿原文的原则对照一下。

  1. 四层在 Claude Code 里各有落点。转录 ≈ 会话的 jsonl 记录；笔记 ≈ memory/ 下一条一事的 md 文件；注入层 ≈ MEMORY.md 索引和 CLAUDE.md。中间的“wiki 层”目前没有，笔记之间靠 [[链接]] 弱连接。
  2. 我的 MEMORY.md 离上限不远，而且“顶层不够小”。2026-11-09 实测 77 行、约 17.9KB，还在 200 行 / 25KB 以内；但最长一行有 1,200 多字，把一个项目的进展流水全写进了索引。按原文，索引只该说“我知道什么、去哪找”，进展细节应下放到对应的笔记文件。
  3. “说用途、不定规则”也适用于 CLAUDE.md。与其写一堆“必须……”的流程，不如写清楚这个项目要什么、为什么，规则只留给真正容易犯的错。
  4. 可以手动做一次“dreaming”。定期让 Claude 对照最近的会话和 git 记录，检查记忆里过时或写错的条目（例如状态已变的待办），合并重复、把细节下沉。这正对应原文的“修正”和“提到顶层 / 下放”。

引用前要核对的地方

来自原文与转述的对照。

  1. “三类组件”的说法不是原文的。新闻摘要里“工作上下文、外部存储与检索、跨会话持久化状态”的划分，在原文中找不到对应；原文是转录 / 笔记 / 表示 / 注入四层，并把会话内上下文管理排除在记忆之外。
  2. 数字都是作者自测，且多为案例。《宝可梦》和 Mt. Moon 是单次运行；CL-Bench 没公布题数和评分细则；Stainless、Harvey LAB 是特定语料。可以用来理解方向，不宜当作通用基准引用。
  3. “wiki + 搜索 54%→61%”要连同条件一起引。它随 dreaming 量增长而上升；仅 wiki 的 48% 是 128 个会话后的最好成绩，2 个会话时只有 13%。
  4. Hacker News 热度未核对。转述里“约 174 点、99 条评论”的数据我没有去 HN 核实。
  5. URL 在 /research 下，但署名团队是 Engineering。引用时可写“Anthropic 工程博客，Lance Martin，2026-11-06”。
