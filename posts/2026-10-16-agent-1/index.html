深入理解 AI Agent · 01对应原书第一章约 20 分钟边读边点

Agent = 大脑 + 眼睛 + 手脚

Cursor 改代码、Deep Research 写报告、Manus 操作浏览器，形态各异，骨架却相同：一个模型在循环里看信息、调工具、再看结果。这一篇把这副骨架拆开，再看生产级 Agent 在骨架外面加了哪些“缰绳”。

本系列是开源书《深入理解 AI Agent：设计原理与工程实践》（李博杰 著，Apache-2.0 协议）的学习笔记。不逐段复述原书，而是用自己的话把关键概念讲一遍，配上能动手点的小实验；原书的实验代码和思考题推荐对照阅读。

三个部件，一个闭环

原书 1.1 节

原书的核心公式只有一句：Agent = LLM + 上下文 + 工具。LLM 是大脑，负责理解意图、规划、判断下一步；上下文是眼睛，是 Agent 在每个决策点能看到的全部信息；工具是手脚，是它读取或改变外部世界的接口。三者缺一个，Agent 就要么看不见，要么动不了。

要注意这个公式只描述 Agent 边界以内的东西。文件、数据库、网页、用户、其他 Agent 都属于 Environment（环境）：环境给出观察，Agent 选择行动，行动改变环境，再产生新的观察。换成强化学习的说法，LLM 对应策略（Policy），上下文对应观察与历史，工具对应观察/行动接口。

原书由此推出一个很实用的判断：模型固定时，提升 Agent 表现最主要的工程手段，往往是扩展观察空间和动作空间。Manus 把 Deep Research、Coding、Computer Use 三条路线的“眼睛和手脚”取了并集；OpenClaw 又把接口延伸到用户已在用的聊天软件和本地文件。很多看似需要“更聪明的模型”的问题，其实只是接口问题。

下面先看五类真实产品怎么分配眼睛和手脚，再亲手做一次“取并集”，看哪些任务因此变得可解。

    上下文的五个部分，缺哪个最疼

    原书 1.1 节 · 实验 1-1

    每次调用模型时，它看到的上下文由五部分拼成：系统提示词（开发者写的“岗位说明书”，也装着用户记忆和环境状态）、工具定义（有哪些工具、参数长什么样）、用户消息、模型回复（可能含思考过程、回复文本、工具调用三部分）、工具执行结果。前两项整轮对话不变，叫静态前缀；后三项随交互不断增长，叫轨迹。

    它们是不是都同样重要？原书用消融实验回答：保留系统提示词，分别去掉另外四个组件中的一个，看 Agent 怎么变。结论有两层。一是组件并不等价，衡量标准是“它承载的信息能不能从别处重建”。二是对工程更重要的一条：“给出了回答”不等于“完成了任务”。上下文残缺时，典型的失败不是报错，而是一份看上去毫无破绽的答案。

    勾掉一个或几个组件，看 Agent 表面上的表现和真实结果有什么不同。

      想、做、看，再想

      原书 1.1 节 · ReAct 循环

      三个部件靠 ReAct（Reasoning + Acting）循环串起来：模型先思考该做什么，调用工具行动，再观察工具结果，接着思考下一步，直到不再调用工具、直接给出答案。名字里只有两个词，循环里其实有三个环节。

      循环里不断变长的那串消息就是轨迹。每次调用模型时，Harness 把“静态前缀 + 当前轨迹”拼成完整上下文交给模型；模型的回复追加进轨迹，工具结果也追加进轨迹，下一轮再整体送进去。所以有一个关键等式：上下文 = 静态前缀 + 轨迹。

      这种“只追加”的设计让模型始终清楚做到了哪一步，轨迹也天然可调试、可分析、可拿去训练。代价是每一轮都要把越来越长的上下文重新读一遍，累计读入量随轮数近似二次方增长，这正是第 2 篇 KV Cache 要解决的问题。

      模型之外的竞争力：Harness

      原书 1.2 节

      能跑的 Demo 和可靠的产品之间差着一大截：模型会幻觉出不存在的工具、选错工具、出错后不会自救。原书把补这一截的工程叫 Harness（原意是马具：不是限制马的力气，而是把力气引到正确方向）。生产形态下的公式写成 Agent = Model + Harness，而 Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正。

      边界要分清：Harness 是“Agent 边界内、模型之外”的运行与治理层。工具定义、调用适配器、沙箱的权限和重置机制属于 Harness；沙箱里随行动变化的文件、外部数据库、网页、用户本身属于环境。即使仿真环境和 Agent 跑在同一个进程里，它仍然是环境。

      原书强调两类功能的重要性是不对称的：早期框架主要做上下文和工具，让 Agent “能做事”；生产级系统的重心转向约束、验证、纠正，让它“不做错事”。Claude Code 的 Harness 里，绝大部分代码就是权限分类、熔断器、多层压缩、错误恢复这类保障机制。

      先玩一局分类：把下面这些机制放进 Harness 的五个格子，或者判断它其实属于环境。

      这属于 Harness 的哪一格

      工程范式是一层套一层的

      点任意一层看它比内层多管了什么。五个阶段不是替代，而是包含。

      一个例证：LangChain 在 Terminal Bench 2.0 上从 52.8% 提到 66.5%，排名从 30 名开外进入前 5，模型没换，改的是 Harness，比如让 Agent 自查执行结果、检测是否陷入重复循环。

      原书对“模型会不会把 Harness 吃掉”的立场是：方向认同，节奏务实。模型每内化一层，Harness 就卸下一层，转去兜底新的能力前沿。

      先简单，再复杂：工作流与自主 Agent

      原书 1.2 节 · 编排模式

      工作流由代码写死执行路径，LLM 只在每个节点内部负责理解和生成。订机票可以设计成“核实身份 → 搜索航班 → 付款 → 确认预订”四个固定节点。好处是流程严格、攻击面小：提示注入最多影响当前节点，跳不到不该去的分支。坏处是不会变通，遇到预设外的情况只能走异常分支或交给人。

      自主 Agent 的路径由模型根据环境反馈实时决定，本质就是“在循环里用工具的 LLM”，也就是 ReAct。它适合步骤数难以预测的开放问题，代价是更高的成本、延迟和错误累积风险，而且必须有明确的停止条件。

      原书给的顺序是：先试单次 LLM 调用，再考虑工作流，最后才上自主 Agent；两者也常混用，合规关键步骤用工作流，灵活部分交给自主。它还提醒一个反面典型：一上来画出一条十几个节点的“严谨”流水线，遇到新例外就继续加节点，越来越复杂、越来越不通用。用 Manus 的话说：Less structure, more intelligence。

      同一个订票任务，切换两种模式，再给它扔几个意外，看谁接得住。

      三层护栏，按“多难绕过”排序

      原书 1.2 节 · 护栏与安全性

      护栏（Guardrails）是分层防线。原书按防护位置分三层，但排序依据不是处理先后，而是被绕过的难度：越往下越不依赖模型自己的判断，越难被一次成功的攻击穿透。

      上下文层管“模型能看到什么”：相关性分类器、越狱和提示注入检测、内容审核、黑名单和正则规则。它有一个结构性上限：处在同一个上下文里的 Agent，很难判断自己是否已经被注入，所以这一层只能降低成功率。执行层管“模型能做什么”：按是否可逆、权限、财务影响给工具评风险等级，高风险操作由上下文之外的机制复核或人工确认；回复用户本身也是动作，所以 PII 过滤等输出检查也在这层。数据层管“世界最终能被改成什么样”：行级安全、约束校验、受控视图，即使上面两层都失守，越权操作仍会被数据库拒绝。

      还有一类失败容易被忽略：误拒绝。护栏评估既要测该拦的有没有拦住，也要测该放的有没有放行。

      选一种攻击，开关三层护栏，看它在哪一层被拦住，或者一路穿透。

      攻击穿透模拟

      贯穿全书的五个设计模式

      原书 1.3 节

      后面九章会反复用到同一批模式，原书在第一章一次性命名。提议者—审核者：产出和评判由两个不共享上下文的角色承担，因为自审不可靠。渐进式披露：先给目录，按需加载细节。只增不改：状态只追加不回改，换来可缓存、可重放、可审计。边界集 + 保留集：任何修改都要同时在“该变的样本”和“不该受影响的样本”上验证。最小 diff + 可回滚：改动尽量小、带来源、能单独回滚。

      同一节还讲了 Agent 改变行为的三条路径，它们按可回滚程度从高到低排列：上下文适应（任务内，示例和检索结果进上下文即时生效）、外部产物更新（跨任务，写成知识文档、Prompt、Skill、程序）、参数更新（训练周期，后训练改模型权重）。

      用几道题检验一下：每个场景对应哪个模式或哪条路径。
