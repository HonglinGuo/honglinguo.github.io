一张卡、16 条请求、7 秒

原书第 8 章给了一道贯穿全章的题：RTX PRO 6000 上留 12 GiB 给 KV，16 条请求同时到达，每条输入 8192（前 6144 相同）、输出 256，7 秒内完成。四种方案里只有一种能过——不共享前缀的放不下，共享了的要 9.01 秒，压缩的反而 14.55 秒。这一章就是把批处理、缓存、压缩、推测这四类手段的账一笔笔算清楚。

本系列是开源书《深入理解 AI Infra：量化分析与系统设计》（李博杰 著，Apache-2.0 协议，初稿持续修订中）的学习笔记。原书的方法是“从约束推导设计”，所以每篇以计算器为主：先自己代入数字估一遍，再对照原书的结论。公式、硬件参数和算例数字都取自原书，为演示设的默认值会标注“示意”。

批处理：权重被摊薄，KV 摊不薄

原书 8.1–8.2.1 节

一条请求的时间线分两段：TTFT = t₁ − ta（排队 + prefill）和后面 G−1 个输出间隔。原书算例：2K 输入短请求 prefill 到首 token 0.096 s，之后每 26.5 ms 一个，排队 0.1 s，0.1 + 0.096 + 255 × 0.0265 = 6.95 s。中间插进另一条请求的 prefill，某个间隔就从 26.5 变成 123 ms，总耗时 7.05 s——计算内容没变，只是换了执行顺序，就超时了。

合批之所以有效，是因为同一份权重被多行复用：Iweight ≈ 2b/sw。但各请求的 KV 是各读各的：

D(b, L) = D_w + b·L·k　　d(b, L) = D_w/b + L·k

Qwen3-8B 的 Dw ≈ 14.1 GiB，每 token KV k = 144 KiB。2K 上下文时 batch 1 → 64，每输出 token 的读取从 14.38 降到 0.50 GiB（约 1/29）；但权重项和 KV 项相等的 batch bKV = ⌈Dw/(Lk)⌉：2K 时 51，8K 时只要 13。上下文一长，KV 读取很快就超过权重读取。

代价是首 token 和输出间隔都变长：batch 1 → 64，总吞吐 37 → 1165 token/s，但首 token 从 96 ms 延后到 3.29 s，平均输出间隔从 27 增到 40 ms。

LoRA 是个有意思的对照：一套 Q、V 投影 r = 16 的 BF16 adapter 只占 14.6 MiB，100 套 1.43 GiB；而 100 条互不共享的 8K 上下文，KV 要 112.5 GiB。能放多少套 adapter 由小矩阵决定，能服务多少条请求仍由 KV 决定。

调度：连续批处理省总时间，却可能拉长一次停顿

原书 8.2.2–8.2.4 节

固定批处理整组进整组出，短请求空出的位置一直闲着；连续批处理在迭代边界重排活跃请求。原书算例（最多同时两条，每轮耗时按实测拟合：固定 26.22 ms + 每新 token 30.4 μs + 每对因果查询键 3 ns）：固定批处理 870 ms；连续批处理 766 ms（省 12%），但 r0 的下一次输出要等 r2 的 8K prefill，最大输出间隔从 26 ms 涨到 376 ms，14 倍。把 r2 的 prefill 按 2048 分块、每轮上限 4096，最大间隔降到 133 ms，总时间 844 ms。

分块也不是越小越好。本块 c 个新 token、已有上下文 h 时 Npair = ch + c(c+1)/2：c = 512 时首块 131,328 对全来自块内，8K 输入的末块（h = 7680）有 4,063,488 对，约 31 倍；实测末块主干矩阵运算多 32%、时间从 25.3 增到 35.1 ms（多 39%）。而块减半又让同一份权重多读一遍（一层 FFN 288 MiB → 576 MiB）。

还有个容易忽略的：少处理一个 token 不一定少做计算。预先捕获 16 行和 32 行两种 CUDA Graph 时，17–32 行都填充到 32 行；18 → 17 行仍执行 32 行图，17 → 16 行才换小图。token 预算从 512 增到 8192：后到请求的排队从 149 ms 降到不足 0.1 ms，最长输出间隔却从 32 增到 183 ms。

KV 分配：分页、共享、写时复制

原书 8.3.1–8.3.2 节

整段预留会浪费尾部，逐步扩展又要求连续。分页分配像活页册：逻辑块是页码、物理块是实际内存、块表记录映射，物理块可以分散放。每块容 p 个 token 时浪费 p⌈L/p⌉ − L ≤ p − 1。块越小浪费越少，块表项和分配次数越多。

原书算例：A、B、C、D 长度 9、13、5、15，上限 16。整段预留共 64 个 token 的空间；p = 4 分页分别给 12、16、8、16 共 52，实际用 42，未用从 22 降到 10。若 A、B 前八个 token 相同再共用两块，降到 44。分页减的是没用上的预留，共享减的是重复保存的上下文——两回事。

共享要靠引用计数：最后一个引用释放、且加速器不再访问时才回空闲池。写共享尾块要写时复制（先复制再各自追加，已填满的只读块继续共享）。四分支实验：公共前缀 95 块、每分支私有 9 块，块表共 4 × (95 + 9) = 416 次引用，物理块只有 95 + 4 × 9 = 131。

前缀复用：命中率要多高才值得留着

原书 8.3.3–8.3.4 节

复用沿前缀连续发生：两条提示前 100 个 token 相同、第 101 个不同，后面即使又相同也不能复用。所以把动态时间戳放在最前面，会让后面很长的工具定义失去复用机会；稳定的系统提示和工具定义在前、本轮变化追加在后，才能保住长前缀。

换出到主机值不值，有个明确门槛。原书算例：6144 个 token 的前缀（864 MiB），重算 Tr = 308 ms；经 PCIe Gen5 x16 取回 Tf = 14.2 ms、换出 Tm = 14.2 ms。ph > Tm/(Tr − Tf) = 14.2/293.7 = 4.8%。换成 Gen4 x16（32 GB/s），取回和换出各 28.3 ms，门槛升到 10.1%。

该保留哪个前缀，比的是单位容量的收益：A（6144 token、864 MiB、重算 308 ms、命中 50%）期望省 132.7 ms，约 0.154 ms/MiB；三个 B（2048 token、288 MiB、重算 94.7 ms）合计 120.9 ms，约 0.140 ms/MiB。重算时间随长度超线性增长（6144 的 prefill 是 2048 的 3.25 倍），所以同样的内存留长前缀更划算。

还有个对照很说明问题：12 轮 Agent 输入共 19,556 个 token，6 GiB 缓存池命中 16,304 个（只需重算 3252），1 GiB 池一个也没命中；把轮间等待延长 0.2 秒，命中数一点没变——是容量不够，不是时间不够。

压缩与卸载：省空间要付多少时间

原书 8.4 节

量化要连元数据一起算。Q2_K 每组 256 个值：2-bit 编码 64 B + scale 等 20 B = 84 B，平均每值 2.625 bit，元数据占 24%。KV 的 q8_0 是每 32 个值 32 B 码 + 2 B scale = 34/64；q4_0 是 18/64。一条 8K 上下文的 BF16 KV 1152 MiB，q8_0 变 612、q4_0 变 324 MiB——不是只看位宽得到的 576 和 288。

压缩能否加快执行看净账：ΔT = ΔD/β − Tc。8K 从 BF16 改 q8_0 少读 540 MiB，按有效带宽 1.16 TB/s 省 0.487 ms；转换花 0.2 ms 净省 0.287，花 0.8 ms 反而亏 0.313。另一组评估（H100、Llama-3.1-8B）拟合出 BF16 和 FP8 的输出间隔分别是 6.44 + 4.37×10⁻⁵L 和 6.58 + 2.37×10⁻⁵L ms，交点约 7000 个 token：2K 时 BF16 更快，16K 时 FP8 更快。

权重卸载的账更难算。Qwen3-8B 每四层卸载一层 FFN（九份 × 288 MiB = 2592 MiB），一组预取缓冲净省 2304 MiB。但每轮都要搬回来：经 PCIe Gen5 x16（64 GB/s）至少 42.5 ms，已经超过 batch 1 一轮 decode 的 26.26 ms；255 轮光搬移就 10.8 秒，7 秒时限直接出局。换 GH200 的 NVLink-C2C（450 GB/s）每轮 6.0 ms，255 轮 1.54 s，预取就能被计算盖住。

先压缩再搬也要算：Rdec > Blink/(1 − r)。96 MiB 压到四分之一，PCIe Gen5 直传 1.57 ms、传压缩数据 0.39 ms，要保住这 1.18 ms，解压器每秒得输出 85.3 GB 原始数据。链路越快，对解压的要求越高。

最后一条提醒：改格式会改答案。一组 Qwen3-8B 实验（权重都是 BF16）：BF16 KV 答对 28/32，原 FP8 实现 26，保留 FP8 KV 但把 Q 恢复成 BF16 又回到 28——只改 Q 的精度结果就变了。而且同样答对 28 次，答错的题目还不一样。

推测解码：一轮多输出几个才划算

原书 8.5 节

先用草稿模型写一段，再让目标模型一次验证多个位置。贪心时：四个草稿，前两个对、第三个错，保留两个 + 修正一个 = 3 个输出（第四个因为依赖错误的第三个也丢掉）；全对时通常还能多生成一个。随机采样要保分布：以 α(x) = min(1, p(x)/q(x)) 接受，拒绝后从归一化的 [p−q]+ 重采样，最终仍是 p(x)。

平均输出数：前面全接受时第 j 位的条件接受率 aj，则 E[Nm] = 1 + Σj Πi≤j ai。原书两符号例：草稿恒为 A 时 a = 1/4，平均 1.33 个；恒为 B 时 a = 3/4，平均 3.05 个。算平均耗时必须用总时间 ÷ 总 token：两轮各 1.5 ms、分别输出 1 和 5 个，是 3/6 = 0.5 ms，不是 (1.5 + 0.3)/2 = 0.9 ms。

要不要加长草稿，判据是 ΔT/ΔN < T/N，其中 ΔN = Πi≤m ai——越靠后的草稿 token 保留概率越低，越难赚回时间。预设执行形状也影响 ΔT：验证 4 个和 5 个都补到八行图时增量很小，从 8 个增到 9 个要换十六行图，计算量就跳一截。

草稿怎么生成也有讲究。DFlash 草稿网络权重 1.95 GiB，按 batch 1 的有效带宽前向一次 3.57 ms：串行生成四个草稿要 4 次前向共 14.28 ms，并行生成整段只要 3.57 ms。目标验证都是 26.26 ms，平均输出 3 个时分别是 13.5 和 9.9 ms/token。但如果并行草稿的接受率低到平均只输出 2 个，就变成 14.9 ms——比串行还慢。

实测也印证了收益递减：Qwen3-8B/DFlash 短提取任务并发 1 时，普通 decode / K7 / K15 的耗时中位数是 90.0 / 30.6 / 29.4 ms——普通改 K7 省 59 ms，K7 改 K15 只再省 1.2 ms；逐轮记录里还有两种块长都只接受一个草稿的轮次（K7 丢 6 个、K15 丢 14 个，输出一样长）。

有效吞吐：正确且按期才算数

原书 8.6.1–8.6.2 节

系统里平均有多少条请求占着状态，由 Little 定律给出：n̄ = λT̄。每秒 4 条、平均停留 0.5 s 就是 2 条；停留 2 s 就是 8 条。准入控制要在接收前检查 KV 空间和剩余时限——短请求 6.95 s 已经用掉，再排 0.1 s 就超时了。

评价服务要同时看正确和按期：Rgood = Σ QiDi / Tobs。原书的检索实验（336 次回答、294 次正确、只有 155 次同时满足 3 秒时限）：
