CLAUDE.md 是拼起来的，不是盖掉的

每次启动 Claude Code，它都会先读一堆“记忆”：公司下发的策略、你的个人偏好、项目约定、你本机的私人补充，还有 Claude 自己记下的笔记。原教程这一章最值得记住的一句话是：这些 CLAUDE.md 文件是拼接进上下文的，不是谁覆盖谁；而 settings.json 恰恰相反，是按优先级覆盖的。分不清这两套规则，就会出现“我明明在项目里改了，怎么没生效”的困惑。

本系列是开源教程《Claude How To》（luongnv89 与社区贡献者编写，MIT 协议；本笔记依据 2026 年 10 月 20 日的仓库版本（commit 188f468），原文标注对应 Claude Code v2.1.302）的学习笔记。原教程按十个模块（01-slash-commands 到 10-cli）组织，配了大量可复制的模板。这里重排成十二篇：先用一篇讲清七种扩展机制的分工，再逐个拆开，每个功能按“它解决什么问题、最小可用配置放在哪个路径、什么时候不该用”来写，并配上“读配置猜行为”、模拟器和场景判定题。功能与字段取自原文（主要依据英文原版，中文版是它的缩写译本），每节标出对应的原文目录；为演示设的场景和数值标“示意”。Claude Code 更新很快，原文里带版本号的细节以原文和官方文档为准。

两套记忆

原文 02-memory「Memory Architecture」「Memory Commands Quick Reference」

Claude Code 里有两套互补的记忆，每次会话开始时都会加载，并且在会话中持续更新，不像网页版 Claude 那样按 24 小时周期整理。一套是 CLAUDE.md 文件：你写的指令，完整加载；另一套是 auto memory：Claude 自己记的笔记，存在 ~/.claude/projects/<项目>/memory/，入口文件 MEMORY.md 只加载前 200 行（或前 25KB）。

往里写的方式有三种：/init 生成一份初始 CLAUDE.md（设 CLAUDE_CODE_NEW_INIT=1 可走多步交互流程）；/memory 用编辑器打开各层记忆文件，也能开关 auto memory；直接在对话里说。注意说法决定去向：说“记住……”写进 auto memory，要写进 CLAUDE.md 得明说“把这条加到 CLAUDE.md”。以前那个以 # 开头快速加记忆的快捷方式已经取消。

先看一张功能卡，然后判断几句话分别会写到哪里。

CLAUDE.md项目级 ./CLAUDE.md，个人级 ~/.claude/CLAUDE.md

解决什么问题
模型本身不记得上一次会话。每次都要重复的项目背景、命令、约定、个人偏好，写一次，之后每个会话自动带上。
最小可用配置
什么时候不该用
多步骤流程（搬去 Skill）；只和某些目录相关的规则（搬去 .claude/rules/ 加 paths:）；会变的实时数据（用 MCP）；密钥和凭据（永远不要写）；“必须执行”的检查（用 Hook）。原文的经验值是控制在 200 行以内。

层级与加载：从哪启动，就读哪些

原文「Memory Hierarchy in Claude Code」「Memory Locations Table」

CLAUDE.md 有四个层级，按“从最宽到最具体”的顺序加载：组织策略（macOS 在 /Library/Application Support/ClaudeCode/CLAUDE.md，Linux 在 /etc/claude-code/CLAUDE.md，个人设置排除不掉）→ 用户级 ~/.claude/CLAUDE.md → 项目级 ./CLAUDE.md 或 ./.claude/CLAUDE.md → 本地级 ./CLAUDE.local.md（个人对这个项目的补充，记得加进 .gitignore）。中间还穿插着规则文件：用户级 ~/.claude/rules/ 在用户 CLAUDE.md 之前，项目级 .claude/rules/ 在项目 CLAUDE.md 之前。

关键在于目录树的走法：Claude Code 从你的启动目录往上走，沿途每一层的 CLAUDE.md 都加载，靠近启动目录的最后读到——原文特意强调这只是“在上下文里更靠后”，不是“优先级更高、把前面的覆盖掉”。启动目录下面子目录里的 CLAUDE.md 不在启动时加载，而是等 Claude 读到那个子目录里的文件时才按需加载。monorepo 里不想要的 CLAUDE.md，可以用 claudeMdExcludes 按绝对路径的 glob 排除（仓库相对的写法要以 **/ 开头）。

拼接、覆盖、合并：三套规则
原文「Settings File Hierarchy」

  

    
同样是“多层配置”，Claude Code 里其实有三种合并方式。CLAUDE.md 是拼接：所有层都进上下文，前后顺序不同而已。settings.json 是覆盖：同一个键出现在多层，高层赢；顺序从高到低是 组织托管（managed-settings.json、plist 或注册表）→ 命令行参数 → .claude/settings.local.json → .claude/settings.json → ~/.claude/settings.json。权限规则（allow / ask / deny）是合并：各层的规则合到一起，不是高层替换低层。

    
还有几个原文点到的细节：/config 里改的设置（v2.1.119 起）会写进 ~/.claude/settings.json，参与正常的优先级链；组织可以用 managed-settings.d/ 目录放多个策略片段，按字母序合并（标量覆盖、数组拼接去重、对象深合并）；有些安全相关的设置项目级文件无权设置（比如 AGENTS.md 的读取方式只认用户和托管设置）。

易混辨析：CLAUDE.md 拼接、settings 覆盖、权限规则合并

    
CLAUDE.md：所有层都进上下文，没有谁“赢”；如果两层写了互相矛盾的话，模型两句都看得到，结果不可控——所以别在不同层写冲突的指令。

    
settings.json：同名键高层覆盖低层（托管 > 命令行 > 本地 > 项目 > 用户）。权限规则：allow / ask / deny 各层合并在一起。

  

  






  
规则文件：只在碰到相关文件时加载
原文「Modular Rules System」「Path-Specific Rules」

  

    
.claude/rules/*.md 是把 CLAUDE.md 拆成主题文件的机制，支持子目录（rules/api/、rules/testing/）和软链接（把一个中心位置的规则软链到多个项目里；从外部软链进来的规则会弹出和 @ 外部导入一样的确认）。用户级的 ~/.claude/rules/ 在项目规则之前加载。

    
真正省上下文的是 paths: frontmatter。没写 paths 的规则无条件加载，和 .claude/CLAUDE.md 地位一样；写了 paths 的规则按需加载：只有当 Claude 读、写或编辑匹配的文件时才进上下文，包括用 cat、head、sed -n、grep 这类单文件 Bash 读取（Write/Edit 从 v2.1.288、Bash 读取从 v2.1.293 起算，以原文为准）。原文特别指出：@ 导入只是整理，导入的内容照样在加载时全部拉进来，拆成带 paths 的规则才真正减少加载量。

AGENTS.md：多个编码代理共用一份约定
原文「AGENTS.md」

  

    
AGENTS.md 和 CLAUDE.md 是同一类文件，写给多个编码代理共用。从 v2.1.277 起 Claude Code 直接把它当项目指令读，不用再手动导入。默认行为（claude-md-or-agents-md）是二选一：只有 AGENTS.md 时读它；两个都有时只读 CLAUDE.md；CLAUDE.md 里写了 @AGENTS.md 就把它展开进来。

    
判断“有没有 CLAUDE.md”时，Claude Code 检查启动目录及以上各层的 CLAUDE.md、.claude/CLAUDE.md、CLAUDE.local.md；用户级、组织级 CLAUDE.md 和 rules 不算。原文的警告值得记一下：新建一个 CLAUDE.local.md 会让 AGENTS.md 静默不再被读，如果“项目指令突然消失了”，多半是这个原因。AGENTS.local.md、AGENTS.override.md 和 .agents/ 下的东西永远不读。读取方式可以在 /config 的 Project instructions 里改成四种之一，但只在用户级和托管设置里生效。

自动记忆：Claude 写给自己的笔记
原文「Auto Memory」「Subagent Memory」

  

    
auto memory 是 Claude 在工作中自己写的、带类型的笔记，类型有四种：user、feedback、project、reference。它会跳过能从代码里推出来的东西（架构、文件路径、某个 bug 的修法），只记你的偏好、你给过的纠正、项目背景和外部参考。目录是 ~/.claude/projects/<项目>/memory/：MEMORY.md 是入口，启动时加载前 200 行或 25KB；每条记忆可以是单独的主题文件（如 prefers-pnpm.md），按需加载。同一个 git 仓库的所有 worktree 和子目录共用同一个 auto memory 目录。

    
它默认开启（需要 v2.1.59 以上）。关掉有三种办法：settings 里 "autoMemoryEnabled": false、会话里 /memory 切换、环境变量 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1（设为 0 反而是强制开启）。目录位置可以用 autoMemoryDirectory 改（绝对路径或 ~/ 开头）。Subagent 也能有自己的持久记忆，用定义里的 memory: user | project | local 指定放哪，详见第 5 篇。

易混辨析：CLAUDE.md 与 auto memory

    
CLAUDE.md：你写、你维护、完整加载，适合团队约定和你明确要求的规则，可以提交进 git 共享。

    
auto memory：Claude 写、存在你的 home 目录下、入口只加载前 200 行，适合“关于你”的东西（偏好、纠正过的做法），不进项目仓库。对 Claude 说“记住”写这里；说“加到 CLAUDE.md”才写那里。

  

  






  
保持精简：200 行与“别写验证提醒”
原文「Keeping CLAUDE.md Small」「Don't Write Verification Reminders」

  

    
原文说 Anthropic 现在的建议和“什么都往 CLAUDE.md 里放”正好相反：这个文件每次会话都加载，你加的每一行都在和与它无关的任务争注意力。经验值是 200 行以内，更长的照样完整加载，但遵循度会下降。变长的时候不是删字，而是搬家：多步流程搬到 Skill；按目录或文件类型的规则搬到带 paths: 的 rules；参考资料和长示例搬到 Skill 的 references/；关于你个人的东西交给 auto memory。v2.1.206 起 /doctor 也会在 CLAUDE.md 过长时建议精简。

    
另一条更反直觉：别写验证提醒。以前常见“说完成之前一定要跑测试”“仔细检查你的工作”这种句子，原文说在 Opus 5 和 Fable 5 上它们会导致过度验证——反复检查已经正确的结果，白白消耗轮次和 token；Anthropic 为 Claude 5 一代删掉了 Claude Code 自身系统提示词的八成以上，没有测到退化。要保留的是真正不显然的项目事实，比如“集成测试需要先启动 Docker”，这是信息，不是提醒。

回扣开头的三个问题
先自己答，再点开

  

    
1. CLAUDE.md 和 auto memory 各存哪、何时加载？说“记住”写进哪个？
CLAUDE.md 是你写的，分组织、用户（~/.claude/CLAUDE.md）、项目（./CLAUDE.md 或 ./.claude/CLAUDE.md）、本地（./CLAUDE.local.md）四层，启动时完整加载，子目录里的按需加载。auto memory 是 Claude 写的，在 ~/.claude/projects/<项目>/memory/，MEMORY.md 启动时加载前 200 行或 25KB，主题文件按需加载。说“记住……”写进 auto memory；要写 CLAUDE.md 得说“加到 CLAUDE.md”或用 /memory 自己改。# 快捷方式已取消。

    
2. CLAUDE.md 各层、settings 各层、权限规则各是什么关系？
CLAUDE.md 是拼接：各层都进上下文，从启动目录往上走，靠近启动目录的后读，后读不等于覆盖。settings.json 是覆盖：托管 > 命令行 > .claude/settings.local.json > .claude/settings.json > ~/.claude/settings.json，同名键高层赢。权限规则 allow/ask/deny 是跨层合并。

    
3. CLAUDE.md 变长了怎么办？为什么不写“完成前务必跑测试”？
控制在 200 行内，靠搬家而不是删字：多步流程→Skill；按目录的规则→.claude/rules/ 加 paths:；参考资料→Skill 的 references/；关于你的偏好→auto memory。@ 导入不省上下文。验证提醒在 Opus 5、Fable 5 上会导致过度验证（反复检查已正确的结果），应删掉；只保留不显然的项目事实，如“集成测试需要 Docker 在运行”。
